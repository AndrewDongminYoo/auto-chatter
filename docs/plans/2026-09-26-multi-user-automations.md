# 다중 사용자 자동화 구현 계획

방향은 [명세](../specs/2026-09-26-multi-user-automations.md)와 운영자의 다중 사용자·응답 후 팔로우 확인 승인에 따릅니다.
작업 공간은 기존 저장소를 사용하며 `.env.example`의 별도 변경은 포함하지 않습니다.
각 단계는 작은 의미 단위로 커밋하며, 운영 DB 변경·실발송·Meta 설정 변경은 별도 배포 검증 범위로 남깁니다.

## 구현 순서와 수용 기준

1. 댓글 규칙: 여러 키워드, 전체 일치·부분 일치·전체 댓글, 제외 키워드와 입력 검증을 구현합니다. → 순수 규칙 테스트 및 로컬 PostgreSQL 수신 테스트에서 기대하는 outbox만 생성되고 재전송으로 중복 생성되지 않습니다.
2. 인증·설정: Supabase Auth 사용자 검증, 작업 공간 membership, 연결·규칙 조회/수정 API와 설정 화면을 연결합니다. → 사용자 A가 사용자 B의 ID를 제출해도 조회·수정할 수 없고 미인증·교차 출처 변경 요청을 거부합니다.
3. Instagram OAuth: state·세션·일회성 검증, 계정 소유권 확인, 암호화한 계정별 토큰을 저장합니다. → 위조·만료·재사용 state를 거부하며 API 응답과 로그에 토큰이 나오지 않습니다.
4. 다중 계정 워커: 계정별 토큰과 발송 허용 상태를 조회하고 Queue·Cron을 연결별로 처리합니다. → 한 계정의 토큰·cooldown이 다른 계정에 적용되지 않고 전역 발송 중지 시 POST가 없습니다.
5. 후속 DM·팔로우 조건: DM webhook과 24시간 발송 창, 대화 상태, 팔로우 세 가지 상태와 명시적 재확인을 구현합니다. → 동의 없음, 거짓·누락 필드, API 오류, 오래된/중복/echo 이벤트에서 잘못된 완료 메시지를 보내지 않습니다.
6. 통합·운영 준비: 공개 개인정보 문안과 삭제 절차를 실제 저장 항목에 맞추고, 로컬 적대적 리뷰와 설정 화면 QA를 수행합니다. → 기존 테스트, 새 DB·경계 테스트, 타입 검사, Trunk와 Worker 번들 검증을 통과합니다.
7. 실계정 검증: 운영자 계정의 제한된 게시물·테스트 수신자·문구로 첫 발송과 각 팔로우 케이스를 확인합니다. → 공급자 message ID·DB 상태와 수신자가 확인한 메시지를 대조합니다.

## 배포 전 필요한 외부 설정

- Supabase Auth의 사이트 URL·이메일 인증 경로 및 외부 사용자 이메일 발송 조건을 확인합니다.
- Meta Instagram Login의 OAuth redirect URI와 요청 권한을 등록하고, 타인 계정 제공용 Advanced Access 상태를 확인합니다.
- 세션 및 Instagram 토큰 암호화 키와 OAuth용 앱 자격 증명을 Worker secrets로 등록합니다.
- 기존 수신 전용 workspace를 검증된 운영자 로그인에 연결하는 이전 절차를 별도로 검증합니다.
- 첫 실발송 대상·문구 확인과 발송용 토큰 등록 전에는 `SEND_ENABLED=false`를 유지합니다.

## 진행 상태

- 명세·공급자 제약 확인 완료.
- 단계 1–5의 코드·로컬 통합 검증을 완료했습니다.
- 단계 6의 독립 리뷰 지적을 수정했고 브라우저 QA를 수행했습니다.
- 단계 7과 운영 배포는 아직 실행하지 않았습니다.
- 상세 증거와 외부 설정 순서는 [배포 전환 기록](../notes/2026-09-26-multi-user-cutover.md)에 기록합니다.
