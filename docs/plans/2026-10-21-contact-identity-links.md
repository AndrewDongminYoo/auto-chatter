# 연락처 식별자 연결·분리 구현 계획

## 상태와 성공 기준

[계약](../specs/2026-10-21-contact-identity-links.md)에 대해 승인받은 구현 계획입니다.
2026-10-21 구현 승인 후 작업 1과 2를 같은 작업 공간에서 구현했으며, 아래는 승인 당시의 작업 구분을 보존합니다.
기준 코드는 `2724f9fcd989929383e62b677408a2ecf2ce590b`이고 구현 후 로컬 검증과 운영자 화면 승인을 마쳤습니다.
[구현 검증](../notes/2026-10-21-contact-identity-links-verification.md)에 실제 검사와 화면 승인과 남은 운영 검증을 기록합니다.

1. 확인·분리 저장 경계 구현 → 실제 PostgreSQL의 권한·동시성·재시도·삭제 테스트에서 계약을 확인합니다.
2. API와 화면 구현 → 로컬 Worker와 DB를 사용하는 브라우저에서 확인·분리·오류·갱신을 확인합니다.
3. 기존 발송·집계 불변성 확인 → 연결 전후 실제 원장 값과 기존 guard의 판정을 비교합니다.
4. 문서와 증거 정리 → 구현된 범위, 검증 SHA, 운영 미검증 상태와 #25의 남은 범위를 함께 기록합니다.

새 의존성은 추가하지 않습니다.
기존 `pg`, API 라우터, 정적 JavaScript 화면과 테스트 실행기를 사용합니다.
범용 사람 모델·연결 그래프·백그라운드 재계산 작업은 이번 범위에 필요하지 않습니다.
기존 문맥 조회 SQL을 변경하지 않고 새 확인 작업에서 재사용합니다.

## 작업 1: 저장·API·개인정보 경계를 하나의 PR로 구현

### 읽을 파일과 변경 범위

- 새 `src/app/contact-identity-links.ts`와 단위·DB 테스트를 만들고, 기존 `src/app/inbox-identity.ts`, `src/app/settings.ts`, `src/app/channel-consent.ts`의 조회·역할·쓰기 관례를 따릅니다.
- `src/app/api.ts`에 계약의 두 경로를 추가하고 `src/app/api.test.ts`에서 경로·메서드·요청 경계를 검사합니다.
- `db/schema.sql`, 구현 시점의 다음 번호 `db/migrations/<next>-contact-identity-links.sql`, `deploy/migrate-multi-user.sql`, `deploy/supabase-access.sql`에 두 테이블·제약·접근 제어와 삭제 처리를 반영합니다.
  마이그레이션 번호는 지금 예약하지 않고 실제 마지막 번호를 확인합니다.
- `src/app/workspace-export.ts`와 관련 테스트에 두 테이블의 분류와 공개 필드를 추가합니다.
- `src/app/person-deletion.db.test.ts`, `src/app/data-deletion.db.test.ts`, `src/app/workspace-deletion.db.test.ts`, `src/cloudflare/access.db.test.ts`에서 새 데이터의 제거·보존·권한을 검사합니다.
- `src/app/workspace-members.ts`와 `deploy/assign-workspace-owner.sql`의 빈 작업 공간 판정은 연결 외래 키로 새 데이터가 함께 제한되는지 대조합니다.
  기존 판정이 충분하면 수정하지 않고 근거를 검증 기록에 남깁니다.
- `package.json`의 명시적인 테스트 파일 목록에 새 테스트를 등록합니다.
  매니페스트 변경 뒤 `corepack pnpm install --frozen-lockfile`로 잠금 파일 일치를 확인하고, 잠금 파일이 변경되면 같은 커밋에 포함합니다.
- `CLAUDE.md`, 이 계약, 기존 연락처 상세 계약과 수용 현황표의 직접 영향을 받는 설명을 같은 PR에서 갱신합니다.
  `README.md`, `AGENTS.md`도 영향 여부를 확인하되 관련 없는 문장은 수정하지 않습니다.

### 구현 순서와 실패 재현

1. 새 API의 미지원, 없는 테이블, 권한 없는 요청 중 실제 변경을 검사하는 실패 테스트부터 추가합니다.
   의도한 실패 이유를 확인한 뒤 최소 저장 구조와 서버 함수를 구현합니다.
2. 테이블 제약으로 작업 공간·연결 범위와 DM 상대별 현재 행의 유일성을 강제합니다.
   기존 `lockWorkspaceForMember` 호출 → 연결 잠금 → 현재 행 → 요청 키·버전 확인 → 현재 근거 검사 → 이벤트·현재 상태 갱신 순서를 구현합니다.
   멤버십 변경 경합은 기존 코드의 잠금 순서를 확인해 맞춥니다.
3. 동일 요청 재시도, 다른 내용의 키 재사용, 근거 ID 교체, 분리 후 새 작성자 확인, 과거 성공 요청의 뒤늦은 재시도를 재현합니다.
   응답의 적용 이벤트와 현재 행을 구분하는지 확인합니다.
4. 두 DB 연결을 사용해 동일 버전의 확인·분리를 경합시킵니다.
   임의 sleep 대신 실제 잠금 또는 명시적인 테스트 장벽으로 첫 요청을 정지시키고, 한 요청만 갱신하며 이벤트와 현재 행이 맞는지 검사합니다.
5. 개인 삭제와 확인의 양쪽 실행 순서를 재현합니다.
   삭제 후 확인은 원본이 없어 거부되고, 확인 후 삭제는 새 행·이벤트를 함께 지우는지 확인합니다.
   삭제와 무관한 다른 사람의 원본 데이터는 보존합니다.
6. 이력과 현재 행이 모두 롤백되는 중간 실패를 만들고, 서버 역할·API 역할의 실제 권한을 별도 연결로 확인합니다.
7. 기존 서비스 답장과 마케팅의 grant/revoke, 대기 발송, 직접 중지와 상담 중지, 고정 대상 명단을 fixture에 실제로 넣습니다.
   확인·분리 후 이 원장과 guard 판정이 유지되는지 읽어서 비교합니다.
   값이 없는 빈 fixture나 테스트 속성만 검사하는 사례로 대체하지 않습니다.

### 검증 명령과 출하 기준

```bash
corepack pnpm install --frozen-lockfile
corepack pnpm check-types
corepack pnpm test
TEST_DATABASE_URL=postgres://postgres@127.0.0.1:<port>/automations_test corepack pnpm test:db
TEST_DATABASE_URL=postgres://postgres@127.0.0.1:<port>/automations_test corepack pnpm test:cloudflare
```

DB·workerd 검사는 전용 임시 PostgreSQL에서 순차 실행합니다.
새 스키마 설치와 기존 스키마에 대한 전체 migration runner 적용이 같은 테이블·제약·권한을 만드는지 별도로 대조합니다.
운영 연결과 `.env`를 테스트에 사용하지 않습니다.
실제로 바꾼 파일만 명시해 Trunk 형식·검사를 실행합니다.

개인정보 삭제와 내보내기까지 통과하기 전에 저장 API를 출하하지 않습니다.
이 PR의 결과는 화면 없는 확인·분리 API이며, #25 전체 완료로 표시하지 않습니다.
저장 구조만 남기고 개인정보 경계를 다음 PR로 미루지 않습니다.
스키마·권한·동시성을 포함하므로 구현 후 리뷰는 핵심 영역 변경에 맞는 깊이로 수행합니다.

## 작업 2: 연락처 상세의 확인·분리 화면

작업 1의 API와 검증된 계약을 사용합니다.
`public/app/app.js`, 필요한 경우 `public/app/index.html`·`public/app/styles.css`와 정적 보안 테스트를 수정합니다.
화면 로직이 기존 파일에 과도하게 섞일 때만 작은 `public/app/contact-identity-links.js`로 분리하며, 새 상태 관리 체계를 도입하지 않습니다.

1. 기존 확인된 대화 목록 옆에 운영자 확인 상태와 현재 공급자 근거 상태를 각각 표시합니다.
   `agent`에게는 조회만 제공하고 `admin` 이상에게 확인·분리 버튼을 표시합니다.
2. 확인 전 정확한 연결 계정·댓글 ID·DM ID를 보여 줍니다.
   분리 전에는 ‘저장한 확인을 해제하며 기존 대화·수신 거부·공급자 연결 근거는 유지된다’는 의미를 설명합니다.
3. 성공 뒤 서버의 현재 행을 다시 읽습니다.
   409는 기존 성공 표시를 지우고 새 상태를 읽게 하며, 자동으로 최신 버전의 변경을 재요청하지 않습니다.
4. 계정·연락처 변경, 접기·다시 열기, 로그아웃 후 이전 응답을 버립니다.
   페이지 커서와 현재 버전도 새 대상에 재사용하지 않습니다.
5. 로컬 실제 Worker·DB에서 두 관리자 화면의 충돌, 근거 유실 후 분리, 분리 후 공급자 대화가 남는 상태를 확인합니다.
   `scripts/segment-acceptance.mjs`는 기존 세그먼트 전용 fixture이므로 무관한 식별자 시나리오를 무조건 추가하지 않습니다.
   기존 fixture 구성에서 필요한 설정만 참고해 이번 기능의 합성 데이터를 준비합니다.
6. 키보드만으로 확인·분리하고, 390px 화면·오류·빈 목록·권한 제한을 캡처합니다.
   실제 근거와 동의 상태가 있는 fixture를 사용하고 화면 수치와 DB를 대조합니다.

해당 단위·DB·workerd 검사와 실제 브라우저 결과를 기록하고 화면 승인을 받습니다.
화면 승인은 이 기능의 새 결과에 대해 받으며 PR #240의 승인을 재사용하지 않습니다.

## 종료 조건과 후속 범위

API와 화면 각각의 검증 SHA·실패 재현·실행 결과를 `docs/notes/`의 구현 검증 기록에 남깁니다.
기존 연락처 상세 계약의 ‘식별자 연결 제외’ 설명은 그 문서의 역사적 범위를 보존하면서 새 계약으로 연결합니다.
수용 현황표에는 제한된 같은 연결의 확인·분리가 구현됐다는 사실과 남은 범위를 함께 적습니다.

아래 항목은 이번 두 PR에 포함하지 않습니다.

- 임의로 입력한 ID, 여러 댓글 작성자, 계정·채널 간 식별자 병합
- 동의 이전, guard 변경, 일괄 발송·캠페인·새 개인정보 정책
- #51 청구 원장 구현이나 과거 기간 재청구
- 운영 마이그레이션·배포·실계정 발송

새로운 공급자 근거 없이 임의 연결이 필요하거나 연결을 발송·삭제 권한으로 쓰라는 요구가 생기면 기존 계약의 구현으로 처리하지 않습니다.
그 변경은 별도 범위와 승인을 먼저 정합니다.
Oracle의 이번 조회 결과는 \[no precedent found\]이며 출처와 조회 한계는 계약에 기록했습니다.
