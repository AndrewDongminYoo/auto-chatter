# 메시징 자동화 플랫폼 구현 계획

상태: ChatbotX 채택 검증을 수행하고 Instagram 웹훅 수신·이벤트 저장·개인 답장 요청 보관·발송 정책·워커 모듈을 구현했습니다.
Facebook Login과 Instagram Login용 발송 어댑터와 실행 명령은 모의 Graph 응답으로 검증했습니다.
Meta 앱의 Instagram Login 설정을 확인했고, 운영자는 Instagram API 설정에서 발급한 토큰으로 개발자 대시보드의 일반 DM 발송에 성공했다고 보고했습니다.
댓글 관리 권한과 이 저장소의 댓글 비공개 답장 발송은 아직 검증하지 않았습니다.
검증 결과와 남은 조건은 [채택 검증 기록](../notes/2026-09-25-chatbotx-validation.md)에 있습니다.
제품 경계는 [명세](../specs/2026-09-25-messaging-automation-platform.md), 외부 사실과 후보 비교는 [조사 보고서](../notes/2026-09-25-manychat-research.md)를 따릅니다.

## 권장 경로

ChatbotX Community Edition의 고정 커밋을 검증했고, 워커 타입 검사 실패와 불명확한 CE 추출 경계 때문에 채택을 보류했습니다.
TypeScript·PostgreSQL로 최소 기능을 직접 구현하고, 지연 작업의 부하가 확인되면 Redis를 검토합니다.
첫 구현은 Instagram 웹훅 검증과 댓글 이벤트 정규화·저장입니다.
PostgreSQL outbox를 처리하는 워커 모듈을 구현했습니다.
Facebook Login과 Instagram Login 어댑터를 실행 진입점에 연결했습니다.
현재 앱에는 Instagram Login 경로가 설정돼 있으며, 실계정 권한과 개인 답장 호출을 확인한 뒤 운영 경로를 확정합니다.
Chatwoot은 인박스 요구가 특히 강할 때 비교 대상이지만, ManyChat식 마케팅 플로를 구현할 추가 비용이 큽니다.
[후보 평가 근거](../notes/2026-09-25-manychat-research.md#유사-오픈소스-평가).

## 단계별 작업과 수용 기준

### 0. 채택 검증과 권한 확인

1. ChatbotX의 검증된 커밋을 별도 실험 디렉터리에 가져와 CE 범위와 상용 라이선스 경계를 목록화합니다.
   검증: `LICENSE`, 상용 디렉터리, 빌드 입력과 런타임 import를 확인합니다.
2. 저장소가 선언한 잠금 파일과 CI 명령으로 설치, 타입 검사, 테스트, 개발 실행을 재현합니다.
   검증: 각 명령의 종료 상태와 실패한 테스트를 기록합니다.
3. 작은 모의 웹훅에서 댓글 이벤트 중복, 한 번의 private reply, 전달 콜백을 실행합니다.
   검증: DB·발송 로그에 하나의 발송만 남습니다.
4. 워커 메모리 증가 [이슈 #1255](https://github.com/ChatbotXIO/ChatbotX/issues/1255)를 재현하거나 해결된 커밋과 장시간 실행 결과를 확인합니다.
   검증: 빈 큐·소량 큐 실험의 메모리 추이를 기록하고 허용 기준을 정합니다.
5. Meta Instagram 테스트 계정과 앱 권한, TikTok 대상 지역, 결제 사업자 소재지의 실제 조건을 확인합니다.
   검증: 승인 화면 또는 공식 회신과 권한별 가능한 API 호출 결과를 기록합니다.

0단계의 채택 결정은 “기능 목록이 있음”이 아니라 실제 실행, 권한, 라이선스, 운영 문제의 증거로 내립니다.
이 결정을 내리기 전에는 ChatbotX 코드를 이 저장소로 대량 복사하지 않습니다.

### 1. Instagram 중심 첫 배포

1. 작업 공간, 관리자·상담원 역할, 공식 Instagram 연결과 웹훅 검증을 연결합니다.
   검증: 다른 작업 공간 토큰으로 연락처·연결 정보를 읽을 수 없습니다.
2. 댓글 키워드 → 조건 → 허용된 개인 메시지 → 태그·리드 기록의 최소 플로를 구현합니다.
   검증: 같은 댓글 웹훅을 중복 재생해도 발송이 한 번만 이뤄집니다.
3. 공유 인박스에 메시지·담당자·상담원 전환·발송 실패를 연결합니다.
   검증: 상담원 전환 후 자동 답장이 멈추고 수동 답장은 감사 기록에 남습니다.
4. 설정 화면에서 연결 권한과 플로 발행 전 오류를 확인할 수 있게 합니다.
   검증: 연결 해제·토큰 만료·권한 부족 상태에서 발행을 차단합니다.

### 2. 유료 MVP

1. Telegram과 WhatsApp Cloud API를 연결하고 채널별 발송 창·템플릿·속도 제한을 정책 계층에서 검사합니다.
   검증: 창 만료와 미승인 템플릿은 실제 발송 전에 거부됩니다.
2. 세그먼트 방송과 예약 발송에 예상 수신자·비용·작업 공간 상한을 표시합니다.
   검증: 한도 초과, 취소, 부분 실패, 재시도를 이벤트 재생으로 확인합니다.
3. 활성 연락처 원장과 플랜 권한, 체험, 초과 사용 한도를 구현합니다.
   검증: 같은 사람의 반복 메시지와 청구월 경계의 사용량이 원장 재계산과 일치합니다.
4. 사업자 소재지에 맞는 결제 공급자를 연결합니다.
   검증: 테스트 결제의 성공·실패·취소·중복 웹훅과 플랜 갱신을 대조합니다.

### 3. 기능 동등성 확장

1. TikTok Business Messaging은 승인 가능한 지역과 계정에서만 활성화합니다.
   검증: 실제 승인된 계정으로 수신·답장 창·실패를 확인합니다.
2. Email·SMS와 Google Sheets·CRM 웹훅을 실제 수요 순서로 추가합니다.
   검증: 옵트인, 수신 거부, 반송, API 할당량, 발송 비용 상한을 확인합니다.
3. FAQ 기반 AI 응답과 상담원 전환을 평가 세트로 도입합니다.
   검증: 근거 없는 질문, 개인정보, 도구 오류에서 자동 발송하지 않습니다.
4. 고급 라우팅, 대시보드, 청구·비용 분석을 추가합니다.
   검증: 이벤트·발송·청구 원장에서 화면 지표를 다시 계산할 수 있습니다.

## 개발 에이전트 스킬과 워크플로

현재 필요한 것은 새 전역 스킬을 만드는 일이 아니라, 단계별 증거를 남기는 작은 워크플로입니다.
반복되는 채널 계약이 3개 이상 안정되기 전에는 플랫폼별 전역 스킬을 만들지 않습니다.

| 작업 | 적용할 기존 스킬 또는 절차 | 결과물 |
| --- | --- | --- |
| 오픈소스 채택 판단 | `oss-adoption`의 문제·라이선스·첫 변경 검증 | 후보별 채택·보류 근거와 고정 커밋 |
| 외부 API 구현 | 공급자 공식 문서, 웹훅 샘플, 권한·속도·비용 계약 테스트 | 채널 어댑터 계약과 실패 사례 |
| 보안 경계 | `security-best-practices`를 인증, 토큰, 테넌트, 웹훅 경계 변경 때 적용 | 재현 가능한 보안 점검 결과 |
| 화면 구현·확인 | UI 작업에만 `frontend-design`, 로컬 화면 검증에 `webapp-testing` | 발행·인박스 주요 경로의 실제 브라우저 확인 |
| 회귀 수정 | 오류 재현 → 최소 수정 → `verify-fix`로 독립 판독 | 실패 전·통과 후 증거 |
| 품질 게이트 | 프로젝트 명령이 정해지면 `setup-trunk` 검토, CI에서 타입·린트·테스트 | 동일 명령의 로컬·CI 결과 |
| 전체 PR 수명주기 | 별도 요청이 있을 때만 `pr-loop` | 검토 가능한 PR과 CI 결과 |

모의 웹훅과 청구 테스트는 먼저 의도적으로 실패시키고 예상 오류를 확인한 뒤 통과를 신뢰합니다.
한 가지 검증이 확인하는 범위를 좁게 설명합니다.
예를 들어 타입 검사는 Instagram 권한 승인을 증명하지 않으며, 모의 웹훅은 실제 공급자 전달을 증명하지 않습니다.
외부 계정 권한은 공급자 개발 환경과 실제 계정에서 별도 확인합니다.

### 최적의 개발 에이전트 모델 배치

- 주 에이전트는 설계 결정, 파일 소유권, 최종 통합과 검증을 맡습니다.
- 범위가 고정된 문구·구성 작업은 Luna, 일반 구현·공식 문서 조사·QA는 Terra, 인증·과금·동시성·플랫폼 정책과 같은 실패 영향이 큰 변경은 Sol 수준의 검토로 배치합니다.
- 두 개 이상의 독립된 읽기 작업이 실제로 시간을 줄일 때만 병렬로 맡깁니다.
- 구현 담당자는 명시한 파일만 수정하고, 통합·스테이징·커밋은 주 에이전트가 수행합니다.
- 과금·권한·외부 발송 변경은 코드 작성자와 별도의 검토자가 수용 기준을 반대로 깨보는 검증을 수행합니다.

### 고객 응답 AI 모델 배치

고객 응답에는 [명세의 단일 응답 에이전트](../specs/2026-09-25-messaging-automation-platform.md#ai-에이전트-모델)를 사용합니다.
모델 선택은 공급자 이름이 아니라 실제 한국어·영어 FAQ 평가, 근거 누락률, 상담원 전환율, 지연, 메시지당 비용으로 결정합니다.
규칙 기반 플로와 발송 정책이 최종 권한을 가지며, 모델은 결제·환불·무동의 마케팅 발송을 직접 실행하지 않습니다.

## 현재 작업의 완료 조건

1. 새 Git 저장소가 이 폴더를 루트로 사용합니다.
   검증: 저장소 루트에서 `test -d .git && test "$(cat .git/HEAD)" = "ref: refs/heads/main"`.
2. 조사·명세·계획이 요청한 세 문서 폴더에 있고 README에서 연결됩니다.
   검증: 세 파일의 존재, 상대 링크, Markdown 기본 형식을 확인합니다.
3. 가격·기능·API·라이선스에 관련된 외부 주장은 원본 링크와 조사일을 포함합니다.
   검증: 문서의 외부 링크와 핵심 표를 직접 대조합니다.
