# Feature invariants

Agent-facing invariants per feature: the rules a code change most easily breaks.
Each feature's spec owns its contract; this file owns only these summaries, and [CLAUDE.md](../../CLAUDE.md) owns the cross-cutting rules and routes here by code path.
Read the section for the code you touch before editing it.
The text moved here unchanged from CLAUDE.md on 2026-11-01, so migration numbers and dated capability notes below are history as well as rules.

## Dashboard, channel and token

### Channel contract

**Channel contract** ([spec](../specs/2026-10-04-channel-contract.md)): `src/channels/` contains advisory capabilities, scoped identity, receipt keys and the existing pure consent/window policy. Instagram ingress uses `channel-adapter.ts` after signature verification and keeps the original storage inputs and ordering. Only the manual worker uses its outcome classification, inside the existing send catch; persistence remains outside. Capability support never replaces eligibility or final guards. The fake second adapter exists only in unit tests.

### API request limits and static client

Signed-in writes outside `/api/auth/*` spend a fixed per-user limit and a per-workspace limit in `appApi` before any route handler (per-user before the database opens; the workspace count is the plan's `api_writes_per_hour`, read with the membership and passed as `limit`, and a value outside the catalog keeps the default), and `GET /api/inbox` spends its own before `listInbox`, all counted by the `AuthLimiter` Durable Object through `durableLimits`; a member's `POST /api/workspace` (the dashboard bootstrap) spends neither write limit and member removal skips the workspace one, and unlike the fail-closed auth and #166 allowances these limits fail open with one fixed log code ([spec](../specs/2026-10-12-api-request-limits.md)).
`public/app/` is a build-free static client (`app.js`, `inbox.js`, `reply-templates.js`, `manual-reply-reports.js`, `flow-run-reports.js`, `handoff-reports.js`, `contact-csv-preview.js`, `segment-snapshots.js`, `contact-identity-links.js`, `api-key-labels.js`) served by Wrangler assets.
The auth client wraps injected fetch in a standalone call because workerd rejects a native fetch invoked with the client object as its receiver.

Dashboard display helpers in `public/app/display-values.js` guard API counts, dates and text before interpolation.
Plain count displays retain their ungrouped form, decimal-string counts retain integer precision, and absent or invalid display values use `–`.
Report range strings and CSV audit timestamps retain their existing ISO representation.

### Dashboard session and auth client

Session invalidation clears the entire protected dashboard, advances its generation and exposes the existing reload action; it does not imply an authentication refusal.
Workspace refresh reads the user, membership, accounts and rules before applying the core snapshot, and only the newest refresh may apply it.
User, workspace or role changes clear the preceding context before further reads; same-context refreshes preserve unrelated drafts and report snapshots.
Discarding a context exposes reload immediately, and a failed replacement read reports its error even when the original action has been retired.
Home bootstrap reads the core workspace snapshot and recent activity only; each menu shares its first feature load until the next core snapshot, and session reset retires that cache.
Detailed reports live in the reports view, including legacy report section hashes; their context configuration still invalidates changed permissions or time zones before optional option-list reads.
The explicit report-list refresh retries option reads without discarding unchanged report inputs or accepted CSV snapshots.
The synthetic browser regression in `scripts/home-actions-acceptance.mjs` measures request counts and menu entry, report/CSV retention and role boundaries; it makes no production latency claim.
Reports own their query and result invalidation: unchanged role, time zone and account options preserve them, while changed context resets them and a session reset retires pending responses.
Flow and campaign report option lists can retry independently of report dates and results.
An in-flight same-context refresh cannot overwrite a time zone saved after that refresh began; new contexts still take their membership's zone.
Network failures keep the existing workspace visible with a retry action; only an authentication refusal shows login, and secondary reads retain their feature-level failure handling.
Actions lock their own form; rule controls additionally follow the rule save's busy state, and a session reset retires action cleanup so an old completion cannot restore a new session's controls.
The comment-rule editor shares one form and save action between composition and preview; mobile switches visibility without replacing inputs or clearing dirty state, while desktop shows both.
Returning from preview restores the last available input focus, and captured native validation reveals composition before invalid-field focus; session reset retires the remembered input.
The mobile save bar and its save-failure error remain available in either mode, and no-account state prioritizes account connection instead of showing an unusable editor.
`scripts/mobile-rule-acceptance.mjs` covers synthetic preview, validation, focus, save failure/retry, busy controls, discard warnings and empty states; viewport checks do not prove physical-device keyboards or Safari behavior.
Account and rule notices expose polite status regions and skip identical text updates; contextual reconnection instructions respect the service connection restriction.
Send settings guidance shares one display policy across home, accounts, rule editor and the selected inbox conversation; it never grants delivery eligibility or changes manual reply controls.
A failed service-wide settings reread marks the displayed setting unknown, preserves drafts and filters, and ignores responses retired by a workspace or session change.
The account guidance uses the last workspace snapshot and distinguishes token expiry from verified provider authorization; `scripts/send-settings-acceptance.mjs` exercises the synthetic settings combinations and input preservation.
The synthetic browser regression in `scripts/workspace-state-acceptance.mjs` covers workspace refresh, rule save, account settings, network retry, partial failure, response ordering and session boundaries; it does not prove live provider behavior.
The shared API wrapper checks the request's workspace generation before starting a 401 refresh and again before replaying the original request, so a retired session cannot automatically replay pending input.
Cookie-changing browser auth requests take an exclusive origin-wide Web Lock; all protected requests, including their initial attempt, take a shared lock. Every parsed protected JSON response, including structured errors, is checked against the captured session before exposing fields; successful text bodies are checked too. The document keeps an accepted session revision instead of adopting fresh storage on every call; only a successful local login or a full document reload accepts a different account. A shared pending/ready revision retires requests across documents before cookie changes and is checked again when a queued refresh or retry acquires the lock. Automatic refresh requires Web Locks and writable localStorage; storage-coordinated auth fails before fetching if its pending marker cannot be published. See the [cookie-ordering verification note](../notes/2026-10-22-auth-cookie-response-order.md) for fallback behavior and browser-lifecycle limits.
Session broadcasts carry a per-document source marker so a local login does not invalidate its own new bootstrap; successful local login clears protected state synchronously before broadcasting.
Received session broadcasts clear local state without publishing another message, so multiple open documents settle after one invalidation.
The dashboard re-reads the global send state from `/api/me` on focus, on a visible page and on a menu change ([#338](https://github.com/AndrewDongminYoo/auto-chatter/issues/338)); that read neither refreshes the session nor resets it on a 401, and it rewrites only the banner, the getting-started steps and the send badges, never the lists, the rule editor or contact drafts.

### Follow flow

**Follow flow** (`follow-flow.ts`, `message-events.ts`):
`instagram_follow_conversations` snapshots the first reply configuration; a nonfollower response returns to waiting, a follower response completes, and ambiguous sends remain unknown.
A missing recipient ID after a successful first DM records `follow_recipient_unavailable` without resending.
Inbound DM text is compared in memory for follow confirmation; receipt IDs and timestamps deduplicate confirmation events.
DM ingestion holds its connections `FOR SHARE` before it locks a follow row, so a rate-limited follow send locks the connection `FOR NO KEY UPDATE` before it updates the follow row and the connection pause ([#130](https://github.com/AndrewDongminYoo/auto-chatter/issues/130)).
Optional `confirmation_button_title` adds a single postback template button to the first DM and nonfollower response; empty defaults preserve text-only delivery.
Button clicks are bound to the queued reply ID and validated against account, recipient and waiting flow; typed confirmation still works.
The service caps button labels at 20 and button-message text at 640.
OAuth subscribes `messaging_postbacks` as well as comments/messages, so existing accounts must reconnect and the app must subscribe that webhook field.

### Token lifecycle

**Token lifecycle**: active Instagram Login connections refresh valid long-lived tokens from 30 days before expiry, after the token is at least 24 hours old.
Inactive, expired, or disconnected connections do not refresh; an expired token requires OAuth reconnection.
A token that Meta rejects gets a display-only reconnect marker; its signals, clearing and deploy order are in the [token refresh spec](../specs/2026-09-28-instagram-token-refresh.md#재연결-필요-표시-16).
A verified Meta deauthorize callback disconnects the matching connections like the settings screen; its contract, ID matching and deploy order are in the [token refresh spec](../specs/2026-09-28-instagram-token-refresh.md#권한-해제-콜백-16).
The cron and the manual status check share one webhook subscription check and store a display-only loss record per token; cadence, recording rules and deploy order are in the [token refresh spec](../specs/2026-09-28-instagram-token-refresh.md#웹후크-구독-유실-표시-179).
Stored tokens and webhook signing secrets use the `v2.<kid>.` envelope of `src/app/secrets.ts`: seal only with `TOKEN_ENCRYPTION_KEY`, open with it or `TOKEN_ENCRYPTION_KEY_PREVIOUS` through `tokenKeys(env)`, and keep the AAD contexts. The cron step `token_key_rewrap` runs only while the previous key is set and differs from the current key, and seals a row again only when its ciphertext is unchanged, writing no other column; every send guard treats the changed ciphertext of a still sendable connection as `token_rotated` (the manual-reply guard blocks it as `delivery_changed` once the connection is inactive, send-disabled or expired, as it would without a rotation) ([key rotation spec](../specs/2026-11-24-token-key-rotation.md)).

### Message reads

**Message reads** ([spec](../specs/2026-11-10-instagram-message-reads.md), #312 PR 1): `parseMessageReadEvents` in `src/instagram/message-reads.ts` reads `messaging_seen` events (Instagram Login only) after signature verification, inside the same 400 range as the channel adapter, and both ingress paths store them last with `ingestMessageReads` (the Worker after its wake, so a failed read write cannot hold back the comments and DMs of the body); a read is never a `ChannelEvent`, and `parseMessageEvents` skips it because it has no `message` or `postback`, so no DM path (inbox, reply wait, follow confirmation, DM start trigger, kept DM, consent) starts from it and the Worker wakes nothing for it. `instagram_message_reads` (migration 070) keeps one row per `(connection_id, message_id, recipient_id)` with `ON CONFLICT DO NOTHING`, so the first `read_at` stays, and only for an active connection whose account is the event recipient and a `read.mid` equal to a `provider_message_id` of that connection in `private_reply_outbox`, `instagram_follow_conversations`, `instagram_manual_replies`, `flow_dm_deliveries` or `campaign_deliveries`, or equal to a follow reply's ID in `instagram_follow_messages`; a new outbound send table with a `provider_message_id` must join that lookup. `instagram_follow_messages` (migration 071, #321) is append-only: the follow worker inserts each sent reply's ID in the same statement as the successful-send update, because the follow row keeps only the latest ID, and the lookup keeps the follow row's ID too for replies sent by a pre-071 worker. The write locks the active connections `FOR SHARE` in its own statement before the insert. OAuth subscribes `messaging_seen`, but `REQUIRED_SUBSCRIPTION_FIELDS` does not include it, so older connections stay `fields_present` and receive reads only after an OAuth reconnect. The three deletion functions remove the rows (person deletion by the `dm_recipient` set), and the table is exported. The manual reply, flow-run and campaign run reports read it (#312 PR 2) only through `EXISTS` on the same `connection_id` and an exact `message_id = provider_message_id` of a `sent` row, so several readers of one message count once; no report infers reads from a later message (no watermark) or reports unread counts or read rates. Each also returns `read_unavailable`: the other `sent` rows, with no matching read, whose connection has `instagram_user_id IS NULL`. Only the Instagram Login OAuth exchange writes that column and a disconnect keeps it, so NULL marks Facebook Login, environment-managed and never-reconnected pre-040 connections, none of which is known to receive `messaging_seen`; a confirmed read stays in `read`, so the two counts are disjoint.

## Campaigns

### Campaign drafts

**Campaign drafts** ([spec](../specs/2026-10-21-campaign-drafts.md)): administrator-only planning records reference existing target snapshots and contain plain text, never send requests or eligibility claims.
Creation uses a client UUID scoped to the workspace plus the original normalized request hash; replay returns current state without undoing edits or archival.
Writes recheck membership under the workspace lock, enforce a total limit of 100 including archived drafts, and require the displayed version for edits and archival.
Reads distinguish original and remaining member counts; person and connection deletion only reduce the referenced membership.
`GET /api/campaign-drafts/:id/preview` (`admin`) is read-only: one statement in a `REPEATABLE READ READ ONLY` transaction, at one `as_of`, gives each remaining member exactly one reason in a fixed order (connection, pause, verified DM identity, opt-out, explicit marketing grant, 24-hour text window, then `candidate`), and a sender with several verified recipients takes its furthest-reaching recipient's stage ([preview](../specs/2026-10-21-campaign-drafts.md#발송-조건비용-미리보기)).
`candidate` means it passed the recorded conditions at `as_of`, never that it can be sent: delivery guards recheck at send time, `channel_marketing_supported` reads the `cloudflare_oauth` marketing capability (true since 2026-10-27; it never implies eligibility), and `estimated_provider_calls` equals the candidate count. `plan_broadcast_limit` is this month's campaign send allowance (`{month, limit, used, reserved, remaining}`, decimal strings, from `campaignSendAllowance`); the preview only reads it.
Migration 063 adds workspace deletion and restricted access; exports omit the internal request hash, and both workspace move checks retain drafts.
An admin records a final execution approval of one draft version (`POST /api/campaign-drafts/:id/approvals`, [approvals](../specs/2026-10-21-campaign-drafts.md#실행-승인)): `campaign_approvals` keeps the name and body copies, the `PREVIEW_SQL` result evaluated in the same transaction, and an immediate or workspace-local schedule (`localDueSql`, at least the scheduled replies' `SCHEDULE_MIN_AHEAD` ahead with no fixed upper bound because #36 applies each recipient's reply window at delivery, never moved by a zone change); at most one is `approved` per draft, and while it is, the draft's edit and archive answer `409 approval_active` under the same workspace and draft locks.
Approvals themselves queue and send nothing (a due approval becomes `executed` when its run starts, and the delivery worker sends the run's rows; see Campaign runs and Campaign delivery below), `campaign_approval_events` is append-only, workspace deletion removes both before the drafts, connection and person deletion leave them, and migration 064 must run through the full runner before code deployment.
The contacts view manages drafts through `public/app/campaign-drafts.js`: unknown writes retain an immutable request for explicit retry, conflicts preserve inputs until an explicit reload, and session/workspace changes discard protected data and late responses.
Archived drafts are read-only and still count toward capacity; snapshot counts never imply send eligibility.
The draft detail's approval area ([approval UI](../specs/2026-10-21-campaign-drafts.md#실행-승인-화면)) finds the open draft's approval as its first entry in `GET /api/campaign-approvals`, approves only after a confirmation step that freezes the request, locks the draft while an approval is in force or its state is being read, re-renders from the `approval` or `draft` a 409 carries (the shared API wrapper forwards both), treats a success body that is not the requested approval in the requested status as an unknown outcome, retries an unknown or throttled write only as the same request, and uses the module's generation and an approval request counter to discard late reads.
The draft detail reads `GET /api/campaign-drafts/:id/preview` only on an explicit button click (archived drafts included), labels `candidate` "조건 통과" and never shows "발송 가능", and the existing generation and request counters discard the preview and its late responses on any edit, save, archive, draft switch, new draft or session reset, as well as a response for another draft or version ([preview UI](../specs/2026-10-21-campaign-drafts.md#발송-조건-미리보기-화면)).

### Campaign runs

**Campaign runs** ([spec](../specs/2026-10-27-campaign-runs.md)): the `campaign_start` cron step runs only while `SEND_ENABLED` is `true`, starts at most `CAMPAIGN_START_LIMIT` due approvals, those with no failed start (`start_failed_at` NULL) oldest due first and then the failed ones least recently failed first, and per approval locks the workspace, the approval, the draft, then the snapshot's connections `FOR SHARE` in ID order, rechecks `approved` and due, and re-runs the preview SQL (`EVALUATION_SQL`) in one statement that also returns each candidate's key and chosen DM recipient (the qualifying recipient with the latest stored text DM).
It writes one `campaign_runs` row per approval (`(workspace_id, approval_id)` unique, because approval IDs are client-supplied; the nine counts at `started_at`) and one `pending` `campaign_deliveries` row per candidate (duplicate key `(run_id, connection_id, sender_id)`), then sets the approval `executed` without a version bump or audit row; an executed approval refuses schedule change and cancel with `409 campaign_approval_executed`. Before the rows, under the same workspace lock, it counts the monthly campaign send limit of the month that holds `started_at` with the approval's own rule (`campaignSendsFit`, the starting approval excluded from `reserved`): when used + the other approvals' reserved + the candidates exceed the limit, or the limit is 0, the run is written `completed` with no delivery row, `candidate: "0"` and the `plan_limit_exceeded`/`plan_limit`/`plan_limit_used`/`plan_limit_reserved` keys in `start_counts`, the approval still becomes `executed` (its draft version is used up), the run read returns `start.broadcast_limit_exceeded`, and approval reads return `run_limited: true`. One failing approval is logged, stamped `start_failed_at` outside its rolled-back transaction, and the rest still start.
The start itself sends nothing: no Graph call, transport, outbox row or queue message. Instagram marketing is supported on the `cloudflare_oauth` surface only, inside the 24-hour window with an exact explicit marketing grant.

### Campaign delivery

**Campaign delivery** ([delivery](../specs/2026-10-27-campaign-runs.md#발송-worker)): `processNextCampaignDelivery` in `src/instagram/campaign-delivery-worker.ts` runs only in the Cloudflare queue consumer, after the manual reply, follow confirmation and private reply steps and only when none of them claimed a row; the Node worker never sends campaigns. It claims one due `pending` row of a `running` run (unpaused connection and contact, campaign budget open; `campaignDeliveryDueSql` is shared with the wake and health) `FOR UPDATE OF d SKIP LOCKED` without locking the run, and sends the approval's body as one plain-text DM to the stored `recipient_id`. The final guard (after the claim, after the account read, and in `beforeSend`) reads the preview's own fragments (`RECIPIENT_STAGE`, `CONNECTION_SENDABLE`, `CONTACT_PAUSED` in `src/app/campaign-drafts.ts`) for the stored recipient plus the run, `SEND_ENABLED`, the token, the approver's active `owner`/`admin` membership and `deliveryRecipientOptedOut`; any block reason wins over any retry reason. Outcomes: retry → `pending` a minute later with the attempt cleared, block → `blocked`, definite rejection → `failed`, rate limit → `pending` at the connection pause end (`max(900 s, Retry-After)`), anything else → `unknown`, never retried. The finish locks the run `FOR SHARE` before the row (the cancel's order) and lands a would-be `pending` row of a cancelled run as `cancelled`; a separate statement then completes a `running` run with no `pending`/`sending` row, as `campaign_start` does for every run after its starts, and `stale_recovery` turns `sending` rows older than 10 minutes `unknown`. `CAMPAIGN_HOURLY_BUDGET` (1,000 provider calls per connection per rolling hour, service policy, deleted rows not carried) is separate from the private reply budget. Re-approving an executed draft version answers `409 campaign_version_executed`; approval and run responses say `delivery_available: true`, and migration 066 must run through the full runner before code deployment. Between the starts and the completion, `campaign_start` runs `endUnreachableCampaignDeliveries` ([sweep](../specs/2026-10-27-campaign-runs.md#도달할-수-없는-행의-정리), #273): in one statement it ends as `blocked`, with the final guard's first block code in the guard's order and from the guard's fragments, at most `CAMPAIGN_SWEEP_LIMIT` (500) oldest `pending` rows of `running` runs whose contact is paused or whose connection cannot send, locking only those rows `FOR UPDATE OF d SKIP LOCKED` and never claiming, setting an attempt or calling a provider; rows with only retry reasons stay `pending`, and migration 067 (which lets a `blocked` row have no attempt) must run through the full runner before code deployment.
`POST /api/campaign-runs/:id/cancel` (`admin`, `expected_version`) cancels the run and its `pending` rows in one transaction (workspace, run, rows); `sending` rows cannot be recalled (`sending_recalled: false`). `GET /api/campaign-runs/:id` returns counts only, no identifiers. The draft detail's run panel ([screen](../specs/2026-10-27-campaign-runs.md#실행-현황-화면)) reads the run only when the approval area shows an approval with a `run_id`, on its refresh button and when a cancel refusal carries no usable run (no polling), and cancels only through a confirmation that freezes the displayed `version` as `expected_version`; an unknown or throttled cancel is retried only as the same request, a 409 re-renders from the `run` the shared API wrapper forwards (`error.run`), and the module's generation and a run request counter discard late responses and responses for another run.
The three deletion functions remove the matching delivery rows (workspace deletion also the runs, before the approvals) and refuse with `sending_in_progress` while one is `sending`; both tables are exported and count in both workspace move checks, and migration 065 must run through the full runner before code deployment.
Approvals recorded before 065 keep `approved` with no age bound, so the first cron after `SEND_ENABLED` turns on starts every due one; review them before migrating and again before that switch ([procedure](../specs/2026-10-27-campaign-runs.md#이미-있는-승인과-배포-순서)).

## Contacts and segments

### Contacts

**Contacts** ([spec](../specs/2026-09-27-instagram-contacts.md)): contacts are derived from stored comment events and are returned without comment text or credentials. Manual tags (max 20) apply only to existing workspace-owned comment participants; empty tag arrays remove tags. The dashboard save (`saveContactTags`) also requires `expected_tags`, the tags the editor started from: after `lockContact` it compares them with the stored tags as sorted sets of the exact strings (not normalized, because two stored strings with one `normalizedStoredTag` form are distinct tags to segments and flows; the client sends back the strings it read) and refuses a difference with `409 contact_tags_stale` without writing, so an editor opened before another write (the external API, a flow run, the CSV import) cannot remove that write's tags; the client rereads the detail, applies the draft's own additions and removals (against the tags the editor started from) to the reread tags, and saves next on them, so a resave without an edit keeps the other write ([spec](../specs/2026-11-27-public-contact-writes-design.md#대시보드-태그-저장의-충돌-검사)). `scripts/contact-tag-conflict-acceptance.mjs` is the synthetic browser regression for it. Comment identities are not merged with DM identities. Each contact's `sender_username` is the commenter's own name from its newest comment that carried a valid webhook `from.username` (1–30 letters, digits, `.` or `_`, also a CHECK on `instagram_comment_events`), or NULL; an invalid or missing value never rejects the comment. `username` stays the connected account's name, and the v1 contact CSV does not carry `sender_username` (#388). Explicit `preview=true` adds exact decimal-string `total`, `evaluated` and disjoint `excluded.tag`/`field`/`both` counts from the same statement as the bounded samples. Evaluation stays within the workspace and selected account, including contacts that fail the filters; zero matches retain the summary, and OR excludes only contacts failing both predicates. It rejects any cursor, and ordinary list queries and response shapes remain unchanged. Optional paired canonical UTC `last_comment_from`/`last_comment_before` bounds filter each contact's latest stored comment in `[from,before)` independently of tag/field AND/OR. With a window, preview first classifies outside contacts as `excluded.activity`, then classifies tag/field mismatches only inside the window; without one, it omits the activity key. Paired `consent_purpose`/`consent_state` filters compare only the exact workspace/connection/Instagram/comment_sender/purpose current recorded grant, revoke or absent row; they never imply send eligibility or bridge DM identities. Paired `dm_consent_purpose`/`dm_consent_state` filters read the advisory verified bridge of the contact detail (`verifiedDmRecipientsSql` in `src/app/inbox-identity.ts`, same connection only) and match when any verified DM recipient has that current `dm_recipient` state; a contact without one never matches, and the filter merges no identities and is not the delivery guard ([DM consent](../specs/2026-10-16-segment-consent-state.md#dm-동의-기록)). An integer `last_dm_days` (1–366, independent of the comment activity forms) matches when any verified DM recipient's latest stored inbox message (text or postback) lies in `[as_of - N*24 hours, as_of)` at the statement's one evaluation clock, independently of which recipient matches DM consent, and returns only the UTC `dm_activity_window` bounds; it opens no messaging window ([DM activity](../specs/2026-10-16-segment-consent-state.md#dm-활동)). Preview excludes activity first, then `excluded.consent`, then `excluded.dm_identity`, `excluded.dm_consent` and `excluded.dm_activity`, then tag/field mismatches; it omits the keys of unselected conditions. A calendar `last_comment_period` (`today`, `yesterday`, `this_month`, `last_month`) excludes the fixed bounds and `last_comment_days`, and one statement computes its half-open local day or month boundaries in PostgreSQL from `statement_timestamp()` and the workspace `time_zone` (`AT TIME ZONE`, so DST gaps and overlaps are PostgreSQL's), returning `activity_window` with `time_zone` ([spec](../specs/2026-10-16-segment-relative-activity.md#달력-기간)). `tag` may repeat 1–5 times with `tag_mode` `all` (default, `tags @> S`) or `any` (`tags && S`), one predicate shared by the list, the preview and `segment_id`; a set that normalizes to one tag is the single-tag condition, and the whole set is one side of the tag/field AND/OR ([multi-tag](../specs/2026-09-27-contact-segments.md#다중-태그-조건)). The legacy `field_id`/`field_operator`/`field_value` keys carry one field condition and `field_conditions` (one bounded JSON array of 1–3 conditions on distinct fields, never mixed with the legacy keys) with `field_mode` `all` (default) or `any` carries a set, evaluated by one predicate (`jsonb_to_recordset` with `bool_and`/`bool_or`) that the legacy condition also passes through as a set of one, and the whole set is one side of the tag/field AND/OR ([multi-field](../specs/2026-09-27-contact-segments.md#다중-필드-조건)). `condition_tree` (one JSON object of at most 16,384 decoded characters) is a third form, never mixed with the tag, field or `condition_operator` keys (`invalid_contact_condition`) or `segment_id`: a root `all`/`any` over 1–5 groups, each `all`/`any` over 1–5 leaves (tag present, tag absent with `negate`, or one field condition), at most 10 leaves, order kept; one fixed SQL text evaluates it from `$19` with the field set's comparison text, the activity, consent and DM limits stay separate ANDs, and the preview reports `excluded.conditions` after the limit reasons instead of `tag`/`field`/`both` ([condition tree](../specs/2026-09-27-contact-segments.md#중첩-조건-그룹)).

### Contact CSV preview

**Contact CSV preview** ([spec](../specs/2026-10-17-contact-csv-preview.md)): `POST /api/contacts/import-preview` requires an active admin and accepts only `{csv}` with the exact exported v1 header, at most 128KiB UTF-8 and 500 records. It removes exactly one sender display apostrophe, preserves string identities and normalizes tags through the existing save validator. Invalid rows precede duplicate detection; all remaining duplicate connection/sender pairs are excluded. One SELECT rechecks role, connection ownership and existing comment contacts and returns current/proposed tag snapshots. It never stores files, applies tags, creates identities, changes consent or schedules delivery. The client clears previews on file/workspace/session changes, ignores stale responses and preserves contact editing drafts. Same-origin login/logout/password-reset events broadcast a data-free session signal that disables and clears every tab's preview; restored back-forward-cache pages also reset. Preview stays unavailable if a BroadcastChannel cannot be created. No migration is added.

### Contact CSV import

**Contact CSV import** ([spec](../specs/2026-10-17-contact-csv-import.md)): `POST /api/contacts/import` (`admin`) takes `{csv, expected}` and shares the preview's parser, classification and snapshot SELECT (`classifyImportRecords`, `readImportSnapshot` in `src/app/contact-csv-preview.ts`). ## Inbox

### Received inbox

**Received inbox** ([spec](../specs/2026-09-27-instagram-inbox.md)): each connection defaults to `inbox_enabled=false`, and its activation timestamp gates storage of new text DMs and confirmation postbacks. Disabling it keeps stored history under the manual deletion policy. `instagram_inbox_messages` deduplicates by connection and provider message ID in the confirmation transaction. DM recipient IDs stay separate from comment participant IDs.
[Attachments, unsupported messages and withdrawals](../specs/2026-11-26-instagram-inbox-attachments-design.md) (#20) are stored as kinds `attachment` and `unsupported` and as `deleted_at`. An attachment keeps only its type and optional title in `attachments`, never a media URL or media ID. These kinds open the 24-hour window and are recorded in `instagram_dm_last_inbound` and the active contact ledger, but `ingestMessages` never passes them to label rules, reply waits, the follow confirmation, kept DMs or DM triggers (`reachesAutomation` in `src/instagram/message-events.ts`); a new automation input needs its own decision. A withdrawal clears the stored text and attachments with UPDATE, because server roles cannot DELETE; it keeps the row, kind and time, and a withdrawal that arrives first stores a `deleted` row so the late original hits `ON CONFLICT DO NOTHING`; `storeInboxMessage` then returns true and that original reaches no automation. `lockInboxConversations` locks the connections of every withdrawal's account in its first ID-ordered statement, also for a withdrawal that stores nothing. A withdrawal opens no window, reopens nothing and is not counted. Copies outside the inbox (flow fields, kept DMs, customer webhooks) are not cleared (#58).
The list's `sender_username` is the stored Instagram User Profile API username of the DM recipient (`instagram_dm_profiles`, #395 stage 2); without one, the newest non-null comment `sender_username` of the commenter that a `confirmed` identity link of the same workspace and connection names for that DM recipient; otherwise it is `null`. It is computed only for the listed page through the link primary key and `instagram_comment_events_contact_lookup_idx`. It is a display hint: it does not merge comment and DM IDs, and it is not evidence of messaging consent or delivery eligibility. Without it, the list and the conversation title stay unchanged. Only `listInbox` calls the profile API (`refreshDmProfiles` in `src/app/inbox-profiles.ts`), never cron or ingestion: per request at most 5 listed conversations of active connections with a stored, unexpired token that decrypts whose profile row is missing or due (`next_fetch_at <= now()`); an OAuth reconnect keeps the new token on an inactive connection until its webhook subscription succeeds, so it is not used before then. One conditional upsert claims them (it moves `next_fetch_at` 5 minutes ahead and returns only the rows it claimed), so concurrent list loads call once per sender; it writes the rows in `(connection_id, recipient_id)` order, not list order, so concurrent claims do not deadlock. The claim runs in its own transaction, committed before any call: it locks the connections `FOR SHARE` in ID order, reads the token under that lock, and claims only conversations that still have stored messages, so it serializes with connection and person deletion and does not recreate a row that a deletion removed. Each claim writes a new `claim_id`, and the answer is stored only on the row that still carries it, so a late answer cannot overwrite a row that a deletion removed and a later claim created again. A messaging ID longer than the table's 40-digit CHECK is never claimed or fetched, so it cannot fail the claim of the other listed conversations. Each call has a 3-second timeout and `redirect: "manual"`, and sends the token only in the `Authorization` header to `graph.instagram.com`. A success stores the username and `fetched_at`, clears `failure_code`, and is fetched again after 7 days; a failure stores one fixed `failure_code` and is fetched again after 1 day, and keeps the username and `fetched_at` of an earlier success, which stays shown. Profile failures, a missing `TOKEN_ENCRYPTION_KEY` and a failed profile write never fail the list request, and logs carry fixed codes only. `name` and the profile picture are not stored. Only the list response carries it: the screen rewrites the open conversation's title when a conversation is chosen and when a list response contains the open conversation (also when the unread filter hides its row), and the existing newest-request check orders list responses. An open conversation that is absent from the latest list response keeps its title until a list that contains it returns or it is chosen again.

**Handoff** ([read contract](../specs/2026-09-27-inbox-handoff-contract.md), [writes and pause](../specs/2026-09-27-inbox-human-handoff.md)): the context read is advisory, masks identity unless one fresh sender is verified, and keeps missing, stale and ambiguous evidence distinct. ### Conversation assignment

**Conversation assignment** ([spec](../specs/2026-10-01-inbox-conversation-assignment.md)): `instagram_inbox_conversations` holds `open`/`closed` and the assignee per inbox conversation; no row means open and unassigned at version 0. `PUT /api/inbox/conversations/<connection>/<recipient>/state` locks the workspace row `FOR SHARE` first (`delete_workspace_data` takes it `FOR UPDATE` before the connections, and `removeMember` takes it `FOR SHARE` before the member row), the caller's and the new assignee's `workspace_members` rows `FOR SHARE`, the connection `FOR SHARE` (so it serializes with the deletion functions), the per-conversation advisory lock exclusive (`lockConversation` in `src/instagram/inbox.ts`), then the conversation row `FOR UPDATE`, checks `expected_version` (stale returns `409 conversation_conflict` with the current state) and writes one append-only `instagram_inbox_conversation_events` row per version. Agents may only claim an unassigned conversation or release their own; admins assign any active member. A newly stored inbox message reopens a closed conversation in the ingestion transaction (`auto_reopen`, no actor); before its first INSERT, `ingestMessages` takes the batch's message-ID locks ([DM start triggers](#dm-start-triggers)), then locks every connection of the batch's accounts `FOR SHARE` in ID order (inactive and inbox-disabled ones too, until COMMIT) and then takes `lockConversation` exclusive for every conversation the batch can store into, in (connection, recipient) order (`lockInboxConversations` in `src/instagram/inbox.ts`), and rereads the status after the INSERT, so it queues behind the deletion functions instead of deadlocking and waits for an uncommitted close (including the first one, which inserts the state row) instead of missing it, while DMs of different conversations never wait on each other and DMs of one conversation are serialized, and `removeMember` unassigns the removed member's conversations in its transaction (`member_removed`). Status and assignment never change the handoff or the automation pause, and neither recalls queued or in-flight sends.

### Inbox search and read state

**Inbox search and read state** ([spec](../specs/2026-09-27-instagram-inbox.md#검색-필터와-읽음-상태)): `GET /api/inbox` lists conversations by last message time DESC, then connection and recipient, with a cursor that carries the time as integer microseconds (a JavaScript `Date` would skip or repeat ties inside one millisecond); `q`, `unread` and the assignee filter choose conversations but every count, time and the order cover all of a conversation's messages, and `q` is a literal case-insensitive `strpos` match with no index; ordering by last message time makes every request scan all of the workspace's DMs, where the old connection-ordered list stopped after one page. `instagram_inbox_read_state` holds one forward-only `last_read_message_id` per workspace, connection, recipient and member, with no foreign key to the message or the member. `POST /api/inbox/conversations/<connection>/<recipient>/read` (`agent`) locks the workspace row `FOR SHARE`, the caller's member row `FOR SHARE` (rechecking `removed_at`), then the connection `FOR SHARE`, the order of the state change, before it checks that the ID is that conversation's message and upserts; a lower ID is a no-op, and it counts unread messages after its commit. The list returns the caller's `last_read_message_id` with each `unread_count`, and the screen keeps the count taken against the higher read position. Message IDs follow allocation, so ingestion holds the exclusive conversation lock from before its INSERT until COMMIT, which keeps one conversation's IDs in commit order and stops a read mark from counting a lower-ID DM that was not yet visible as read ([#127](https://github.com/AndrewDongminYoo/auto-chatter/issues/127)). Read state changes nothing else.

### Inbox labels and notes

**Inbox labels and notes** ([spec](../specs/2026-10-03-inbox-labels-notes.md)): labels belong to inbox conversations (connection and DM recipient) only, never to comment participants or contact tags, and no flow, webhook or reply reads them. `instagram_inbox_labels` is archive-only, at most 50 active per workspace (creation locks the workspace row `FOR UPDATE` before counting) with case-insensitive unique active names; `GET /api/inbox/labels` is `agent`, create, rename and archive are `admin`. `PUT /api/inbox/conversations/<connection>/<recipient>/labels` (`agent`) takes the whole set (at most 10 `uuid[]`, stored in place because server roles have no DELETE) and `expected_version` with the state change's lock order (workspace `FOR SHARE`, the caller's member row `FOR SHARE`, the connection `FOR SHARE`, `lockConversation` exclusive, the label-set row `FOR UPDATE`), then locks newly added labels `FOR SHARE` so a concurrent archive cannot slip between the check and the write; a stale version returns `409 label_conflict` with the current set, an unchanged set writes nothing, and each change writes one append-only `instagram_inbox_label_events` row. An archived label stays on a conversation that has it but can never be added. `instagram_inbox_notes` is append-only for server roles (no edit, no delete; a correction is a new note), written under the same workspace, member and connection locks (the workspace row `FOR NO KEY UPDATE` instead of `FOR SHARE`, for the [user record limit](#plan-entitlements)), and never sent, searched by `q`, listed as a message or read by a flow or webhook. `GET /api/inbox?label=<id>` combines with the other filters and the cursor. The three deletion functions remove label sets, their audit and notes (person deletion by DM recipient), and only workspace deletion removes the label definitions.

### Inbox reminders

**Inbox reminders** ([spec](../specs/2026-10-04-inbox-reminders.md)): a reminder belongs to the member who created it (`creator_id`); no other member, admin or owner can read or change it (another member's ID answers `404 reminder_not_found`), it is shown only in the app, and nothing sends it or runs it on a cron. `instagram_inbox_reminders` holds at most one `pending` row per workspace, connection, recipient and creator (partial unique index; a second create returns `409 reminder_exists` with the existing one), status changes are UPDATEs because server roles have no DELETE, and `instagram_inbox_reminder_events` is append-only with no actor only for the automatic `conversation_closed` and `member_removed` cancellations. Due is computed when read (`pending` and `due_at <= now()`). The screen sends a workspace-local `YYYY-MM-DDTHH:MM` and PostgreSQL converts it with the workspace's `time_zone` at write time (`localDueSql` in `src/app/inbox-reminders.ts`; a DST gap reads with the offset before the change and an overlap takes the later occurrence, unlike `wait_until`), from 1 minute to 2,160 hours ahead of `clock_timestamp()`; a later time zone change moves nothing. Writes take the state change's lock order (workspace `FOR SHARE`, the caller's member row `FOR SHARE`, the connection `FOR SHARE`, `lockConversation` exclusive, then the reminder row) and check `expected_version` (`409 reminder_conflict` with the current reminder). A closed conversation holds no pending reminder: closing (`PUT .../state`, open to closed) cancels every member's pending reminders on it in the same transaction, creating one on a closed conversation returns `409 conversation_closed`, and no reopen revives them; `removeMember` cancels the removed member's pending reminders in its transaction after locking their connections `FOR SHARE` in ID order. `GET /api/inbox?reminder=due` combines with the other filters and the cursor, and the list carries the caller's pending reminder per conversation plus `due_reminder_count` for the badge. The three deletion functions remove every member's reminders and their audit (person deletion by DM recipient), and the workspace export leaves both tables out (`EXCLUDED_TABLES`), so an admin's export carries no other member's reminders.

### Inbox label rules

**Inbox label rules** ([spec](../specs/2026-10-04-inbox-label-rules.md)): `instagram_inbox_label_rules` is workspace-wide (no connection), archive-only, at most 50 active per workspace (creation locks the workspace row `FOR UPDATE` via `lockWorkspaceForMember` before counting), `admin` for every route, with `contains`/`exact` only (no `all`) and keywords stored in the comment-rule normalization (`normalizeMatchText` in `src/instagram/comment-rule.ts`). `storeInboxMessage` applies them (`applyLabelRules` in `src/instagram/inbox.ts`) only to a text DM its INSERT stored, never to a postback, a redelivery or an earlier DM; after the ingestion locks it reads the rules unlocked and decides with the candidate labels already locked `FOR SHARE` by ID (so a fully skipped DM, even one that waited on a label archive, leaves no row), then takes the manual path's order (version 0 placeholder, label-set row `FOR UPDATE`, labels `FOR SHARE`) and skips, rather than throws on, an archived label, a label already present, a label a member ever removed from that conversation (`actor_id` set in `removed`), labels beyond 10 (kept in rule order) and a sender ID longer than the label tables' 40 digits, because a throw would roll back the DM and the batch's confirmations. One DM writes one version and one audit row whose `rule_id` is the first matching rule by `(created_at, id)`, even when that rule's own label was skipped, and whose `actor_id` is NULL (CHECK: exactly one of the two). A rule edit locks the rule `FOR NO KEY UPDATE` and, only when its content changes, the new label `FOR SHARE`; an archive is one non-key UPDATE and locks no label; neither takes a connection or conversation lock. Only `delete_workspace_data` removes rules (after the label events, before the labels), and the rules count in both workspace move checks.

### Manual replies

**Manual replies** ([server](../specs/2026-09-27-inbox-manual-replies.md), [UI](../specs/2026-09-28-inbox-manual-reply-ui.md)): requests carry a UUID key and the active handoff version; identical repeats return the existing row and payload reuse is refused. Only a fresh stored inbound text, attachment or unsupported DM opens the 24-hour window (#20); a postback and a withdrawal-first `deleted` row do not. Cloudflare delivery rechecks the claim, token version and expiry, connection, handoff, identity bridge, derived pause and window immediately before POST. Earlier due pending rows preserve creation order; any sending or unresolved unknown row blocks every other reply in the same conversation, regardless of creation order. Future scheduled pending rows do not block immediate replies. One-shot [scheduled replies](../specs/2026-10-16-inbox-scheduled-replies.md) store an absolute `scheduled_at`, the accepted workspace time zone and a version; migration 049 must run before code deployment. Only the creator or an active admin may edit or cancel a pending scheduled row, with a version and idempotent operation key. The claim, wake and health queries exclude future schedules. The worker rechecks the scheduled creator’s active membership before sending; removal blocks delivery, while an admin-to-agent change remains allowed. Definite unsent failures allow an audited retry as a new linked row; unknown never allows retry, and an audited `no_retry` releases waiting rows. Stale sends become unknown with audit in the same transaction. Server roles cannot UPDATE or DELETE the audit.

### Reply templates

**Reply templates** ([spec](../specs/2026-10-16-inbox-reply-templates.md)): `workspace_reply_templates` stores workspace snippets, with 50 active names unique case-insensitively. Admins manage them; agents may list and preview. The restricted `{{name}}` grammar accepts at most 10 distinct names, and preview substitutes explicit strings once without reading customer fields or writing deliveries or consent. Both stored and rendered text use the manual composer's 1,000 UTF-16-unit limit. Edits require `expected_version`; archive is idempotent. The composer appends a successful preview to its current draft and refuses pending/unknown acceptance operations or combined overflow. Values, conversation changes and session reset invalidate previews and late responses. The table belongs in export, whole-workspace deletion and both empty-workspace movement checks; migration 048 must run through the full runner before code deployment. It does not schedule or send messages.

**Flow versions** ([spec](../specs/2026-09-29-flow-version-contract.md)): `src/app/flow-schema.ts` is the pure document parser and publish validator; `flows` holds the draft, its revision and the publish pointer, and `flow_versions` rows are immutable (no server UPDATE/DELETE). ### Flow runs

**Flow runs** ([spec](../specs/2026-09-30-flow-runs.md)): publishing never sends; only an `enabled` flow runs, and enabling (or republishing an enabled flow) requires an OAuth trigger connection and a version that `flowExecutionErrors` in `src/app/flow-runtime.ts` accepts; archiving the flow or disconnecting its trigger connection turns it off. Comment ingestion starts at most one run per `(flow_id, event_id)`, pinned to the published version, only when no enabled legacy rule owns the media. Its reply is a `private_reply_outbox` row with `flow_run_id` instead of `rule_id` (exactly one is set), so every existing delivery guard applies; the shared claim check and the Cloudflare final guard block a disabled flow's reply as `inactive_flow`. Publish and enable lock the flow row `FOR NO KEY UPDATE`, so they never block the foreign-key checks of an ingestion batch that holds a connection lock. Tag and field actions run in the ingestion transaction under the contact-write connection lock (`FOR SHARE`, rechecking `active`), field row locks and `lockContact` (a per-contact advisory lock in `src/app/contact-fields.ts`) taken before the read; manual tag and field saves take the same `lockContact`, so recorded outcomes match what is stored. Actions apply to paused contacts too. A `delay` node (1 to 10,020 minutes, and at most that in total on any path to a message, so the reply fits the 7-day comment window) leaves the run `waiting` with a UTC `resume_at`; only the Cloudflare cron resumes it (`resumeDueFlowRuns` in `src/instagram/store.ts`), locking the connection `FOR SHARE` before the run row (`FOR UPDATE SKIP LOCKED`, still `waiting`), the same order as the deletion functions, and rereading contact facts; a run whose flow is off or whose connection is inactive when due ends `cancelled` without running later nodes, and re-enabling never revives it. A `wait_until` node (`HH:MM`, counted as 1,560 minutes toward that total, a day plus the largest clock-back shift) also leaves the run `waiting`, with `resume_at` the next occurrence of that wall-clock time strictly after `clock_timestamp()` in the workspace's `time_zone`, read when the run reaches the node and computed in PostgreSQL (`nextWallClockSql` in `src/instagram/store.ts`), so daylight-saving shifts are PostgreSQL's, a time that occurs twice resumes at its first occurrence still ahead, and a later zone change moves no waiting run. On a day the clocks go back a time wait can last a day plus the shift (under 1,560 minutes in `Antarctica/Troll`), so a path at the 10,020-minute total can reach a message after the 7-day window; that reply is blocked as `comment_expired` before the send, never sent late. A message may lead only to a `wait_for_reply` node (1 to 10,080 minutes, optional text `save_field_id`), and no message may follow the wait; queuing that message leaves the run `awaiting_reply` at the wait with no `resume_at`. `resumeRepliedFlowRun` in `ingestMessages` continues it on `replied` for a text DM (not a postback) from the reply's `recipient_id` dated from its `sent_at` to before `sent_at` plus the timeout, most recent reply first, locking the connection `FOR SHARE` and then the run `FOR UPDATE` (still `awaiting_reply`, else it retries the next most recent run), and records the message in `flow_runs.reply_message_id` so a redelivered message advances no other run on that connection; the cron continues it on `timeout` only after its reply is `sent` and the wait has passed, so a reply that never becomes `sent` keeps the run waiting. Flow off or connection inactive cancels it as for a delay, and a paused contact's reply still advances it. Message variables render once, so comment text is never re-parsed; a missing value, a boolean, or an empty or over-1000-character result fails the run without queuing a reply. `flow_step_runs` is append-only for server roles. The Node environment-token worker never sends flow replies.

### Early replies

**Early replies** ([spec](../specs/2026-09-30-flow-runs.md#발송-기록-전에-도착한-응답)): a text DM or confirmation postback that matched neither a follow conversation nor an awaiting run is kept in `instagram_unmatched_replies` only while the same connection has a reply in `sending` whose attempt started within 10 minutes and no later than the DM; `ingestMessages` reads that condition before the lookups and locks the connection `FOR SHARE` with it, so a deletion cannot commit before the kept row is written. After a reply is recorded as `sent`, a separate best-effort transaction (and the Cloudflare cron, or the Node worker's recovery tick) offers kept DMs from its `recipient_id` dated at or after its `attempt_started_at` to the reply wait and the follow confirmation, with `sent_at` widened to `attempt_started_at` for this path only; it locks the connection `FOR SHARE` before the kept row, rechecks the 15-minute boundary at that claim, and marks `matched_at` whether or not anything advanced. Both passes skip a kept DM while its connection still has a reply in `sending` that started within 10 minutes and no later than the DM, so an earlier sent reply to the same person cannot use it up; the only exception is that the post-send pass takes a confirmation postback bound to its own reply, and it leaves one bound to another reply alone. A reply wait does not time out while an unlinked kept text DM from its recipient, dated from the reply's attempt start to before the wait ends and under 15 minutes old, may still answer it. Kept text is no longer linked 15 minutes after receipt and is removed by the first scheduled run after that (no hard upper bound; `/privacy` says so), and the export omits it.

### Flow test runs

**Flow test runs** ([spec](../specs/2026-09-30-flow-runs.md#테스트-실행)): `POST /api/flows/<id>/test-run` (`admin`) walks the draft or the published version with `planFlowRun` over synthetic `comment_text`, `tags`, `fields`, `reply_text` and one `reply_branch`, continuing at once from every delay, time wait and reply wait. After the role check, it reads the flow and its publish context in one `REPEATABLE READ READ ONLY` transaction after the role check, never reads stored contact, comment or message data, and writes, queues or sends nothing. An optional `expected_revision` (draft only) returns `409 revision_conflict` when the stored draft has moved on, read in the same snapshot as the draft. A draft that fails publish validation, or a document that fails `flowExecutionErrors`, returns only its errors (422). Publish and the test run share `readPublishContext` in `src/app/flows.ts` (publish with its locks, the test run without), and the run's `flowWebhookPayload`, `fieldWriteTargets` and `webhookFieldIds` build its webhook previews, writable fields and #117 exclusions.

### Flow webhooks

**Flow webhooks** ([spec](../specs/2026-10-01-flow-webhook-delivery.md)): a `webhook` node (`{endpoint_id, field_ids, include_tags}`, port `next`) queues one `webhook_deliveries` row per `(flow_run_id, node_id)` in the run's transaction and the run continues without waiting; a delivery outcome never changes a run, a later node or a reply row. The payload holds only the chosen tags and field values and processing identifiers, never comment or DM text, a username or an Instagram identifier. A field that any published version of the workspace saves a reply into (`wait_for_reply.save_field_id`, current version or not) is never sent: publish refuses it on the `webhook` node, and on a reply wait that would save into a field another flow's webhook sends (`reply_field_not_sendable`), and `planFlowRun` leaves it out of every payload whatever was published (`replySavedFields` in `src/app/contact-fields.ts`, read after the contact facts). `sender_id` is stored beside it for person deletion only, and the payload is removed by the UPDATE that marks the row `sent`. Only the Cloudflare cron step `webhook_delivery` delivers (`deliverDueWebhooks` in `src/app/webhook-delivery.ts`), after the message steps and only while `SEND_ENABLED` is `true`; the Node worker never does. Each claim takes the workspaces in turn, by the [delivery order](../specs/2026-10-01-flow-webhook-delivery.md#전달-순서). Every attempt reads the endpoint again (inactive ends `dead / endpoint_inactive`), applies the URL rules again (`parseWebhookUrl`, shared with endpoint creation) and resolves A and AAAA through DNS-over-HTTPS immediately before the POST, refusing when any address is not public; Workers `fetch` resolves the name itself, so that check and the request are not atomic. The POST uses `redirect: "manual"` and a timeout that covers the body, and the response is read up to a size limit and never stored. A claim uses `FOR UPDATE SKIP LOCKED` and a fresh `attempt_id`, and later changes require `status = 'sending'` and that ID; a failure retries on the fixed schedule and then ends `dead`, and a stale `sending` row counts as an attempt, so delivery is at-least-once and `event_id` (kept across retries and a manual redelivery) is the receiver's deduplication key. Signing secrets are sealed with `TOKEN_ENCRYPTION_KEY` under `signingKeyContext` (workspace, endpoint, key), returned once at creation or rotation, at most two valid per endpoint, and every valid key signs each request. Every `/api/webhooks/*` route needs `admin`. Server roles have no DELETE on the four tables and no UPDATE on `webhook_redelivery_events`; the three deletion functions remove the rows and refuse with `sending_in_progress` while a delivery in their scope is `sending`. Delivery logs carry fixed codes only: never a URL, host, payload, secret or response.

### DM start triggers

**DM start triggers** ([spec](../specs/2026-11-08-instagram-dm-start-triggers.md)): `instagram_dm_keyword` (`{connection_id, keywords, match_mode: contains|exact|all, excluded_keywords}`, keywords required unless `all`) and `instagram_dm_default` (`{connection_id}`) are trigger nodes; a flow has exactly one trigger of any type. A DM-triggered flow holds only the trigger and `instagram_message` nodes without variables (`dm_trigger_unsupported_node`, `dm_trigger_unsupported_variable`), because a DM run has no comment, no 7-day window and no outbox, and its messaging sender ID is never linked to a comment contact; the refusals beyond `{{comment.text}}`, `wait_for_reply` and `delay` are a narrowing the spec lists separately. `flow_versions.trigger_type` keys a version: comment versions keep `(connection, media)`, DM versions have a NULL `trigger_media_id` (CHECK `flow_versions_trigger_key`). Publish (even of a disabled flow) and enable compare the trigger with the other enabled DM flows of the connection after the connection `FOR NO KEY UPDATE` lock: one enabled default-reply flow per connection (`dm_default_conflict`) and no overlapping keyword sets (`dm_keyword_conflict`, `dmTriggersOverlap` in `src/app/flow-schema.ts`; an `all` trigger overlaps every keyword trigger). `ingestMessages` calls `startDmTriggerFlow` (`src/instagram/dm-start-trigger.ts`) only for a typed DM that neither `resumeRepliedFlowRun` nor `offerMessage` took, after `keepUnmatched`; it reads flows and versions without row locks (publish and enable lock flow then connection) and takes the connection `FOR SHARE`. A keyword flow beats the default flow, the oldest matching flow wins, and one DM starts at most one run. Nothing starts for a message ID already in `instagram_message_receipts`, `flow_runs.reply_message_id` or `instagram_unmatched_replies`, or for a sender with a resumable run, a follow conversation in `waiting`/`pending`/`sending` under an enabled rule, an unlinked kept DM under 15 minutes old, a `service_reply` revoke of the messaging ID or of a comment sender bridged to it by a provider-acknowledged reply, with that sender's other bridged DM recipients (`messagingRecipientOptedOut` in `src/instagram/channel-consent.ts`, built on `deliveryRecipientOptedOutSql`), or an active inbox handoff; a blocked DM writes no row. In reverse (#291), a message ID already in `instagram_dm_start_events` for the consumer's connection is taken by neither `offerMessage` (also on the kept-DM reconcile) nor `resumeRepliedFlowRun` and is not kept by `keepUnmatched`, so a redelivery of a DM dated ahead of a later private reply writes no receipt, `reply_message_id` or kept row; each check is a read in the consumer's own statement, and a concurrent redelivery sees the start event because `ingestMessages` first takes a transaction advisory lock per distinct (account ID, message ID) of the batch (`'instagram-message:'` key, `lockMessageIds` in `src/instagram/follow-flow.ts`), before every other lock and in key order, whether or not inbox storage is on. `instagram_dm_start_events` (unique `(connection_id, message_id)`, never DM text), the run (`flow_runs.dm_start_event_id`, exactly one source by CHECK `flow_runs_source`) and the first message in `flow_dm_deliveries` (recipient = messaging sender ID, written `pending`, never `private_reply_outbox`) are written in the ingestion transaction; the run history and the flow-run report read its status, failure code and send time as the run's delivery state, and the run itself stays `delivering`, as a comment run does after its private reply. Delivery (#291, migration 069): only the Cloudflare queue consumer sends these rows, through `processNextDmFlowDelivery` in `src/instagram/dm-flow-delivery-worker.ts`, after manual replies and follow confirmations and before private replies and campaign rows; the Node worker never reads them, and no other claim, worker or resume does. `dmFlowDeliveryDueSql` is the one due predicate of the claim, `wakeDueReplies` and operations health: pending, due, no messaging-ID pause (`instagram_dm_automation`, keyed by workspace, connection and messaging ID, never linked to `instagram_contact_automation`) and no active `instagram_inbox_handoffs` row for the recipient; held rows stay pending. The claim takes one row `FOR UPDATE SKIP LOCKED` with a fresh `attempt_id`, and every later write is conditional on `status='sending' AND attempt_id`. `assertDmFlowDeliveryAllowed` runs after the claim, after the account read and as the transport's `beforeSend` immediately before the POST, in one statement: claim, run `delivering`, flow enabled and not archived (a republish does not stop the pinned version), connection sendable, token unchanged, no connection pause, the 24-hour window, the pause and the handoff, then `messagingRecipientOptedOut`; any block beats any retry. The window is open while the database clock is under 24 hours after the latest of the sender's DM start events, stored inbox `kind='text'` messages and last inbound text DM time on the connection, each capped at its stored time because ingestion accepts DMs up to 60 s ahead; a stored postback is excluded on purpose, as in the manual-reply window. The last inbound time (#300, migration 072, `instagram_dm_last_inbound`, keyed by connection and messaging ID, a time only) is written by `recordLastInboundDms` in `src/instagram/follow-flow.ts` once per batch, as the last statement before COMMIT (so its row locks never queue the reply wait or the DM triggers), for every active connection of the account whether or not inbox storage is on: text DMs only, not more than 60 s ahead, at most 40-digit sender IDs, the connections locked `FOR SHARE` in ID order first, rows written in `(connection, messaging ID)` order, capped at `now()` and never moved back. Outcomes follow the campaign worker; a rate limit uses the private-reply tiers (`rateLimitRetryDelaysSeconds`, `rate_limit_retries`, `failed` after the third) and pauses the connection; a pause seen after the guard defers as `connection_paused` without spending a retry; a stale `sending` row becomes `unknown`/`worker_interrupted` in the cron's `stale_recovery`. No hourly delivery budget applies: the send-quota spec exempts Send API DMs. The starts are bounded instead (#400, migration 075, [spec](../specs/2026-10-12-send-quotas.md#dm-시작-한도)): after `startBlocked` passes and before any run row, `dmStartSkipCodeSql` in `src/instagram/send-quota.ts` (the one definition) gives `sender_cooldown` when the sender has a started event on the connection in the last `DM_START_SENDER_COOLDOWN_MINUTES` (10), else `connection_hourly_limit` when the connection has `DM_START_HOURLY_LIMIT` (700) started events in the last hour; both count rows with `skip_code IS NULL` by `created_at` against one `clock_timestamp()` read per decision (the caller's `decided_at` subquery), the clock that writes `created_at`, because `now()` is fixed at transaction start and would judge a DM that waited on a lock or followed earlier DMs of its batch against an older window, and a volatile `clock_timestamp()` inside the conditions cannot bound the `created_at` index scans. A skipped DM writes its start event with `skip_code` and no run, delivery or step rows; a precedence block still writes no row. `ingestMessages` takes a transaction advisory lock per distinct (account ID, sender ID) of the batch's typed DMs (`'dm-start-sender:'` key, `lockDmStartSenders`) right after the message locks, in key order, so two DMs of one sender cannot both start; the hourly limit takes no lock and can be exceeded by the starts of concurrently ingesting batches. Operations health reports the skipped starts of the last 24 hours as `dm_start_cooldown_24h` and `dm_start_hourly_limit_24h`; the claims and the wake are unchanged because a skipped DM creates nothing to send. The pause has no API route or screen yet. `CLAIMED_RUN` joins both sources, and a DM run that reaches `continueFlowRun` ends `cancelled`/`unsupported_trigger`. The editor (#292) creates both DM triggers from a trigger-less flow, never changes a trigger's type, offers only `instagram_message` after a DM trigger (so one message) and no message variables there, and sends a DM test run only the source and text (plus the revision for a draft); for the published source the published version as read decides the trigger kind, never the draft, and no run is sent before it is read (`flowTestDocument`, #305). The three deletion functions lock DM flow rows `FOR UPDATE NOWAIT` and refuse `sending_in_progress` while one is held or sending, remove deliveries, steps, runs, then start events, and remove the messaging-ID pause and the last inbound time (person deletion by the `dm_recipient` set); all three tables, `instagram_dm_automation` and `instagram_dm_last_inbound` are exported, and migrations 068, 069 and 072 must run through the full runner before code deployment.

## Deletion, workspace and operations

### Connection data deletion

**Connection data deletion** ([spec](../specs/2026-09-29-connection-data-deletion.md), [UI](../specs/2026-09-30-connection-deletion-ui.md)): `public.delete_connection_data` is the only path that deletes product rows, apart from `public.delete_expired_oauth_states`, which the cron uses to remove expired OAuth states (migration 038). It is an administrator-owned SECURITY DEFINER function; server roles have EXECUTE on it and still no table DELETE. It requires the workspace-owned connection to be disconnected (inactive, send off, no token), the confirmed account ID, and no `sending` rows, checked after locking the connection `FOR UPDATE` and its delivery rows `FOR UPDATE NOWAIT`; a row held by another transaction refuses with `sending_in_progress` instead of waiting, which would deadlock with a send being finalized (migration 023). It keeps revoke consent records, the connection row and user configuration (the outbox `AFTER DELETE` trigger still updates the connection's private-reply carry columns when deleted rows called Meta within the hour, as in person deletion; [carry](../specs/2026-10-12-send-quotas.md#삭제한-행의-호출-이월)), and writes a counts-only `data_deletion_records` row that runtime roles can read but not write. Before deleting the reply bridge it re-records bridged DM-recipient opt-outs on the comment sender. Contact tag, field value and automation writes, and the inbox profile claim, lock the connection row `FOR SHARE` first so they serialize with deletion.

### Person data deletion

**Person data deletion** ([spec](../specs/2026-09-30-person-data-deletion.md)): `public.delete_person_data` is an administrator-only SECURITY INVOKER function with EXECUTE revoked from PUBLIC, API and server roles; there is no API. From a comment sender or DM recipient it follows the provider-acknowledged reply bridge and handoff pairs to a closure, locks that person's delivery rows, and deletes only that person's rows in one connection. It refuses while any of that person's rows is `sending`, keeps revokes (re-recording bridged DM-recipient opt-outs on the comment sender), does not create an opt-out, and writes a `scope=person` evidence row without the identifier.

### Workspace deletion

**Workspace deletion** ([spec](../specs/2026-09-30-workspace-data-deletion.md)): `public.delete_workspace_data` is an administrator-only SECURITY INVOKER function with EXECUTE revoked from PUBLIC, API and server roles; there is no API. It locks the workspace and all its connections `FOR UPDATE`, refuses while any connection is still connected or any delivery row is `sending` or held by another transaction (`FOR UPDATE NOWAIT`, migration 023), deletes every product row of the workspace including revokes and `data_deletion_records`, then the OAuth states, membership and workspace. It writes a counts-only `workspace_deletion_records` row (no foreign keys, no member IDs, no runtime access) and returns `owner_user_id`, the only Supabase Auth user the administrator deletes, plus informational `member_user_ids`.

### Workspace roles

**Workspace roles** ([spec](../specs/2026-09-30-workspace-roles.md)): `workspace_members.role` is `owner`, `admin` or `agent`, with at most one owner per workspace and one workspace per user. `workspaceFor(pool, user, role)` takes the least role as a required argument and reads membership and role on every request, so a removal or downgrade applies to the next request; agents keep inbox, handoff, manual reply, contact and consent work and read-only settings, and every settings change, account connection, data deletion and the export needs `admin`. `workspaces.time_zone` (default `Asia/Seoul`) is returned to every role by `POST /api/workspace` and changed only by admins through `PUT /api/workspace/settings`, which stores only exact `pg_timezone_names` names (`invalid_time_zone`; no CHECK constraint, because that list can change). Owner-only invites (`workspace_invites`, SHA-256 of a single-use 7-day link token, bound to the confirmed email) and member removal (`removed_at`, since server roles have no DELETE) live in `src/app/workspace-members.ts`; every membership read excludes removed rows. Accepting an invite moves a sole owner only out of an empty workspace (`currentWorkspaceMovable`, mirrored in `deploy/assign-workspace-owner.sql`), so a new workspace-scoped table whose rows do not require an `instagram_connections` row must be added to both checks.

### Workspace export

**Workspace export** ([spec](../specs/2026-09-30-workspace-export.md)): `GET /api/workspace/export` returns the caller's workspace as one JSON file read in a single `REPEATABLE READ READ ONLY` transaction. Every public table must be listed in `EXPORTED_TABLES` or `EXCLUDED_TABLES` in `src/app/workspace-export.ts`, and secret-like columns must be in that table's `omit`; `workspace-export.db.test.ts` enforces both. A per-user request limit (`WORKSPACE_EXPORT_LIMIT`) runs before the database, and a size check in the same snapshot refuses an oversized workspace whole before any `jsonb_agg` (`WORKSPACE_EXPORT_LIMITS`; numbers in the [spec](../specs/2026-09-30-workspace-export.md#요청-한도와-크기-한도)); it never truncates.

### Workspace API keys

**Workspace API keys** ([spec](../specs/2026-11-27-workspace-api-keys-design.md), #48, migration 080): `src/app/api-keys.ts` issues, lists and revokes keys through `/api/workspace/api-keys`, and every route needs `admin`. A key is `ac_live_` plus 43 base64url characters; it is returned once in the issue response, and `api_keys` stores only its SHA-256 hex (`key_hash`, unique) and its first 12 characters (`key_prefix`). The list, the export (`omit: ["key_hash"]`) and `GET /v1/key` never return the key or the hash. Every key expires after 30, 90, 180 or 365 days, and a workspace has at most `MAX_ACTIVE_API_KEYS` (10) keys that are neither revoked nor expired, counted under the workspace row lock (`409 api_key_limit_reached`). A key's scopes are `{contacts:read}` or `{contacts:read,contacts:write}` in that order: `parseApiKeyRequest` requires `contacts:read` and stores `API_KEY_SCOPES` order, and the CHECK `api_keys_scopes_check` (migration 081) admits only those two arrays; the issue form has an unchecked "연락처 쓰기 허용" checkbox. An issue locks the workspace `FOR NO KEY UPDATE` and then the caller's membership row `FOR SHARE` and checks the role again: a removal or demotion that commits first refuses the issue, and one that commits later revokes the new key. `removeMember`, and `changeMemberRole` to `agent`, call `revokeMemberApiKeys` in their own transaction (`member_removed` or `member_demoted`); a change that keeps `admin` leaves the keys alone. `api_key_events` is append-only (server roles have no UPDATE or DELETE) and records `created` and `revoked` with the actor and the two automatic kinds without one; expiry is not recorded. `/v1/*` is routed in the Worker before the webhook path and never through `appApi`: `src/app/public-api.ts` spends the per-IP limit (`api-ip:<IP>`, 600 a minute, every request) before it reads the `Authorization: Bearer` header, reads the key row by hash only, then spends the per-key limit (`api-key:<id>`, 60 a minute); only a successful response writes `last_used_at` and `last_used_ip` (`CF-Connecting-IP`), at most once a minute, so a 404 or 405 does not. Both limits fail closed (`503 api_key_limit_unavailable`), every key refusal is the same `401 invalid_api_key`, there are no CORS headers, and logs carry fixed codes only. Both tables are workspace rows without a connection, so they are in both workspace move checks and `delete_workspace_data`. The synthetic browser regression in `scripts/api-key-settings-acceptance.mjs` covers the list states, the key shown once, its absence from browser storage, the revoke confirmation and an out-of-order list response that must not restore a revoked key and the write checkbox; it does not prove the deployed API.

**External contacts read** ([spec](../specs/2026-11-27-public-contacts-api-design.md), #48, no migration): `PUBLIC_API_ROUTES` in `src/app/public-api.ts` lists every `/v1/` path and method, and a unit test compares it with `docs/api/openapi-v1.json` (OpenAPI 3.1, not served); change both together. The path and method are checked only after the key and the per-key limit, so an unknown path is a 401 without a key. `GET /v1/contacts` needs the `contacts:read` scope (`403 insufficient_scope` otherwise) and then `parseContactsQuery` in `src/app/public-contacts.ts`: only `limit` (1-100, default 100), `after` and `connection_id`, each at most once, else `400 invalid_request`. The cursor is the canonical base64url of the JSON array `[connection_id, sender_id]` of the last row; it holds no workspace, and the page statement always binds the key's workspace, so a cursor at another workspace's position reads nothing of it. A cursor of another connection than `connection_id` is a 400, and a `connection_id` outside the key's workspace is `404 connection_not_found`, the same as an ID that exists nowhere. One page is one statement without a transaction or lock (`query_timeout` 10 s) that reads `limit + 1` rows in the order of the connection ID and then the sender ID in the column's collation (not the CSV export's `COLLATE "C"`, so that `instagram_comment_events_contact_lookup_idx` drives the cursor range and the grouping; the connection and cursor conditions are in the statement text only when the request has them) and builds each row with `CONTACT_ROWS_SQL`, the row SQL the CSV export v1 also uses, so the API sends no more personal data than the CSV: no sender username, consent, comment or DM text, or credentials. `tags_json` and `fields_json` are spliced into the response as PostgreSQL's JSON text so numbers keep every digit, and `sender_id` and `comment_count` stay strings. Only a 200 records the key's use; a 400, 403 or 404 does not. A contact recorded during a full read at a position already passed is missing from that read, and the OpenAPI document states this limit.

**External contact writes** ([spec](../specs/2026-11-27-public-contact-writes-design.md), #48, migration 081): `PATCH /v1/contacts/{connection_id}/{sender_id}` (`contacts:write`) and `GET /v1/fields` (`contacts:read`) are in `PUBLIC_API_ROUTES`; `matchPublicApiRoute` turns each `{param}` of a template into one path segment. `src/app/public-contact-writes.ts` parses the body (`tags.add`/`tags.remove` through `normalizeContactTags`, the same tag in both lists, an unknown key, a key named twice in one object (`hasDuplicateJsonKey` over the raw text, since `JSON.parse` keeps only the last value), more than 20 fields or no change are `400 invalid_request`; a non-scalar or lone-surrogate value, or a number whose double is not the decimal value of its source text (`exactNumberReviver`), is `400 invalid_field_value`), then reads the fields without a lock (`404 field_not_found`, a wrong type `400 invalid_field_value`), and only then spends the workspace write limit, so a 400, 401, 403, 413 or 415 spends nothing of it. The limit is the dashboard's `API_WRITE_WORKSPACE_LIMIT` with the workspace ID as key and the plan's `api_writes_per_hour` (`spendApiAllowance` in `src/app/auth-rate-limit.ts`, fail open with `api_limit_unavailable`); the per-IP and per-key limits stay fail closed. One transaction takes the workspace row `FOR KEY SHARE` first (a field value insert takes that lock through its foreign key, and `delete_workspace_data` locks the workspace before its connections, so taking it later deadlocks with a workspace deletion), then the connection `FOR SHARE` (`404 connection_not_found`), the fields `FOR SHARE` in ID order, then `lockContact`, reads the stored tags (`404 contact_not_found` without a comment), removes stored tags matched by `normalizedStoredTag` (the tag normalization is not idempotent), then adds each tag in the single-pass `normalizeContactTags` form the dashboard save stores unless that exact string is stored (another single-pass string of the same `normalizedStoredTag` form stays beside it, because segment and flow tag conditions compare exact strings), refuses more than 20 with `409 contact_tag_limit`, upserts the tags and each field value (null stores NULL; no DELETE), and answers the contact in the `GET /v1/contacts` shape from `CONTACT_ROWS_SQL`. Unnamed tags and fields stay, and a repeated request gives the same result, so there is no idempotency key. The key check runs outside the transaction, so a write that started before its key was revoked can still commit. The last-use record runs after the commit; its failure logs `api_key_use_unrecorded` and the write still answers 200.

### Active contact ledger

**Active contact ledger** ([spec](../specs/2026-11-24-active-contact-ledger-design.md), #51, migrations 077 and 078): `active_contacts` holds one row per workspace, billing month, connection and person key, with no foreign keys; the unique key `active_contacts_person` keeps the default NULLS DISTINCT, so a cleared key never collides.
Comment ingestion takes only the connection's foreign-key KEY SHARE lock, so it does not wait for `delete_person_data` (FOR NO KEY UPDATE): a comment and its ledger row that commit after the deletion are a new record, which the person data deletion spec already keeps for comments, and running the same deletion again clears that row's key.
The connected account's own comments are stored but never recorded: the comment write, the backfill and the recompute all skip a sender equal to the connection's `account_id` or `instagram_user_id` (the Graph profile ID that the private reply check also compares is not stored, so a comment under only that ID is still recorded).
`record_active_contacts` in `db/schema.sql` is the one writer: it takes the billing month from the workspace `time_zone` at write time and stores that zone on the row, resolves the person key, keeps the earliest activity of each key in the call and inserts in key order with `ON CONFLICT DO NOTHING`.
`first_activity_at` and `activity_kind` are the time and kind of the activity that created the row: the earliest activity of the first write of that key in that month, not the earliest activity of the month, because a later write of an earlier activity (a delayed or reverse-order DM) conflicts and changes nothing.
The person key is the comment sender ID, the DM recipient ID, or for a DM recipient the comment sender that `active_contact_linked_sender` returns: a `confirmed` identity link whose evidence is the current verified evidence, the rule of `verifiedDmRecipientsSql` in `src/app/inbox-identity.ts` (change both together; the DB test compares them). A later link, detach or time zone change rewrites no stored row.
Writers, each the last lock-taking statement of its transaction, so an uncommitted ledger key is never held while the transaction waits on another lock:

- Comments: `recordActiveContactComments` in `src/instagram/store.ts`, the last statement of `ingestComments`, for the comments the batch stored (`created_at`). A comment trigger would hold the sender's key while the same transaction's private reply insert waits on a send finalize of that sender's reply, whose ledger write waits on that key (a deadlock; the DB race test reproduces it with a trigger).
- Inbound DMs: `recordActiveContactDms` in `src/instagram/follow-flow.ts`, the last statement of `ingestMessages`, for every inbound DM of the batch on active connections (inbox on or off, confirmation postbacks included, not more than 60 s ahead, capped at `now()`, 1 to 40 digit sender IDs), after it locks the connections `FOR SHARE` outside its savepoint.
- Sends: the `record_active_contact` triggers (one function, `record_active_contact_activity`) after a `private_reply_outbox`, `instagram_manual_replies`, `campaign_deliveries` or `flow_dm_deliveries` row becomes `sent` (`sent_at`), and after an `instagram_follow_messages` insert with a `sent_at` (the comment sender of its private reply). A send finalizer must keep that statement last; the spec lists each finalizer.

A ledger error never fails the source write: the two ingestion writes run through `recordActiveContacts` in `src/instagram/active-contacts.ts` (a savepoint with `SET LOCAL lock_timeout = '2s'`, a bound on each lock wait, not on the whole statement, then `active_contact_ledger_failed` with `comment_record_failed` or `inbound_dm_record_failed`), and the trigger function (`SET lock_timeout = '2s'` as a function attribute) catches it in an exception block and raises a WARNING with the SQLSTATE only. The server-side lock timeout bounds a wait on another transaction's uncommitted key; a client query timeout does not cancel the server statement. `record_active_contacts` skips the activities of a workspace whose zone `active_contact_time_zone_valid` rejects, so one such workspace does not drop the other rows of a batch. A new outbound send table or inbound message path must write the ledger the same way.
The three deletion functions set `person_key` to NULL for the rows in their scope (person deletion by the `comment_sender` and `dm_recipient` identity sets); workspace deletion keeps the rows after it removes the workspace. The connection and person deletion records add `retained_counts.active_contacts`, the number of rows whose key that run cleared (`GET DIAGNOSTICS` after the `UPDATE`, migration 078); the dashboard label is in `public/app/deletion-labels.js`. The workspace deletion record is unchanged, because it holds only `deleted_counts` and the ledger rows are not deleted. After a deletion a row keeps its ID, workspace, connection, billing month, person key kind, microsecond `first_activity_at`, activity kind, zone and `recorded_at`, and no Instagram ID; treat it as de-identified, not anonymous. Server roles have SELECT and INSERT on the table and EXECUTE on the three ledger functions (`record_active_contacts`, `active_contact_linked_sender`, `active_contact_time_zone_valid`), no UPDATE or DELETE; the API roles have none. The workspace export leaves the rows out (`EXCLUDED_TABLES`) and exports only `active_contact_months`, the row count per billing month and connection (`EXPORTED_AGGREGATES` in `src/app/workspace-export.ts`), which counts toward the export limits. The table needs no workspace move check, because every row comes from a connection row, which only workspace deletion removes.
Usage read: `activeContactUsage` in `src/app/plans.ts` returns `usage.active_contacts` (`time_zone`, `month`, `count`, `previous_month`, `previous_count`) inside `workspaceEntitlements`, so `POST /api/workspace` (every role) and `GET /api/workspace/members` (owner) carry it with no new route. It picks this and the previous month from `statement_timestamp()` in the workspace's current `time_zone` and counts the rows whose stored `billing_month` equals each month, cleared keys included, summed over the connections. It never re-buckets `first_activity_at`, so a time zone change changes which month is "this month" but moves no row. The settings card shows this month's count against `limits.active_contacts_per_month` and last month's count, with no price ([spec](../specs/2026-11-25-active-contact-limit-design.md), "화면"); `planActiveContactsOver` and `planActiveContactsFull` in `public/app/plan-labels.js` mirror the server rule for the at-limit hint and the over-limit warning, and the campaign approval control is disabled with a reason while the workspace is over its allowance. The inbox composer needs no plan state: `reply-status` returns `active_contact_limit` for the recipient through `manualReplyStatus`.
The recompute in `src/app/active-contacts.db.test.ts` rebuilds the rows from the source tables with each row's stored zone and key; an inbound DM that no table stored has no source. Migration 077 writes no ledger row, because the runner replays every migration on every rollout and a replayed backfill would record old activity again under that rollout's links and zone. It must run through the full runner before the code deploy; after the deploy, `deploy/backfill-active-contacts.sql` runs exactly once (never again after it succeeded, and not while a deletion function runs) and records each workspace's current billing month, including the comments and DMs between the migration and the deploy ([procedure](../specs/2026-11-24-active-contact-ledger-design.md), "채우기 절차").

### Plan entitlements

**Plan entitlements** ([spec](../specs/2026-10-12-plan-entitlements.md)): `workspaces.plan` is one of the keys of `PLANS` in `src/app/plans.ts`, which holds every limit; the `workspaces_plan` CHECK lists the same keys. Existing workspaces were set to `advanced` and new ones start on `free`; only an administrator `UPDATE` changes a plan, because server roles have only column grants on `workspaces` (INSERT `id`, `time_zone`; UPDATE `time_zone`), so a new server-written `workspaces` column must be added to those grants in `deploy/supabase-access.sql` and `deploy/init-app-user.sh`. Seats are active members plus open invites; creating an invite (workspace `FOR UPDATE`) and accepting one (target workspace `FOR NO KEY UPDATE`) refuse with `409 seat_limit_reached`. Connected accounts are rows that hold a token or are active; OAuth completion locks the workspace `FOR NO KEY UPDATE` and refuses an account not connected in that workspace with `409 connection_limit_reached`, never a re-authorization. `campaign_sends_per_month` ([monthly campaign sends](../specs/2026-10-12-plan-entitlements.md#월-캠페인-발송-한도); free 0) is counted only by `campaignSendAllowance` in `src/app/plans.ts`: `used` is the delivery rows of runs whose `started_at` is in the workspace-time-zone calendar month, except rows cancelled with no `provider_called_at`; `reserved` is the stored candidate counts of approvals in force due in that month (`greatest(coalesce(scheduled_at, now()), now())`). Approval creation, and a reschedule that changes the due month, refuse with `409 broadcast_limit_reached` (writing nothing) when the limit is 0 or used + reserved + the request exceeds it; the run start applies the same count with its own approval left out of `reserved`. All three count after the workspace row `FOR UPDATE` they already take first; no lock was added. Deletion functions remove delivery rows, so they lower `used`. A downgrade removes nothing.
`active_contacts_per_month` ([spec](../specs/2026-11-25-active-contact-limit-design.md), #52) is enforced only by `activeContactLimitBlocks` in `src/app/plans.ts`: one read of the plan, the current billing month count of the [ledger](#active-contact-ledger) (the `activeContactUsage` month and rule) and whether the recipient's ledger key (the key `record_active_contacts` would write, including `active_contact_linked_sender` for a DM recipient) already has a row on that connection this month. Over the limit every send stops; at the limit a send to a person not yet counted stops; a zone that `AT TIME ZONE` rejects measures nothing and allows the send. It reads without a lock, so concurrent sends can pass the limit by the number in flight. Every send's final guard calls it after the opt-out check (`assertActiveContactLimit` in `src/instagram/active-contact-limit.ts` for the Cloudflare and Node private reply and follow guards, the follow worker's permission check, `manualReplyStatus`, and the DM flow and campaign guards, last in their block list): a stop ends the row with `active_contact_limit` (`blocked`, or `failed` with `safe_to_retry` for a manual reply, whose status CHECK has no `blocked`), never replayed when the plan goes up or the month changes, and a failed read defers it as `active_contact_limit_unavailable`. `processNextPrivateReply` in `src/instagram/reply-worker.ts` also checks it after the opt-out check and before it stamps `provider_called_at`, so a stopped private reply never counts toward the hourly budget. Claims, wakes and the campaign sweep do not read it, so a stopped row is claimed and then ended; `campaign_start` is unchanged. Manual reply create, reschedule and retry refuse with `409 active_contact_limit` through `manualReplyStatus`; campaign approval creation refuses with the same code when the workspace is over its limit in the current month, whatever the due month. Ingestion never reads it. A test that puts a workspace over its limit uses `exceedActiveContactLimit` in `src/app/workspace-fixture.ts`. No workspace cascade empties `active_contacts`, so a DB test file whose sends reuse one workspace ID across tests truncates it too, or the free plan's 25 fill up and later sends stop.
`user_records_per_workspace` ([user record limit](../specs/2026-11-27-user-record-limit-design.md); free 1,000 to advanced 500,000) caps each kind separately: every `instagram_inbox_notes` row of the workspace, and every `channel_consent_events` row of the workspace (grants, revokes and deletion bridge carries). `requireUserRecordSlot` in `src/app/plans.ts` refuses a new record with `409 user_record_limit_reached` (writing nothing) when the count is at or above the limit, after the workspace row `FOR NO KEY UPDATE`: `addInboxNote` raised its first lock from `FOR SHARE` in place, and `recordChannelConsentEvent` takes it before the connection `FOR UPDATE` only for a grant with `enforceUserRecordLimit` (set only by the dashboard API), and counts after its `ON CONFLICT DO NOTHING` INSERT only when that INSERT returned a row (`written = 1`), so the conflict itself, not an earlier read, decides a replay. A revoke, a replayed request key and a caller without the flag are never refused. After a note save, after a `user_record_limit_reached` refusal and after a connection data deletion (`forgetDeletedConnection`), the dashboard re-reads the plan card through `POST /api/workspace`; that read and `GET /api/workspace/members` spend no request limit, so the counts' cost is bounded only by the measured per-call cost in the spec. Use `FOR NO KEY UPDATE`, not `FOR UPDATE`: it serializes the counting writers but admits the key-share locks of inserts that reference the workspace. The counts read `workspace_id`-leading indexes with no counter table; `usage.user_records` (`inbox_notes`, `consent_events`) shows them. Audit tables written with a state change have no count cap. A downgrade removes nothing.

### Operations health

**Operations health** ([spec](../specs/2026-10-01-operations-health.md)): every runtime log goes through `logOperation` in `src/app/operations-log.ts`, which keeps only allow-listed fields of a fixed shape; do not call `console.*` directly or log an error message, request body or provider response. `failureCode` reads an error's class and code, never its message, except for an exact match on the two fixed `pg` messages that carry no code: a query read timeout is `database_timeout` and a dropped connection is `database_unavailable` ([#367](https://github.com/AndrewDongminYoo/auto-chatter/issues/367)); a real `pg` client test pins both strings. Each Cloudflare cron step records its outcome in `scheduled_steps` (service-wide, no workspace data, excluded from the export and the deletion functions), and a failed step does not stop the later ones. `GET /api/workspace/health` needs `admin`; alert thresholds live in `ALERT_THRESHOLDS` in `src/app/operations-health.ts`, and the cron logs each alert start or clear once, plus each new `unknown` outcome while `alert_unknown_outcome` is on. The `cron` row is written after the `alerts` step, so it counts that step's failure too. The 24-hour outcome counts date a row that stale recovery turned `unknown` / `worker_interrupted` by its recovery (`recovered_at` on the outbox and follow rows, added by migration 067 and set by every stale-recovery statement; the manual reply's `unknown` event; the campaign and DM flow rows' `updated_at`), and every other outcome by its last claim or creation ([#274](../specs/2026-10-01-operations-health.md#지표와-api)).

## Reports

### Manual reply reports

**Manual reply reports** ([spec](../specs/2026-10-16-manual-reply-reports.md)): `GET /api/reports/manual-replies` requires an active admin and reads current request counts by creation date in the workspace time zone, optionally scoped to an owned connection. Exact local-date bounds are half-open and limited to 366 calendar days; `expected_time_zone` rejects stale interpretation. One aggregate statement rechecks membership, zone and connection and returns decimal-string disjoint status counts, including separate unresolved and resolved unknown. Event rows do not multiply counts; explicit retry rows count separately; deleted rows disappear. `sent` means provider accepted only; `read` counts the `sent` requests with a stored read of their exact message ID ([Message reads](#message-reads)) and `read_unavailable` the other `sent` requests on a connection without `instagram_user_id`; both are outside the status partition. The home screen exports its displayed snapshot as CSV and clears it on filter or workspace/session changes; no customer text or provider delivery/read inference is included. The creation-period index `(workspace_id,created_at,connection_id)` bounds reads with or without an account filter; run migration 050 through the full runner before deploying the report.

### Flow-run reports

**Flow-run reports** ([spec](../specs/2026-10-16-flow-run-reports.md)): `GET /api/reports/flow-runs` requires an active admin and selects runs by `flow_runs.created_at` in a workspace-local half-open period of 1–366 days. Optional owned account and flow filters use the run’s pinned IDs, including inactive accounts and archived flows. One statement rechecks membership, time zone and filter ownership, then returns separate decimal-string partitions for current run state and the linked first-reply outbox state, including absent outbox. Neither `ended` nor `sent` proves delivery or conversion; `reply_counts.read` (top level and every group) counts the runs whose `sent` first message, outbox or DM delivery, has a stored read of its exact message ID ([Message reads](#message-reads)) and `read_unavailable` the other such runs on a connection without `instagram_user_id`; both are outside the first-reply partition; steps and webhook deliveries do not multiply counts. Home displays and exports the same response, clears it on input/session changes, and excludes labels/customer data from CSV. The flow picker lists existing non-archived flows, while all-flow reports include archived history. Run migration 051 through the full runner before deployment to add the workspace/creation-period index. `reply_wait_counts` (`reached`, `replied`, `not_replied`) counts runs that are `awaiting_reply`, carry `reply_message_id`, or queued a private reply and left `delivering`; `replied` is `reply_message_id IS NOT NULL` (a recipient DM, not delivery or a read), and the report reads no `flow_step_runs`, because a wait leaves a step only when it resumes. Optional `group_by=day|connection|flow` adds `groups` (absent otherwise) keyed by workspace-local creation date or pinned UUID, only for groups with runs; every group partition sums to its own total and the groups sum to the top level, both read from one cohort CTE with a single period-index scan.

### Handoff reports

**Handoff reports** ([spec](../specs/2026-10-16-handoff-reports.md)): `GET /api/reports/handoffs` requires an active admin and counts retained handoff transition events by `created_at` in a workspace-local half-open period of 1–366 days, with an optional owned account filter. One statement rechecks membership, time zone and account ownership. Decimal-string metrics are total events, started, cleared and distinct `(connection_id,recipient_id)` conversations. Idempotent handoff requests add no event; repeated real cycles count separately. Cleared does not imply automated sending or consultation resolution. No current-state count, conversion rate or flow attribution is inferred from identity evidence. The home report exports the displayed snapshot and invalidates results on input/session changes. Run migration 052 through the full runner before deployment to add the workspace/creation-period index.

### Campaign run reports

**Campaign run reports** ([spec](../specs/2026-11-09-campaign-run-reports.md)): `GET /api/reports/campaign-runs` requires an active admin and selects runs by `campaign_runs.started_at` in a workspace-local half-open period of 1–366 days, with an optional owned `draft_id` filter (archived drafts included; a foreign or missing draft is `404 campaign_draft_not_found`). There is no account filter, because one run's pinned audience can span several connections. One statement rechecks membership, time zone and draft ownership, reads `statement_timestamp()` once, and returns three decimal-string partitions: run states (`running`, `cancelled`, `completed`, `limit_not_started`, where a run with the `plan_limit_exceeded` start key counts only as `limit_not_started`), summed stored start counts (the eight reasons, `plan_limit_exceeded` included, add up to `remaining_member_count`), and the current statuses of the cohort's delivery rows. Delivery rows are counted per cohort run in a LATERAL aggregate through the `run_id`-leading unique index `campaign_deliveries_member`; joining them flat would let the planner scan every row. Connection and person deletion remove delivery rows but keep runs and `start_counts`, so the `candidate` sum and the delivery total can differ; `sent` means provider accepted only, and `delivery_counts.read`, counted in the same LATERAL aggregate, is the `sent` rows with a stored read of their exact message ID ([Message reads](#message-reads)) and `read_unavailable` the other `sent` rows on a connection without `instagram_user_id`, both outside the status partition. No message text, identifiers, approvers, failure text or draft names leave the endpoint or the CSV. Home displays and exports the same response and clears it on input/session changes; the picker lists non-archived drafts. No migration is needed.
