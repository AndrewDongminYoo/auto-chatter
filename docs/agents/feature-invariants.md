# Feature invariants

Agent-facing invariants per feature: the rules a code change most easily breaks.
Each feature's spec owns its contract; this file owns only these summaries, and [CLAUDE.md](../../CLAUDE.md) owns the cross-cutting rules and routes here by code path.
Read the section for the code you touch before editing it.
The text moved here unchanged from CLAUDE.md on 2026-11-01, so migration numbers and dated capability notes below are history as well as rules.

## Dashboard, channel and token

### Channel contract

**Channel contract** ([spec](../specs/2026-10-04-channel-contract.md)): `src/channels/` contains advisory capabilities, scoped identity, receipt keys and the existing pure consent/window policy. Instagram ingress uses `channel-adapter.ts` after signature verification and keeps the original storage inputs and ordering. Only the manual worker uses its outcome classification, inside the existing send catch; persistence remains outside. Capability support never replaces eligibility or final guards. The fake second adapter exists only in unit tests.

### API request limits and static client

Signed-in writes outside `/api/auth/*` spend fixed default per-user and per-workspace limits in `appApi` before any route handler (per-user before the database opens), and `GET /api/inbox` spends its own before `listInbox`, all counted by the `AuthLimiter` Durable Object through `durableLimits`; a member's `POST /api/workspace` (the dashboard bootstrap) spends neither write limit and member removal skips the workspace one, and unlike the fail-closed auth and #166 allowances these limits fail open with one fixed log code ([spec](../specs/2026-10-12-api-request-limits.md)).
`public/app/` is a build-free static client (`app.js`, `inbox.js`, `reply-templates.js`, `manual-reply-reports.js`, `flow-run-reports.js`, `handoff-reports.js`, `contact-csv-preview.js`, `segment-snapshots.js`, `contact-identity-links.js`) served by Wrangler assets.
The auth client wraps injected fetch in a standalone call because workerd rejects a native fetch invoked with the client object as its receiver.

### Dashboard session and auth client

Session invalidation advances the workspace-load generation and exposes the existing reload action; a membership response is checked against that generation before configuring the card.
The shared API wrapper checks the request's workspace generation before starting a 401 refresh and again before replaying the original request, so a retired session cannot automatically replay pending input.
Cookie-changing browser auth requests take an exclusive origin-wide Web Lock; all protected requests, including their initial attempt, take a shared lock. Every parsed protected JSON response, including structured errors, is checked against the captured session before exposing fields; successful text bodies are checked too. The document keeps an accepted session revision instead of adopting fresh storage on every call; only a successful local login or a full document reload accepts a different account. A shared pending/ready revision retires requests across documents before cookie changes and is checked again when a queued refresh or retry acquires the lock. Automatic refresh requires Web Locks and writable localStorage; storage-coordinated auth fails before fetching if its pending marker cannot be published. See the [cookie-ordering verification note](../notes/2026-10-22-auth-cookie-response-order.md) for fallback behavior and browser-lifecycle limits.
Session broadcasts carry a per-document source marker so a local login does not invalidate its own new bootstrap; successful local login clears protected state synchronously before broadcasting.

### Follow flow

**Follow flow** (`follow-flow.ts`, `message-events.ts`):
`instagram_follow_conversations` snapshots the first reply configuration; a nonfollower response returns to waiting, a follower response completes, and ambiguous sends remain unknown.
A missing recipient ID after a successful first DM records `follow_recipient_unavailable` without resending.
Inbound DM text is compared in memory for follow confirmation; receipt IDs and timestamps deduplicate confirmation events.
DM ingestion holds its connections `FOR SHARE` before it locks a follow row, so a rate-limited follow send locks the connection `FOR NO KEY UPDATE` before it updates the follow row and the connection pause ([#130](https://github.com/AndrewDongminYoo/auto-chatter/issues/130)).
Optional `confirmation_button_title` adds a single postback template button to the first DM and nonfollower response; empty defaults preserve text-only delivery.
Button clicks are bound to the queued reply ID and validated against account, recipient and waiting flow; typed confirmation still works.
The service caps button labels at 20 and button-message text at 640.
OAuth subscribes `messaging_postbacks` as well as comments/messages, so existing accounts must reconnect and the app must subscribe that webhook field.

### Token lifecycle

**Token lifecycle**: active Instagram Login connections refresh valid long-lived tokens from 30 days before expiry, after the token is at least 24 hours old.
Inactive, expired, or disconnected connections do not refresh; an expired token requires OAuth reconnection.
A token that Meta rejects gets a display-only reconnect marker; its signals, clearing and deploy order are in the [token refresh spec](../specs/2026-09-28-instagram-token-refresh.md#재연결-필요-표시-16).
A verified Meta deauthorize callback disconnects the matching connections like the settings screen; its contract, ID matching and deploy order are in the [token refresh spec](../specs/2026-09-28-instagram-token-refresh.md#권한-해제-콜백-16).
The cron and the manual status check share one webhook subscription check and store a display-only loss record per token; cadence, recording rules and deploy order are in the [token refresh spec](../specs/2026-09-28-instagram-token-refresh.md#웹후크-구독-유실-표시-179).

## Campaigns

### Campaign drafts

**Campaign drafts** ([spec](../specs/2026-10-21-campaign-drafts.md)): administrator-only planning records reference existing target snapshots and contain plain text, never send requests or eligibility claims.
Creation uses a client UUID scoped to the workspace plus the original normalized request hash; replay returns current state without undoing edits or archival.
Writes recheck membership under the workspace lock, enforce a total limit of 100 including archived drafts, and require the displayed version for edits and archival.
Reads distinguish original and remaining member counts; person and connection deletion only reduce the referenced membership.
`GET /api/campaign-drafts/:id/preview` (`admin`) is read-only: one statement in a `REPEATABLE READ READ ONLY` transaction, at one `as_of`, gives each remaining member exactly one reason in a fixed order (connection, pause, verified DM identity, opt-out, explicit marketing grant, 24-hour text window, then `candidate`), and a sender with several verified recipients takes its furthest-reaching recipient's stage ([preview](../specs/2026-10-21-campaign-drafts.md#발송-조건비용-미리보기)).
`candidate` means it passed the recorded conditions at `as_of`, never that it can be sent: delivery guards recheck at send time, `channel_marketing_supported` reads the `cloudflare_oauth` marketing capability (true since 2026-10-27; it never implies eligibility), and `estimated_provider_calls` equals the candidate count. `plan_broadcast_limit` is this month's campaign send allowance (`{month, limit, used, reserved, remaining}`, decimal strings, from `campaignSendAllowance`); the preview only reads it.
Migration 063 adds workspace deletion and restricted access; exports omit the internal request hash, and both workspace move checks retain drafts.
An admin records a final execution approval of one draft version (`POST /api/campaign-drafts/:id/approvals`, [approvals](../specs/2026-10-21-campaign-drafts.md#실행-승인)): `campaign_approvals` keeps the name and body copies, the `PREVIEW_SQL` result evaluated in the same transaction, and an immediate or workspace-local schedule (`localDueSql`, at least the scheduled replies' `SCHEDULE_MIN_AHEAD` ahead with no fixed upper bound because #36 applies each recipient's reply window at delivery, never moved by a zone change); at most one is `approved` per draft, and while it is, the draft's edit and archive answer `409 approval_active` under the same workspace and draft locks.
Approvals themselves queue and send nothing (a due approval becomes `executed` when its run starts, and the delivery worker sends the run's rows; see Campaign runs and Campaign delivery below), `campaign_approval_events` is append-only, workspace deletion removes both before the drafts, connection and person deletion leave them, and migration 064 must run through the full runner before code deployment.
The contacts view manages drafts through `public/app/campaign-drafts.js`: unknown writes retain an immutable request for explicit retry, conflicts preserve inputs until an explicit reload, and session/workspace changes discard protected data and late responses.
Archived drafts are read-only and still count toward capacity; snapshot counts never imply send eligibility.
The draft detail's approval area ([approval UI](../specs/2026-10-21-campaign-drafts.md#실행-승인-화면)) finds the open draft's approval as its first entry in `GET /api/campaign-approvals`, approves only after a confirmation step that freezes the request, locks the draft while an approval is in force or its state is being read, re-renders from the `approval` or `draft` a 409 carries (the shared API wrapper forwards both), treats a success body that is not the requested approval in the requested status as an unknown outcome, retries an unknown or throttled write only as the same request, and uses the module's generation and an approval request counter to discard late reads.
The draft detail reads `GET /api/campaign-drafts/:id/preview` only on an explicit button click (archived drafts included), labels `candidate` "조건 통과" and never shows "발송 가능", and the existing generation and request counters discard the preview and its late responses on any edit, save, archive, draft switch, new draft or session reset, as well as a response for another draft or version ([preview UI](../specs/2026-10-21-campaign-drafts.md#발송-조건-미리보기-화면)).

### Campaign runs

**Campaign runs** ([spec](../specs/2026-10-27-campaign-runs.md)): the `campaign_start` cron step runs only while `SEND_ENABLED` is `true`, starts at most `CAMPAIGN_START_LIMIT` due approvals, those with no failed start (`start_failed_at` NULL) oldest due first and then the failed ones least recently failed first, and per approval locks the workspace, the approval, the draft, then the snapshot's connections `FOR SHARE` in ID order, rechecks `approved` and due, and re-runs the preview SQL (`EVALUATION_SQL`) in one statement that also returns each candidate's key and chosen DM recipient (the qualifying recipient with the latest stored text DM).
It writes one `campaign_runs` row per approval (`(workspace_id, approval_id)` unique, because approval IDs are client-supplied; the nine counts at `started_at`) and one `pending` `campaign_deliveries` row per candidate (duplicate key `(run_id, connection_id, sender_id)`), then sets the approval `executed` without a version bump or audit row; an executed approval refuses schedule change and cancel with `409 campaign_approval_executed`. Before the rows, under the same workspace lock, it counts the monthly campaign send limit of the month that holds `started_at` with the approval's own rule (`campaignSendsFit`, the starting approval excluded from `reserved`): when used + the other approvals' reserved + the candidates exceed the limit, or the limit is 0, the run is written `completed` with no delivery row, `candidate: "0"` and the `plan_limit_exceeded`/`plan_limit`/`plan_limit_used`/`plan_limit_reserved` keys in `start_counts`, the approval still becomes `executed` (its draft version is used up), the run read returns `start.broadcast_limit_exceeded`, and approval reads return `run_limited: true`. One failing approval is logged, stamped `start_failed_at` outside its rolled-back transaction, and the rest still start.
The start itself sends nothing: no Graph call, transport, outbox row or queue message. Instagram marketing is supported on the `cloudflare_oauth` surface only, inside the 24-hour window with an exact explicit marketing grant.

### Campaign delivery

**Campaign delivery** ([delivery](../specs/2026-10-27-campaign-runs.md#발송-worker)): `processNextCampaignDelivery` in `src/instagram/campaign-delivery-worker.ts` runs only in the Cloudflare queue consumer, after the manual reply, follow confirmation and private reply steps and only when none of them claimed a row; the Node worker never sends campaigns. It claims one due `pending` row of a `running` run (unpaused connection and contact, campaign budget open; `campaignDeliveryDueSql` is shared with the wake and health) `FOR UPDATE OF d SKIP LOCKED` without locking the run, and sends the approval's body as one plain-text DM to the stored `recipient_id`. The final guard (after the claim, after the account read, and in `beforeSend`) reads the preview's own fragments (`RECIPIENT_STAGE`, `CONNECTION_SENDABLE`, `CONTACT_PAUSED` in `src/app/campaign-drafts.ts`) for the stored recipient plus the run, `SEND_ENABLED`, the token, the approver's active `owner`/`admin` membership and `deliveryRecipientOptedOut`; any block reason wins over any retry reason. Outcomes: retry → `pending` a minute later with the attempt cleared, block → `blocked`, definite rejection → `failed`, rate limit → `pending` at the connection pause end (`max(900 s, Retry-After)`), anything else → `unknown`, never retried. The finish locks the run `FOR SHARE` before the row (the cancel's order) and lands a would-be `pending` row of a cancelled run as `cancelled`; a separate statement then completes a `running` run with no `pending`/`sending` row, as `campaign_start` does for every run after its starts, and `stale_recovery` turns `sending` rows older than 10 minutes `unknown`. `CAMPAIGN_HOURLY_BUDGET` (1,000 provider calls per connection per rolling hour, service policy, deleted rows not carried) is separate from the private reply budget. Re-approving an executed draft version answers `409 campaign_version_executed`; approval and run responses say `delivery_available: true`, and migration 066 must run through the full runner before code deployment. Between the starts and the completion, `campaign_start` runs `endUnreachableCampaignDeliveries` ([sweep](../specs/2026-10-27-campaign-runs.md#도달할-수-없는-행의-정리), #273): in one statement it ends as `blocked`, with the final guard's first block code in the guard's order and from the guard's fragments, at most `CAMPAIGN_SWEEP_LIMIT` (500) oldest `pending` rows of `running` runs whose contact is paused or whose connection cannot send, locking only those rows `FOR UPDATE OF d SKIP LOCKED` and never claiming, setting an attempt or calling a provider; rows with only retry reasons stay `pending`, and migration 067 (which lets a `blocked` row have no attempt) must run through the full runner before code deployment.
`POST /api/campaign-runs/:id/cancel` (`admin`, `expected_version`) cancels the run and its `pending` rows in one transaction (workspace, run, rows); `sending` rows cannot be recalled (`sending_recalled: false`). `GET /api/campaign-runs/:id` returns counts only, no identifiers. The draft detail's run panel ([screen](../specs/2026-10-27-campaign-runs.md#실행-현황-화면)) reads the run only when the approval area shows an approval with a `run_id`, on its refresh button and when a cancel refusal carries no usable run (no polling), and cancels only through a confirmation that freezes the displayed `version` as `expected_version`; an unknown or throttled cancel is retried only as the same request, a 409 re-renders from the `run` the shared API wrapper forwards (`error.run`), and the module's generation and a run request counter discard late responses and responses for another run.
The three deletion functions remove the matching delivery rows (workspace deletion also the runs, before the approvals) and refuse with `sending_in_progress` while one is `sending`; both tables are exported and count in both workspace move checks, and migration 065 must run through the full runner before code deployment.
Approvals recorded before 065 keep `approved` with no age bound, so the first cron after `SEND_ENABLED` turns on starts every due one; review them before migrating and again before that switch ([procedure](../specs/2026-10-27-campaign-runs.md#이미-있는-승인과-배포-순서)).

## Contacts and segments

### Contacts

**Contacts** ([spec](../specs/2026-09-27-instagram-contacts.md)): contacts are derived from stored comment events and are returned without comment text or credentials. Manual tags (max 20) apply only to existing workspace-owned comment participants; empty tag arrays remove tags. Comment identities are not merged with DM identities. Explicit `preview=true` adds exact decimal-string `total`, `evaluated` and disjoint `excluded.tag`/`field`/`both` counts from the same statement as the bounded samples. Evaluation stays within the workspace and selected account, including contacts that fail the filters; zero matches retain the summary, and OR excludes only contacts failing both predicates. It rejects any cursor, and ordinary list queries and response shapes remain unchanged. Optional paired canonical UTC `last_comment_from`/`last_comment_before` bounds filter each contact's latest stored comment in `[from,before)` independently of tag/field AND/OR. With a window, preview first classifies outside contacts as `excluded.activity`, then classifies tag/field mismatches only inside the window; without one, it omits the activity key. Paired `consent_purpose`/`consent_state` filters compare only the exact workspace/connection/Instagram/comment_sender/purpose current recorded grant, revoke or absent row; they never imply send eligibility or bridge DM identities. Paired `dm_consent_purpose`/`dm_consent_state` filters read the advisory verified bridge of the contact detail (`verifiedDmRecipientsSql` in `src/app/inbox-identity.ts`, same connection only) and match when any verified DM recipient has that current `dm_recipient` state; a contact without one never matches, and the filter merges no identities and is not the delivery guard ([DM consent](../specs/2026-10-16-segment-consent-state.md#dm-동의-기록)). An integer `last_dm_days` (1–366, independent of the comment activity forms) matches when any verified DM recipient's latest stored inbox message (text or postback) lies in `[as_of - N*24 hours, as_of)` at the statement's one evaluation clock, independently of which recipient matches DM consent, and returns only the UTC `dm_activity_window` bounds; it opens no messaging window ([DM activity](../specs/2026-10-16-segment-consent-state.md#dm-활동)). Preview excludes activity first, then `excluded.consent`, then `excluded.dm_identity`, `excluded.dm_consent` and `excluded.dm_activity`, then tag/field mismatches; it omits the keys of unselected conditions. A calendar `last_comment_period` (`today`, `yesterday`, `this_month`, `last_month`) excludes the fixed bounds and `last_comment_days`, and one statement computes its half-open local day or month boundaries in PostgreSQL from `statement_timestamp()` and the workspace `time_zone` (`AT TIME ZONE`, so DST gaps and overlaps are PostgreSQL's), returning `activity_window` with `time_zone` ([spec](../specs/2026-10-16-segment-relative-activity.md#달력-기간)). `tag` may repeat 1–5 times with `tag_mode` `all` (default, `tags @> S`) or `any` (`tags && S`), one predicate shared by the list, the preview and `segment_id`; a set that normalizes to one tag is the single-tag condition, and the whole set is one side of the tag/field AND/OR ([multi-tag](../specs/2026-09-27-contact-segments.md#다중-태그-조건)). The legacy `field_id`/`field_operator`/`field_value` keys carry one field condition and `field_conditions` (one bounded JSON array of 1–3 conditions on distinct fields, never mixed with the legacy keys) with `field_mode` `all` (default) or `any` carries a set, evaluated by one predicate (`jsonb_to_recordset` with `bool_and`/`bool_or`) that the legacy condition also passes through as a set of one, and the whole set is one side of the tag/field AND/OR ([multi-field](../specs/2026-09-27-contact-segments.md#다중-필드-조건)). `condition_tree` (one JSON object of at most 16,384 decoded characters) is a third form, never mixed with the tag, field or `condition_operator` keys (`invalid_contact_condition`) or `segment_id`: a root `all`/`any` over 1–5 groups, each `all`/`any` over 1–5 leaves (tag present, tag absent with `negate`, or one field condition), at most 10 leaves, order kept; one fixed SQL text evaluates it from `$19` with the field set's comparison text, the activity, consent and DM limits stay separate ANDs, and the preview reports `excluded.conditions` after the limit reasons instead of `tag`/`field`/`both` ([condition tree](../specs/2026-09-27-contact-segments.md#중첩-조건-그룹)).

### Contact CSV preview

**Contact CSV preview** ([spec](../specs/2026-10-17-contact-csv-preview.md)): `POST /api/contacts/import-preview` requires an active admin and accepts only `{csv}` with the exact exported v1 header, at most 128KiB UTF-8 and 500 records. It removes exactly one sender display apostrophe, preserves string identities and normalizes tags through the existing save validator. Invalid rows precede duplicate detection; all remaining duplicate connection/sender pairs are excluded. One SELECT rechecks role, connection ownership and existing comment contacts and returns current/proposed tag snapshots. It never stores files, applies tags, creates identities, changes consent or schedules delivery. The client clears previews on file/workspace/session changes, ignores stale responses and preserves contact editing drafts. Same-origin login/logout/password-reset events broadcast a data-free session signal that disables and clears every tab's preview; restored back-forward-cache pages also reset. Preview stays unavailable if a BroadcastChannel cannot be created. No migration is added.

### Contact CSV import

**Contact CSV import** ([spec](../specs/2026-10-17-contact-csv-import.md)): `POST /api/contacts/import` (`admin`) takes `{csv, expected}` and shares the preview's parser, classification and snapshot SELECT (`classifyImportRecords`, `readImportSnapshot` in `src/app/contact-csv-preview.ts`). In one transaction it takes the workspace import advisory lock (`contact-import:<workspace>`), the referenced connections `FOR SHARE` in ID order and `lockContact` per unique row in `(connection_id, sender_id)` order before the snapshot read (up to 500 advisory locks; a comment ingestion batch with flow actions takes the same contact locks in webhook event order, so PostgreSQL may abort one side with a deadlock, `40P01`: an aborted apply writes nothing and the admin checks and applies again, an aborted batch answers 5xx and Meta redelivers it, as for any ingestion failure). Any `invalid`, `duplicate` or `not_found` row refuses the whole file with `422 contact_import_rejected`; a `changed` row missing from `expected` or whose sorted `current_tags` differ from the stored tags, or a write that touches fewer rows than the changed set, refuses with `409 contact_import_stale`; both carry the fresh `checked_at`/`counts`/`rows` and write nothing. The write is `saveContactTags`'s statement over the changed set; a repeated file applies 0 rows. No new contacts, identity merge, consent, field, pause or inbox change, no audit table, no migration, no DELETE. The client offers the apply only for a clean preview with changes, sends the held CSV string, withdraws the offer on every preview invalidation, and reloads contacts only without unsaved drafts, saying in the status line when it skipped the reload.

### Saved segments

**Saved segments** ([spec](../specs/2026-09-27-contact-segments.md)): archive instead of delete. Creation locks the workspace row before checking the 50-active-segment limit; normalized active names are unique per workspace. `segment_id` cannot be mixed with manual account, tag, field, operator, activity or consent filters. Saved activity bounds require migration 046 and saved consent purpose/state require 047 through the full runner before code deployment; legacy segments omit absent bounds and consent keys in responses. Optional integer `last_comment_days` (1–366) is mutually exclusive with fixed bounds and requires migration 053. Each lookup uses one SQL statement clock and `[as_of - N*24 hours, as_of)` against the latest stored comment; preview samples and counts share it and expose microsecond UTC `activity_window` bounds. Relative pagination re-evaluates time per request and is not a frozen audience. Legacy responses omit absent relative keys. A saved `last_comment_period` is mutually exclusive with both other activity forms (CHECK `contact_segment_calendar_period`), is re-evaluated in the workspace time zone on every request including after a time zone change, is omitted when absent, and requires migration 055 through the full runner before code deployment. `PUT /api/contact-segments/<id>` (`admin`) replaces an active segment's whole definition with the create parser plus `expected_version`; a stale version answers `409 segment_conflict` with the current segment, an unchanged definition keeps the version, and archived, missing and foreign IDs all answer `404 segment_not_found`. It locks the workspace (`lockWorkspaceForMember`), then the segment row `FOR UPDATE`, then the referenced field `FOR SHARE`, which serializes it with `archiveContactField`; there is no edit history, and migration 054 (`version`) must run through the full runner before code deployment. A one-tag set stays in the legacy `tag` column and response key, while 2–5 sorted tags are stored in `tags`/`tag_mode` with `tag` NULL (CHECK `contact_segment_multi_tag`; migration 056 also lets the OR CHECK accept `tags`), the edit's unchanged check includes both columns, and 056 must run through the full runner before code deployment. Likewise one field condition stays in the legacy field columns and keys, while 2–3 conditions sorted by lowercase `field_id` are stored in `field_conditions` jsonb with `field_mode` and the legacy field columns NULL (CHECK `contact_segment_multi_field`; migration 057 also lets the OR CHECK accept `field_conditions`), writes lock every referenced field `FOR SHARE` in `field_id` order, the unchanged check includes both columns, and 057 must run through the full runner before code deployment. A tree segment stores `condition_tree` jsonb with every tag and field column NULL and `condition_operator='and'` (CHECK `contact_segment_condition_tree` checks only the root shape; leaves stay with the parser), returns `condition_tree` and no tag or field key, locks each distinct tree field `FOR SHARE` once in `field_id` order, reads create and edit bodies up to `SEGMENT_REQUEST_BYTES`, counts a reorder as a change in the unchanged check, and requires migration 060 through the full runner before code deployment; the dashboard builds trees in a group editor whose draft operations and limits live in the pure `public/app/condition-tree-model.js` (the server stays the authority), and selects, previews, saves and edits tree segments, comparing the tree in order for unsaved changes. A saved DM consent pair (`dm_consent_purpose`/`dm_consent_state`, CHECK `contact_segment_dm_consent`) is omitted when absent, is part of the unchanged check, and requires migration 058 through the full runner before code deployment; a saved `last_dm_days` (CHECK `contact_segment_dm_activity`) likewise is omitted when absent, is part of the unchanged check, and requires migration 059 through the full runner before code deployment; 059 also adds `instagram_inbox_messages_latest_idx` (`message_at DESC` per conversation), which the DM activity predicate probes once per verified conversation, and builds it without `CONCURRENTLY` inside the runner's transaction. `GET /api/contacts/export.csv?segment_id=<uuid>` (`admin`, the full export's allowance, limits and v1 rows) exports only a saved segment's contacts ([spec](../specs/2026-10-04-contact-csv-export.md#저장된-세그먼트-내보내기)): it reads the segment in the export's `REPEATABLE READ READ ONLY` snapshot after the role check, selects through the list's own `savedSegmentConditions` and `segmentConditionSql` in `src/app/contacts.ts`, evaluates them once in one statement that returns only the member keys at one `as_of`, the file's `exported_at` (more than the row limit refuses the whole file), and reads the rows by key in 25-key batches.

### Segment snapshots

**Segment snapshots** ([spec](../specs/2026-10-18-segment-target-snapshots.md)): `POST /api/contact-segments/<id>/snapshots` (`admin`, empty body or `{}`) freezes the comment senders a saved segment selects at one `as_of` and sends nothing. It runs in READ COMMITTED, not REPEATABLE READ: it locks the workspace (`lockWorkspaceForMember`), the active segment `FOR SHARE`, then every connection the evaluation can include `FOR SHARE` in ID order, counts the workspace's snapshots (at most 200, `409 snapshot_limit_reached`) and their stored member rows (at most 20,000 with the new list, `409 snapshot_members_limit_reached`, so member rows, which the export counts and server roles cannot delete, keep 60% of the export's 50,000-row limit free), and only then evaluates in one statement, so the members (the segment CSV export's selection) and the counts (`segmentPreviewSql`, shared with the contact preview) share one snapshot taken after the locks at that statement's `statement_timestamp()`; more than 5,000 members refuses the whole request (`409 snapshot_too_large`). `instagram_segment_snapshots` stores the definition copy (the segment API item without `id` and `name`), the name, `as_of`, the preview counts and `member_count`; `instagram_segment_snapshot_members` stores `(connection_id, sender_id)` only, never a DM recipient, text, tag, field value or eligibility. Server roles have only SELECT and INSERT on both; the three deletion functions remove member rows (workspace deletion also the snapshots, before the segments) and never recompute the stored counts, so `member_count` may exceed the remaining rows. There is no expiry. Reads (`GET /api/contact-segments/<id>/snapshots`, `GET /api/segment-snapshots` for every snapshot of the workspace with `segment_archived` and the limit usage, `GET /api/segment-snapshots/<id>` with 50-row pages, `.../members.csv` on the contact export allowance) are `admin` only. Both tables are exported and count in both workspace move checks; migration 061 must run through the full runner before code deployment. `GET /api/segment-snapshots/<id>/comparison` compares remaining stored keys with the current active saved definition in one `REPEATABLE READ READ ONLY` transaction, including the admin membership read. It returns decimal-string original/baseline/current/added/removed/retained counts and both segment versions, uses one evaluation clock without the freeze or page limits, writes nothing, and answers `segment_not_found` for an archived segment ([comparison](../specs/2026-10-19-segment-snapshot-comparison.md)).

### Segment acceptance fixture

## Inbox

### Received inbox

**Received inbox** ([spec](../specs/2026-09-27-instagram-inbox.md)): each connection defaults to `inbox_enabled=false`, and its activation timestamp gates storage of new text DMs and confirmation postbacks. Disabling it keeps stored history under the manual deletion policy. `instagram_inbox_messages` deduplicates by connection and provider message ID in the confirmation transaction. DM recipient IDs stay separate from comment participant IDs.

### Handoff

**Handoff** ([read contract](../specs/2026-09-27-inbox-handoff-contract.md), [writes and pause](../specs/2026-09-27-inbox-human-handoff.md)): the context read is advisory, masks identity unless one fresh sender is verified, and keeps missing, stale and ambiguous evidence distinct. Starting a handoff requires a currently verified comment bridge; resuming uses the captured sender. Writes are version-checked with append-only audit.

### Conversation assignment

**Conversation assignment** ([spec](../specs/2026-10-01-inbox-conversation-assignment.md)): `instagram_inbox_conversations` holds `open`/`closed` and the assignee per inbox conversation; no row means open and unassigned at version 0. `PUT /api/inbox/conversations/<connection>/<recipient>/state` locks the workspace row `FOR SHARE` first (`delete_workspace_data` takes it `FOR UPDATE` before the connections, and `removeMember` takes it `FOR SHARE` before the member row), the caller's and the new assignee's `workspace_members` rows `FOR SHARE`, the connection `FOR SHARE` (so it serializes with the deletion functions), the per-conversation advisory lock exclusive (`lockConversation` in `src/instagram/inbox.ts`), then the conversation row `FOR UPDATE`, checks `expected_version` (stale returns `409 conversation_conflict` with the current state) and writes one append-only `instagram_inbox_conversation_events` row per version. Agents may only claim an unassigned conversation or release their own; admins assign any active member. A newly stored inbox message reopens a closed conversation in the ingestion transaction (`auto_reopen`, no actor); before its first INSERT, `ingestMessages` takes the batch's message-ID locks ([DM start triggers](#dm-start-triggers)), then locks every connection of the batch's accounts `FOR SHARE` in ID order (inactive and inbox-disabled ones too, until COMMIT) and then takes `lockConversation` exclusive for every conversation the batch can store into, in (connection, recipient) order (`lockInboxConversations` in `src/instagram/inbox.ts`), and rereads the status after the INSERT, so it queues behind the deletion functions instead of deadlocking and waits for an uncommitted close (including the first one, which inserts the state row) instead of missing it, while DMs of different conversations never wait on each other and DMs of one conversation are serialized, and `removeMember` unassigns the removed member's conversations in its transaction (`member_removed`). Status and assignment never change the handoff or the automation pause, and neither recalls queued or in-flight sends.

### Inbox search and read state

**Inbox search and read state** ([spec](../specs/2026-09-27-instagram-inbox.md#검색-필터와-읽음-상태)): `GET /api/inbox` lists conversations by last message time DESC, then connection and recipient, with a cursor that carries the time as integer microseconds (a JavaScript `Date` would skip or repeat ties inside one millisecond); `q`, `unread` and the assignee filter choose conversations but every count, time and the order cover all of a conversation's messages, and `q` is a literal case-insensitive `strpos` match with no index; ordering by last message time makes every request scan all of the workspace's DMs, where the old connection-ordered list stopped after one page. `instagram_inbox_read_state` holds one forward-only `last_read_message_id` per workspace, connection, recipient and member, with no foreign key to the message or the member. `POST /api/inbox/conversations/<connection>/<recipient>/read` (`agent`) locks the workspace row `FOR SHARE`, the caller's member row `FOR SHARE` (rechecking `removed_at`), then the connection `FOR SHARE`, the order of the state change, before it checks that the ID is that conversation's message and upserts; a lower ID is a no-op, and it counts unread messages after its commit. The list returns the caller's `last_read_message_id` with each `unread_count`, and the screen keeps the count taken against the higher read position. Message IDs follow allocation, so ingestion holds the exclusive conversation lock from before its INSERT until COMMIT, which keeps one conversation's IDs in commit order and stops a read mark from counting a lower-ID DM that was not yet visible as read ([#127](https://github.com/AndrewDongminYoo/auto-chatter/issues/127)). Read state changes nothing else.

### Inbox labels and notes

**Inbox labels and notes** ([spec](../specs/2026-10-03-inbox-labels-notes.md)): labels belong to inbox conversations (connection and DM recipient) only, never to comment participants or contact tags, and no flow, webhook or reply reads them. `instagram_inbox_labels` is archive-only, at most 50 active per workspace (creation locks the workspace row `FOR UPDATE` before counting) with case-insensitive unique active names; `GET /api/inbox/labels` is `agent`, create, rename and archive are `admin`. `PUT /api/inbox/conversations/<connection>/<recipient>/labels` (`agent`) takes the whole set (at most 10 `uuid[]`, stored in place because server roles have no DELETE) and `expected_version` with the state change's lock order (workspace `FOR SHARE`, the caller's member row `FOR SHARE`, the connection `FOR SHARE`, `lockConversation` exclusive, the label-set row `FOR UPDATE`), then locks newly added labels `FOR SHARE` so a concurrent archive cannot slip between the check and the write; a stale version returns `409 label_conflict` with the current set, an unchanged set writes nothing, and each change writes one append-only `instagram_inbox_label_events` row. An archived label stays on a conversation that has it but can never be added. `instagram_inbox_notes` is append-only for server roles (no edit, no delete; a correction is a new note), written under the same workspace, member and connection locks, and never sent, searched by `q`, listed as a message or read by a flow or webhook. `GET /api/inbox?label=<id>` combines with the other filters and the cursor. The three deletion functions remove label sets, their audit and notes (person deletion by DM recipient), and only workspace deletion removes the label definitions.

### Inbox reminders

**Inbox reminders** ([spec](../specs/2026-10-04-inbox-reminders.md)): a reminder belongs to the member who created it (`creator_id`); no other member, admin or owner can read or change it (another member's ID answers `404 reminder_not_found`), it is shown only in the app, and nothing sends it or runs it on a cron. `instagram_inbox_reminders` holds at most one `pending` row per workspace, connection, recipient and creator (partial unique index; a second create returns `409 reminder_exists` with the existing one), status changes are UPDATEs because server roles have no DELETE, and `instagram_inbox_reminder_events` is append-only with no actor only for the automatic `conversation_closed` and `member_removed` cancellations. Due is computed when read (`pending` and `due_at <= now()`). The screen sends a workspace-local `YYYY-MM-DDTHH:MM` and PostgreSQL converts it with the workspace's `time_zone` at write time (`localDueSql` in `src/app/inbox-reminders.ts`; a DST gap reads with the offset before the change and an overlap takes the later occurrence, unlike `wait_until`), from 1 minute to 2,160 hours ahead of `clock_timestamp()`; a later time zone change moves nothing. Writes take the state change's lock order (workspace `FOR SHARE`, the caller's member row `FOR SHARE`, the connection `FOR SHARE`, `lockConversation` exclusive, then the reminder row) and check `expected_version` (`409 reminder_conflict` with the current reminder). A closed conversation holds no pending reminder: closing (`PUT .../state`, open to closed) cancels every member's pending reminders on it in the same transaction, creating one on a closed conversation returns `409 conversation_closed`, and no reopen revives them; `removeMember` cancels the removed member's pending reminders in its transaction after locking their connections `FOR SHARE` in ID order. `GET /api/inbox?reminder=due` combines with the other filters and the cursor, and the list carries the caller's pending reminder per conversation plus `due_reminder_count` for the badge. The three deletion functions remove every member's reminders and their audit (person deletion by DM recipient), and the workspace export leaves both tables out (`EXCLUDED_TABLES`), so an admin's export carries no other member's reminders.

### Inbox label rules

**Inbox label rules** ([spec](../specs/2026-10-04-inbox-label-rules.md)): `instagram_inbox_label_rules` is workspace-wide (no connection), archive-only, at most 50 active per workspace (creation locks the workspace row `FOR UPDATE` via `lockWorkspaceForMember` before counting), `admin` for every route, with `contains`/`exact` only (no `all`) and keywords stored in the comment-rule normalization (`normalizeMatchText` in `src/instagram/comment-rule.ts`). `storeInboxMessage` applies them (`applyLabelRules` in `src/instagram/inbox.ts`) only to a text DM its INSERT stored, never to a postback, a redelivery or an earlier DM; after the ingestion locks it reads the rules unlocked and decides with the candidate labels already locked `FOR SHARE` by ID (so a fully skipped DM, even one that waited on a label archive, leaves no row), then takes the manual path's order (version 0 placeholder, label-set row `FOR UPDATE`, labels `FOR SHARE`) and skips, rather than throws on, an archived label, a label already present, a label a member ever removed from that conversation (`actor_id` set in `removed`), labels beyond 10 (kept in rule order) and a sender ID longer than the label tables' 40 digits, because a throw would roll back the DM and the batch's confirmations. One DM writes one version and one audit row whose `rule_id` is the first matching rule by `(created_at, id)`, even when that rule's own label was skipped, and whose `actor_id` is NULL (CHECK: exactly one of the two). A rule edit locks the rule `FOR NO KEY UPDATE` and, only when its content changes, the new label `FOR SHARE`; an archive is one non-key UPDATE and locks no label; neither takes a connection or conversation lock. Only `delete_workspace_data` removes rules (after the label events, before the labels), and the rules count in both workspace move checks.

### Manual replies

**Manual replies** ([server](../specs/2026-09-27-inbox-manual-replies.md), [UI](../specs/2026-09-28-inbox-manual-reply-ui.md)): requests carry a UUID key and the active handoff version; identical repeats return the existing row and payload reuse is refused. Only a fresh stored inbound text DM opens the 24-hour window. Cloudflare delivery rechecks the claim, token version and expiry, connection, handoff, identity bridge, derived pause and window immediately before POST. Earlier due pending rows preserve creation order; any sending or unresolved unknown row blocks every other reply in the same conversation, regardless of creation order. Future scheduled pending rows do not block immediate replies. One-shot [scheduled replies](../specs/2026-10-16-inbox-scheduled-replies.md) store an absolute `scheduled_at`, the accepted workspace time zone and a version; migration 049 must run before code deployment. Only the creator or an active admin may edit or cancel a pending scheduled row, with a version and idempotent operation key. The claim, wake and health queries exclude future schedules. The worker rechecks the scheduled creator’s active membership before sending; removal blocks delivery, while an admin-to-agent change remains allowed. Definite unsent failures allow an audited retry as a new linked row; unknown never allows retry, and an audited `no_retry` releases waiting rows. Stale sends become unknown with audit in the same transaction. Server roles cannot UPDATE or DELETE the audit.

### Reply templates

**Reply templates** ([spec](../specs/2026-10-16-inbox-reply-templates.md)): `workspace_reply_templates` stores workspace snippets, with 50 active names unique case-insensitively. Admins manage them; agents may list and preview. The restricted `{{name}}` grammar accepts at most 10 distinct names, and preview substitutes explicit strings once without reading customer fields or writing deliveries or consent. Both stored and rendered text use the manual composer's 1,000 UTF-16-unit limit. Edits require `expected_version`; archive is idempotent. The composer appends a successful preview to its current draft and refuses pending/unknown acceptance operations or combined overflow. Values, conversation changes and session reset invalidate previews and late responses. The table belongs in export, whole-workspace deletion and both empty-workspace movement checks; migration 048 must run through the full runner before code deployment. It does not schedule or send messages.

## Consent and flows

### Channel consent

**Channel consent** ([spec](../specs/2026-09-29-channel-consent.md)): `channel_consent_events` is append-only and `channel_consent_state` is its exact-scope projection, updated in the same transaction under the connection lock. `service_reply` grants need explicit evidence, `all` can only revoke, and marketing without an exact explicit grant is denied. Client `occurred_at` is evidence, not ordering. Private, follow and manual delivery check service revokes after claim and immediately before POST, for the comment sender and every DM recipient bridged by a provider-acknowledged same-sender reply. Only a later server-recorded explicit re-consent releases a revoke in the same scope; a delivery row already blocked or failed by an opt-out (`recipient_opted_out`) is terminal and never replays after re-consent. A consent read error defers the send (`pending / consent_unavailable`).

### Flow versions

**Flow versions** ([spec](../specs/2026-09-29-flow-version-contract.md)): `src/app/flow-schema.ts` is the pure document parser and publish validator; `flows` holds the draft, its revision and the publish pointer, and `flow_versions` rows are immutable (no server UPDATE/DELETE). Draft saves check shape only; publish checks the full graph, variables, fields and the trigger connection under the flow and connection row locks. A legacy comment rule and a non-archived published flow never share one connection/media: publish returns `legacy_rule_conflict` or `flow_trigger_conflict`, and enabling a rule returns `flow_trigger_conflict`. A field referenced by a current published version cannot be archived (`field_in_use`).

### Flow runs

**Flow runs** ([spec](../specs/2026-09-30-flow-runs.md)): publishing never sends; only an `enabled` flow runs, and enabling (or republishing an enabled flow) requires an OAuth trigger connection and a version that `flowExecutionErrors` in `src/app/flow-runtime.ts` accepts; archiving the flow or disconnecting its trigger connection turns it off. Comment ingestion starts at most one run per `(flow_id, event_id)`, pinned to the published version, only when no enabled legacy rule owns the media. Its reply is a `private_reply_outbox` row with `flow_run_id` instead of `rule_id` (exactly one is set), so every existing delivery guard applies; the shared claim check and the Cloudflare final guard block a disabled flow's reply as `inactive_flow`. Publish and enable lock the flow row `FOR NO KEY UPDATE`, so they never block the foreign-key checks of an ingestion batch that holds a connection lock. Tag and field actions run in the ingestion transaction under the contact-write connection lock (`FOR SHARE`, rechecking `active`), field row locks and `lockContact` (a per-contact advisory lock in `src/app/contact-fields.ts`) taken before the read; manual tag and field saves take the same `lockContact`, so recorded outcomes match what is stored. Actions apply to paused contacts too. A `delay` node (1 to 10,020 minutes, and at most that in total on any path to a message, so the reply fits the 7-day comment window) leaves the run `waiting` with a UTC `resume_at`; only the Cloudflare cron resumes it (`resumeDueFlowRuns` in `src/instagram/store.ts`), locking the connection `FOR SHARE` before the run row (`FOR UPDATE SKIP LOCKED`, still `waiting`), the same order as the deletion functions, and rereading contact facts; a run whose flow is off or whose connection is inactive when due ends `cancelled` without running later nodes, and re-enabling never revives it. A `wait_until` node (`HH:MM`, counted as 1,560 minutes toward that total, a day plus the largest clock-back shift) also leaves the run `waiting`, with `resume_at` the next occurrence of that wall-clock time strictly after `clock_timestamp()` in the workspace's `time_zone`, read when the run reaches the node and computed in PostgreSQL (`nextWallClockSql` in `src/instagram/store.ts`), so daylight-saving shifts are PostgreSQL's, a time that occurs twice resumes at its first occurrence still ahead, and a later zone change moves no waiting run. On a day the clocks go back a time wait can last a day plus the shift (under 1,560 minutes in `Antarctica/Troll`), so a path at the 10,020-minute total can reach a message after the 7-day window; that reply is blocked as `comment_expired` before the send, never sent late. A message may lead only to a `wait_for_reply` node (1 to 10,080 minutes, optional text `save_field_id`), and no message may follow the wait; queuing that message leaves the run `awaiting_reply` at the wait with no `resume_at`. `resumeRepliedFlowRun` in `ingestMessages` continues it on `replied` for a text DM (not a postback) from the reply's `recipient_id` dated from its `sent_at` to before `sent_at` plus the timeout, most recent reply first, locking the connection `FOR SHARE` and then the run `FOR UPDATE` (still `awaiting_reply`, else it retries the next most recent run), and records the message in `flow_runs.reply_message_id` so a redelivered message advances no other run on that connection; the cron continues it on `timeout` only after its reply is `sent` and the wait has passed, so a reply that never becomes `sent` keeps the run waiting. Flow off or connection inactive cancels it as for a delay, and a paused contact's reply still advances it. Message variables render once, so comment text is never re-parsed; a missing value, a boolean, or an empty or over-1000-character result fails the run without queuing a reply. `flow_step_runs` is append-only for server roles. The Node environment-token worker never sends flow replies.

### Early replies

**Early replies** ([spec](../specs/2026-09-30-flow-runs.md#발송-기록-전에-도착한-응답)): a text DM or confirmation postback that matched neither a follow conversation nor an awaiting run is kept in `instagram_unmatched_replies` only while the same connection has a reply in `sending` whose attempt started within 10 minutes and no later than the DM; `ingestMessages` reads that condition before the lookups and locks the connection `FOR SHARE` with it, so a deletion cannot commit before the kept row is written. After a reply is recorded as `sent`, a separate best-effort transaction (and the Cloudflare cron, or the Node worker's recovery tick) offers kept DMs from its `recipient_id` dated at or after its `attempt_started_at` to the reply wait and the follow confirmation, with `sent_at` widened to `attempt_started_at` for this path only; it locks the connection `FOR SHARE` before the kept row, rechecks the 15-minute boundary at that claim, and marks `matched_at` whether or not anything advanced. Both passes skip a kept DM while its connection still has a reply in `sending` that started within 10 minutes and no later than the DM, so an earlier sent reply to the same person cannot use it up; the only exception is that the post-send pass takes a confirmation postback bound to its own reply, and it leaves one bound to another reply alone. A reply wait does not time out while an unlinked kept text DM from its recipient, dated from the reply's attempt start to before the wait ends and under 15 minutes old, may still answer it. Kept text is no longer linked 15 minutes after receipt and is removed by the first scheduled run after that (no hard upper bound; `/privacy` says so), and the export omits it.

### Flow test runs

**Flow test runs** ([spec](../specs/2026-09-30-flow-runs.md#테스트-실행)): `POST /api/flows/<id>/test-run` (`admin`) walks the draft or the published version with `planFlowRun` over synthetic `comment_text`, `tags`, `fields`, `reply_text` and one `reply_branch`, continuing at once from every delay, time wait and reply wait. After the role check, it reads the flow and its publish context in one `REPEATABLE READ READ ONLY` transaction after the role check, never reads stored contact, comment or message data, and writes, queues or sends nothing. An optional `expected_revision` (draft only) returns `409 revision_conflict` when the stored draft has moved on, read in the same snapshot as the draft. A draft that fails publish validation, or a document that fails `flowExecutionErrors`, returns only its errors (422). Publish and the test run share `readPublishContext` in `src/app/flows.ts` (publish with its locks, the test run without), and the run's `flowWebhookPayload`, `fieldWriteTargets` and `webhookFieldIds` build its webhook previews, writable fields and #117 exclusions.

### Flow webhooks

**Flow webhooks** ([spec](../specs/2026-10-01-flow-webhook-delivery.md)): a `webhook` node (`{endpoint_id, field_ids, include_tags}`, port `next`) queues one `webhook_deliveries` row per `(flow_run_id, node_id)` in the run's transaction and the run continues without waiting; a delivery outcome never changes a run, a later node or a reply row. The payload holds only the chosen tags and field values and processing identifiers, never comment or DM text, a username or an Instagram identifier. A field that any published version of the workspace saves a reply into (`wait_for_reply.save_field_id`, current version or not) is never sent: publish refuses it on the `webhook` node, and on a reply wait that would save into a field another flow's webhook sends (`reply_field_not_sendable`), and `planFlowRun` leaves it out of every payload whatever was published (`replySavedFields` in `src/app/contact-fields.ts`, read after the contact facts). `sender_id` is stored beside it for person deletion only, and the payload is removed by the UPDATE that marks the row `sent`. Only the Cloudflare cron step `webhook_delivery` delivers (`deliverDueWebhooks` in `src/app/webhook-delivery.ts`), after the message steps and only while `SEND_ENABLED` is `true`; the Node worker never does. Each claim takes the workspaces in turn, by the [delivery order](../specs/2026-10-01-flow-webhook-delivery.md#전달-순서). Every attempt reads the endpoint again (inactive ends `dead / endpoint_inactive`), applies the URL rules again (`parseWebhookUrl`, shared with endpoint creation) and resolves A and AAAA through DNS-over-HTTPS immediately before the POST, refusing when any address is not public; Workers `fetch` resolves the name itself, so that check and the request are not atomic. The POST uses `redirect: "manual"` and a timeout that covers the body, and the response is read up to a size limit and never stored. A claim uses `FOR UPDATE SKIP LOCKED` and a fresh `attempt_id`, and later changes require `status = 'sending'` and that ID; a failure retries on the fixed schedule and then ends `dead`, and a stale `sending` row counts as an attempt, so delivery is at-least-once and `event_id` (kept across retries and a manual redelivery) is the receiver's deduplication key. Signing secrets are sealed with `TOKEN_ENCRYPTION_KEY` under `signingKeyContext` (workspace, endpoint, key), returned once at creation or rotation, at most two valid per endpoint, and every valid key signs each request. Every `/api/webhooks/*` route needs `admin`. Server roles have no DELETE on the four tables and no UPDATE on `webhook_redelivery_events`; the three deletion functions remove the rows and refuse with `sending_in_progress` while a delivery in their scope is `sending`. Delivery logs carry fixed codes only: never a URL, host, payload, secret or response.

### DM start triggers

**DM start triggers** ([spec](../specs/2026-11-08-instagram-dm-start-triggers.md)): `instagram_dm_keyword` (`{connection_id, keywords, match_mode: contains|exact|all, excluded_keywords}`, keywords required unless `all`) and `instagram_dm_default` (`{connection_id}`) are trigger nodes; a flow has exactly one trigger of any type. A DM-triggered flow holds only the trigger and `instagram_message` nodes without variables (`dm_trigger_unsupported_node`, `dm_trigger_unsupported_variable`), because a DM run has no comment, no 7-day window and no outbox, and its messaging sender ID is never linked to a comment contact; the refusals beyond `{{comment.text}}`, `wait_for_reply` and `delay` are a narrowing the spec lists separately. `flow_versions.trigger_type` keys a version: comment versions keep `(connection, media)`, DM versions have a NULL `trigger_media_id` (CHECK `flow_versions_trigger_key`). Publish (even of a disabled flow) and enable compare the trigger with the other enabled DM flows of the connection after the connection `FOR NO KEY UPDATE` lock: one enabled default-reply flow per connection (`dm_default_conflict`) and no overlapping keyword sets (`dm_keyword_conflict`, `dmTriggersOverlap` in `src/app/flow-schema.ts`; an `all` trigger overlaps every keyword trigger). `ingestMessages` calls `startDmTriggerFlow` (`src/instagram/dm-start-trigger.ts`) only for a typed DM that neither `resumeRepliedFlowRun` nor `offerMessage` took, after `keepUnmatched`; it reads flows and versions without row locks (publish and enable lock flow then connection) and takes the connection `FOR SHARE`. A keyword flow beats the default flow, the oldest matching flow wins, and one DM starts at most one run. Nothing starts for a message ID already in `instagram_message_receipts`, `flow_runs.reply_message_id` or `instagram_unmatched_replies`, or for a sender with a resumable run, a follow conversation in `waiting`/`pending`/`sending` under an enabled rule, an unlinked kept DM under 15 minutes old, a `service_reply` revoke of the messaging ID or of a comment sender bridged to it by a provider-acknowledged reply, with that sender's other bridged DM recipients (`messagingRecipientOptedOut` in `src/instagram/channel-consent.ts`, built on `deliveryRecipientOptedOutSql`), or an active inbox handoff; a blocked DM writes no row. In reverse (#291), a message ID already in `instagram_dm_start_events` for the consumer's connection is taken by neither `offerMessage` (also on the kept-DM reconcile) nor `resumeRepliedFlowRun` and is not kept by `keepUnmatched`, so a redelivery of a DM dated ahead of a later private reply writes no receipt, `reply_message_id` or kept row; each check is a read in the consumer's own statement, and a concurrent redelivery sees the start event because `ingestMessages` first takes a transaction advisory lock per distinct (account ID, message ID) of the batch (`'instagram-message:'` key, `lockMessageIds` in `src/instagram/follow-flow.ts`), before every other lock and in key order, whether or not inbox storage is on. `instagram_dm_start_events` (unique `(connection_id, message_id)`, never DM text), the run (`flow_runs.dm_start_event_id`, exactly one source by CHECK `flow_runs_source`) and the first message in `flow_dm_deliveries` (recipient = messaging sender ID, written `pending`, never `private_reply_outbox`) are written in the ingestion transaction; the run history and the flow-run report read its status, failure code and send time as the run's delivery state, and the run itself stays `delivering`, as a comment run does after its private reply. Delivery (#291, migration 069): only the Cloudflare queue consumer sends these rows, through `processNextDmFlowDelivery` in `src/instagram/dm-flow-delivery-worker.ts`, after manual replies and follow confirmations and before private replies and campaign rows; the Node worker never reads them, and no other claim, worker or resume does. `dmFlowDeliveryDueSql` is the one due predicate of the claim, `wakeDueReplies` and operations health: pending, due, no messaging-ID pause (`instagram_dm_automation`, keyed by workspace, connection and messaging ID, never linked to `instagram_contact_automation`) and no active `instagram_inbox_handoffs` row for the recipient; held rows stay pending. The claim takes one row `FOR UPDATE SKIP LOCKED` with a fresh `attempt_id`, and every later write is conditional on `status='sending' AND attempt_id`. `assertDmFlowDeliveryAllowed` runs after the claim, after the account read and as the transport's `beforeSend` immediately before the POST, in one statement: claim, run `delivering`, flow enabled and not archived (a republish does not stop the pinned version), connection sendable, token unchanged, no connection pause, the 24-hour window, the pause and the handoff, then `messagingRecipientOptedOut`; any block beats any retry. The window is open while the database clock is under 24 hours after the latest of the sender's DM start events and stored inbox `kind='text'` messages on the connection, each capped at its stored time because ingestion accepts DMs up to 60 s ahead; a stored postback is excluded on purpose, as in the manual-reply window. Outcomes follow the campaign worker; a rate limit uses the private-reply tiers (`rateLimitRetryDelaysSeconds`, `rate_limit_retries`, `failed` after the third) and pauses the connection; a pause seen after the guard defers as `connection_paused` without spending a retry; a stale `sending` row becomes `unknown`/`worker_interrupted` in the cron's `stale_recovery`. No hourly budget applies: the send-quota spec exempts Send API DMs. The pause has no API route or screen yet. `CLAIMED_RUN` joins both sources, and a DM run that reaches `continueFlowRun` ends `cancelled`/`unsupported_trigger`. The editor (#292) creates both DM triggers from a trigger-less flow, never changes a trigger's type, offers only `instagram_message` after a DM trigger (so one message) and no message variables there, and sends a DM test run only the source and text (plus the revision for a draft). The three deletion functions lock DM flow rows `FOR UPDATE NOWAIT` and refuse `sending_in_progress` while one is held or sending, remove deliveries, steps, runs, then start events, and remove the messaging-ID pause (person deletion by the `dm_recipient` set); all three tables and `instagram_dm_automation` are exported, and migrations 068 and 069 must run through the full runner before code deployment.

## Deletion, workspace and operations

### Connection data deletion

**Connection data deletion** ([spec](../specs/2026-09-29-connection-data-deletion.md), [UI](../specs/2026-09-30-connection-deletion-ui.md)): `public.delete_connection_data` is the only path that deletes product rows, apart from `public.delete_expired_oauth_states`, which the cron uses to remove expired OAuth states (migration 038). It is an administrator-owned SECURITY DEFINER function; server roles have EXECUTE on it and still no table DELETE. It requires the workspace-owned connection to be disconnected (inactive, send off, no token), the confirmed account ID, and no `sending` rows, checked after locking the connection `FOR UPDATE` and its delivery rows `FOR UPDATE NOWAIT`; a row held by another transaction refuses with `sending_in_progress` instead of waiting, which would deadlock with a send being finalized (migration 023). It keeps revoke consent records, the connection row and user configuration (the outbox `AFTER DELETE` trigger still updates the connection's private-reply carry columns when deleted rows called Meta within the hour, as in person deletion; [carry](../specs/2026-10-12-send-quotas.md#삭제한-행의-호출-이월)), and writes a counts-only `data_deletion_records` row that runtime roles can read but not write. Before deleting the reply bridge it re-records bridged DM-recipient opt-outs on the comment sender. Contact tag, field value and automation writes lock the connection row `FOR SHARE` first so they serialize with deletion.

### Person data deletion

**Person data deletion** ([spec](../specs/2026-09-30-person-data-deletion.md)): `public.delete_person_data` is an administrator-only SECURITY INVOKER function with EXECUTE revoked from PUBLIC, API and server roles; there is no API. From a comment sender or DM recipient it follows the provider-acknowledged reply bridge and handoff pairs to a closure, locks that person's delivery rows, and deletes only that person's rows in one connection. It refuses while any of that person's rows is `sending`, keeps revokes (re-recording bridged DM-recipient opt-outs on the comment sender), does not create an opt-out, and writes a `scope=person` evidence row without the identifier.

### Workspace deletion

**Workspace deletion** ([spec](../specs/2026-09-30-workspace-data-deletion.md)): `public.delete_workspace_data` is an administrator-only SECURITY INVOKER function with EXECUTE revoked from PUBLIC, API and server roles; there is no API. It locks the workspace and all its connections `FOR UPDATE`, refuses while any connection is still connected or any delivery row is `sending` or held by another transaction (`FOR UPDATE NOWAIT`, migration 023), deletes every product row of the workspace including revokes and `data_deletion_records`, then the OAuth states, membership and workspace. It writes a counts-only `workspace_deletion_records` row (no foreign keys, no member IDs, no runtime access) and returns `owner_user_id`, the only Supabase Auth user the administrator deletes, plus informational `member_user_ids`.

### Workspace roles

**Workspace roles** ([spec](../specs/2026-09-30-workspace-roles.md)): `workspace_members.role` is `owner`, `admin` or `agent`, with at most one owner per workspace and one workspace per user. `workspaceFor(pool, user, role)` takes the least role as a required argument and reads membership and role on every request, so a removal or downgrade applies to the next request; agents keep inbox, handoff, manual reply, contact and consent work and read-only settings, and every settings change, account connection, data deletion and the export needs `admin`. `workspaces.time_zone` (default `Asia/Seoul`) is returned to every role by `POST /api/workspace` and changed only by admins through `PUT /api/workspace/settings`, which stores only exact `pg_timezone_names` names (`invalid_time_zone`; no CHECK constraint, because that list can change). Owner-only invites (`workspace_invites`, SHA-256 of a single-use 7-day link token, bound to the confirmed email) and member removal (`removed_at`, since server roles have no DELETE) live in `src/app/workspace-members.ts`; every membership read excludes removed rows. Accepting an invite moves a sole owner only out of an empty workspace (`currentWorkspaceMovable`, mirrored in `deploy/assign-workspace-owner.sql`), so a new workspace-scoped table whose rows do not require an `instagram_connections` row must be added to both checks.

### Workspace export

**Workspace export** ([spec](../specs/2026-09-30-workspace-export.md)): `GET /api/workspace/export` returns the caller's workspace as one JSON file read in a single `REPEATABLE READ READ ONLY` transaction. Every public table must be listed in `EXPORTED_TABLES` or `EXCLUDED_TABLES` in `src/app/workspace-export.ts`, and secret-like columns must be in that table's `omit`; `workspace-export.db.test.ts` enforces both. A per-user request limit (`WORKSPACE_EXPORT_LIMIT`) runs before the database, and a size check in the same snapshot refuses an oversized workspace whole before any `jsonb_agg` (`WORKSPACE_EXPORT_LIMITS`; numbers in the [spec](../specs/2026-09-30-workspace-export.md#요청-한도와-크기-한도)); it never truncates.

### Plan entitlements

**Plan entitlements** ([spec](../specs/2026-10-12-plan-entitlements.md)): `workspaces.plan` is one of the keys of `PLANS` in `src/app/plans.ts`, which holds every limit; the `workspaces_plan` CHECK lists the same keys. Existing workspaces were set to `advanced` and new ones start on `free`; only an administrator `UPDATE` changes a plan, because server roles have only column grants on `workspaces` (INSERT `id`, `time_zone`; UPDATE `time_zone`), so a new server-written `workspaces` column must be added to those grants in `deploy/supabase-access.sql` and `deploy/init-app-user.sh`. Seats are active members plus open invites; creating an invite (workspace `FOR UPDATE`) and accepting one (target workspace `FOR NO KEY UPDATE`) refuse with `409 seat_limit_reached`. Connected accounts are rows that hold a token or are active; OAuth completion locks the workspace `FOR NO KEY UPDATE` and refuses an account not connected in that workspace with `409 connection_limit_reached`, never a re-authorization. `campaign_sends_per_month` ([monthly campaign sends](../specs/2026-10-12-plan-entitlements.md#월-캠페인-발송-한도); free 0) is counted only by `campaignSendAllowance` in `src/app/plans.ts`: `used` is the delivery rows of runs whose `started_at` is in the workspace-time-zone calendar month, except rows cancelled with no `provider_called_at`; `reserved` is the stored candidate counts of approvals in force due in that month (`greatest(coalesce(scheduled_at, now()), now())`). Approval creation, and a reschedule that changes the due month, refuse with `409 broadcast_limit_reached` (writing nothing) when the limit is 0 or used + reserved + the request exceeds it; the run start applies the same count with its own approval left out of `reserved`. All three count after the workspace row `FOR UPDATE` they already take first; no lock was added. Deletion functions remove delivery rows, so they lower `used`. A downgrade removes nothing.

### Operations health

**Operations health** ([spec](../specs/2026-10-01-operations-health.md)): every runtime log goes through `logOperation` in `src/app/operations-log.ts`, which keeps only allow-listed fields of a fixed shape; do not call `console.*` directly or log an error message, request body or provider response. Each Cloudflare cron step records its outcome in `scheduled_steps` (service-wide, no workspace data, excluded from the export and the deletion functions), and a failed step does not stop the later ones. `GET /api/workspace/health` needs `admin`; alert thresholds live in `ALERT_THRESHOLDS` in `src/app/operations-health.ts`, and the cron logs each alert start or clear once, plus each new `unknown` outcome while `alert_unknown_outcome` is on. The `cron` row is written after the `alerts` step, so it counts that step's failure too. The 24-hour outcome counts date a row that stale recovery turned `unknown` / `worker_interrupted` by its recovery (`recovered_at` on the outbox and follow rows, added by migration 067 and set by every stale-recovery statement; the manual reply's `unknown` event; the campaign and DM flow rows' `updated_at`), and every other outcome by its last claim or creation ([#274](../specs/2026-10-01-operations-health.md#지표와-api)).

## Reports

### Manual reply reports

**Manual reply reports** ([spec](../specs/2026-10-16-manual-reply-reports.md)): `GET /api/reports/manual-replies` requires an active admin and reads current request counts by creation date in the workspace time zone, optionally scoped to an owned connection. Exact local-date bounds are half-open and limited to 366 calendar days; `expected_time_zone` rejects stale interpretation. One aggregate statement rechecks membership, zone and connection and returns decimal-string disjoint status counts, including separate unresolved and resolved unknown. Event rows do not multiply counts; explicit retry rows count separately; deleted rows disappear. `sent` means provider accepted only. The home screen exports its displayed snapshot as CSV and clears it on filter or workspace/session changes; no customer text or provider delivery/read inference is included. The creation-period index `(workspace_id,created_at,connection_id)` bounds reads with or without an account filter; run migration 050 through the full runner before deploying the report.

### Flow-run reports

**Flow-run reports** ([spec](../specs/2026-10-16-flow-run-reports.md)): `GET /api/reports/flow-runs` requires an active admin and selects runs by `flow_runs.created_at` in a workspace-local half-open period of 1–366 days. Optional owned account and flow filters use the run’s pinned IDs, including inactive accounts and archived flows. One statement rechecks membership, time zone and filter ownership, then returns separate decimal-string partitions for current run state and the linked first-reply outbox state, including absent outbox. Neither `ended` nor `sent` proves delivery or conversion; steps and webhook deliveries do not multiply counts. Home displays and exports the same response, clears it on input/session changes, and excludes labels/customer data from CSV. The flow picker lists existing non-archived flows, while all-flow reports include archived history. Run migration 051 through the full runner before deployment to add the workspace/creation-period index. `reply_wait_counts` (`reached`, `replied`, `not_replied`) counts runs that are `awaiting_reply`, carry `reply_message_id`, or queued a private reply and left `delivering`; `replied` is `reply_message_id IS NOT NULL` (a recipient DM, not delivery or a read), and the report reads no `flow_step_runs`, because a wait leaves a step only when it resumes. Optional `group_by=day|connection|flow` adds `groups` (absent otherwise) keyed by workspace-local creation date or pinned UUID, only for groups with runs; every group partition sums to its own total and the groups sum to the top level, both read from one cohort CTE with a single period-index scan.

### Handoff reports

**Handoff reports** ([spec](../specs/2026-10-16-handoff-reports.md)): `GET /api/reports/handoffs` requires an active admin and counts retained handoff transition events by `created_at` in a workspace-local half-open period of 1–366 days, with an optional owned account filter. One statement rechecks membership, time zone and account ownership. Decimal-string metrics are total events, started, cleared and distinct `(connection_id,recipient_id)` conversations. Idempotent handoff requests add no event; repeated real cycles count separately. Cleared does not imply automated sending or consultation resolution. No current-state count, conversion rate or flow attribution is inferred from identity evidence. The home report exports the displayed snapshot and invalidates results on input/session changes. Run migration 052 through the full runner before deployment to add the workspace/creation-period index.

### Campaign run reports

**Campaign run reports** ([spec](../specs/2026-11-09-campaign-run-reports.md)): `GET /api/reports/campaign-runs` requires an active admin and selects runs by `campaign_runs.started_at` in a workspace-local half-open period of 1–366 days, with an optional owned `draft_id` filter (archived drafts included; a foreign or missing draft is `404 campaign_draft_not_found`). There is no account filter, because one run's pinned audience can span several connections. One statement rechecks membership, time zone and draft ownership, reads `statement_timestamp()` once, and returns three decimal-string partitions: run states (`running`, `cancelled`, `completed`, `limit_not_started`, where a run with the `plan_limit_exceeded` start key counts only as `limit_not_started`), summed stored start counts (the eight reasons, `plan_limit_exceeded` included, add up to `remaining_member_count`), and the current statuses of the cohort's delivery rows. Delivery rows are counted per cohort run in a LATERAL aggregate through the `run_id`-leading unique index `campaign_deliveries_member`; joining them flat would let the planner scan every row. Connection and person deletion remove delivery rows but keep runs and `start_counts`, so the `candidate` sum and the delivery total can differ; `sent` means provider accepted only. No message text, identifiers, approvers, failure text or draft names leave the endpoint or the CSV. Home displays and exports the same response and clears it on input/session changes; the picker lists non-archived drafts. No migration is needed.
