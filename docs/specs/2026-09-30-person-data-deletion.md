# 이용자 단위 데이터 삭제

## 범위

[이슈 #82](https://github.com/AndrewDongminYoo/auto-chatter/issues/82)의 계약입니다.
앱 사용자가 아닌 Instagram 이용자가 이메일로 삭제를 요청하면, 운영자가 본인 확인을 마친 뒤 한 연결 안에서 그 사람의 기록만 삭제합니다.
[연결 단위 삭제](2026-09-29-connection-data-deletion.md)와 같은 삭제 증적 테이블을 쓰며, 증적의 `scope`는 `person`입니다.
대시보드 화면과 작업 공간 API는 제공하지 않습니다.
삭제는 수신 거부를 만들지 않으므로, 삭제한 뒤 같은 사람이 다시 댓글을 달면 규칙에 따라 다시 답장할 수 있습니다.

## 대상자 확인

운영자는 요청 이메일의 Instagram 계정명과 게시물·댓글 링크로 대상 연결과 댓글 작성자 ID 또는 DM 수신자 ID를 찾습니다.
함수는 주어진 ID에서 아래 연결 고리를 번갈아 따라가며, 새 ID가 더 나오지 않을 때까지 같은 사람의 다른 ID를 모읍니다.

- 댓글 작성자 ID에서는 공급자가 발송을 확인한 비공개 답장의 DM 수신자 ID를 찾습니다. 동의 검사가 쓰는 것과 같은 연결입니다.
- DM 수신자 ID에서는 같은 연결로 그 수신자에게 답장을 받은 댓글 작성자 ID를 찾습니다. 그 작성자가 다른 확인된 수신자에게 받은 답장도 다시 따라갑니다.
- 상담 전환은 검증된 연결로만 시작되므로, 찾은 ID가 포함된 상담 전환의 작성자·수신자 쌍도 같은 사람으로 봅니다.

연결 고리가 없는 DM 수신자는 그 DM 기록과 동의 허용 기록만 삭제합니다.

## 삭제하는 기록

- 찾은 DM 수신자의 수동 답장과 감사 기록, 인박스 메시지
- 찾은 ID가 포함된 상담 전환과 이력
- 찾은 댓글 작성자의 연락처 자동화 상태, 태그, 필드 값, 비공개 답장 outbox, 댓글
- 그 outbox 또는 DM 수신자에 연결된 팔로우 대화
- 찾은 ID의 동의 허용(grant) 상태와, 현재 상태가 참조하지 않는 허용 이벤트

## 보관하는 기록

- 수신 거부 이벤트와 상태. 연결 고리로 댓글 작성자에게 이어진 DM 수신자의 수신 거부는 연결을 지우기 전에 댓글 작성자 ID로 한 번 더 기록합니다.
- 확인 메시지 수신 기록: 메시지 ID와 시각만 있고 사람 식별자가 없어 삭제 대상에서 제외합니다.
- 다른 사람과 다른 연결의 기록, 연결 행, 운영자 설정
- 삭제 증적: 연결 ID, 처리한 운영자 ID, 완료 시각, `scope=person`, 테이블별 건수만 가지며 대상자 ID는 남기지 않습니다.

## 거부와 동시성

- 연결이 해당 작업 공간에 없으면 `AC001`, 식별자 종류가 `comment_sender`·`dm_recipient`가 아니거나 값이 비어 있으면 `AC005`를 반환합니다.
- 함수는 그 사람의 비공개 답장, 팔로우 후속 메시지, 수동 답장 행을 먼저 `FOR UPDATE`로 잠근 뒤 상태를 확인합니다. `sending` 상태가 있으면 `AC003`을 반환하고 아무것도 지우지 않습니다.
- 워커는 `FOR UPDATE SKIP LOCKED`로 선점하므로, 잠그기 전에 끝난 선점은 `sending`으로 보여 거부되고 잠근 뒤의 선점은 이 행을 건너뜁니다.
- 잠근 뒤 새로 들어온 댓글과 그 답장은 새 기록이므로 남기며, 같은 요청을 다시 실행해 지울 수 있습니다.
- 연결은 해제하지 않아도 되며, 함수는 연결 행을 `FOR NO KEY UPDATE`로 잠가 연락처 쓰기와 직렬화합니다.
- 같은 요청을 다시 실행하면 건수가 모두 0인 증적을 하나 더 남깁니다.

## 권한과 실행

`public.delete_person_data(workspace, connection, actor, identity_kind, identity_value)`는 관리자가 소유하는 `SECURITY INVOKER` 함수입니다.
PUBLIC, Supabase API 역할, 서버 역할 모두 실행 권한이 없으므로 관리자 세션에서만 실행할 수 있습니다.
운영자는 관리자 연결에서 트랜잭션을 열고 함수를 실행한 뒤, 반환된 건수를 확인하고 커밋합니다.

```sql
BEGIN;
SELECT public.delete_person_data('<workspace_id>', '<connection_id>', '<operator_user_id>', 'comment_sender', '<sender_id>');
COMMIT;
```

`actor`에는 처리한 운영자의 Supabase 사용자 ID를 넣습니다.
처리 결과는 요청자에게 이메일로 안내하고, 대상자 ID는 증적이 아니라 요청 이메일에만 남습니다.
