# 버전 고정 플로 실행 계약 (첫 구현)

## 범위

[이슈 #29](https://github.com/AndrewDongminYoo/auto-chatter/issues/29)의 첫 구현입니다.
발행된 플로 버전이 댓글에 따라 결정적으로 실행되고, 실행 경로와 발송 결과를 이력으로 남깁니다.
이번 구현은 댓글 트리거, `has_tag`·`field_equals` 분기, 그리고 경로의 첫 `instagram_message`를 댓글 비공개 답장으로 보내는 동작을 실행합니다.
[이슈 #31](https://github.com/AndrewDongminYoo/auto-chatter/issues/31)의 첫 구현으로 `add_tag`·`remove_tag`·`set_field` 동작과 메시지 변수도 실행하며, 계약은 아래 [태그·필드 동작과 메시지 변수](#태그필드-동작과-메시지-변수)에 있습니다.
[이슈 #32](https://github.com/AndrewDongminYoo/auto-chatter/issues/32)의 첫 구현으로 고정 지연(`delay`)과 그 재개도 실행하며, 계약은 아래 [지연과 재개](#지연과-재개)에 있습니다.
#32의 두 번째 구현으로 메시지 뒤의 사용자 응답 대기(`wait_for_reply`)와, #31의 나머지인 응답 수집(응답 본문을 text 필드에 저장)도 실행하며, 계약은 아래 [응답 대기](#응답-대기)에 있습니다.
#32의 세 번째 구현으로 작업 공간 시간대 기준의 시각 대기(`wait_until`)도 실행하며, 계약은 아래 [시각 대기](#시각-대기)에 있습니다.
팔로우 확인, 메시지 버튼, 응답 뒤의 후속 메시지와 편집 화면(#30)은 포함하지 않습니다.
문서 형식과 발행 검증은 [플로 초안·버전·발행 검증 계약](2026-09-29-flow-version-contract.md)을 따릅니다.

## 켜기 스위치

`flows.enabled`의 기본값은 false이며, 발행만으로는 실행되지 않습니다.
켜기(`POST /api/flows/:id/enable`)는 플로 행과 트리거 연결 행을 차례로 잠근 뒤, 현재 발행 버전이 다음 조건을 모두 만족할 때만 성공합니다.

- 보관되지 않았고 발행 버전이 있습니다. 아니면 각각 `409 flow_archived`, `409 flow_not_published`를 반환합니다.
- 트리거 연결이 활성이고 OAuth 자격 증명을 가집니다. 환경 변수로 관리하는 연결의 Node 워커는 플로 답장을 발송하지 않으므로 `login_mode_required`로 거부합니다.
- 모든 노드를 이 실행기가 실행할 수 있습니다.

실행할 수 없으면 `422 {error: "flow_not_executable", errors}`를 반환하고, 오류는 발행 검증과 같은 `code`·`path`·`node_id`·`edge_index` 형식을 씁니다.

| 코드                        | 뜻                                                |
| --------------------------- | ------------------------------------------------- |
| `unsupported_node`          | 이번 구현이 실행하지 않는 노드 타입               |
| `unsupported_message`       | `button_title`을 쓰는 메시지                      |
| `unsupported_variable`      | boolean 필드를 변수로 쓰는 메시지                 |
| `unsupported_after_message` | 메시지 노드에서 응답 대기가 아닌 노드로 가는 연결 |
| `connection_unavailable`    | 트리거 연결이 없거나 비활성                       |
| `login_mode_required`       | 트리거 연결에 OAuth 자격 증명이 없음              |

켜진 플로를 다시 발행하면 새 버전도 같은 조건을 통과해야 하며, 통과하지 못하면 `422 flow_invalid`로 버전을 만들지 않습니다.
끄기(`POST /api/flows/:id/disable`)는 항상 성공하고, 보관은 스위치를 함께 끕니다.
끄기나 보관이 커밋되기 전에 플로를 켜진 상태로 읽은 실행은 그대로 끝나며, 이는 그 댓글이 끄기 직전에 처리된 것과 같습니다.
그 실행의 태그·필드 동작은 적용되고, 답장은 발송 직전 검사에서 `blocked / inactive_flow`로 막힙니다.
기존 댓글 규칙처럼, 연결을 해제하면 그 연결을 트리거로 쓰는 플로도 꺼지므로 다시 연결해도 자동으로 실행되지 않습니다.
DB 제약은 켜진 플로가 보관되지 않았고 발행 버전을 가리키도록 강제합니다.

## 실행 시작

댓글 수집 트랜잭션에서, 같은 연결·게시물에 켜진 기존 댓글 규칙이 없으면 켜진 발행 플로를 찾습니다.
두 기능은 발행과 규칙 켜기 검사 때문에 한 게시물을 함께 소유할 수 없습니다.
트리거는 기존 댓글 규칙과 같은 매칭 함수로 키워드·모드·제외어를 검사하며, 맞지 않으면 실행을 만들지 않습니다.
실행은 그 시점의 발행 버전 ID를 기록하고, 이후 다시 발행하거나 초안을 바꿔도 이미 만든 실행과 그 답장은 바뀌지 않습니다.
분기는 같은 트랜잭션에서 읽은 연락처 태그와 필드 값만으로 평가하므로, 같은 문서와 같은 값은 항상 같은 경로를 만듭니다.
`field_equals`는 저장된 세그먼트 조건과 같게 NULL 값을 미설정으로 보고, `eq`는 JSON 값과 타입이 모두 같을 때만 참입니다.

중복은 제약으로 막습니다.
같은 댓글의 재전송은 댓글 이벤트 고유 제약에서 멈추고, 실행은 `(flow_id, event_id)`마다 하나이며, 답장은 기존 outbox의 이벤트별·보낸 사람과 게시물별 고유 제약을 그대로 따릅니다.

## 상태와 단계 기록

| 실행 상태        | 뜻                                                                                                                                             |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `delivering`     | 메시지를 outbox에 넣었습니다. 발송 결과는 outbox 행이 소유합니다.                                                                              |
| `ended`          | 연결이 없는 포트에 도달해 메시지 없이 끝났습니다.                                                                                              |
| `skipped`        | 같은 보낸 사람과 게시물에 이미 답장이 있어 큐에 넣지 않았습니다(`duplicate_recipient`).                                                        |
| `failed`         | 실행할 수 없는 노드에 도달했거나(`unsupported_node`), 문서를 해석하지 못했거나(`invalid_definition`), 동작·변수 절의 실패 코드에 해당합니다.   |
| `waiting`        | 지연이나 시각 대기 노드에서 멈췄고 `resume_at`에 재개합니다.                                                                                   |
| `awaiting_reply` | 메시지를 outbox에 넣었고, 그 메시지 뒤의 응답 대기 노드에서 사용자 응답이나 대기 만료를 기다립니다.                                            |
| `cancelled`      | 재개 시점에 플로가 꺼졌거나(`inactive_flow`) 연결이 비활성이어서(`connection_unavailable`) 지연이나 응답 대기 뒤의 노드를 실행하지 않았습니다. |

`flow_step_runs`는 실행이 지난 노드마다 노드 ID, 타입, 결과를 순서대로 기록합니다.
결과는 조건의 `true`·`false`, 트리거의 `next`, 메시지의 `queued`·`duplicate_recipient`, 동작의 결과, 또는 실행을 실패시킨 코드입니다.
실행되지 않는 노드를 건너뛰지 않으며, 켜기 검사를 통과한 버전에서는 `unsupported_node`에 도달하지 않습니다.
지연 노드와 시각 대기 노드는 `waiting`을 결과로 남깁니다.
재개한 실행은 그 노드 다음부터 순서 번호를 이어서 기록하므로, 단계 목록은 하나의 경로로 읽힙니다.
응답 대기 노드는 메시지를 큐에 넣을 때 기록하지 않고, 응답이나 만료로 재개할 때 `replied`·`timeout`을 결과로 남깁니다. 응답을 필드에 저장하는 대기는 같은 노드에 저장 결과를 한 번 더 남깁니다.

## 태그·필드 동작과 메시지 변수

동작 노드는 경로 순서대로 실행되고, 뒤따르는 분기와 변수는 바뀐 값을 읽습니다.

| 노드         | 단계 결과                                                                              |
| ------------ | -------------------------------------------------------------------------------------- |
| `add_tag`    | `added`, 이미 있으면 `already_present`, 태그가 20개이면 `tag_limit`(실행은 계속합니다) |
| `remove_tag` | `removed`, 없으면 `absent`                                                             |
| `set_field`  | `set`, 같은 값이면 `unchanged`, 필드가 보관되었으면 실행 실패(`field_unavailable`)     |

실행은 수집 트랜잭션에서 읽은 태그와 필드 값에 대한 최종 변경분만 저장합니다.
같은 경로에서 추가한 뒤 제거한 태그처럼 결과가 원래 값과 같으면 쓰지 않습니다.
동작이 있는 버전의 실행은 연락처 쓰기와 같은 연결 행 `FOR SHARE` 잠금을 잡고 연결이 여전히 활성인지 확인하며, 비활성이면 실행을 만들지 않습니다.
쓰는 필드 행도 `FOR SHARE`로 잠가 보관과 직렬화합니다.
그다음 연결과 보낸 사람 단위의 연락처 잠금(트랜잭션 advisory 잠금)을 잡은 뒤 태그와 필드 값을 읽습니다.
수동 태그 저장과 수동 필드 값 저장도 같은 잠금을 잡으므로, 같은 연락처에 대한 다른 실행이나 수동 편집은 이 실행이 커밋할 때까지 기다리고, 단계 결과와 분기는 항상 실제로 저장된 값을 기준으로 합니다.
발행과 켜기는 플로 행을 `FOR NO KEY UPDATE`로 잠급니다. 이 모드는 `flow_runs` 삽입의 외래 키 검사(`FOR KEY SHARE`)와 충돌하지 않으므로, 한 배치에서 연결 잠금을 쥔 수집과 발행·켜기가 서로를 기다리는 교착 상태가 생기지 않습니다.
서로 다른 연락처의 댓글을 반대 순서로 담은 두 배치가 동시에 수집되면 연락처 잠금끼리 교착 상태가 날 수 있습니다. 이때 PostgreSQL이 한 배치를 롤백하고 웹훅은 오류를 반환하므로, 기존 outbox 고유 제약에서와 같이 Meta의 재전송으로 다시 처리됩니다.
연락처의 수동 중지나 상담 전환 중지는 동작을 막지 않습니다. 큐에 들어간 답장은 기존 중지 계약에 따라 재개될 때까지 발송되지 않습니다.
실패한 노드 이전의 동작은 실행 순서대로 이미 적용된 것으로 저장하고 단계 기록에 남깁니다.
답장이 중복으로 큐에 들어가지 않아 실행이 `skipped`가 되어도, 메시지 노드 앞의 동작은 적용됩니다.

메시지 변수는 `{{comment.text}}`(실행을 시작한 댓글 본문)와 `{{field:<id>}}`(text·number·date 필드 값)입니다.
발행 검증은 형식과 필드 존재를 확인하고, 켜기 검사는 boolean 필드 변수를 `unsupported_variable`로 거부합니다.
치환은 한 번만 하므로 댓글 본문이나 저장된 값에 들어 있는 `{{...}}`는 다시 해석하지 않고 글자 그대로 보냅니다.
HTML이나 지시문으로 해석하는 단계는 없습니다.
다음 경우에는 답장을 큐에 넣지 않고 실행을 `failed`로 기록합니다.

| 코드                   | 뜻                                            |
| ---------------------- | --------------------------------------------- |
| `variable_missing`     | 변수가 가리키는 필드 값이 없거나 NULL입니다.  |
| `unsupported_variable` | 저장된 값이 boolean입니다.                    |
| `message_empty`        | 치환 결과가 공백뿐입니다.                     |
| `message_too_long`     | 치환 결과가 1000자를 넘습니다.                |
| `field_unavailable`    | `set_field`가 가리키는 필드가 보관되었습니다. |

## 지연과 재개

`delay` 노드는 설정한 분만큼 실행을 멈추며, 1분부터 10,020분(7일에서 1시간을 뺀 값)까지 정수로 지정합니다.
비공개 답장은 댓글 작성 후 7일 안에 보내야 하는데(`reply-policy.ts`), 지연은 웹훅이 도착한 시점부터 셉니다.
그래서 웹훅·cron·재시도에 걸리는 시간으로 1시간을 남겨 둡니다. 이 값은 서비스 정책이며 Meta가 정한 지연 상한이 아닙니다.
발행 검증은 메시지로 가는 모든 경로에서 지연의 합계가 같은 상한을 넘지 않는지도 확인하고, 넘으면 그 메시지 노드에 `delay_exceeds_reply_window`를 반환합니다.
메시지에 도달하지 않는 경로의 지연은 이 합계 검사에 포함하지 않습니다.
실행이 수집 트랜잭션에서 지연 노드에 도달하면, 그 앞의 동작과 단계를 저장하고 실행을 `waiting`으로 남깁니다.
재개 시각 `resume_at`은 실행이 지연 노드에 도달한 시점의 DB 시각(`clock_timestamp()`)에 지연을 더한 timestamptz(UTC)이고, `resume_node_id`는 실행이 멈춘 지연 노드입니다.
DB 제약은 두 값이 `waiting`일 때만 있도록 강제합니다.
지연 노드나 시각 대기 노드를 거치는 순환은 허용하지 않습니다. 시간만 기다리는 순환은 같은 경로를 타이머로 반복하기 때문입니다. 응답 대기는 메시지 바로 뒤에만 올 수 있고 그 뒤에 메시지를 둘 수 없으므로 순환을 닫을 수 없어, 모든 순환을 거부합니다.

재개는 Cloudflare cron이 매분 `resumeDueFlowRuns`로 수행하며, 발송 스위치가 꺼져 있어도 실행합니다.
재개는 답장을 outbox에 넣기만 하고, 실제 발송 여부는 기존과 같이 발송 스위치와 guard가 결정합니다.
Node 환경 변수 토큰 워커는 플로 답장을 보내지 않으므로 실행을 재개하지도 않습니다.
due 실행은 실행마다 별도 트랜잭션에서 처리합니다.
먼저 연결 행을 `FOR SHARE`로 잠그고, 그다음 실행 행을 `FOR UPDATE SKIP LOCKED`로 잠근 뒤, 실행이 여전히 `waiting`이고 due인지 확인합니다.
연결을 먼저 잠그는 순서는 연결 행을 잠근 뒤 그 연결의 행을 지우는 세 삭제 함수와 같으므로, 재개와 삭제가 서로를 기다리는 교착 상태가 생기지 않습니다.
상태 전이가 이 잠금 안에서 일어나므로 cron이 겹치거나 재배포가 일어나도 한 실행은 한 번만 진행하며, outbox 고유 제약도 그대로 적용됩니다.
재개에는 큐 메시지를 쓰지 않으므로 큐 유실로 잃을 알림이 없고, 처리하지 못한 due 실행은 다음 cron이 이어서 처리합니다.
한 cron은 실행을 최대 50개까지 처리합니다.
한 실행이 오류로 실패하면 그 실행만 롤백하고 다음 실행을 처리합니다. cron은 발송 복구와 깨우기를 마친 뒤 실패를 보고하고, 실패한 실행은 `waiting`으로 남아 다음 cron이 다시 시도합니다.

| 재개 시점의 상태       | 결과                                 |
| ---------------------- | ------------------------------------ |
| 연결이 비활성          | `cancelled / connection_unavailable` |
| 플로가 꺼졌거나 보관됨 | `cancelled / inactive_flow`          |

취소된 실행은 지연 뒤의 노드를 실행하지 않으며, 플로를 다시 켜도 되살아나지 않습니다.
그 밖의 경우에는 고정된 버전 문서로 지연 다음 노드부터 실행을 이어 갑니다.
동작이 있는 버전은 수집과 같은 필드 잠금과 연락처 잠금을 잡고, 태그와 필드 값은 재개 시점에 다시 읽습니다. 따라서 지연 중에 바뀐 연락처 값이 분기와 동작에 반영됩니다.
메시지 변수 `{{comment.text}}`는 저장된 댓글 본문으로 치환합니다.
같은 보낸 사람과 게시물에 이미 답장이 있으면, 수집할 때와 같이 실행이 `skipped / duplicate_recipient`가 됩니다.
다음 지연 노드를 만나면 새 재개 시각으로 다시 `waiting`이 됩니다. 이 시각도 잠금을 기다린 뒤 지연 노드에 도달한 시점부터 세므로, 잠금 대기 시간이 다음 지연을 줄이지 않습니다.
삭제 함수는 대기 중인 실행도 지우며, 지워진 실행은 재개 대상에서 빠집니다.

재개가 큐에 넣은 답장도 다른 플로 답장과 같은 발송 guard를 통과해야 합니다.
플로 꺼짐(`inactive_flow`), 수동 중지와 상담 전환 중지, 수신 거부(`recipient_opted_out`), 7일 댓글 창(`comment_expired`)은 지연이 끝난 뒤 실제 발송 직전에 다시 검사합니다.

## 시각 대기

`wait_until` 노드는 작업 공간 시간대의 지정한 벽시계 시각까지 실행을 멈추며, 설정은 24시간제 `HH:MM`(`00:00`부터 `23:59`까지) 하나이고 포트는 `next` 하나입니다.
작업 공간 시간대는 [작업 공간 역할](2026-09-30-workspace-roles.md#작업-공간-설정)의 설정이며 기본값은 `Asia/Seoul`입니다.
실행이 노드에 도달하면 지연과 같이 앞의 동작과 단계를 저장하고 `waiting`으로 남으며, `resume_node_id`는 그 시각 대기 노드입니다.
재개 시각 `resume_at`은 PostgreSQL이 계산합니다. 도달한 시점의 DB 시각(`clock_timestamp()`)을 한 번 읽고, 그 순간 작업 공간 시간대의 날짜에서 지정 시각이 아직 지나지 않았으면 오늘, 지났거나 같으면 내일의 그 시각입니다.
따라서 재개 시각은 항상 도달 시점보다 늦고, 같은 분에 도달하면 다음 날 같은 시각입니다.
날짜는 세션 시간대가 아니라 작업 공간 시간대로 정하고, 일광 절약 시간 전환은 PostgreSQL의 시간대 규칙을 따릅니다.
시계를 앞당기는 날 건너뛴 시각(예: `America/New_York`의 2026-03-08 `02:30`)은 전환 전 오프셋으로 읽어 `03:30`에 재개하고, 시계를 되돌리는 날 두 번 오는 시각(2026-11-01 `01:30`)은 아직 지나지 않은 것 중 먼저 오는 것입니다.
첫 `01:30`(EDT) 전에 도달하면 그 시각에, 첫 `01:30`과 두 번째 `01:30`(EST) 사이에 도달하면 두 번째 시각에 재개합니다.
시간대는 실행이 노드에 도달하는 순간에 읽습니다. 작업 공간 시간대를 나중에 바꿔도 이미 `waiting`인 실행의 재개 시각은 바뀌지 않고, 지연에서 재개한 실행이 시각 대기에 도달하면 그 순간의 시간대를 씁니다.
재개, 취소, 잠금 순서와 발송 guard는 [지연과 재개](#지연과-재개)와 같습니다.

발행 검증의 비공개 답장 창 합계에서 시각 대기는 1,560분(26시간)으로 셉니다.
지연과 시각 대기를 합한 값이 10,020분을 넘는 메시지 경로는 `delay_exceeds_reply_window`로 거부되며, 시각 대기만으로는 6개까지 메시지 앞에 둘 수 있습니다.
실제 대기는 보통 하루 이내이지만, 시계를 되돌리는 날에는 하루에 되돌린 폭을 더한 시간에 가까워질 수 있습니다.
PostgreSQL 17.11의 `pg_timezone_names` 598개를 2026-2027년 매시간 조회하면 시계를 되돌리는 존은 189개가 1시간, 2개가 30분, `Antarctica/Troll` 하나만 2시간이므로, 한 시각 대기는 1,560분(26시간) 미만입니다.
시각 대기를 이 최댓값인 1,560분으로 세므로, 어느 존에서도 지연 상한에 남겨 둔 1시간(웹훅, cron, 재시도 지연용)이 시각 대기 때문에 줄지 않습니다.
이 계산은 운영자 결정(2026-10-01)이며, 처음 구현에서는 1,440분으로 셌습니다.
그래도 댓글 작성 후 7일이 지난 답장은 발송 전 검증(`evaluatePrivateReply`)이 `comment_expired`로 막으므로 늦게 가지 않습니다.
시각 대기는 순환을 허용하는 대기로 세지 않습니다.

## 응답 대기

`wait_for_reply` 노드는 바로 앞 메시지 노드가 보낸 비공개 답장에 대한 사용자의 DM 응답을 기다립니다.
설정은 `timeout_minutes`(1분부터 10,080분, 즉 7일까지의 정수)와 선택 `save_field_id`(작업 공간의 보관되지 않은 text 필드)입니다.
출력 포트는 응답이 왔을 때의 `replied`와 대기가 만료됐을 때의 `timeout`입니다.
발행 검증은 응답 대기로 들어오는 연결이 메시지 노드의 `next` 포트에서만 오는지(`wait_requires_message`), 응답 대기에서 도달할 수 있는 메시지가 없는지(`message_after_wait`), 저장 필드가 text인지(`invalid_field_type`)를 확인합니다.
따라서 응답 대기 뒤에는 동작, 조건, 지연, 시각 대기만 올 수 있고, 이번 구현은 응답 뒤에 아무것도 보내지 않습니다.
켜기 검사는 메시지 노드에서 응답 대기로 가는 연결만 허용하고, 그 밖의 연결은 계속 `unsupported_after_message`로 거부합니다.
`save_field_id`는 버전의 참조 필드에 포함되므로, 발행 버전이 쓰는 저장 필드는 보관할 수 없습니다(`field_in_use`).

메시지 뒤에 응답 대기가 있으면, 실행은 답장을 outbox에 넣은 뒤 `awaiting_reply`가 되고 `resume_node_id`에 응답 대기 노드를 남깁니다.
`resume_at`은 비워 둡니다. 대기는 답장이 실제로 발송된 시각(`private_reply_outbox.sent_at`)부터 고정된 버전의 `timeout_minutes`만큼이기 때문입니다.
DB 제약은 `waiting`일 때만 `resume_at`이, `waiting`과 `awaiting_reply`일 때만 `resume_node_id`가 있도록 강제합니다.
같은 보낸 사람과 게시물에 이미 답장이 있어 실행이 `skipped / duplicate_recipient`가 되면 대기 지점도 지웁니다.

응답은 Node 수신기와 Cloudflare가 함께 쓰는 메시지 수집(`ingestMessages`)이 처리합니다.
버튼 postback이 아닌 텍스트 DM마다, 같은 계정의 연결에서 `awaiting_reply`인 실행 중 다음을 모두 만족하는 실행을 찾고, 여럿이면 가장 최근에 발송된 답장의 실행 하나만 진행합니다.

- 실행의 플로 답장이 `sent`이고, 그 `recipient_id`가 DM 보낸 사람과 같습니다.
- 답장 `sent_at`이 메시지 시각 이전이거나 같고, 메시지 시각이 `sent_at`에 대기 시간을 더한 시각보다 이릅니다.

메시지 수집은 기존과 같이 수신 시각보다 60초 넘게 미래이거나 24시간 넘게 지난 메시지를 처리하지 않습니다.
답장의 발송 결과(`sent`와 `recipient_id`)가 기록되기 전에 도착한 응답은 연결할 실행을 찾지 못하므로 대기와 연결하지 않습니다. 기존 팔로우 확인 흐름과 같은 경계이며, 나중에 맞춰 보는 방법은 [#108](https://github.com/AndrewDongminYoo/auto-chatter/issues/108)에서 다룹니다.
찾은 실행은 연결 행을 `FOR SHARE`로 잠근 뒤 실행 행을 `FOR UPDATE`로 잠그고, 위 조건과 `awaiting_reply` 상태를 다시 확인합니다.
연결을 먼저 잠그는 순서는 지연 재개와 세 삭제 함수와 같습니다.
실행 행은 `SKIP LOCKED` 없이 기다리므로, 만료 처리나 다른 메시지가 먼저 잡았으면 그 커밋 뒤에 상태가 바뀐 것을 봅니다.
그러면 그 실행을 빼고 조건을 다시 조회해 다음으로 최근인 실행을 잡으므로, 같은 사람을 기다리는 실행 둘에 서로 다른 DM 두 개가 동시에 와도 차례로 왔을 때와 같이 두 실행이 모두 진행합니다.
응답으로 진행하거나 취소한 실행은 그 메시지의 제공자 ID를 `flow_runs.reply_message_id`에 남깁니다.
같은 연결에서 이 ID로 끝난 실행이 이미 있으면 메시지를 건너뛰므로, 다시 전달된 메시지는 같은 실행도, 같은 사람을 기다리는 다음으로 최근인 실행도 진행하지 않습니다.
같은 메시지가 동시에 두 번 전달되면 둘 다 같은 실행을 고르고, 나중 것은 실행 행 잠금을 기다린 뒤 다시 조회할 때 먼저 커밋된 메시지 ID를 보고 멈춥니다.
메시지 ID로 중복을 막는 기존 수신 기록(`instagram_message_receipts`)은 팔로우 확인이 쓰므로, 응답 대기가 함께 쓰면 같은 DM의 팔로우 확인이 막힙니다.
그래서 응답 대기는 실행 행에 따로 기록합니다.
연결이 비활성이면 `cancelled / connection_unavailable`, 플로가 꺼졌거나 보관됐으면 `cancelled / inactive_flow`로 끝나며, 지연 재개와 같이 응답 대기 뒤의 노드를 실행하지 않습니다.
그 밖의 경우에는 지연 재개와 같은 필드 잠금과 연락처 잠금을 잡고 태그와 필드 값을 다시 읽은 뒤, 고정된 버전 문서로 `replied` 포트부터 실행을 이어 갑니다.
첫 단계로 응답 대기 노드와 `replied`를 기록합니다.

`save_field_id`가 있으면 응답 본문을 댓글 작성자(실행을 시작한 댓글의 보낸 사람) 연락처의 그 필드 값으로 저장하고, 같은 노드에 저장 결과를 한 번 더 기록합니다.
저장하지 못해도 실행은 실패하지 않고 `replied` 포트로 계속합니다.

| 저장 결과           | 뜻                                                                                     |
| ------------------- | -------------------------------------------------------------------------------------- |
| `set`               | 응답 본문을 저장했습니다.                                                              |
| `unchanged`         | 같은 값이 이미 저장돼 있습니다.                                                        |
| `field_unavailable` | 필드가 보관됐습니다.                                                                   |
| `reply_invalid`     | 응답이 text 필드 값 상한(1,000자, 줄바꿈·탭 외 제어 문자와 서식 문자 불가)을 넘습니다. |

저장된 값은 뒤따르는 `field_equals` 분기가 읽습니다.
저장은 연결의 받은 메시지함 설정(`inbox_enabled`)과 무관하게, 플로 작성자가 `save_field_id`를 지정했을 때만 일어납니다.
연락처의 수동 중지나 상담 전환 중지는 응답에 따른 진행을 막지 않습니다. 이번 구현은 응답 뒤에 아무것도 보내지 않고, 동작은 원래 중지된 연락처에도 적용되기 때문입니다.
응답 뒤 지연을 만나면 지연 재개와 같이 다시 `waiting`이 되고, 그 밖에는 연결이 없는 포트에서 `ended`로 끝납니다.

만료는 지연 재개와 같은 cron(`resumeDueFlowRuns`)이 처리하며, due 지연과 만료된 응답 대기를 due 시각 순으로 함께 최대 50개까지 처리합니다.
답장이 `sent`이고 `sent_at`에 대기 시간을 더한 시각이 지난 실행만 만료되며, 연결 `FOR SHARE`, 실행 `FOR UPDATE SKIP LOCKED` 순서로 잠근 뒤 `timeout` 포트로 이어 가고 첫 단계로 응답 대기 노드와 `timeout`을 기록합니다.
플로 꺼짐과 연결 비활성은 응답과 같이 실행을 취소합니다.
답장이 `sent`가 되지 않은 실행(대기, 차단, 실패, `unknown`)은 만료되지 않고 `awaiting_reply`로 남습니다. 답장이 발송되지 않았으니 기다릴 응답도 없기 때문입니다.
발송은 됐지만 Meta가 DM 수신자 ID를 돌려주지 않아 `recipient_id`가 비어 있는 답장은 응답과 짝지을 수 없으므로, 그 실행은 만료로만 끝납니다.
응답 조회와 만료 검사는 `awaiting_reply` 실행만 담은 부분 인덱스(`flow_runs_awaiting_reply_idx`)를 씁니다.
재전달 확인은 `reply_message_id`가 있는 실행만 담은 부분 인덱스(`flow_runs_reply_message_idx`)를 씁니다.

## 발송

플로 답장은 `private_reply_outbox`에 `rule_id` 대신 `flow_run_id`를 가진 행으로 들어가며, 두 값 중 정확히 하나만 설정할 수 있습니다.
따라서 claim, 재시도, 속도 제한, stale 복구, 동의·연락처 중지·상담 전환 검사와 `unknown` 비재시도 규칙은 기존 비공개 답장과 같습니다.
발송 직전 검사는 규칙 대신 플로가 켜져 있는지 확인하고, 꺼졌으면 `blocked / inactive_flow`로 기록합니다.
다시 발행해도 이미 큐에 들어간 답장은 고정된 버전의 문구로 발송됩니다.
플로 답장에는 팔로우 설정(`follow_config`)이 없습니다.

## 이력 API

`GET /api/flows/:id/runs`는 최근 실행 50건을 최신순으로 반환합니다.
각 항목은 실행 ID, 버전 번호, 실행 상태와 실패 코드, 대기 중인 실행의 재개 시각 `resume_at`(UTC), 단계 목록, 그리고 답장이 있으면 outbox의 `delivery_status`·`delivery_failure_code`·`sent_at`을 가집니다.
`awaiting_reply` 실행은 `resume_at`이 없으며, 대기는 함께 반환하는 `sent_at`부터 버전의 `timeout_minutes`만큼입니다.
보낸 사람 ID와 댓글 본문은 이력에 포함하지 않습니다.
다른 작업 공간의 플로는 404로 보입니다.

## 저장과 삭제

서버 역할은 `flow_step_runs`를 추가만 할 수 있고, `flow_runs`는 중복 답장을 기록하기 위해 UPDATE할 수 있으며, 두 테이블 모두 DELETE할 수 없습니다.
`delete_connection_data`, `delete_person_data`, `delete_workspace_data`는 해당 범위의 실행과 단계 기록을 지우고 삭제 건수에 포함합니다.
`awaiting_reply` 실행도 같으며, 이용자 단위 삭제는 댓글 작성자로 요청해도, 답장 연결을 따라 DM 수신자로 요청해도 그 실행을 지웁니다.
이용자 단위 삭제는 잠금 뒤에 새 답장이나 실행이 생긴 댓글 이벤트를 남깁니다.
작업 공간 내보내기는 두 테이블을 포함합니다.

## 운영 적용

migration 021은 관리자 migration 러너와 접근 권한 스크립트에 포함됩니다.
migration 021은 020의 작업 공간 삭제 함수를 포함해 세 삭제 함수의 본문을 다시 정의합니다.
2026-09-30 운영 DB에 migration 021을 적용하고 이 계약을 포함한 Worker를 배포했습니다. 적용 결과와 권한 조회는 [운영 적용 기록](../notes/2026-09-26-cloudflare-runbook.md)에 있습니다.
실계정에서의 동작은 아직 검증하지 않았습니다.
태그·필드 동작과 메시지 변수(#31)는 migration 없이 2026-09-30 PR #100 병합 커밋으로 운영에 배포했으며, 배포 기록은 같은 [운영 적용 기록](../notes/2026-09-26-cloudflare-runbook.md)에 있습니다.
배포 뒤 운영 DB와 플로 상태는 조회하지 않았고, 실계정에서의 동작도 검증하지 않았습니다.
지연과 재개(#32)의 migration 025는 관리자 migration 러너에 포함되며, 2026-10-01 운영 DB에 적용하고 이 계약을 포함한 Worker를 배포했습니다. 적용 결과는 같은 [운영 적용 기록](../notes/2026-09-26-cloudflare-runbook.md)에 있고, 운영에 플로가 없으므로 지연과 재개는 운영 데이터로 실행하지 않았습니다.
