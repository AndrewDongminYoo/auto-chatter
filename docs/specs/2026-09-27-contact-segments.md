# 저장된 연락처 세그먼트

## 목적

반복해서 사용하는 연락처 계정·태그 검색 조건을 이름으로 저장합니다.
[ManyChat 연락처 문서](https://help.manychat.com/hc/en-us/articles/14281110746012-Contacts-tab-Overview)의 저장된 검색 조건을 기준으로 2026-09-27 확인했습니다.
연락처 목록은 조건을 실행할 때 계산하며 참여자 스냅샷이나 발송 동의로 취급하지 않습니다.

## 계약

- 세그먼트는 작업 공간에 속하며 이름, 선택적인 Instagram 연결과 태그를 저장합니다.
- 이름은 NFC·앞뒤 공백 제거 후 1–60자이며 제어 문자는 거부합니다.
- 태그는 기존 연락처와 같은 정규화를 사용하며 빈 입력은 조건 없음입니다.
- 세그먼트 생성 시 다른 작업 공간의 계정을 참조하거나 다른 작업 공간의 세그먼트를 조회·보관하면 404입니다.
- 기존 수동 connection_id 필터의 다른 작업 공간·존재하지 않는 계정에 대한 빈 목록 응답은 유지합니다.
- 계정이 없는 조건은 작업 공간의 모든 계정에 적용하며 동일 sender를 다른 계정과 합치지 않습니다.
- 작업 공간당 활성 세그먼트는 최대 50개이며 같은 이름은 하나만 허용합니다.
- 생성·[수정](#이름과-조건-수정)·보관 처리는 서버 인증·동일 출처 검사 후 수행합니다.
- 보관은 archived 설정을 바꾸고 연락처·태그·댓글을 제거하지 않습니다.
- 저장된 조건으로 연락처를 조회하면 최신 태그 상태와 기존 50건 페이지 이동을 사용합니다.
- 태그 조건은 태그 하나 또는 [다중 태그](#다중-태그-조건) 2~5개의 집합입니다.
- 필드 조건은 조건 하나 또는 [다중 필드](#다중-필드-조건) 2~3개의 집합입니다.
- 태그와 단일 사용자 정의 필드는 `condition_operator=and|or`로 결합합니다. 생략한 기존 필터는 AND이며 응답에도 기존 형태를 유지합니다. OR는 태그와 필드 조건이 모두 있을 때만 허용하고 저장·복원·보관 뒤 수동 조회에도 보존합니다.
- 선택적인 [마지막 댓글 저장 기간](2026-10-16-segment-comment-activity.md)을 고정 UTC `[from,before)`로 저장·복원합니다.
  기간은 태그/필드 AND/OR와 별도로 적용하고 기존 세그먼트 응답은 기간 키를 생략합니다.
- [최근 댓글 활동](2026-10-16-segment-relative-activity.md)은 `last_comment_days` 정수 1~366만 저장하고 매 조회의 직전 N×24시간을 계산합니다.
  고정 기간과 동시에 사용할 수 없고 미리보기·페이지의 실제 UTC 경계를 반환합니다.
- [달력 기간](2026-10-16-segment-relative-activity.md#달력-기간)은 `last_comment_period`(`today`·`yesterday`·`this_month`·`last_month`)만 저장하고 매 조회에서 작업 공간 시간대의 경계를 계산합니다.
  고정 기간·최근 일수와 동시에 사용할 수 없고 실제 UTC 경계와 시간대를 반환합니다.
  다음 페이지도 다시 계산하므로 전체 대상의 시점 고정은 아닙니다.
- 선택적인 [목적별 동의 기록](2026-10-16-segment-consent-state.md)은 `consent_purpose`·`consent_state` 쌍으로 저장·복원하며 정확한 댓글 식별자의 현재 상태만 비교합니다.
- 선택적인 [DM 동의 기록](2026-10-16-segment-consent-state.md#dm-동의-기록)은 `dm_consent_purpose`·`dm_consent_state` 쌍으로 저장·복원하며 연락처 상세와 같은 확인된 DM 대화의 현재 상태를 비교합니다.
  확인된 DM 대화가 없는 연락처는 어떤 상태에도 맞지 않으며 식별자를 합치거나 발송 가능 여부를 판정하지 않습니다.
- 선택적인 [DM 활동](2026-10-16-segment-consent-state.md#dm-활동)은 정수 `last_dm_days`(1–366)로 저장·복원하며, 확인된 DM 상대의 마지막 받은 DM(텍스트·버튼 응답)이 조회 시점 직전 N×24시간 안에 있는지 비교합니다.
  댓글 활동 형태와 독립이고, DM 동의와 함께 쓰면 각각 확인된 상대 중 하나라도 맞으면 되며, 24시간 답장 가능 시간이나 발송 가능 여부를 뜻하지 않습니다.
- workspace·계정·활동 기간·동의 기록·DM 동의 기록·DM 활동·페이지 커서는 항상 별도의 AND 제한입니다. OR에 맞는 태그가 있어도 외부·보관된 필드나 잘못된 타입·값을 허용하지 않습니다. 필드의 eq·입력됨·미입력·숫자/날짜 비교 계약은 그대로 적용합니다.
- 화면은 태그와 필드가 모두 있을 때 조건 결합을 선택하게 합니다. 하나가 제거되면 AND로 돌아가며 저장 실패 때 결합과 초안을 유지합니다.
- 세그먼트와 수동 조건을 한 요청에서 혼합하면 400입니다.
- UI는 조건 저장·선택·보관을 제공하며 태그 초안 확인, 실패 뒤 입력 보존과 로그아웃 뒤 늦은 응답 차단을 유지합니다.
- 저장 영역의 [초안 대상 미리보기](2026-10-16-segment-draft-preview.md)는 현재 폼 조건의 전체 대상 수와 선택 계정 범위의 평가 수·태그/추가 정보별 제외 사유를 조회 시점의 값으로 표시하며 최대 50명을 읽고 5명까지 예시를 표시합니다.
  기간을 지정하면 기간 밖 연락처를 먼저 제외하고, 동의 기록 조건을 지정하면 그 다음에 기록이 맞지 않는 연락처를 제외합니다.
  DM 동의 기록이나 DM 활동 조건을 지정하면 그 다음에 확인된 DM 대화가 없는 연락처, 이어서 DM 동의 기록이 맞지 않는 연락처, 최근 받은 DM이 없는 연락처를 제외합니다.
  이를 통과한 연락처를 태그만·필드만·둘 다 불일치로 나누며 OR는 둘 다 불일치만 추가로 제외합니다.
  마지막으로 적용한 목록과 연락처 편집값은 유지하며 발송 가능 여부·고정 대상을 뜻하지 않습니다.

## 이름과 조건 수정

2026-10-17에 [#26](https://github.com/AndrewDongminYoo/auto-chatter/issues/26)의 일부로 활성 세그먼트의 이름과 조건 수정을 추가했습니다.
수정해도 세그먼트 ID는 유지됩니다.

- `PUT /api/contact-segments/<id>`는 활성 `admin` 이상만 호출할 수 있으며, `agent`와 제거된 멤버는 403입니다.
- 본문은 생성과 같은 키에 필수 `expected_version`(1 이상의 안전한 정수)을 더한 전체 정의이며 부분 변경이 아닙니다.
  생략한 선택 조건 키는 생성과 같이 그 조건이 없다는 뜻이므로 기존 조건을 지웁니다.
- 생성과 수정은 `parseSegmentDefinition` 하나로 본문을 검사하므로 같은 정의를 받아들이고 같은 코드로 거부합니다.
  모양·이름 오류는 `400 invalid_segment`이고, 조건 값 오류는 생성과 같은 `invalid_field_condition`·`invalid_contact_activity`·`invalid_contact_consent`·`invalid_contact_condition`·`invalid_contact_tags`입니다.
  `expected_version`은 수정에서만 허용하며, 생성 본문에 넣으면 `400 invalid_segment`입니다.
- 트랜잭션은 다음 순서로 잠급니다.
  1. `lockWorkspaceForMember`가 생성과 같이 작업 공간 행을 `FOR UPDATE`로 잠그고 호출자의 활성 멤버십과 역할을 다시 확인합니다.
  2. 세그먼트 행을 `FOR UPDATE`로 잠급니다.
     없거나 다른 작업 공간의 세그먼트, 보관된 세그먼트는 모두 `404 segment_not_found`입니다.
     보관된 세그먼트는 수정할 수 없으며, 같은 코드를 사용하므로 보관된 ID와 없는 ID를 응답으로 구별할 수 없습니다.
  3. 저장된 `version`이 `expected_version`과 다르면 아무것도 쓰지 않고 `409 segment_conflict`와 현재 세그먼트(`segment`, 목록 항목과 같은 형태)를 반환합니다.
  4. 참조하는 필드를 `FOR SHARE`로 잠그고 생성과 같이 계정 소유를 확인합니다.
     `archiveContactField`는 필드를 `FOR UPDATE`로 잠근 뒤 활성 세그먼트의 참조를 확인합니다.
     따라서 수정이 먼저 필드를 잡으면 보관은 수정이 커밋할 때까지 기다린 뒤 `409 field_in_use`가 되고, 보관이 먼저 커밋하면 수정은 `404 field_not_found`가 됩니다.
  5. 이름과 모든 조건 열이 저장된 값과 같으면 쓰지 않고 현재 버전 그대로 현재 세그먼트를 반환합니다.
     비교는 정규화한 값에 대해 SQL `IS DISTINCT FROM`으로 하므로, 앞뒤 공백이나 대소문자만 다른 태그도 변경 없음입니다.
  6. 다르면 모든 정의 열을 바꾸고 `version`을 1 올립니다.
     다른 활성 세그먼트와 정규화한 이름이 같으면 `409 segment_name_exists`이며, 보관된 세그먼트의 이름은 사용할 수 있습니다.
- 성공 응답은 200이며 목록 항목과 같은 형태에 `version`을 포함합니다.
  `GET /api/contact-segments` 항목과 생성 응답에도 `version`이 추가되며 다른 필드는 바뀌지 않습니다.
- 활성 세그먼트 50개 제한은 생성만 세며, 수정은 활성 수를 바꾸지 않습니다.
- 세그먼트는 고정 대상이 아닙니다.
  `segment_id`로 조회하는 연락처 목록과 미리보기는 요청마다 저장된 현재 정의를 읽으므로, 수정 뒤 다음 요청부터 새 조건으로 계산합니다.
  `segment_id`와 수동 조건을 섞을 수 없다는 규칙은 그대로입니다.
- 수정 이력과 감사 테이블은 없습니다.
  생성과 보관에도 이력이 없으므로 수정도 같은 수준으로 둡니다.
- 마이그레이션 054는 `version integer NOT NULL DEFAULT 1`과 `CHECK(version >= 1)`을 추가하며, 기존 행은 1에서 시작합니다.
  기존 DB는 코드 배포 전에 054를 전체 실행기(`deploy/migrate-multi-user.sql`)로 적용해야 합니다.
- `deploy/supabase-access.sql`과 `deploy/init-app-user.sh`는 이 테이블에 열 단위가 아닌 표 단위 SELECT·INSERT·UPDATE를 부여하므로 새 열에 권한을 추가하지 않습니다.
  작업 공간 내보내기는 이 테이블의 모든 열을 내보내므로 `version`도 자동으로 포함되며, 내보내는 열 목록을 고정한 테스트는 없습니다.
- 화면은 소유자와 관리자에게 선택한 저장 필터의 "필터 수정"을 표시합니다.
  수정을 시작하면 기존 조건 폼과 필터 이름 입력에 저장된 값을 채우고, 저장 버튼을 "변경 저장"으로 바꾸며 "수정 취소"를 제공합니다.
  새 필터 이름을 입력해 둔 상태라면 그 이름을 버릴지 먼저 확인하고, 취소하면 수정을 시작하지 않습니다.
  수정 중에는 다른 저장 필터를 고를 수 없습니다.
- 화면은 200을 받으면 수정 모드를 끝내고 목록을 다시 불러온 뒤 수정한 필터를 선택한 채 저장된 조건을 폼에 채웁니다.
  저장 요청(생성과 수정 모두)이 진행되는 동안에는 조건 폼을 비활성화하므로, 응답을 받을 때 화면의 조건은 보낸 조건과 같습니다.
- 화면은 `409 segment_conflict`를 받으면 입력값을 유지하고 지금 저장된 값을 텍스트로 표시합니다.
  보관하던 버전은 운영자가 "저장된 값 불러오기"를 누를 때만 바뀌므로 다른 변경을 조용히 덮어쓰지 않습니다.
- 화면은 `404 segment_not_found`를 받으면 수정 모드를 끝내고 목록을 다시 불러오며, 입력한 이름과 조건은 새 필터로 저장할 수 있게 남깁니다.
  작업 공간 다시 불러오기, 세션 초기화, 필터 보관도 수정 모드를 끝냅니다.
  수정 모드가 끝날 때 화면은 기본으로 입력한 이름과 조건을 남기고, 바꾼 값이 있으면 저장하지 않은 변경으로 표시합니다.
  이름을 비우고 저장하지 않은 표시를 지우는 경우는 운영자가 고른 수정 취소, 확인을 받은 필터 보관, 방금 저장한 변경 저장 성공, 세션 초기화뿐입니다.
- 기존 생성·보관 버튼은 화면에서 역할별로 숨기지 않으며, `agent`의 요청은 서버가 `403 role_forbidden`으로 거부합니다.

## 다중 태그 조건

2026-10-17에 [#26](https://github.com/AndrewDongminYoo/auto-chatter/issues/26)의 일부로 한 조건에 여러 태그를 지정하게 했습니다.
태그 부정, 중첩 조건, 다중 필드 조건, DM 조건은 추가하지 않았습니다(DM 동의 기록은 이후 [별도 조건](2026-10-16-segment-consent-state.md#dm-동의-기록)으로 추가했습니다).

- 태그 집합은 1~5개이며 각 태그는 연락처 태그와 같은 규칙(NFC·앞뒤 공백 제거·소문자, 1~40자, 제어 문자 거부)으로 정규화합니다.
  정규화한 값이 같은 태그는 하나로 합치고, 순서는 의미가 없으므로 정렬해 저장하고 반환합니다.
- `tag_mode`는 `all`(모든 태그를 가진 연락처)이나 `any`(하나 이상 가진 연락처)이며 기본값은 `all`입니다.
  합친 뒤 태그가 하나만 남으면 모드와 관계없이 기존 단일 태그 조건과 같습니다.
- 태그 행이 없는 연락처는 태그가 없는 연락처로 판정합니다.
- 태그 조건 전체가 기존 태그/필드 AND/OR의 한쪽입니다.
  `condition_operator=or`는 여전히 태그 조건과 필드 조건이 모두 있어야 합니다.
- 목록, 미리보기의 `tag_matches`, `segment_id` 조회는 같은 SQL 조건 하나를 씁니다.
  집합 `S`에 대해 `all`은 `tags @> S`, `any`는 `tags && S`입니다.
  미리보기의 제외 순서와 키(활동, 동의, `excluded.tag`·`field`·`both`)는 바뀌지 않습니다.
- 오류 코드는 기존 태그 검사와 같습니다.
  5개를 넘는 태그, 잘못된 태그, 모르는 모드는 `400 invalid_contact_tags`입니다.
  태그 없이 `tag_mode`만 보내면 `400 invalid_contact_condition`입니다.

### 연락처 조회

- `GET /api/contacts`의 `tag`는 1~5번 반복할 수 있습니다(`tag=a&tag=b`).
  다른 키는 그대로 한 번만 허용하며, `tag_mode`도 한 번만 허용하는 새 키입니다.
  `tag`를 6번 이상 보내면 정규화 전에 `400 invalid_contact_tags`입니다.
- `segment_id`는 `tag`나 `tag_mode`와 함께 쓸 수 없습니다(`400 invalid_contact_request`).
- `tag` 하나와 `tag_mode` 없는 요청의 동작과 응답은 이전과 같습니다.

### 세그먼트 저장 형태

- 생성(`POST /api/contact-segments`)과 수정(`PUT /api/contact-segments/<id>`)은 기존 `tag`(문자열) 또는 `tags`(문자열 1~5개 배열)와 선택적인 `tag_mode`를 받습니다.
  `tag`와 `tags`를 함께 보내면 `400 invalid_segment`입니다.
  값이 `null`이거나 빈 문자열인 `tag`는 태그 없음으로 보며 `tags`와 함께 보낼 수 있습니다.
  빈 배열이나 배열이 아닌 `tags`는 `400 invalid_contact_tags`입니다.
- 데이터 이전 없이 기존 형태를 유지합니다.
  태그 하나로 합쳐지는 집합은 기존 `tag` 열에 저장하고 `tags`·`tag_mode`는 `NULL`입니다.
  두 개 이상은 새 `tags` 열과 `tag_mode`에 저장하고 `tag`는 `NULL`입니다.
- 응답도 같은 규칙을 따릅니다.
  태그 하나인 세그먼트와 기존 세그먼트는 `tag` 키를 그대로 반환하고, 다중 태그 세그먼트는 정렬한 `tags`와 `tag_mode`를 반환하며 `tag` 키가 없습니다.
- 수정의 변경 없음 판정(`IS DISTINCT FROM`)에 새 열을 포함합니다.
  순서나 대소문자만 다른 같은 집합과 같은 모드를 다시 보내면 버전이 유지되고, 모드만 바꿔도 변경입니다.
- 마이그레이션 056은 `tags text[]`와 `tag_mode text`를 추가하고 `contact_segment_multi_tag` 제약을 둡니다.
  제약은 두 열이 모두 `NULL`이거나, `tags`가 1차원 배열로 2~5개이고 `NULL` 원소가 없으며 각 원소가 1~40자이고 `tag_mode`가 `all`·`any`이며 `tag`가 `NULL`인 경우만 허용합니다.
  같은 마이그레이션은 `contact_segment_condition_operator`를 다시 만들어 OR가 `tag` 또는 `tags`와 필드 조건을 요구하게 합니다.
  기존 DB는 코드 배포 전에 056을 전체 실행기(`deploy/migrate-multi-user.sql`)로 적용해야 합니다.
- 서버 역할 권한은 표 단위이므로 새 열에 권한을 추가하지 않습니다.
  작업 공간 내보내기는 이 테이블의 모든 열을 내보내고, 삭제 함수는 행 단위로 지우므로 바꾸지 않습니다.

### 화면

- 연락처 필터는 태그 입력칸을 최대 5개 제공합니다.
  앞 칸에 값이 있으면 다음 칸이 나타나며, 쉼표를 나누지 않으므로 쉼표가 들어간 태그도 하나로 다룹니다.
- "여러 태그 결합"(모두 포함·하나 이상 포함)은 서로 다른 태그가 두 개 이상일 때만 선택할 수 있고, 그보다 적으면 모두 포함으로 돌아갑니다.
- 목록 요청은 `tag`를 반복하고 태그가 두 개 이상일 때만 `tag_mode`를 보냅니다.
  저장 요청은 태그가 하나면 `tag`, 두 개 이상이면 `tags`와 `tag_mode`를 보냅니다.
- 저장, 선택, 수정 모드(초안 보호와 요청 중 조건 폼 잠금 포함), 충돌 뒤 저장된 값 표시, 보관 뒤 직접 조건 전환이 태그 집합과 모드를 유지합니다.

## 다중 필드 조건

2026-10-18에 [#26](https://github.com/AndrewDongminYoo/auto-chatter/issues/26)의 일부로 한 조건에 여러 필드 조건을 지정하게 했습니다.
중첩 조건, `is_unset` 밖의 필드 부정, DM 조건, 캠페인은 추가하지 않았습니다(DM 동의 기록은 이후 [별도 조건](2026-10-16-segment-consent-state.md#dm-동의-기록)으로 추가했습니다).

- 필드 조건 집합은 1~3개이며 각 조건은 기존 단일 조건과 같은 규칙(연산자 목록, 필드 타입별 값 규칙, 값 없는 `is_set`·`is_unset`)으로 검사합니다.
  한 집합에 같은 `field_id`가 두 번 나오면 `400 invalid_field_condition`입니다.
  필드 ID는 소문자로 바꾸고 `field_id` 순으로 정렬해 저장하고 반환합니다.
- `field_mode`는 `all`(모든 조건을 만족)이나 `any`(하나 이상 만족)이며 기본값은 `all`입니다.
  조건이 하나인 집합은 모드와 관계없이 기존 단일 필드 조건과 같습니다.
- 필드 조건 없이 `field_mode`만 보내거나 모르는 모드를 보내면 `400 invalid_field_condition`입니다.
- 필드 조건 집합 전체가 기존 태그/필드 AND/OR의 한쪽입니다.
  `condition_operator=or`는 여전히 태그 조건과 필드 조건이 모두 있어야 합니다.
- 목록, 미리보기의 `field_matches`, `segment_id` 조회는 같은 SQL 조건 하나를 씁니다.
  정규화한 집합을 jsonb 매개변수 하나로 넘기고 `jsonb_to_recordset`의 조건마다 기존 비교 규칙(`jsonb_typeof` 타입 확인, `eq`·`gt`·`gte`·`lt`·`lte`, `is_set`, `is_unset`)으로 판정한 뒤 `all`은 `bool_and`, `any`는 `bool_or`로 묶습니다.
  기존 단일 조건도 조건 하나인 집합으로 같은 조건을 지나며, 기존 단일 필드 시험은 수정 없이 통과합니다.
  미리보기의 제외 순서와 키(활동, 동의, `excluded.tag`·`field`·`both`)는 바뀌지 않습니다.

### 다중 필드 연락처 조회

- `GET /api/contacts`의 기존 `field_id`·`field_operator`·`field_value`는 조건 하나에 그대로 쓰며, 이 키만 쓴 요청의 동작과 응답은 이전과 같습니다.
- 새 키 `field_conditions`는 `{field_id, field_operator, field_value?}` 객체 1~3개의 JSON 배열 하나를 한 번만 받고, `field_mode`도 한 번만 받습니다.
  `field_value`는 JSON 값 그대로이며, 기존 `field_value` 키처럼 다시 문자열로 감싸지 않습니다.
- `field_conditions`와 기존 필드 키를 함께 보내거나, 잘못된 JSON, 배열이 아닌 값, 빈 배열, 3개를 넘는 조건, 허용하지 않은 키가 든 조건은 `400 invalid_field_condition`입니다.
  값의 길이는 디코딩한 뒤 8,192자까지입니다.
  1,000자 텍스트 값 세 개를 JSON이 따옴표·역슬래시 이스케이프로 두 배 가까이 늘려도 약 6,300자이므로, 이 디코딩 상한은 화면이 만드는 값을 막지 않으면서 무한한 문자열을 거부합니다.
  인코딩한 URL 길이는 확인하지 않았습니다. 긴 한국어 값 세 개는 이 상한보다 먼저 Cloudflare가 받는 URL 길이에 걸릴 수 있으며, 그 근거는 [검증 노트](../notes/2026-10-18-segment-multi-field-verification.md)에 있습니다.
- JSON 이스케이프로 만든 짝 없는 서로게이트(`"\ud800"` 등)가 든 문자열 값은 PostgreSQL jsonb가 받지 않으므로, 기존 `field_value` 키와 저장 요청을 포함해 `400 invalid_field_condition`입니다.
- `segment_id`는 기존 필드 키뿐 아니라 `field_conditions`·`field_mode`와도 함께 쓸 수 없습니다(`400 invalid_contact_request`).
- 각 필드는 `field_id` 순으로 작업 공간의 활성 필드인지 확인합니다.
  다른 작업 공간의 필드나 보관된 필드는 `404 field_not_found`, 필드 타입에 맞지 않는 연산자는 `400 invalid_field_condition`, 맞지 않는 값은 `400 invalid_field_value`입니다.

### 다중 필드 저장 형태

- 생성과 수정은 기존 필드 키 또는 `field_conditions`(조건 1~3개 배열)와 선택적인 `field_mode`를 받습니다.
  둘을 함께 보내면 GET과 같은 `400 invalid_field_condition`입니다.
  값이 `null`인 `field_conditions`와 `field_id`는 조건 없음으로 봅니다.
- 데이터 이전 없이 기존 형태를 유지합니다.
  조건 하나인 집합은 기존 `field_id`·`field_operator`·`field_value` 열에 저장하고 새 열은 `NULL`입니다.
  두세 개는 새 `field_conditions` jsonb 열과 `field_mode`에 저장하고 기존 필드 열은 `NULL`입니다.
  저장하는 조건 객체는 `field_id`, `field_operator`와 값이 필요한 연산자의 `field_value`만 가집니다.
- 응답도 같은 규칙을 따릅니다.
  조건 하나인 세그먼트와 기존 세그먼트는 기존 필드 키를 그대로 반환하고, 다중 필드 세그먼트는 정렬한 `field_conditions`와 `field_mode`를 반환하며 기존 필드 키가 없습니다.
- 수정의 변경 없음 판정(`IS DISTINCT FROM`)에 새 열을 포함합니다.
  순서나 ID 대소문자만 다른 같은 집합과 같은 모드를 다시 보내면 버전이 유지되고, 모드만 바꿔도 변경입니다.
- 생성과 수정은 참조하는 모든 필드를 `field_id` 순으로 `validateFieldCondition(..., lock = true)`로 확인해 `FOR SHARE`로 잡습니다.
  필드 보관(`archiveContactField`)은 필드를 `FOR UPDATE`로 잡은 뒤 활성 세그먼트를 확인하므로, 보관이 먼저 끝나면 세그먼트 쓰기가 `404 field_not_found`이고 세그먼트 쓰기가 먼저 필드를 잡으면 보관이 기다린 뒤 `409 field_in_use`입니다.
- 필드 보관은 `field_conditions` 안에서만 참조하는 필드도 `409 field_in_use`로 거부합니다.
  확인은 jsonb 포함 검사(`field_conditions @> jsonb_build_array(jsonb_build_object('field_id', <id>))`)이며, 저장한 ID가 소문자이므로 `uuid`를 문자열로 바꾼 값과 같습니다.
  작업 공간당 활성 세그먼트가 50개 이하이고 검사가 작업 공간으로 제한되므로 인덱스는 추가하지 않습니다.
- 마이그레이션 057은 `field_conditions jsonb`와 `field_mode text`를 추가하고 `contact_segment_multi_field` 제약을 둡니다.
  제약은 두 열이 모두 `NULL`이거나, `field_conditions`가 원소 2~3개의 배열이고 `field_mode`가 `all`·`any`이며 기존 필드 열이 모두 `NULL`인 경우만 허용합니다.
  각 원소는 `field_id`(소문자 UUID 문자열), 허용한 `field_operator`, 연산자가 값을 요구할 때만 있는 `field_value`만 가진 객체여야 하고, `field_id`는 순서대로 커져야 하므로 중복될 수 없습니다.
  제약은 필드의 존재·소유·활성 상태, 필드 타입에 맞는 값과 숫자·날짜 필드에만 허용하는 순서 비교를 확인하지 않으며, 이는 애플리케이션 파서와 `validateFieldCondition`이 맡습니다.
  같은 마이그레이션은 `contact_segment_condition_operator`를 다시 만들어 OR가 태그 조건(`tag` 또는 `tags`)과 필드 조건(`field_id` 또는 `field_conditions`)을 요구하게 합니다.
  056은 이 규칙이 이미 `field_conditions`를 읽으면 다시 실행돼도 자기 규칙으로 되돌리지 않으므로, 태그와 필드 집합의 OR 세그먼트가 저장된 DB에서도 전체 실행기를 다시 돌릴 수 있습니다.
  `contact_segment_field_condition`은 기존 필드 열이 모두 `NULL`인 행을 이미 허용하므로 바꾸지 않습니다.
  기존 DB는 코드 배포 전에 057을 전체 실행기(`deploy/migrate-multi-user.sql`)로 적용해야 합니다.
- 서버 역할 권한은 표 단위이므로 새 열에 권한을 추가하지 않습니다.
  작업 공간 내보내기는 이 테이블의 모든 열을 내보내고, 삭제 함수는 행 단위로 지우며, 흐름과 웹후크는 세그먼트 필드 열을 읽지 않으므로 바꾸지 않습니다.

### 다중 필드 화면

- 연락처 필터의 추가 정보 조건은 최대 3행(필드, 조건, 찾을 값)입니다.
  "추가 정보 조건 추가"는 마지막 행에 필드를 고른 뒤 다음 행을 열고, 2·3행의 삭제 버튼은 그 행을 지우고 뒤 행을 한 칸 올립니다.
  행마다 필드 타입에 맞는 조건 선택지와 값 입력을 기존과 같이 보여 줍니다.
- "여러 정보 결합"(모두 만족·하나 이상 만족)은 필드를 고른 행이 두 개 이상일 때만 선택할 수 있고, 그보다 적으면 모두 만족으로 돌아갑니다.
- 같은 필드를 두 행에서 고르면 요청 전에 안내하고 보내지 않습니다.
- 목록과 저장 요청은 조건이 하나면 기존 필드 키, 두세 개면 `field_conditions`와 `field_mode`를 보냅니다.
- 저장, 선택, 수정 모드(초안 보호와 요청 중 조건 폼 잠금 포함), 충돌 뒤 저장된 값 표시, 보관 뒤 직접 조건 전환이 필드 조건 집합과 모드를 유지하며 다중 태그와 함께 동작합니다.
- 필드를 보관하면 그 필드를 고른 모든 행의 선택을 해제합니다.

## 비목표와 한계

중첩 조건 조합 언어, 발송 대상 지정은 후속 범위입니다.
저장된 세그먼트의 연락처 CSV는 [세그먼트 내보내기](2026-10-04-contact-csv-export.md#저장된-세그먼트-내보내기)가 연락처 목록과 같은 조건으로 만듭니다.
태그와 필드의 AND/OR와 이름·조건 수정은 #26의 일부이며 전체 이슈를 완료하지 않습니다. AND/OR는 마이그레이션 037, 고정 활동 기간은 046, 목적별 동의 기록은 047, 최근 일수는 053, 수정 버전은 054, 다중 태그는 056, 다중 필드는 057, DM 동의 기록은 058, DM 활동은 059를 전체 실행기로 적용한 뒤 사용하는 계약입니다.
수정은 이력을 남기지 않으므로, 이전 조건을 남겨야 하면 새 세그먼트로 저장합니다.
운영 마이그레이션·배포·실발송은 이 PR에서 수행하지 않습니다.
