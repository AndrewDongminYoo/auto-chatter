# 세그먼트 통합 수용 검증

## 목적

[#26](https://github.com/AndrewDongminYoo/auto-chatter/issues/26)의 필터 저장·미리보기·대상 고정·변경 비교를 실제 대시보드와 Worker API, PostgreSQL을 연결해 확인합니다.
기존 [변경 비교 검증](../notes/2026-10-19-segment-snapshot-comparison-verification.md)은 DB·workerd와 합성 응답을 사용하는 화면 조각을 각각 검사했으며, 전체 대시보드와 API를 연결한 사용자 흐름은 확인하지 않았습니다.
이번 작업은 그 경계를 보완하고 남은 수용 조건을 명시합니다.

## 범위

- 기존 Miniflare와 PostgreSQL을 사용하는 로컬 검증 서버를 추가합니다.
- 실제 정적 대시보드, 인증 라우트, Worker API와 제한된 서버 DB 역할을 사용합니다.
- 외부 Supabase 인증 응답만 합성 계정으로 대체하며, 그 밖의 외부 HTTP 요청은 거절합니다.
- 로그인부터 필터 저장·미리보기·명단 고정·조건 변경·비교·CSV 다운로드까지 실제 브라우저로 확인합니다.
- 관리자와 상담원, 다른 작업 공간의 접근, 보관·삭제 이후 동작, 오류와 늦은 응답의 화면 처리를 확인합니다.
- 재현한 결함만 좁게 수정하고 회귀 근거를 남깁니다.

## 실행 경계

검증 서버는 loopback에만 바인딩하고, 로컬 `automations_test` 데이터베이스의 빈 `public` 스키마만 허용합니다.
기존 테이블을 지우거나 운영 자격 증명을 읽지 않습니다.
합성 연락처와 계정을 직접 준비하며 실제 고객 데이터는 사용하지 않습니다.
`SEND_ENABLED=false`와 공개 계정 연결 비활성화를 유지합니다.
새 의존성, 운영 마이그레이션, 배포, Meta 호출과 실제 발송은 포함하지 않습니다.

합성 인증은 실제 Supabase 이메일·비밀번호 검증이나 운영 세션 설정을 증명하지 않습니다.
로컬 화면 확인은 운영자의 화면 승인을 대신하지 않습니다.
#25의 동의 있는 식별자 병합·분리와 #27의 외부 검증은 이번 작업으로 완료하지 않으며, #26 전체를 자동 종료하지 않습니다.
#35의 메시지·비용·승인·예약은 구현하지 않습니다.

## 수용 조건

1. 원격 주소, 다른 데이터베이스 이름, 이미 사용 중인 스키마를 거절하는 실패를 실제로 확인합니다.
2. 전체 로그인 화면에서 합성 계정으로 로그인하고, 실제 API가 반환한 작업 공간과 연락처를 표시합니다.
3. 고정 당시 명단과 조건 변경 후 현재 명단의 추가·제외·유지 수를 DB와 대조합니다.
4. 실제 다운로드한 CSV의 내용과 저장 명단을 대조합니다.
5. 다른 작업 공간과 상담원은 관리자 전용 명단·비교에 접근하지 못합니다.
6. 보관한 필터의 비교는 거절하고 기존 명단은 계속 조회할 수 있습니다.
7. 삭제 후 원래 인원과 남은 기준 인원을 구분합니다.
8. 오류·필터 수정·선택 전환 이후 이전 결과나 늦은 응답이 잘못 표시되지 않습니다.
9. 좁은 화면과 키보드 조작을 확인하고, 캡처와 검증 한계를 운영자가 확인할 수 있는 경로에 보존합니다.

## 판단 근거

Oracle 선례 `wiki/concepts/plan-audit-verify-against-code.md`에 따라 이슈의 체크 상태보다 현재 코드와 실제 검사 대상을 기준으로 판단합니다.
세그먼트 전용 선례는 `[no precedent found]`이며 위키 최신성은 확인하지 못했습니다.
이번 작업의 방향은 운영자가 추천 작업을 `pr-loop`로 구현하도록 요청한 범위입니다.
