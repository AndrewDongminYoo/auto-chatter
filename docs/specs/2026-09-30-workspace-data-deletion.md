# 작업 공간·로그인 계정 전체 삭제

## 범위

[이슈 #83](https://github.com/AndrewDongminYoo/auto-chatter/issues/83)의 두 번째 PR입니다.
작업 공간과 로그인 계정 전체의 삭제 요청은 이메일로 받고, 운영자가 본인 확인을 마친 뒤 관리자 연결에서 처리합니다.
앱 API와 화면은 두지 않으며, 서버 역할의 권한도 넓히지 않습니다.
데이터 내보내기는 [작업 공간 데이터 내보내기](2026-09-30-workspace-export.md)가 다룹니다.

## 운영자 절차

1. 요청 이메일의 로그인 이메일 주소로 Supabase 사용자와 작업 공간을 찾고, 요청자가 그 계정의 소유자인지 확인합니다.
2. 작업 공간의 모든 연결을 해제된 상태(비활성, 발송 꺼짐, 저장된 토큰 없음)로 만듭니다. 연결 해제 API나 관리자 SQL을 사용합니다.
3. 관리자 연결에서 트랜잭션을 열고 `SELECT public.delete_workspace_data('<workspace>', '<운영자 사용자 ID>');`를 실행한 뒤, 반환된 건수와 `member_user_ids`를 확인하고 커밋합니다.
4. `member_user_ids`의 Supabase Auth 사용자를 Supabase 대시보드의 Authentication 화면이나 관리자 API로 삭제합니다. 이 단계는 서버 코드가 아니라 운영자가 수행합니다.
5. 관리자 연결에서 `SELECT workspace_id FROM workspace_members WHERE user_id = ANY('<member_user_ids>')`가 아무 행도 반환하지 않는지 확인합니다.
   요청자가 대시보드를 연 상태에서 3번과 4번 사이에 새로고침하면 `POST /api/workspace`가 새 작업 공간을 만들 수 있기 때문입니다. 행이 있으면 그 작업 공간에도 3번을 실행합니다.
   4번 뒤에는 모든 API 요청이 Supabase `/user`로 세션을 다시 확인하므로(`src/app/api.ts`의 `auth.user`) 삭제된 사용자는 더 이상 작업 공간을 만들 수 없습니다.
6. 처리 결과를 요청자에게 이메일로 안내합니다.

## 삭제하는 기록

함수는 한 트랜잭션에서 작업 공간의 모든 제품 행을 삭제합니다.
여기에는 연결 단위·이용자 단위 삭제에서는 보관하는 수신 거부 이벤트와 상태, 기존 삭제 증적(`data_deletion_records`)도 포함됩니다.
수신 거부 기록은 작업 공간 범위에서만 발송을 막으므로, 작업 공간이 사라지면 보관해도 막을 발송이 없습니다.
같은 사람이 다시 가입하면 새 작업 공간이 만들어지고 이전 기록은 적용되지 않습니다.
연결 행이 삭제되므로 같은 Instagram 계정을 다른 작업 공간에서 다시 연결할 수 있습니다.
마지막으로 OAuth state, 멤버십과 작업 공간 행을 삭제합니다.

## 삭제 증적

`workspace_deletion_records`에 작업 공간 ID, 처리한 운영자 ID, 완료 시각과 테이블별 삭제 건수만 남깁니다.
작업 공간과 연결이 사라지므로 외래 키가 없고, 삭제된 멤버의 사용자 ID와 댓글·메시지 내용은 저장하지 않습니다.
멤버 ID는 Auth 사용자 삭제를 위해 함수 결과로만 반환합니다.
이 테이블은 작업 공간 내보내기에서 제외합니다.

## 거부 조건

| 코드    | 조건                                                                     |
| ------- | ------------------------------------------------------------------------ |
| `AC001` | 작업 공간이 없음                                                         |
| `AC002` | 연결 중 하나라도 활성, 발송 켜짐, 저장된 토큰이 있음                     |
| `AC003` | 비공개 답장, 팔로우 후속 메시지, 수동 답장 중 `sending` 상태인 행이 있음 |
| `AC006` | 운영자 ID가 없음                                                         |

거부되면 아무 행도 삭제하지 않습니다.

## 동시 쓰기와 권한

함수는 작업 공간 행과 모든 연결 행을 `FOR UPDATE`로 잠급니다.
발송 상태를 확인하기 전에 비공개 답장, 팔로우 후속 메시지, 수동 답장 행도 `FOR UPDATE`로 잠급니다. 아직 커밋되지 않은 발송 선점이 있으면 그 결과를 기다린 뒤 `sending`이면 `AC003`으로 거부하며, DB 테스트가 이 경합을 재현합니다.
따라서 연결을 참조하는 새 행의 삽입과 연결 행을 `FOR SHARE`로 잠그는 쓰기는 삭제가 끝날 때까지 기다리며, 삭제 뒤에는 참조할 행이 없어 실패합니다.
`delete_workspace_data`는 SECURITY INVOKER 함수이고, PUBLIC과 서버·API 역할의 EXECUTE를 모두 회수합니다.
`workspace_deletion_records`는 RLS를 켜고 서버·API 역할의 모든 권한을 회수합니다.
새 작업 공간 범위 테이블은 이 함수에도 추가해야 합니다. 연결이나 작업 공간을 참조하는 테이블을 누락하면 외래 키 때문에 삭제가 실패하고, DB 테스트는 내보내기 대상의 모든 테이블에서 행이 남지 않았는지 확인합니다.

## 공개 문구

`/privacy`와 `/data-deletion`에 전체 삭제 시 수신 거부 기록과 삭제 처리 기록까지 삭제한다는 문장을, `/privacy` 열람 요청 문단에 설정 화면의 데이터 내보내기 경로를 추가합니다.

## 검증

1. DB 테스트는 모든 제품 테이블에서 작업 공간의 행이 사라지고 다른 작업 공간은 그대로인지, 거부 조건에서 아무것도 삭제되지 않는지, 증적에 멤버 ID가 없는지 확인합니다.
2. Cloudflare 권한 테스트는 서버·Compose·API 역할이 함수를 실행하거나 증적을 읽지 못하는지 확인합니다.
3. 운영 DB 적용과 실제 삭제 실행은 별도로 승인을 받습니다.
