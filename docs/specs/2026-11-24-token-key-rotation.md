# 토큰 암호화 키 교체

## 범위

[이슈 #61](https://github.com/AndrewDongminYoo/auto-chatter/issues/61)의 완료 조건 3 가운데 "키 교체"를 다루고, [이슈 #16](https://github.com/AndrewDongminYoo/auto-chatter/issues/16)의 완료 조건 3에 남은 "키 교체 중 이전 토큰을 쓰지 않는지 보는 테스트"를 더합니다.
#61의 백업 범위, RPO/RTO, 키 보관 담당자, 분리된 환경의 복구 훈련은 이 문서의 범위가 아닙니다.
migration은 없습니다. 운영 키 교체는 이 PR의 범위가 아니며, 절차는 [Cloudflare 런북](../notes/2026-09-26-cloudflare-runbook.md#토큰-암호화-키-교체)에 있습니다.

이전에는 `TOKEN_ENCRYPTION_KEY` 하나로 모든 비밀값을 봉인하고 열었습니다.
키를 바꾸면 저장된 Instagram 토큰과 웹훅 서명 키를 모두 열 수 없었으므로, 계정마다 다시 연결하고 서명 키를 교체해야 했습니다.

## 봉인 대상

`TOKEN_ENCRYPTION_KEY`로 봉인하는 열은 두 개입니다.

| 열                                             | 맥락(AAD)                                     |
| ---------------------------------------------- | --------------------------------------------- |
| `instagram_connections.access_token_encrypted` | `<workspace_id>:<account_id>`                 |
| `webhook_signing_keys.secret_encrypted`        | `signingKeyContext(workspace, endpoint, key)` |

맥락은 바뀌지 않으므로, 다른 작업 공간이나 계정의 행으로 옮긴 암호문은 여전히 열리지 않습니다.

## 봉투 형식

`src/app/secrets.ts`의 `sealSecret`은 이제 `v2.<kid>.<iv>.<tag>.<ciphertext>`를 씁니다.
`kid`는 키로 고정 문자열의 HMAC-SHA256을 계산한 값의 앞 8바이트(base64url)이며, 키 값에 대해 아무것도 알려 주지 않습니다.
`kid`가 있으므로 SQL만으로 현재 키로 봉인되지 않은 행을 찾고 셀 수 있습니다.

`openSecret`은 두 형식을 모두 엽니다.

- v2는 `kid`가 가리키는 키링의 키로만 엽니다. 키링에 그 키가 없으면 `Unknown token encryption key`로 실패합니다.
- v1(#61 이전, `kid` 없음)은 키링의 키를 현재 키부터 차례로 시도합니다. GCM 인증 태그가 봉인하지 않은 키를 거부하므로 잘못된 키로 열리는 경우는 없습니다.

## 키링

| 이름                            | 용도                                       |
| ------------------------------- | ------------------------------------------ |
| `TOKEN_ENCRYPTION_KEY`          | 현재 키, 새로 봉인하는 모든 값에 씁니다.   |
| `TOKEN_ENCRYPTION_KEY_PREVIOUS` | 교체 중에만 두는 이전 키, 열기에만 씁니다. |

`tokenKeys(env)`가 두 값으로 키링을 만들고, 비어 있는 이전 키는 없는 것으로 봅니다.
키링을 쓰는 모든 경로는 이전 키도 현재 키와 같이 검증합니다. 이전 키가 32바이트 canonical base64가 아니면 토큰 갱신, 구독 확인, OAuth 시작, 발송이 현재 키가 잘못되었을 때와 같이 실패합니다.
잘못된 이전 키를 조용히 무시하면 교체가 끝나지 않은 채 이전 토큰을 열 수 없게 되므로, 일부러 실패하게 했습니다.

## 다시 봉인하는 cron 단계

`token_key_rewrap`은 `TOKEN_ENCRYPTION_KEY_PREVIOUS`가 있고 현재 키와 다를 때만 실행합니다.
이전 키가 없거나 현재 키와 같으면 단계 자체가 돌지 않으므로 쿼리도, `scheduled_steps` 행도, 암호문 변경도 생기지 않습니다.
런북은 현재 키를 먼저 이전 키로 등록하므로, 이 조건이 없으면 새 키를 넣기 전에 v1 행이 모두 이전 키의 `v2.<kid>`로 바뀌어 완료 판정을 속입니다.
수신과 토큰 갱신처럼 발송 스위치(`SEND_ENABLED`)와 관계없이 실행합니다. 구독 확인 뒤, 초기 응답 연결 전에 둡니다.

`rewrapSealedSecrets`(`src/app/token-key-rewrap.ts`)는 두 열에서 현재 키의 접두어(`v2.<kid>.`)가 없는 행을 ID 순서로 100행씩, 표마다 최대 5쪽까지 읽습니다.
연결은 비활성 연결과 재연결 대기 중인 연결도 포함하고, 서명 키는 폐기되지 않은 키만 포함합니다.
각 행을 키링으로 열고 현재 키로 다시 봉인한 뒤, 쪽마다 UPDATE 한 번으로 씁니다.

- 쓰기는 ID와 읽은 암호문이 그대로일 때만 적용되고, 그 열 하나만 바꿉니다. `token_obtained_at`, 재연결 표시, 갱신 시도 시각, 구독 확인 열은 그대로입니다.
- 어떤 키로도 열리지 않는 행은 실패로 세고 그대로 둡니다. 읽기는 ID 순서로 그 행을 지나가므로, 같은 실행 안에서 뒤의 행을 막지 않습니다. 매 실행은 가장 작은 ID부터 다시 읽으므로, 한 표에 열리지 않는 행이 500개를 넘으면 그 뒤의 행에는 닿지 않습니다. 현재 운영 규모에서는 생기지 않는 경우라 따로 다루지 않습니다.
- 실패가 하나라도 있으면 단계가 `token_key_rewrap_failed`로 실패하고, 그 행이 바뀌거나 폐기될 때까지 매 실행 실패합니다. 그동안 cron 실행 전체가 실패로 기록되므로 `cron_stale` 경보가 켜져 있습니다.
- 이전 키가 잘못된 값이면 단계는 `not_configured`로 실패하고 아무 행도 바꾸지 않습니다.

## 동시성

다시 봉인한 행은 평문 토큰이 같아도 암호문이 바뀝니다.
이 서비스는 암호문 자체를 토큰 버전으로 비교하므로, 다시 봉인은 토큰 교체와 같은 경로를 탑니다.

- 진행 중인 발송: 비공개 답장(`tokenRotated`), 수동 답장, 캠페인, DM 플로 발송은 발송 직전 재확인에서 암호문이 바뀐 것을 보고 POST 전에 `token_rotated`로 다시 시도합니다. 연결이 비활성, 발송 중지, 만료 상태이면 키 교체와 관계없이 막히던 대로 막힙니다(수동 답장은 `delivery_changed`). 다시 시도한 발송은 새 키로 연 같은 토큰을 보냅니다.
- 토큰 갱신: 다시 봉인 전에 토큰을 읽은 갱신은 조건부 쓰기에서 지고, 갱신 결과는 저장하지 않습니다. 이때 그 시도의 시각을 조건부로 지우므로 연결이 하루를 기다리지 않고 바로 다시 갱신 대상이 되며, 다음 시도는 다시 봉인한 토큰을 새 키로 열어 갱신합니다. 더 새로운 갱신이 남긴 시도 시각은 지우지 않습니다.
- 다시 봉인보다 늦게 커밋된 토큰 갱신, 재연결, 서명 키 폐기는 다시 봉인의 조건부 쓰기를 이깁니다. 다시 봉인은 이전 토큰을 새 토큰 위에 쓰지 않습니다.
- 재연결 표시와 구독 확인 기록은 읽은 암호문이 바뀌면 쓰지 않습니다. 표시가 한 번 늦어질 수 있지만 다음 확인에서 다시 기록합니다. 같은 cron 실행 안에서는 구독 확인이 다시 봉인보다 먼저 끝나므로 겹치지 않고, 겹치는 cron 실행이나 수동 상태 확인과 만나면 그 확인 한 번이 실패로 셀 수 있습니다.
- OAuth 콜백은 봉인한 암호문을 조건으로 연결을 활성화합니다. 새 키를 등록하기 직전에 이전 키로 봉인한 콜백이 다시 봉인과 겹치면 `409 instagram_connection_changed`로 끝나고 사용자가 다시 연결해야 합니다. 데이터는 손상되지 않습니다. 그런 콜백은 완료 확인 뒤에도 이전 키의 행을 쓸 수 있습니다. 클라이언트의 `query_timeout`은 서버에서 실행 중인 문장을 취소하지 않으므로 그 시각에는 확인된 상한이 없습니다. 그래서 런북은 새 키를 등록하고 10분이 지난 뒤의 성공한 실행만 완료 근거로 받고, 이전 키를 지운 뒤에도 다시 조회해서 늦은 행이 보이면 백업한 이전 키를 다시 등록합니다.

## 되돌리기 한계

#61 이전 Worker 버전은 v2 봉투를 읽지 못합니다.
이 코드가 배포된 뒤 새로 연결하거나 갱신한 토큰과 새로 만든 서명 키는 키 교체가 없어도 v2로 저장되므로, 그 이전 버전으로 되돌리면 해당 계정의 발송과 웹훅 서명이 실패합니다.
저장된 값은 바뀌지 않으므로 #61 이후 버전으로 다시 배포하면 복구됩니다.
키 교체가 없을 때 v1으로 계속 쓰는 방법도 검토했지만, 같은 키의 봉투 형식이 설정에 따라 달라지는 복잡성에 비해 이득이 작아 택하지 않았습니다.

## 검증

- `src/app/secrets.test.ts`: v1과 v2 열기, 이전 키로 열기, 현재 키로만 봉인, 잘못된 이전 키 거부.
- `src/app/token-key-rewrap.db.test.ts`: 이전 키가 없으면 쿼리 없음, 두 열의 다시 봉인과 다른 열 유지, 열리지 않는 행, 읽은 뒤 커밋된 쓰기의 우선, 토큰 갱신과의 경합.
- `src/cloudflare/worker.db.test.ts`: 발송 중 키 교체가 `token_rotated` 재시도 뒤 같은 토큰으로 발송됨(#16 완료 조건 3), cron 단계가 이전 키가 있을 때만 실행되고 잘못된 이전 키에서 `not_configured`로 실패함.

격리된 로컬 DB와 모의 Graph 응답에서 확인한 결과이며, 운영 키 교체는 아직 실행하지 않았습니다.
