# 활성 연락처 한도 집행 설계

이슈: [#52](https://github.com/AndrewDongminYoo/auto-chatter/issues/52) (요금제 권한의 남은 일 중 활성 연락처 한도).
선행 작업: [#51 활성 연락처 원장](2026-11-24-active-contact-ledger-design.md), [요금제 권한](2026-10-12-plan-entitlements.md).

## 의도

#51은 청구월마다 메시지를 주고받은 사람을 원장(`active_contacts`)에 기록하고 요금제 카드에 숫자만 보여 줍니다.
이 설계는 그 숫자를 요금제별 포함량과 비교해 집행합니다.
작업 공간이 이번 달 포함량을 넘으면, 요금제를 올리거나 다음 청구월이 될 때까지 기존 기록을 열람하고 설정을 수정하는 일만 할 수 있습니다.
받은 댓글과 DM은 계속 저장하고, 밖으로 나가는 메시지는 모두 멈춥니다.

## 목표

- 요금제마다 월 활성 연락처 포함량을 둡니다.
- 포함량을 넘은 작업 공간은 자동·수동·캠페인 발송을 모두 멈추고, 멈춘 이유를 화면과 발송 행에 남깁니다.
- 포함량을 넘기기 전에는 이번 달 원장에 없는 사람에게 보내서 포함량을 넘기게 되는 발송만 막습니다.
- 수신, 저장, 원장 기록, 열람, 설정 수정, 내보내기, 삭제는 초과 상태에서도 그대로 동작합니다.

## 비목표

- 결제, 초과 사용 승인과 상한, 사용량 경고 알림, 결제로 바뀌는 요금제: [#54](https://github.com/AndrewDongminYoo/auto-chatter/issues/54)가 맡습니다.
- AI 예산, API 요청 한도와 저장량 상한을 요금제별 값으로 바꾸는 일: #52의 다른 남은 일입니다.
- 멈춘 발송을 나중에 다시 보내는 일. 멈춘 행은 `blocked`로 끝나며 되살리지 않습니다.

## 실패로 보는 결과

- 초과 상태에서 받은 댓글이나 DM이 저장되지 않거나 원장에 기록되지 않습니다.
- 초과 상태가 풀린 뒤 그동안 멈춘 답장이 한꺼번에 나갑니다.
- 초과 상태에서 규칙, 플로우, 설정을 수정하거나 데이터를 내보내거나 지울 수 없습니다.
- 한도 검사가 실패해서(조회 오류 등) 수신 트랜잭션이 실패합니다.

## 정한 것 (2026-11-25)

- 포함량을 넘으면 "추가로 결제하지 않는 한 기존 기록 열람과 설정 수정만" 할 수 있습니다.
- 제안한 동작을 그대로 채택했습니다: 수신·열람·설정은 계속 허용하고, 모든 발송은 `blocked`로 끝냅니다. 멈춘 발송을 `pending`으로 남겨 나중에 보내는 방식과, 수동 답장만 허용하는 방식은 고르지 않았습니다.
- 포함량은 ManyChat의 2026년 플랜과 같게 둡니다([조사 노트](../notes/2026-09-25-manychat-research.md#manychat-기준선)).

| 요금제      | 월 활성 연락처 포함량 |
| ----------- | --------------------- |
| `free`      | 25                    |
| `essential` | 250                   |
| `pro`       | 2,500                 |
| `business`  | 7,500                 |
| `advanced`  | 25,000                |

이 값은 집행을 위한 현재 값이며 출시 가격이나 포함량에 대한 약속이 아닙니다([제품 spec](2026-09-25-messaging-automation-platform.md): "가격과 포함량은 출시 시 별도로 정합니다").
`PLANS`의 새 키 `active_contacts_per_month`에 둡니다.

## 동작

### 이번 달 숫자와 초과 상태

- 이번 달 숫자는 `activeContactUsage`가 이미 계산하는 `count`입니다: 작업 공간의 현재 `time_zone`으로 정한 이번 달 `billing_month` 행 수이며, 키가 지워진 행도 셉니다.
- 작업 공간은 `count > 포함량`일 때 "초과" 상태입니다. `count = 포함량`이면 아직 초과가 아니므로 포함된 인원과는 계속 주고받을 수 있습니다.
- 원장은 받은 댓글과 DM도 셉니다. 그래서 새 사람의 댓글 하나로 초과 상태가 될 수 있으며, 이것은 의도된 동작입니다.

### 발송별 판정

발송 하나를 판정하는 규칙은 하나이며, 모든 발송 경로가 같은 판정 함수(`activeContactLimitBlocks`)를 씁니다(아래 "검사 위치").

1. 작업 공간이 초과 상태이면 막습니다.
2. 초과 상태가 아니어도 받는 사람이 이번 달 원장에 없고 `count >= 포함량`이면 막습니다. 이 발송이 성공하면 원장 행이 생겨 포함량을 넘기 때문입니다.
3. 나머지는 보냅니다.

막힌 발송의 결과는 `failure_code = active_contact_limit`이고, 상태는 표마다 다음과 같습니다.

- `private_reply_outbox`, `instagram_follow_conversations`, `flow_dm_deliveries`, `campaign_deliveries`: `blocked`. 기존 의미대로 끝난 상태이며, 요금제를 올리거나 다음 달이 되어도 다시 보내지 않습니다.
- `instagram_manual_replies`: 이 표의 상태 CHECK에는 `blocked`가 없습니다(`db/schema.sql`). 그래서 기존 `failed`에 `safe_to_retry = true`를 씁니다. 공급자를 부르기 전에 막혔으므로 보내지 않았다는 것이 확실하기 때문입니다. 자동으로 다시 보내지 않으며, 사람이 기존 재시도 기능으로 새 행을 만들 때만 다시 나갑니다. 그 재시도도 아래의 생성 시 판정을 거칩니다. (`blocked` 상태를 더하면 migration과 수동 답장 화면·보고서·운영 집계 변경이 따라오므로 고르지 않았습니다.)

이 코드는 기존 `failure_code` 제약(`^[a-z_]{1,40}$`와 `^[a-z][a-z0-9_]{0,63}$`)을 만족합니다.

"받는 사람이 이번 달 원장에 있다"는 원장이 기록할 사람 키로 판정합니다: 댓글 답장은 댓글 작성자 ID, DM은 받는 사람 ID 또는 `active_contact_linked_sender`가 돌려주는 댓글 작성자 ID입니다.
판정은 원장의 키 규칙(`record_active_contacts`)과 같아야 합니다. 다르면 이미 센 사람을 새 사람으로 보고 막거나, 그 반대가 됩니다.

### 경로별 동작

| 경로                                                    | 초과 상태에서의 동작                                                                                                                                                                                                 |
| ------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 비공개 답장(`private_reply_outbox`, 플로우 답장 포함)   | 수집과 outbox 행 생성은 그대로 하고, 발송 worker가 claim한 뒤 `blocked`로 끝냅니다.                                                                                                                                  |
| 팔로우 확인과 후속 DM(`instagram_follow_conversations`) | 같습니다. 확인 버튼 수신과 기록은 그대로입니다.                                                                                                                                                                      |
| DM 플로우(`flow_dm_deliveries`)                         | 같습니다.                                                                                                                                                                                                            |
| 인박스 수동 답장(`instagram_manual_replies`)            | 생성·재시도·예약 변경 API가 위의 판정(1번과 2번 모두)을 받는 사람에게 적용해, 막히면 `409 active_contact_limit`으로 거절하고 아무것도 쓰지 않습니다. 이미 쌓인 행(예약 답장 포함)은 발송 시점에 `failed`로 끝냅니다. |
| 캠페인 승인                                             | 작업 공간이 지금 초과 상태이면 승인 생성을 `409 active_contact_limit`으로 거절합니다. 예정된 달과 무관하게 현재 상태로 판정하고, 예약 변경은 막지 않습니다.                                                          |
| 캠페인 시작(`campaign_start`)                           | 바꾸지 않습니다. 초과 상태에서 시작한 실행의 발송 행은 아래 발송 가드가 하나씩 막습니다.                                                                                                                             |
| 캠페인 발송(`campaign_deliveries`)                      | 최종 가드가 `blocked`로 끝냅니다. 캠페인 대상자는 이번 달 원장에 없는 사람이 많으므로 위의 2번 판정이 주로 여기에 걸립니다.                                                                                          |

오류 코드는 행에 남기는 `failure_code`와 API의 `409` 본문(`{"error":"active_contact_limit"}`)이 같은 `active_contact_limit`입니다. 수동 답장 API는 발송 가드의 실패 코드를 그대로 `409`의 오류 코드로 돌려주므로, 코드를 하나로 두면 두 곳이 어긋나지 않습니다.

캠페인 시작을 바꾸지 않은 이유(구현 중 결정, 2026-11-25): 시작 단계에서 막으려면 `start_counts`에 새 표시 키를 더해야 하고, 실행 조회의 `broadcast_limit_exceeded`, 승인 조회의 `run_limited`, 보고서의 사유 목록(`CAMPAIGN_REPORT_START_REASONS`)이 함께 바뀝니다. 발송 행 단위로 막아도 아무것도 나가지 않고, 막힌 이유는 실행의 `delivery_counts`와 행의 `failure_code`에 남습니다. 다만 막힌 행도 기존 규칙대로 월 캠페인 발송 수(`used`)에 셉니다. 초과 상태에서는 승인이 거절되므로, 이 경우는 초과 전에 승인한 캠페인이 초과 뒤에 시작할 때만 생깁니다.

화면은 초과 상태에서 수동 답장 보내기와 캠페인 승인 버튼을 비활성화하고 이유를 보여 줍니다.
버튼이 꺼지는 것은 편의이고, 서버의 `409`가 계약입니다.
초과 전에 새 사람에게 보내는 수동 답장이 2번 판정에 걸리는 경우는 버튼을 끄지 않고 `409` 문구로 알립니다.

아래는 설계 검토에서 정한 결정입니다(2026-11-25).

- 캠페인 승인은 현재 초과 상태로 판정합니다. 예정된 달의 원장은 거의 비어 있어 예정 달로 판정하면 검사가 의미를 잃기 때문입니다. 실제로 보낼지는 시작 시점의 달로 캠페인 시작과 발송 가드가 다시 판정하므로, 예약 변경은 막지 않습니다.
- 수동 답장은 생성 시점에 2번 판정까지 적용합니다. 받아 두고 발송 시점에 조용히 막으면, 사용자는 보냈다고 생각하기 때문입니다.
- 고객 웹훅 전달(`webhook_deliveries`)은 멈추지 않습니다. 연락처에게 가는 메시지가 아니라 운영자 자신의 엔드포인트로 가는 기록 전달이며, 원장도 세지 않습니다.

### 검사 위치

- 판정은 `src/app/plans.ts`의 `activeContactLimitBlocks` 하나이며, 조회 한 번으로 요금제, 이번 달 숫자, 받는 사람의 원장 존재 여부를 읽습니다. migration은 없습니다.
  모든 발송 경로의 claim 뒤 최종 가드가 부릅니다: Cloudflare의 비공개 답장(`graphFetch`)과 팔로우(`beforeSend`), Node의 두 가드(`node-delivery.ts`), 팔로우 worker의 허가 판정(`follow-flow.ts`), 수동 답장의 `manualReplyStatus`, DM 플로우와 캠페인 worker의 가드.
- Node worker(환경 변수 연결)도 같은 판정을 거칩니다.
- 비공개 답장의 공통 worker(`processNextPrivateReply`)는 시간당 예산에 세는 `provider_called_at`을 기록하기 전에도 판정합니다. 최종 가드에서만 막으면, 초과 상태의 작업 공간에 쌓인 답장이 실제 호출 없이 예산 700건을 소진합니다. 그러면 요금제를 올린 뒤에도 그 기록이 1시간 동안 남아 새 답장을 붙잡습니다.
- claim 쿼리, wake, 캠페인 정리 쿼리(`endUnreachableCampaignDeliveries`)에서 초과 작업 공간의 행을 빼지 않습니다. 빼면 행이 `pending`으로 계속 남아 초과가 풀릴 때 한꺼번에 나가기 때문입니다. 행은 claim된 뒤 막힙니다.
- 각 가드에서 판정은 수신 거부(opt-out) 검사 뒤에 둡니다. 수신 거부로 끝나야 할 행이 `active_contact_limit`으로 끝나면, 수동 답장에서는 `safe_to_retry = true`가 되어 재시도할 수 있게 되기 때문입니다. DM 플로우와 캠페인 가드는 막는 이유를 모은 목록의 마지막에 둡니다.
- 판정 조회가 오류를 내면 그 발송은 보내지 않고 기존의 재시도 경로(`pending`, 1분 뒤, `active_contact_limit_unavailable`)로 돌립니다. 한도를 확인하지 못한 채 보내지 않습니다.
- 작업 공간의 시간대를 `AT TIME ZONE`이 거절하면 원장이 그 작업 공간을 기록하지 않으므로 숫자를 잴 수 없습니다. 이때 판정은 발송을 허용합니다.
- 수집 경로(`ingestComments`, `ingestMessages`)는 한도를 읽지 않습니다. 수집은 초과 상태와 무관하게 동작해야 합니다.

### 동시성과 초과 폭

판정은 작업 공간 행을 잠그지 않고 원장을 읽습니다.
그래서 같은 순간에 진행 중인 발송들이 각각 "아직 포함량 안"으로 판정되면, 원장 숫자가 포함량을 몇 명 넘을 수 있습니다.
초과 폭은 그 작업 공간에서 판정과 `sent` 기록 사이에 동시에 진행 중인 새 사람 발송 수를 넘지 않습니다.
정확히 막으려면 새 사람에게 보낼 때마다 작업 공간 행을 잠가야 하므로 발송 핫 경로가 직렬화됩니다. 이 설계는 그 비용을 받아들이지 않고 초과 폭을 문서로 남깁니다.
받은 댓글과 DM은 원래부터 포함량과 무관하게 숫자를 늘립니다.
원장 쓰기는 오류나 2초 잠금 대기 초과를 삼키고 건너뛸 수 있습니다(#51). 그렇게 빠진 사람은 이번 달 숫자에 없으므로 다음 판정에서 새 사람으로 보이고, 숫자는 실제보다 작을 수 있습니다.

### 풀리는 조건

- 다음 청구월이 되면 이번 달 숫자가 새로 시작하므로 풀립니다.
- 관리자 SQL로 요금제를 올리면 다음 판정부터 풀립니다.
- 시간대를 바꾸면 "이번 달"이 바뀔 수 있습니다. 행은 저장된 달을 유지합니다(#51 규칙).
- 요금제를 내려서 숫자가 포함량을 넘으면 바로 초과 상태가 됩니다. 기존 행은 지우지 않습니다.

## 화면

- 요금제 카드의 이번 달 숫자를 `N / 포함량`으로 바꾸고, 초과 상태이면 초과 상태와 그 영향("발송이 멈췄습니다", 열람과 설정은 가능)을 한 문장으로 보여 줍니다.
  #51 PR ②에서 뺀 청구 안내 문장은 이번에도 넣지 않습니다.
- 수동 답장과 캠페인 승인 버튼은 초과 상태에서 비활성화하고 이유를 보여 줍니다.
- `409 active_contact_limit`의 한국어 문구를 `public/app/`의 오류 문구 목록에 더합니다.
- 화면 변경은 PR 전에 로컬 미리보기로 확인합니다.
