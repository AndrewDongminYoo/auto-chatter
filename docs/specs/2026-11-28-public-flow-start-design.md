# 외부 플로 시작 API 설계

## 목적

[이슈 #48](https://github.com/AndrewDongminYoo/auto-chatter/issues/48)의 마지막 완료 조건입니다.
CRM이나 자체 서버가 API 키로 기존 연락처 한 명에게 발행된 플로를 시작할 수 있게 합니다.
예를 들어 결제가 끝난 고객에게 안내 DM 플로를 보내는 경우입니다.
앞 단계의 [API 키](2026-11-27-workspace-api-keys-design.md), [연락처 읽기 API](2026-11-27-public-contacts-api-design.md), [연락처 쓰기 API](2026-11-27-public-contact-writes-design.md)는 운영에 배포되어 있습니다.

이 단계는 이 서비스에서 처음으로 외부 요청이 메시지 발송을 일으키는 경로입니다.
그래서 앞 단계와 달리 멱등성, 동의, 24시간 응답 창, 활성 연락처 한도, 발송 스위치를 모두 검사합니다.

## Andrew가 정한 것

- 2026-11-28에 질문 없이 기본값으로 설계하라고 정했습니다. 기본값은 다음 두 가지입니다.
- 시작할 수 있는 플로는 DM으로 시작하는 플로(트리거 `DM_TRIGGER_TYPES`)뿐입니다.
- 수신자의 24시간 응답 창이 닫혀 있으면 시작하지 않고 거절합니다.

## 목표

- `POST /v1/flows/{flow_id}/starts`가 연락처 한 명에게 플로 실행 하나를 만들고, 첫 DM을 기존 DM 플로 발송 경로로 보냅니다.
- `GET /v1/flows`가 이 키로 시작할 수 있는 플로의 ID, 이름, 연결 ID를 돌려줍니다.
- 같은 요청을 재시도해도 실행과 메시지는 하나만 생깁니다.
- 동의, 수신 거부, 24시간 창, 일시 중지, 상담 전환, 활성 연락처 한도, 발송 스위치는 요청을 받을 때 한 번 검사해 빠르게 거절하고, 발송 직전에 다시 검사합니다. 발송 직전의 검사가 최종 판단입니다.
- 새 권한 `flows:start`가 없는 키는 플로를 시작할 수 없고, 다른 작업 공간의 플로와 연락처는 어떤 입력으로도 다룰 수 없습니다.
- OpenAPI 계약 문서와 권한 침해 테스트를 이 경로까지 넓힙니다.

## 비목표

- 댓글로 시작하는 플로의 시작. 그 플로의 답장은 특정 댓글 ID에 묶인 비공개 답장이라 외부 요청으로 만들 수 없습니다.
- 24시간 창 밖의 발송(message tag 등). 이 저장소에 선례가 없습니다.
- 플로별로 외부 시작을 허용하는 설정. 이 단계에서는 키의 `flows:start` 권한이 관리자의 허용입니다.
- 실행 상태를 읽는 API, 결과를 웹훅으로 알리는 일, 여러 연락처를 한 요청으로 시작하는 일괄 시작.
- 플로 본문에 외부 값을 넘기는 변수.
- 연락처 생성. 댓글을 남긴 적이 있는 기존 연락처만 대상입니다.

## 피해야 할 결과

- 같은 요청의 재시도가 같은 사람에게 메시지를 두 번 보내는 것.
- 저장된 연락처, 태그, 필드가 동의나 발송 자격으로 해석되는 것. 기존 규칙대로 이 기록들은 메시지 동의나 발송 자격을 증명하지 않습니다.
- 수신 거부, 일시 중지, 상담 전환 상태인 사람에게 외부 요청이 메시지를 보내는 것.
- 외부 시스템이 짧은 시간에 많은 시작을 보내 연결의 발송 한도나 DM 시작 한도를 우회하는 것.
- 발송이 꺼진 동안 쌓인 시작이 한참 뒤에, 외부 시스템이 이미 포기한 시점에 발송되는 것.
- 읽기 키나 연락처 쓰기 키가 메시지를 보낼 수 있는 것.

## 설계 결정 (작성자의 판단)

### 요청과 응답

- 본문은 `{ "request_key": "<UUID>", "connection_id": "<UUID>", "sender_id": "<댓글 작성자 ID>" }`입니다. 연락처는 `/v1/contacts`와 같은 `(connection_id, sender_id)` 키로 지정합니다.
- 플로는 작업 공간 안에서 켜져 있고(`enabled`), 보관되지 않았고, 발행된 버전이 있고, 그 버전의 트리거가 `DM_TRIGGER_TYPES` 중 하나이며, 트리거 연결이 `connection_id`와 같아야 합니다. 작업 공간 밖이거나 없는 플로는 `404 flow_not_found`, 조건을 채우지 못한 플로는 `409 flow_unavailable`입니다.
- 실행은 발행된 버전에 고정되며, DM 트리거 실행과 같은 `dmPlan`으로 계획합니다. 그래서 첫 메시지 하나만 보내고, 태그·필드 변경이나 대기가 있는 버전은 지금처럼 `unsupported_node`로 실패합니다.
- 성공 응답은 `202`이며 본문은 `{ "start_id", "run_id", "status": "queued" }`입니다. `202`는 발송을 약속하지 않습니다. 발송 직전의 검사가 실행을 막을 수 있습니다.
- 본문 크기는 4 KiB까지이며, 앞 단계처럼 한 객체 안의 중복 키는 `400 invalid_request`입니다.
- `GET /v1/flows`는 위의 조건을 채우는 플로만, 최대 100개를 생성 순서로 돌려줍니다. 플로 정의와 메시지 문구는 돌려주지 않습니다.

### 수신자

- 댓글 연락처의 `sender_id`는 메시징 ID가 아닙니다. 캠페인과 같이 `verifiedDmRecipientsSql`(`src/app/inbox-identity.ts`)로 같은 연결의 검증된 DM 수신자를 찾습니다.
- 수신자가 여럿이면 캠페인과 같이, 아래 수신자별 검사(수신 거부, marketing 동의, 24시간 창)를 모두 통과한 수신자 중 가장 최근에 저장된 text·attachment·unsupported DM이 있는 수신자를 고릅니다(`src/app/campaign-drafts.ts`의 단계 7 선택).
- 통과한 수신자가 없으면, 가장 최근 DM이 있는 수신자가 처음 걸린 검사의 코드로 거절합니다.
- 검증된 수신자가 없으면 `409 no_dm_identity`입니다.
- 고른 수신자를 시작 행과 발송 행에 기록하고, 발송 직전에는 그 수신자를 기준으로 검사합니다.

### 멱등성

- 연락처 쓰기와 달리 플로 시작은 실행할 때마다 새 메시지를 만드는 연산이라서 요청 키가 필요합니다.
- 수동 답장과 캠페인 승인의 선례를 따라, 클라이언트가 UUID `request_key`를 보내고 서버는 요청 내용의 해시를 함께 저장합니다.
- 같은 키와 같은 내용이면 저장된 결과를 같은 `202` 본문으로 다시 돌려주고, 아무것도 새로 만들지 않습니다.
- 같은 키에 다른 내용(플로, 연결, 연락처가 다름)이면 `409 idempotency_conflict`입니다.
- 키는 작업 공간 안에서 유일하며 만료되지 않습니다. 오래된 키로 다시 요청해도 다시 보내지 않습니다. 결과가 불명확한 발송을 자동으로 다시 보내지 않는 기존 원칙과 같습니다.
- 사람이나 연결의 데이터를 지운 뒤에도 같은 키로 다시 보내지 않도록, 키는 개인 정보가 없는 별도 테이블에 남깁니다(아래 "데이터"). 지운 시작을 같은 키로 다시 요청하면 `409 idempotency_conflict`입니다.
- 거절된 요청(`4xx`)은 아무것도 저장하지 않습니다. 그래서 거절된 뒤 상황이 바뀌면 같은 키로 다시 시도할 수 있습니다.
- 같은 키의 동시 요청은 유일 제약이 하나만 통과시키고, 나머지는 저장된 결과를 돌려받습니다.

### 요청을 받을 때의 검사

아래 검사는 한 트랜잭션에서 플로와 연결을 `FOR SHARE`로 잠근 뒤 실행하며, 하나라도 걸리면 아무것도 쓰지 않고 거절합니다.
순서는 위에서 아래이며, 응답은 처음 걸린 하나의 코드입니다.

| 코드                         | 상태  | 조건                                                                                                                                                                        |
| ---------------------------- | ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `sending_disabled`           | `409` | 전역 `SEND_ENABLED`가 `true`가 아니거나, 연결이 활성·`send_enabled`·유효한 토큰을 갖추지 못함                                                                               |
| `contact_not_found`          | `404` | 그 연결에 그 작성자의 댓글이 없음                                                                                                                                           |
| `no_dm_identity`             | `409` | 검증된 DM 수신자가 없음                                                                                                                                                     |
| `recipient_opted_out`        | `409` | 수신자 또는 댓글 작성자가 marketing이나 service_reply를 철회함                                                                                                              |
| `marketing_consent_required` | `409` | 정확한 범위의 명시적 marketing 동의가 없음(캠페인의 단계 5와 같은 기준)                                                                                                     |
| `reply_window_closed`        | `409` | 수신자의 `WINDOW_ANCHOR` 기준 24시간 창이 닫힘                                                                                                                              |
| `contact_paused`             | `409` | 연락처 또는 수신자의 자동화가 일시 중지됨                                                                                                                                   |
| `contact_busy`               | `409` | `startBlocked`가 막는 상태(활성 상담 전환, 진행 중인 실행, 대기 중인 팔로우 대화, 15분 안의 보관 DM), 또는 그 수신자에게 아직 `pending`·`sending`인 `flow_dm_deliveries` 행 |
| `active_contact_limit`       | `409` | 활성 연락처 한도 때문에 발송이 막힐 수신자                                                                                                                                  |
| `rate_limited`               | `429` | 수신자의 10분 대기 또는 연결의 시간당 DM 시작 한도                                                                                                                          |

- 동의 기준은 캠페인을 따릅니다. 외부 시작은 사람이 먼저 보낸 DM에 대한 답이 아니라 사업자가 먼저 보내는 메시지라서, DM 트리거 플로보다 캠페인에 가깝기 때문입니다.
- 발송이 꺼져 있으면 시작을 쌓아 두지 않고 거절합니다. DM 트리거는 발송이 꺼진 동안에도 실행을 만들지만, 그것은 사람이 보낸 DM에 대한 기록이기 때문입니다. 외부 시작을 쌓아 두면 24시간 창이 닫히거나 외부 시스템이 포기한 뒤에 발송될 수 있습니다.
- 10분 대기와 시간당 DM 시작 한도(`dmStartSkipCodeSql`)는 DM 시작과 외부 시작을 함께 셉니다. 따로 세면 외부 시작이 연결의 한도를 우회합니다.
- 작업 공간의 시간당 쓰기 한도(`api_writes_per_hour`)도 연락처 쓰기와 함께 씁니다. 이것이 이 단계의 요금제 검사이며, 플로 실행 수 자체의 요금제 한도는 지금 없으므로 만들지 않습니다.
- 이 한도는 Cloudflare 한도 객체라서 트랜잭션 안에 넣을 수 없고 되돌릴 수도 없습니다. 그래서 위 표의 검사 전에, 인증·권한·본문 검증 뒤에 씁니다. 표의 검사에서 거절된 요청과 재요청도 한도를 씁니다. 넘으면 `429 rate_limited`입니다.
- 연락처 쓰기와 달리 이 경로는 한도 객체를 쓸 수 없으면 닫힌 쪽으로 실패합니다(`503 api_limit_unavailable`). 이 경로는 메시지를 보내기 때문입니다.
- 같은 수신자의 연속 시작은 위의 `contact_busy`(아직 보내지 않은 첫 DM)와 10분 대기가 함께 막습니다. DM 트리거의 시작 규칙은 바꾸지 않습니다.

### 발송

- 첫 메시지는 기존 `flow_dm_deliveries` 행으로 보내고, 기존 DM 플로 발송 작업(`src/instagram/dm-flow-delivery-worker.ts`)이 그대로 처리합니다. 새 발송 테이블은 만들지 않습니다.
- 그래서 발송 직전의 기존 검사를 모두 그대로 받습니다: 전역 발송 스위치, 실행 상태, 플로 켜짐, 연결과 토큰, 연결 일시 중지, `WINDOW_ANCHOR` 24시간 창, 수신자 일시 중지, 상담 전환, 수신 거부, 활성 연락처 한도.
- `WINDOW_ANCHOR`는 실행의 시작 이벤트가 아니라 발송 행의 `recipient_id`로 계산하므로, 외부 시작 실행에도 바뀌지 않고 적용됩니다.
- 외부 시작 실행에는 발송 직전 검사에 두 가지를 더합니다. 기존 DM 플로 발송은 수신자 ID로만 검사하고 댓글 연락처를 읽지 않기 때문입니다(`flow_dm_deliveries`에는 `sender_id`가 없음). 두 검사는 `flow_api_starts`를 통해 댓글 연락처를 찾습니다.
  - 동의: 캠페인의 수신자 단계 SQL(`recipientStageSql`)의 단계 4·5와 같은 기준입니다. 기존 검사(`messagingRecipientOptedOut`)는 service_reply 철회만 보므로, marketing 철회와 marketing 동의 없음을 여기서 막습니다.
  - 댓글 연락처의 일시 중지: 캠페인과 같이 `instagram_contact_automation`의 `paused`와 `handoff_paused`를 읽습니다.
- 위 두 검사에 걸린 행은 다시 시도하지 않고 `blocked`가 됩니다. 기다렸다가 보내면 외부 시스템이 포기한 뒤에 발송될 수 있기 때문입니다.
- 활성 연락처 기록은 기존 발송 작업의 `sent` 갱신이 씁니다.

### 데이터

- 새 테이블 `flow_api_starts`가 받아들인 시작 하나를 한 행으로 저장합니다: `id`, `workspace_id`, `connection_id`, `sender_id`, `recipient_id`, `flow_id`, `flow_version_id`, `api_key_id`, `request_key`(UUID), `request_hash`, `created_at`. `(workspace_id, request_key)`가 유일합니다.
- `flow_runs`에 `api_start_id`를 더하고, `flow_runs_source` CHECK를 세 출처(`event_id`, `dm_start_event_id`, `api_start_id`) 중 정확히 하나로 바꿉니다. `(flow_id, api_start_id)`가 유일합니다.
- DM 시작 한도(`dmStartSkipCodeSql`)는 지금 `instagram_dm_start_events`의 `sender_id`만 셉니다. 외부 시작의 수신자(`flow_api_starts.recipient_id`)도 함께 세도록 넓힙니다.
- `flow_api_starts`는 연결 범위이며 사람을 키로 가지므로 `delete_connection_data`, `delete_workspace_data`, `delete_person_data`에 등록하고, `src/app/workspace-export.ts`의 `EXPORTED_TABLES` 또는 `EXCLUDED_TABLES`에 넣습니다.
- 요청 키는 별도 테이블 `flow_api_start_keys`(`workspace_id`, `request_key`, `request_hash`, `created_at`)에도 씁니다. 개인 정보와 연결 ID가 없는 작업 공간 범위 테이블이라 `delete_workspace_data`에만 등록하고, 두 작업 공간 이동 검사에도 넣습니다. 사람이나 연결을 지워도 남으므로, 지운 시작의 키로 다시 보내지 않습니다.
- 사람이나 연결을 지우면 그 시작이 DM 시작 한도에서 빠집니다. DM 시작 이벤트도 같은 삭제로 지워지므로 기존 DM 시작 한도와 같은 동작이며, 이월은 만들지 않습니다.
- 서버 역할에는 SELECT와 INSERT만 줍니다. 행은 바뀌지 않습니다.
- migration `082`가 위 테이블과 열, CHECK를 만들고 `api_keys_scopes_check`를 넓힙니다. `db/schema.sql`과 `deploy/migrate-multi-user.sql`에 함께 반영합니다.

### 권한과 키

- 키 권한 목록에 `flows:start`를 더합니다. 시작 키는 항상 `contacts:read`도 가집니다. 허용하는 배열은 `{contacts:read}`, `{contacts:read,contacts:write}`, `{contacts:read,flows:start}`, `{contacts:read,contacts:write,flows:start}`입니다. 기존 키 행은 바꾸지 않습니다.
- `POST /v1/flows/{flow_id}/starts`와 `GET /v1/flows`는 `flows:start`가 없으면 `403 insufficient_scope`입니다.
- 키 발급 화면에 체크박스 "플로 시작 허용"을 더하며, 기본은 꺼짐입니다.
- 인증, IP별·키별 한도, 마지막 사용 기록은 앞 단계와 같습니다. 시작은 커밋한 뒤에 마지막 사용을 기록하며, 기록이 실패해도 `202`를 돌려줍니다.
- 로그는 앞 단계처럼 고정 코드만 남기고, 수신자 ID와 메시지 문구는 남기지 않습니다.

### 보고서

- 플로 실행 보고서(`src/app/flow-run-reports.ts`)는 실행의 출처 열을 읽지 않으므로, 외부 시작 실행은 바꾸지 않아도 다른 실행과 함께 집계됩니다. 출처별로 나눠 보여 주는 일은 이 단계에 넣지 않습니다.

## 빌더에게 맡기는 것

- 요청 해시를 만드는 방식(정규화한 `flow_id`, `connection_id`, `sender_id`의 고정 순서 문자열 등).
- 요청 시 검사를 기존 SQL(`startBlocked`, `dmStartSkipCodeSql`, 캠페인의 단계 SQL, `WINDOW_ANCHOR`)과 어떻게 나눠 쓸지. 한 곳에서 바꾼 규칙이 다른 경로와 어긋나지 않게 공유하는 쪽을 고릅니다.
- 같은 수신자의 동시 시작을 직렬화하는 잠금(DM 시작의 `dm-start-sender:` advisory lock을 같이 쓰는 방식 등).
- OpenAPI 설명 문장과 체크박스 옆의 안내 문구. 이웃 문구의 해요체를 따릅니다.

## 검증

- 단위: 요청 본문 검증, 요청 해시, 권한 검사, OpenAPI 경로 일치, 응답 코드 표의 각 코드.
- DB: 같은 키와 같은 내용의 재요청이 같은 결과를 돌려주고 행을 더 만들지 않음, 같은 키와 다른 내용의 `409`, 동시 요청이 실행 하나만 만듦, 위 표의 각 거절이 아무것도 쓰지 않음, DM 시작과 외부 시작이 대기와 시간당 한도를 함께 씀, 다른 작업 공간의 플로·연결·연락처 거절, 세 삭제 함수와 내보내기 등록, 사람·연결 삭제 뒤 같은 키의 재요청이 `409 idempotency_conflict`이고 아무것도 보내지 않음, 여러 수신자 중 검사를 통과한 수신자 선택, migration 082 재실행.
- 발송: 요청 뒤 marketing 철회, 댓글 연락처 일시 중지, 수신자 일시 중지, 상담 전환, 창 닫힘, 발송 스위치 꺼짐이 각각 발송을 막음(모의 Graph 응답).
- 한도: 쓰기 한도 객체를 쓸 수 없을 때 `503 api_limit_unavailable`이고 아무것도 쓰지 않음.
- workerd: 실제 Worker에서 키, 한도, 라우팅을 거친 `202`와 `GET /v1/flows`.
- 화면: 로컬 mock 미리보기에서 "플로 시작 허용" 체크박스와 권한 표시.
- 보고서: 외부 시작 실행이 플로 실행 보고서의 집계에 들어감(DB).
- 단위·DB·workerd 테스트와 모의 Graph 테스트는 운영 Worker, 운영 DB, 실제 발송을 증명하지 않습니다. 운영 적용, 배포, 실제 키로 하는 실제 발송 확인은 각각 따로 승인을 받습니다.
