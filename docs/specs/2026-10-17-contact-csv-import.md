# CSV 태그 변경 적용

## 범위

[#25](https://github.com/AndrewDongminYoo/auto-chatter/issues/25)의 가져오기 적용 단계를 구현합니다.
[CSV 태그 변경 사전 검사](2026-10-17-contact-csv-preview.md)가 변경 예상으로 판정한 기존 댓글 연락처의 태그를 파일의 값으로 교체합니다.
파서·행 분류·단일 SELECT 스냅샷은 사전 검사와 같은 함수를 사용하므로 두 경로의 판정이 어긋나지 않습니다.
사전 검사의 요청·응답 형태와 동작은 바뀌지 않습니다.

새 연락처 생성, 식별자 병합·분리, 동의·필드·자동화 중지·인박스 변경, 파일 저장, 발송, DELETE는 하지 않습니다.
식별자 병합·분리는 [#17](https://github.com/AndrewDongminYoo/auto-chatter/issues/17)의 결정에 달려 있어 이 범위 밖입니다.
감사 테이블과 마이그레이션은 추가하지 않습니다.
수동 태그 저장에 감사 행이 없으므로 적용에도 두지 않는다는 결정이며, 필요해지면 두 경로에 함께 추가합니다.

## 입력과 결과

`POST /api/contacts/import`는 쿼리 없이 JSON `{csv: string, expected: array}`만 받습니다.
`csv`는 사전 검사와 같은 규칙(UTF-8, 최대 128KiB, 헤더 제외 500개 레코드, v1 헤더)을 따르며 화면이 검사에 보낸 것과 같은 문자열입니다.
`expected`는 사전 검사가 변경 예상으로 판정한 행마다 `{row, current_tags}`를 담습니다.
`row`는 1 이상 레코드 수 이하의 정수이고 서로 다르며, `current_tags`는 문자열 배열(최대 20개)입니다.
다른 형태는 `400 invalid_contact_import_request`입니다.
HTTP 본문 한도 `CONTACT_IMPORT_APPLY_REQUEST_BYTES`는 사전 검사 한도에 500행 × 20태그 × 40자(JSON 이스케이프 6바이트)를 더해 상수에서 계산합니다.
활성 관리자(`owner`·`admin`)만 호출할 수 있고, 같은 출처·인증·사용자 및 작업 공간 API 쓰기 한도를 그대로 적용합니다.

처리는 한 클라이언트의 한 트랜잭션에서 다음 순서로 진행합니다.

1. 사전 검사와 같은 함수로 레코드를 파싱·분류합니다(형식·범위·태그 오류, 그다음 중복).
2. 작업 공간 단위 가져오기 자문 잠금 `hashtextextended('contact-import:' || workspace, 0)`을 잡아 같은 작업 공간의 두 적용을 직렬화합니다.
3. 유효 행이 참조하는 연결을 ID 순서로 `FOR SHARE` 잠금합니다(삭제 함수·`ingestMessages`와 같은 순서).
4. 유효 행마다 `lockContact`를 `(connection_id, sender_id)` 순서로 잡습니다.
   정렬된 서브쿼리 위의 한 문장으로 잡으며, 스냅샷 SELECT보다 앞서므로 수동 태그 저장과 같은 잠금 아래에서 읽습니다.
   한 트랜잭션이 최대 500개의 자문 잠금을 쥐는 비용이 있습니다.
   액션이 있는 플로우의 댓글 수집 배치(`ingestComments` → `startFlowRun`)는 같은 `lockContact`를 웹후크 이벤트 순서로 잡으므로, 파일에 있는 두 연락처의 댓글이 같은 순간 수집되면 PostgreSQL이 한쪽을 교착(`40P01`)으로 중단할 수 있습니다.
   적용이 중단되면 아무것도 쓰지 않고 일반 오류로 끝나며 관리자가 다시 검사하고 적용합니다.
   수집 배치가 중단되면 웹후크는 다른 수집 실패와 같이 5xx로 응답하고 Meta의 재전송에 맡깁니다.
   수집 순서를 바꾸지 않는 이유는 이 교착이 드물고(같은 파일의 두 발신자가 밀리초 안에 겹쳐야 함) 어느 쪽도 부분 쓰기를 남기지 않기 때문입니다.
5. 사전 검사와 같은 스냅샷 SELECT로 멤버십·연결 소유권·댓글 연락처 존재·현재 태그를 읽습니다.
   멤버십이 사라졌으면 `403 role_forbidden`입니다.
6. 오류·중복·조회 불가 행이 하나라도 있으면 아무것도 쓰지 않고 롤백하며 `422 contact_import_rejected`를 반환합니다.
   본문은 사전 검사와 같은 `checked_at`·`counts`·`rows`를 담아 화면이 고칠 행을 보여줄 수 있습니다.
7. 서버가 변경 예상으로 판정한 행이 `expected`에 없거나 `current_tags`가 정렬 비교로 저장된 태그와 다르면 `409 contact_import_stale`을 반환합니다.
   본문은 6과 같은 최신 결과입니다.
   변경 없음으로 바뀐 여분의 `expected` 행은 무시합니다.
8. 변경 예상 행을 `saveContactTags`와 같은 문장(`INSERT ... SELECT ... WHERE EXISTS(댓글 이벤트) ON CONFLICT DO UPDATE SET tags`)으로 한 번에 씁니다.
   쓴 행 수가 변경 집합보다 적으면(조회와 쓰기 사이에 연락처가 삭제됨) 롤백하고 `409 contact_import_stale`을 반환합니다.
9. 커밋합니다.

`200` 응답은 `{applied_at, counts: {total, applied, unchanged}, rows: [{row, status: "applied" | "unchanged", connection_id, sender_id, previous_tags, tags}]}`입니다.
`applied_at`은 쓰기 문장의 `statement_timestamp()`입니다.
같은 파일을 다시 적용하면 `applied: 0`이고 모든 행이 `unchanged`입니다.
적용은 전부 아니면 전무이며, 부분 성공은 없습니다.
잠금 뒤에 읽고 쓰므로 사전 검사와 적용 사이의 수동 저장은 `409`로 드러나고, 적용 중 시작된 수동 저장은 적용이 커밋될 때까지 기다립니다.

## 화면

오류·중복·조회 불가가 없고 변경 예상이 1행 이상인 검사 결과에서만 `#contacts-import` 안에 적용 컨트롤을 보입니다.
컨트롤은 교체를 확인하는 체크박스("N행의 태그를 파일의 값으로 교체합니다")와 "태그 변경 적용" 버튼이며, 버튼은 체크박스가 켜져 있고 검사 결과가 현재일 때만 활성입니다.
`window.confirm`·`alert`·`prompt`는 사용하지 않습니다.
적용 요청은 검사에 보낸 것과 같은 `csv` 문자열을 현재 세대 동안 메모리에 보관해 보내고, `expected`는 검사 결과의 변경 예상 행에서 만듭니다.
파일 변경·다시 검사·세션 초기화·작업 공간 재조회·연결 삭제·탭 간 세션 신호·뒤로 가기 캐시 복원은 사전 검사와 같이 적용 컨트롤을 제거하고 보관한 CSV를 지우며 지연된 적용 응답을 무시합니다.

`200`이면 적용·변경 없음·적용 시각 요약과 적용된 행 목록을 보이고, 파일 선택은 유지하되 검사 결과는 무효화해 다음 적용 전에 다시 검사하게 합니다.
기존 `loadContacts()`로 연락처 목록을 다시 불러오되, 저장하지 않은 연락처 태그·필드 초안이 있으면 불러오지 않고 목록을 새로 고치지 않았다는 안내를 요약 뒤에 붙입니다.
`422 contact_import_rejected`·`409 contact_import_stale`이면 서버의 최신 `rows`를 기존 검사 결과 렌더러로 보이고, 저장하지 않았으며 다시 검사해야 한다는 안내를 붙입니다.
문자열은 모두 텍스트로 렌더링합니다.
소유자·관리자만 컨트롤을 봅니다.
`public/_headers`의 no-cache 동작과 정적 제공 방식은 바뀌지 않습니다.

## 검증

관리자가 변경·변경 없음 행이 섞인 파일을 적용하면 변경 행만 바뀌는지 모든 public 테이블의 전후 비교로 확인합니다.
오류·중복·조회 불가 행이 하나씩 있는 파일은 `422`와 행별 결과를 반환하고 아무것도 쓰지 않습니다.
사전 검사 뒤 `saveContactTags`로 바뀐 태그는 `409`를 반환하고 쓰지 않으며, 수정이 적용의 읽기 전에 커밋된 경우와 적용의 잠금 뒤에 시작된 경우(두 번째 클라이언트가 잠금을 쥐고 있을 때 적용이 읽기 전에 대기하는지 `pg_locks`로 확인) 모두 검사합니다.
조회와 쓰기 사이의 연락처 삭제는 `409`로 거절되고 부분 쓰기가 없음을 확인합니다.
상담원·제거된 멤버·타 작업 공간 연결·요청 형태·본문 한도를 확인하고, 같은 파일의 두 번째 적용이 `applied: 0`임을 확인합니다.
제한된 Worker 역할로 적용과 상담원 거절을 확인합니다.
화면은 적용 컨트롤의 노출 조건, 모든 무효화에서의 제거, 보관한 CSV와 행 전송, 지연 응답 무시, `422`/`409` 행 렌더링을 검사합니다.
타입·단위·DB·Cloudflare·Trunk를 실행하며 운영 DB·배포·Meta 호출은 제외합니다.
결과는 [검증 기록](../notes/2026-10-17-contact-csv-import-verification.md)에 있습니다.
