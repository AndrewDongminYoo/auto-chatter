# 작업 공간 API 키 설계

## 목적

[이슈 #48](https://github.com/AndrewDongminYoo/auto-chatter/issues/48)의 첫 단계입니다.
고객사의 CRM이나 자체 서버가 auto-chatter에 모인 연락처를 읽어 갈 수 있도록, 작업 공간이 외부 시스템에 건넬 API 키를 발급하고 관리합니다.
이번 단계는 키의 발급, 저장, 확인, 폐기, 감사와 설정 화면까지만 만듭니다.
연락처를 실제로 내주는 외부 API는 다음 단계입니다.

가장 피해야 할 실패는 키가 새어 나갔는데 아무도 알아채지 못하는 상황입니다.
그래서 모든 키에 만료일이 있고, 마지막 사용 시각과 위치를 보여 주며, 키를 만든 관리자가 떠나면 그 키도 함께 멈춥니다.

## 목표

- 관리자가 설정 화면에서 이름과 만료 기간을 정해 키를 발급하고, 원문을 한 번만 봅니다.
- 서버는 키의 해시만 저장하고, 원문은 다시 보여 주지 않습니다.
- 키마다 권한(scope)을 가지며, 이번 단계의 권한은 `contacts:read` 하나입니다.
- 키 목록에서 만든 사람, 만든 시각, 만료일, 마지막 사용 시각과 IP, 상태를 봅니다.
- 관리자는 키를 즉시 폐기할 수 있습니다.
- 키를 만든 멤버가 제거되거나 `admin` 아래 역할로 바뀌면 그 멤버가 만든 키는 같은 트랜잭션에서 자동으로 폐기됩니다.
- 발급, 폐기, 자동 폐기는 추가 전용 감사 기록으로 남습니다.
- 외부 시스템이 키가 동작하는지 확인할 수 있는 최소 경로 하나(`GET /v1/key`)를 둡니다.

## 비목표

- 연락처 읽기 API, 연락처 쓰기 API, 플로 시작 API: 다음 단계입니다.
- OpenAPI 문서와 외부 API 전체의 권한 침해 테스트: 외부 API와 함께 다음 단계에서 만듭니다.
- 요금제별 API 사용 제한과 유료 요금제 전용 제한: #52·#54와 함께 정합니다. 이번 단계에서는 모든 요금제가 키를 만들 수 있습니다.
- 키 원문 복구, 만료 없는 키, 만료일 연장.

## 피해야 할 결과

- 새어 나간 키가 계속 동작하는데 화면에서 그 사실을 알아챌 방법이 없는 상태.
- 떠난 관리자가 만든 키가 계속 동작하는 상태.
- 키 원문이 로그, 응답 본문(발급 응답 제외), 브라우저 저장소, 내보내기 파일에 남는 상태.

## Andrew가 정한 것

- 첫 쓰임은 CRM이 연락처를 읽어 가는 것이며, 첫 권한은 읽기 전용입니다.
- 가장 피할 실패는 유출된 키를 모르는 것입니다.
- 키를 만든 멤버가 제거되거나 `admin` 아래로 강등되면 그 멤버가 만든 키를 자동으로 폐기합니다.
- 마지막 사용 IP를 그대로 저장해 화면과 작업 공간 내보내기에 포함하고, 같은 PR에서 공개 개인정보처리방침(`/privacy`, `src/cloudflare/public-pages.ts`)의 보관 정보 범주에 "API 키의 마지막 사용 시각과 IP"를 추가합니다.

## 설계 결정 (작성자의 판단)

아래는 대화에서 정하지 않았고 작성자가 기존 선례를 근거로 정한 값입니다.

### 키 형식과 저장

- 원문은 `ac_live_` 뒤에 `randomBytes(32)`의 base64url 43자를 붙인 문자열입니다.
- 저장 값은 원문 전체의 SHA-256 hex이며, `key_hash`에 유일 색인을 둡니다. 근거는 작업 공간 초대 토큰(`src/app/workspace-members.ts`)이 같은 방식으로 해시만 저장하는 것입니다.
- 화면에서 키를 구별하도록 원문의 앞 12자(`ac_live_` 포함)를 `key_prefix`로 따로 저장합니다.
- 확인은 요청 키의 해시로 행을 찾고, 폐기와 만료만 확인합니다. 작업 공간에는 상태 열이 없고, 작업 공간을 삭제하면 키 행도 함께 지워지므로 키 행 하나만 읽습니다. 해시 조회이므로 문자열 비교의 시간 차이를 따로 다루지 않습니다.

### 만료와 개수

- 만료는 필수이며, 발급할 때 30일, 90일, 180일, 365일 가운데 고릅니다. 기본값은 90일입니다.
- 만료가 7일 안으로 다가온 키는 목록에서 경고로 표시합니다.
- 작업 공간마다 폐기되지 않고 만료되지 않은 키는 최대 10개입니다(`MAX_ACTIVE_API_KEYS`). 초과하면 `409 api_key_limit_reached`입니다.
- 교체는 따로 만들지 않습니다. 새 키를 발급해 외부 시스템에 바꿔 넣은 뒤 이전 키를 폐기합니다. 키를 여러 개 둘 수 있으므로 끊김 없이 교체할 수 있습니다.

### 권한과 역할

- 발급, 폐기, 목록 조회는 `admin` 이상이 합니다(`workspaceFor(..., "admin")`). 웹훅 서명 키 관리와 같은 기준입니다.
- 권한 목록은 코드의 상수(`API_KEY_SCOPES = ["contacts:read"]`)가 가지며, 발급 요청은 이 목록의 부분 집합만 받습니다. DB에는 `text[]`와 CHECK로 저장합니다.

### 사용 기록

- 키로 인증된 요청이 성공하면 `last_used_at`과 `last_used_ip`(`CF-Connecting-IP`)를 기록합니다.
- 같은 키의 기록은 1분에 한 번만 갱신해, 요청마다 쓰기가 생기지 않게 합니다.
- IP는 외부 시스템 서버의 주소이며, 화면에 그대로 보여 줘야 유출을 알아챌 수 있으므로 줄이지 않고 저장합니다.

### 자동 폐기

- `removeMember`는 제거 트랜잭션 안에서, 그 멤버가 만든 폐기되지 않은 키를 `revoked_reason = 'member_removed'`로 폐기합니다.
- `changeMemberRole`은 새 역할이 `admin` 아래(`agent` 등)일 때 같은 방식으로 `member_demoted`로 폐기합니다.
- 소유권 이전처럼 역할이 `admin` 이상으로 남는 변경은 키를 건드리지 않습니다.
- 자동 폐기 감사 기록은 actor 없이 남습니다. 리마인더 자동 취소(`member_removed`)와 같은 형태입니다.
- 요청할 때마다 만든 사람의 멤버십을 다시 확인하지는 않습니다. 폐기 시점에 한 번 처리하므로, 확인 경로는 키 행만 읽습니다.

### 외부 경로

- 외부 경로는 `/v1/` 접두사를 쓰고, 세션과 같은 출처 검사를 쓰는 `/api/*`와 분리합니다.
- 인증은 `Authorization: Bearer <키>`만 받습니다. 쿼리 문자열의 키는 받지 않습니다.
- 이번 단계의 경로는 `GET /v1/key` 하나이며, 키 ID, 이름, 권한, 작업 공간 ID, 만료일을 돌려줍니다. 원문과 해시는 돌려주지 않습니다.
- 키가 없거나, 형식이 틀리거나, 모르는 키이거나, 폐기·만료된 키는 모두 같은 `401 invalid_api_key`입니다. 어떤 이유인지 구별하지 않습니다.
- 키마다 1분 고정 창 60회의 요청 한도를 둡니다(Durable Object 이름 `api-key:<키 ID>`). 한도를 넘으면 `429 rate_limited`, 한도 객체를 쓸 수 없으면 닫힌 쪽으로 실패해 `503 api_key_limit_unavailable`입니다. 외부에 열린 경로이므로 #166의 요청별 한도와 같은 방향을 택했습니다.
- 모든 `/v1/` 요청은 키 조회 전에 클라이언트 IP(`CF-Connecting-IP`)마다 1분 고정 창 600회 한도를 씁니다(Durable Object 이름 `api-ip:<IP>`). 넘으면 `429 rate_limited`, 한도 객체를 쓸 수 없으면 `503 api_key_limit_unavailable`입니다. 기존 한도 객체는 요청을 세지 않고 횟수를 읽을 수 없어서 실패만 셀 수 없으므로, 성공과 실패를 모두 셉니다. 값은 한 서버 IP에서 키 여러 개를 쓰는 CRM이 키별 60회 한도에 먼저 닿도록 넉넉하게 잡았고, 실패 요청이 DB 조회를 무한히 만들지 않게 합니다.

### 감사 기록

- `api_key_events`는 추가 전용이며 `created`, `revoked`, `member_removed`, `member_demoted` 네 종류를 기록합니다. 만료는 시각으로 알 수 있으므로 기록하지 않습니다.
- 행은 키 ID, 작업 공간 ID, 종류, actor(자동 폐기는 NULL), 시각을 가집니다.

### 설정 화면

- 설정의 웹훅 섹션 옆에 "API 키" 섹션을 두며, `admin` 이상에게만 보입니다.
- 발급 양식: 이름(1~80자), 만료 기간 선택(기본 90일). 권한은 `contacts:read` 하나라 고정 표시합니다.
- 발급 뒤 원문은 닫을 수 있는 읽기 전용 입력 칸에 한 번만 보여 주고, 저장소에 넣지 않으며, 닫기·새로 고침·로그아웃 때 지웁니다. 웹훅 서명 비밀의 화면과 같은 방식입니다.
- 목록: 이름, 앞 12자, 권한, 만든 사람 이메일, 만든 시각, 만료일, 마지막 사용 시각과 IP, 상태(사용 중, 만료 임박, 만료, 폐기와 그 이유).
- 폐기는 확인 단계를 거칩니다.
- 색은 기존 primary/secondary/tertiary 토큰만 씁니다.

### 데이터 경로

- 새 테이블 `api_keys`, `api_key_events`를 migration `080`으로 추가하고, `db/schema.sql`, `deploy/migrate-multi-user.sql`에 반영합니다.
- 두 테이블은 작업 공간 범위이므로 `public.delete_workspace_data`가 지웁니다.
- 작업 공간 내보내기는 두 테이블을 내보내되 `key_hash`는 뺍니다(`EXPORTED_TABLES`의 비밀 열 제외 규칙).
- 연결이 필요 없는 작업 공간 행이므로 두 작업 공간 이동 검사에 등록합니다.
- 서버 역할에는 `api_keys`의 SELECT/INSERT/UPDATE와 `api_key_events`의 SELECT/INSERT만 주고, 어느 테이블에도 DELETE는 주지 않습니다. `api_key_events`는 추가 전용이므로 UPDATE도 주지 않습니다.
- 운영 migration 적용과 배포는 이 설계의 범위가 아니며 따로 승인을 받습니다.

### 그 밖의 작성자 판단

- 키 발급과 멤버 제거가 동시에 일어나면, 발급은 만든 사람의 멤버십 행을 잠근 뒤 역할을 다시 확인합니다. 제거나 강등이 먼저 끝나면 발급은 `403`이고, 발급이 먼저 끝나면 그 키는 뒤이은 제거·강등에서 폐기됩니다.
- 작업 공간 이동 검사에서 폐기된 키를 어떻게 셀지는 `webhook_endpoints`의 기존 규칙을 따릅니다.
- `/v1/`에는 CORS 응답 헤더를 두지 않습니다. 서버 간 호출만 대상으로 합니다.

## 빌더에게 맡기는 것

- 테이블의 정확한 열 이름, 색인, CHECK 제약.
- 1분 간격 사용 기록 갱신을 SQL 조건(`last_used_at < now() - interval '1 minute'`)으로 할지 다른 방식으로 할지.
- 화면 문구의 세부 표현. 이웃 화면의 해요체와 기존 오류 문구 형식을 따릅니다.

## 검증

- 단위: 키 형식, 해시, 권한 목록 검사, `GET /v1/key`의 401 구별 없음, 한도 거절과 장애 시 503.
- DB: 발급과 한 번만 보이는 원문, 해시만 저장, 개수 상한의 동시 요청, 폐기와 재사용 불가, 만료 키 거절, 멤버 제거와 강등 시 자동 폐기와 actor 없는 감사 기록, `admin` 유지 역할 변경은 영향 없음, 사용 기록의 1분 간격, 작업 공간 삭제와 내보내기의 해시 제외.
- workerd: 실제 Durable Object로 키별 한도와 IP별 한도.
- 공개 페이지: `/privacy`에 새 보관 범주가 있음.
- 화면: 로컬 mock 미리보기에서 발급, 한 번만 보이는 원문, 목록 상태, 폐기 확인.
- 단위·DB·workerd 테스트는 운영 Worker나 운영 DB의 동작을 증명하지 않습니다.
