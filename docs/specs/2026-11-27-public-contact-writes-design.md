# 외부 연락처 쓰기 API 설계

## 목적

[이슈 #48](https://github.com/AndrewDongminYoo/auto-chatter/issues/48)의 세 번째 단계입니다.
CRM이나 자체 서버가 고객 등급, 구매 여부 같은 정보를 auto-chatter의 연락처 태그와 사용자 정의 필드로 보낼 수 있게 합니다.
앞 단계의 [API 키](2026-11-27-workspace-api-keys-design.md)와 [연락처 읽기 API](2026-11-27-public-contacts-api-design.md)는 2026-11-27 운영에서 실제 키로 확인했습니다.

이 단계는 메시지를 보내지 않습니다.
외부 시스템이 플로를 시작하는 API는 다음 단계입니다.

## Andrew가 정한 것

- 첫 쓰기 API는 연락처 태그와 필드 쓰기입니다. 플로 시작은 그다음입니다.
- 태그는 추가와 제거만 받습니다. 요청에서 언급하지 않은 태그는 그대로 두어, 상담원이 대시보드에서 붙인 태그를 덮지 않습니다.
- 필드는 필드 ID로 지정하고, 외부 시스템이 필드 ID·이름·자료형을 읽을 수 있는 필드 목록 API를 함께 둡니다.
- 쓰기에는 새 권한 `contacts:write`가 필요하며, 관리자가 키를 발급할 때 고릅니다. 이미 발급한 키는 읽기 전용으로 남습니다.
- 대시보드의 태그 저장에 충돌 검사를 더합니다. 상담원이 편집기를 열어 둔 사이 API가 태그를 바꿨다면, 상담원의 저장이 그 변경을 지우지 않고 `409`로 거절됩니다(아래 "대시보드 태그 저장의 충돌 검사").

## 목표

- `PATCH /v1/contacts/{connection_id}/{sender_id}`가 한 연락처의 태그 추가·제거와 필드 값 설정을 한 트랜잭션으로 적용하고, 적용 뒤의 연락처를 돌려줍니다.
- `GET /v1/fields`가 작업 공간의 활성 사용자 정의 필드를 돌려줍니다.
- 같은 요청을 다시 보내도 결과가 같습니다(멱등성).
- `contacts:write`가 없는 키는 쓸 수 없고, 다른 작업 공간의 연락처와 필드는 어떤 입력으로도 바꿀 수 없습니다.
- 쓰기는 작업 공간의 요금제별 시간당 쓰기 한도를 함께 씁니다.
- OpenAPI 계약 문서와 권한 침해 테스트를 쓰기 API까지 넓힙니다.

## 비목표

- 연락처 생성. 댓글을 남긴 적이 있는 기존 연락처만 바꿀 수 있습니다.
- 필드 생성·이름 변경·보관, 태그 이름 목록 관리.
- 여러 연락처를 한 요청으로 바꾸는 일괄 쓰기.
- 동의 기록 쓰기와 플로 시작.
- 쓰기를 웹훅으로 알리는 일.

## 피해야 할 결과

- CRM의 쓰기가 상담원이 붙인 태그나 다른 필드 값을 지우는 것.
- 읽기용으로 발급한 키가 연락처를 바꿀 수 있는 것.
- 같은 요청이 재시도되면서 결과가 달라지는 것.
- 태그나 필드가 동의나 발송 자격처럼 해석되는 것. 기존 규칙대로, 저장된 연락처·필드 기록은 메시지 동의나 발송 자격을 증명하지 않습니다.

## 설계 결정 (작성자의 판단)

### 요청과 응답

- 본문은 `{ "tags": { "add": [...], "remove": [...] }, "fields": { "<필드 ID>": <값 또는 null> } }`입니다. `tags`와 `fields`는 각각 생략할 수 있지만, 둘 다 없거나 둘 다 비어 있으면 `400 invalid_request`입니다.
- 태그 값은 대시보드와 같은 정규화(`normalizeContactTags`의 규칙: 앞뒤 공백 제거, NFC, 소문자, 40자 이하, 제어 문자와 짝 없는 서로게이트 금지)를 거칩니다. 소문자로 바꾼 뒤 NFC가 다시 합치는 문자(예: `J` + U+030C)가 있으므로, 제거할 태그와 저장된 태그는 값이 더 바뀌지 않을 때까지 정규화를 반복한 형태(`normalizedStoredTag`)로 비교합니다. 그래서 같은 태그를 원래 형태, 한 번 정규화한 형태, 조회 결과의 형태 중 무엇으로 보내도 지울 수 있습니다. 추가하는 태그는 대시보드 저장과 같이 한 번 정규화한 형태로 저장하고, 그 문자열이 그대로 저장되어 있을 때만 건너뜁니다. 세그먼트와 플로의 태그 조건은 한 번 정규화한 문자열을 그대로 비교하므로, 반복한 형태만 같은 다른 문자열(예: `j` + U+030C와 U+01F0)은 대시보드 저장처럼 둘 다 남깁니다. 이 경우 두 문자열이 모두 20개 한도에 들어가고, 한 번의 제거가 둘 다 지웁니다. 반복한 형태가 같은 태그가 `add`와 `remove`에 모두 있으면 `400 invalid_request`입니다.
- 적용 순서는 제거 뒤 추가입니다. 결과 태그가 20개를 넘으면 아무것도 쓰지 않고 `409 contact_tag_limit`입니다.
- 필드 값은 대시보드의 필드 값 검증(`validateValue`)과 같은 자료형 규칙을 따르고, `null`은 값을 지웁니다. 64비트 부동소수점으로 정확히 담을 수 없는 숫자(예: `9007199254740993`)는 저장하면 값이 바뀌므로 `400 invalid_field_value`로 거절합니다. 보관된 필드나 작업 공간 밖의 필드 ID는 `404 field_not_found`입니다. 한 요청의 필드는 최대 20개입니다.
- 한 요청 안의 모든 변경은 한 트랜잭션이며, 하나라도 실패하면 아무것도 쓰지 않습니다.
- 성공 응답은 `200`이며 본문은 `GET /v1/contacts`의 연락처 한 건과 같은 형식입니다.
- 연락처가 없으면(그 연결에 그 작성자의 댓글이 없으면) `404 contact_not_found`, 연결이 작업 공간 밖이면 `404 connection_not_found`입니다.
- 본문 크기는 16 KiB까지입니다.
- 한 객체 안에서 같은 키가 두 번 나오면(이스케이프를 푼 값 기준) `400 invalid_request`입니다. `JSON.parse`는 마지막 값만 남기므로, 거절하지 않으면 보낸 것과 다른 값이 저장됩니다.

### 멱등성

- 태그 추가·제거와 필드 값 설정은 결과 상태를 정하는 연산이라서, 같은 요청을 여러 번 보내도 결과가 같습니다.
- 그래서 `Idempotency-Key` 헤더와 저장 테이블은 두지 않습니다. 계약 문서에 이 성질과 재시도 방법을 적습니다.

### 권한과 한도

- 키 권한 목록에 `contacts:write`를 추가합니다. 쓰기 키는 항상 `contacts:read`도 가집니다(쓰기 결과를 응답으로 돌려주기 때문).
- migration `081`이 `api_keys.scopes`의 CHECK 제약을 `{contacts:read}` 또는 `{contacts:read, contacts:write}`로 넓힙니다. 기존 키 행은 바꾸지 않습니다.
- `PATCH`는 `contacts:write`가 없으면 `403 insufficient_scope`입니다. `GET /v1/fields`는 `contacts:read`로 읽습니다.
- 인증과 IP별·키별 한도는 앞 단계와 같습니다. 쓰기는 여기에 더해 키의 작업 공간의 시간당 쓰기 한도(`api_writes_per_hour`, `API_WRITE_WORKSPACE_LIMIT`)를 씁니다. 대시보드 쓰기와 같은 창을 나눠 쓰며, 한도를 넘으면 `429 rate_limited`입니다. 이것이 이 단계의 요금제 검사입니다.
- 쓰기의 작업 공간 한도는 대시보드와 같이 열린 쪽으로 실패합니다(한도 객체를 쓸 수 없으면 쓰기를 허용하고 고정 코드 한 줄을 남김). IP별·키별 한도는 앞 단계대로 닫힌 쪽으로 실패합니다.
- 성공한 `200` 응답만 키의 마지막 사용을 기록합니다. 쓰기는 커밋 뒤에 이 기록을 하므로, 기록이 실패해도 고정 코드 한 줄만 남기고 `200`을 돌려줍니다. 커밋된 쓰기를 오류로 답하면 클라이언트가 재시도하면서 그사이 상담원의 변경을 덮을 수 있기 때문입니다.
- `401`, `403`, `400`으로 거절된 요청은 작업 공간 쓰기 한도를 쓰지 않습니다. 그래서 읽기 전용 키나 잘못된 요청이 대시보드의 쓰기 한도를 소모하지 못합니다. 유효한 쓰기 키는 한도를 소모할 수 있습니다(예: `free`는 시간당 500회를 대시보드와 나눠 씀).
- 키 확인은 쓰기 트랜잭션 밖에서 하므로, 키가 폐기되거나 만든 멤버가 제거되는 순간 이미 진행 중이던 쓰기는 커밋될 수 있습니다. 읽기 API와 같은 수 밀리초의 틈이며 허용합니다.

### 잠금

- 대시보드의 태그·필드 저장과 같은 잠금 순서를 씁니다: 연결 행 `FOR SHARE`, 필드 행 `FOR SHARE`, `lockContact`. 데이터 삭제와 직렬화되는 기존 순서를 바꾸지 않습니다.
- 그 앞에 작업 공간 행을 `FOR KEY SHARE`로 먼저 잠급니다. 태그·필드 값 삽입이 외래 키로 어차피 이 잠금을 잡는데, `delete_workspace_data`는 작업 공간을 `FOR UPDATE`로 잠근 뒤 연결을 잠그므로, 연결 뒤에 잡으면 작업 공간 삭제와 교착될 수 있습니다.
- 태그는 현재 행을 잠근 뒤 읽어 계산하므로, 대시보드 저장과 동시에 일어나도 한쪽 변경이 사라지지 않습니다.

### 대시보드 태그 저장의 충돌 검사

- 지금 대시보드 태그 저장(`saveContactTags`)은 화면의 태그 목록 전체로 저장된 값을 바꿉니다. 오래된 목록은 브라우저에 있으므로 트랜잭션 잠금으로는 이 손실을 막을 수 없습니다.
- 저장 요청에 편집을 시작할 때 읽은 태그 목록 `expected_tags`를 함께 보냅니다. 서버는 연락처를 잠근 뒤 저장된 태그(없으면 빈 목록)와 `expected_tags`를 순서만 무시하고 문자열 그대로 비교하고, 다르면 아무것도 쓰지 않고 `409 contact_tags_stale`을 돌려줍니다. CSV 가져오기의 `current_tags`·`contact_import_stale` 방식과 같습니다.
- `expected_tags`는 필수입니다. 대시보드와 서버는 같이 배포되므로 이전 클라이언트를 위한 호환 경로는 두지 않습니다.
- 화면은 `409 contact_tags_stale`을 받으면 "다른 곳에서 이 연락처의 태그가 바뀌어 저장하지 않았습니다." 같은 안내를 보여 주고, 연락처를 다시 읽어 최신 태그를 보여 줍니다. 상담원이 입력한 내용은 버리지 않고, 편집을 시작할 때의 태그와 비교한 추가·제거만 최신 태그에 적용해 입력란에 둡니다. 그래서 고치지 않고 다시 저장해도 다른 곳에서 바뀐 태그가 지워지지 않습니다.
- 추가·제거는 서버와 같은 정규화 값(앞뒤 공백 제거, NFC, 소문자)으로 비교합니다. 그래서 초안이 태그의 표기만 바꾼 경우(`vip`를 `VIP`로)는 추가도 제거도 아니며, 최신 태그는 저장된 표기를 그대로 유지합니다.
- 한계: 태그 정규화는 한 번 더 적용하면 결과가 달라지는 일부 결합 문자 조합(예: `J` + U+030C)에서 멱등하지 않습니다. 그런 태그는 대시보드가 전체 목록을 다시 저장할 때 표기가 바뀌거나 다른 태그와 합쳐질 수 있습니다. 이 문제는 이 변경 이전부터 있었으며 [#419](https://github.com/AndrewDongminYoo/auto-chatter/issues/419)에서 다룹니다.
- API의 `PATCH`는 추가·제거 방식이라 이 검사를 쓰지 않습니다.

### 필드 목록

- `GET /v1/fields`는 `{ "fields": [{ "id", "name", "type" }] }`를 돌려주며, 보관된 필드는 넣지 않습니다. 정렬은 대시보드 필드 목록과 같습니다.

### 키 발급 화면

- 설정의 API 키 발급 양식에 "연락처 쓰기 허용" 체크박스를 둡니다. 기본은 꺼져 있습니다.
- 목록의 권한 표시에 `contacts:write`가 보입니다.
- 화면 변경이므로 로컬 mock 미리보기로 확인합니다.

### 계약 문서와 테스트

- `docs/api/openapi-v1.json`에 두 경로를 추가하고, 기존 경로 일치 테스트가 새 경로도 확인합니다.
- 권한 침해 테스트(DB): 읽기 전용 키의 쓰기 `403`, 다른 작업 공간의 연결·연락처·필드 ID로 쓰기 시도, 보관된 필드 쓰기, 키를 만든 멤버 제거 뒤 쓰기, 실패한 요청이 아무것도 쓰지 않음.
- 동시성 테스트(DB): API 태그 추가가 겹친 트랜잭션에서도 사라지지 않음. 대시보드가 API 쓰기 전에 읽은 `expected_tags`로 저장하면 `409 contact_tags_stale`이고 API가 추가한 태그가 남음.

### 데이터 경로

- 새 테이블은 없습니다. `api_keys.scopes`의 CHECK만 바뀌므로 삭제 함수, 내보내기, 권한 부여는 바뀌지 않습니다.
- migration은 `db/migrations/081_*.sql`, `db/schema.sql`, `deploy/migrate-multi-user.sql`에 반영하고, 운영 적용과 배포는 따로 승인을 받습니다.

## 빌더에게 맡기는 것

- 대시보드 저장 함수와 공용 부분을 어떻게 나눌지(검증과 SQL 재사용 방식).
- 공개 API에 트랜잭션을 쓸 수 있는 연결을 넘기는 방식, 경로 패턴을 경로 목록과 OpenAPI 일치 테스트에 넣는 방식, 여러 필드를 잠그는 순서(ID 순).
- OpenAPI 설명 문장.
- 체크박스의 정확한 문구. 이웃 문구의 해요체를 따릅니다.

## 검증

- 단위: 요청 본문 검증, 태그 정규화와 충돌, 권한 검사, OpenAPI 경로 일치.
- DB: 태그 추가·제거와 다른 태그 보존, 20개 상한, 필드 설정과 지우기, 자료형 오류, 한 트랜잭션의 전부 또는 전무, 같은 요청 재전송의 같은 결과, 위의 권한 침해와 동시성 테스트, migration 081 재실행.
- workerd: 실제 Worker에서 `PATCH`와 `GET /v1/fields`가 키·한도를 거쳐 응답함.
- 화면: 로컬 mock 미리보기에서 체크박스와 권한 표시, 태그 저장 `409 contact_tags_stale`의 안내, 최신 태그에 합친 입력, 고치지 않은 재저장의 다른 태그 보존.
- 단위·DB·workerd 테스트는 운영 Worker나 운영 DB의 동작을 증명하지 않습니다.
