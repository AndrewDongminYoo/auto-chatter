# 대시보드 API 기본 요청 한도

## 범위

[이슈 #167](https://github.com/AndrewDongminYoo/auto-chatter/issues/167)에서 남은 결정입니다(웹훅 전달 순서는 #190에서 끝났습니다).
로그인한 사용자의 `/api/*` 요청 가운데 인증 경로와 #166의 요청별 한도(작업 공간 내보내기, Instagram OAuth 시작)를 뺀 나머지에는 요청 한도가 없었습니다.
개수 상한이 있는 자원은 묶여 있지만, 추가만 하는 쓰기(받은 편지함 내부 메모, 동의 이벤트)와 보관했다가 다시 만드는 반복은 멤버 누구나 DB를 끝없이 키울 수 있고, `GET /api/inbox`는 요청마다 작업 공간의 DM 전체를 읽습니다([받은 편지함 명세](2026-09-27-instagram-inbox.md#검색-필터와-읽음-상태)).
이 변경은 고정된 기본 요청 한도를 둡니다.
요금제별 한도([#52](https://github.com/AndrewDongminYoo/auto-chatter/issues/52))가 나중에 이 기본값을 대신하며, 저장량의 절대 상한도 그쪽에서 정합니다.
운영 배포는 이 PR의 범위가 아닙니다.

## 한도

세 한도 모두 인증 한도와 같은 Durable Object(`AUTH_LIMITER` 바인딩, `src/cloudflare/auth-limiter.ts`의 `AuthLimiter`)가 셉니다.
Worker는 `src/cloudflare/index.ts`에서 `durableLimits(env.AUTH_LIMITER)`로 바인딩을 만들어 `appApi`에 넘기므로, 같은 클래스와 바인딩을 쓰는 이 변경에는 `wrangler.json` 변경이 없습니다.

| 바인딩                      | 대상                                                                               | 키                    | 한도                  |
| --------------------------- | ---------------------------------------------------------------------------------- | --------------------- | --------------------- |
| `API_WRITE_USER_LIMIT`      | 로그인한 사용자의 `/api/*` 쓰기(GET·HEAD가 아닌 모든 메서드), `/api/auth/*`는 제외 | 사용자 ID             | 1분 고정 창 120회     |
| `API_WRITE_WORKSPACE_LIMIT` | 같은 쓰기                                                                          | 호출자의 작업 공간 ID | 1시간 고정 창 3,000회 |
| `INBOX_LIST_LIMIT`          | `GET /api/inbox`                                                                   | 사용자 ID             | 1분 고정 창 60회      |

- 키는 사용자와 작업 공간의 UUID 그대로이며, 요청 본문이나 경로 같은 요청 입력은 키에 넣지 않습니다. Durable Object 이름은 `api-write-user:<사용자 ID>`, `api-write-workspace:<작업 공간 ID>`, `inbox-list:<사용자 ID>`입니다.
- 작업 공간은 `workspace_members`에서 제거되지 않은 호출자의 행 하나를 읽어 정합니다(사용자당 작업 공간은 하나). 작업 공간이 아직 없는 사용자는 사용자 한도만 씁니다. `workspaceFor`의 계약은 바꾸지 않습니다.
- 두 쓰기 한도에는 예외가 둘 있습니다.
  - `POST /api/workspace`는 대시보드가 화면을 열 때와 멤버, 연결, 설정 동작 뒤에 부르는 시작 요청입니다. 멤버십이 있으면 멤버십을 읽고 저장된 이메일이 다를 때만 그 한 칸을 고치므로(같은 값으로 수렴하는 갱신), 읽기처럼 두 쓰기 한도를 모두 쓰지 않습니다. 멤버십이 없어 첫 작업 공간을 만들 때만 사용자 한도를 씁니다.
  - 멤버 제거(`DELETE /api/workspace/members/<사용자 ID>`, 소유자만)는 작업 공간 한도를 쓰지 않고 사용자 한도만 씁니다. 제거는 남아 있는 멤버 수만큼만 할 수 있습니다. 이 예외는 역할이 아니라 메서드와 경로로 정하므로, 소유자가 아닌 멤버의 같은 요청도 작업 공간 한도를 쓰지 않지만 사용자 한도는 쓰고 처리기가 아무것도 쓰지 않고 거절합니다.
- 거절된 요청도 한 번으로 셉니다. 경로 처리기가 나중에 거절할 쓰기(권한, 입력 검증, 없는 경로)도 셉니다. 작업 공간 한도에서 거절된 쓰기는 사용자 한도를 이미 썼습니다.
- 고정 창이므로 창 경계에 몰린 요청은 짧은 시간에 한도의 두 배까지 지날 수 있습니다(사용자당 쓰기 240회, 작업 공간당 6,000회, 받은 편지함 목록 120회).
- 작업 공간 한도는 멤버가 함께 씁니다. 한 멤버(가장 낮은 역할인 `agent`도)가 사용자 한도 안에서 25분 동안 계속 쓰면 그 시간 창의 나머지 동안 같은 작업 공간의 다른 멤버도 쓰지 못합니다. 그동안에도 다른 멤버는 대시보드를 열고 읽을 수 있으며(시작 요청과 GET은 이 한도를 쓰지 않음), 소유자는 그 멤버를 제거할 수 있습니다. 제거해도 이미 쓴 횟수는 돌아오지 않으므로 쓰기는 다음 시간 창에 다시 열립니다. 받은 편지함의 읽음 표시(`POST .../read`)도 쓰기라서 그동안 거절되지만, 화면은 그 실패를 삼키고 대화를 그대로 보여 주며 다음에 열 때 다시 표시합니다. 이 값은 저장량 증가를 묶는 기본값이며, 요금제별 한도(#52)가 대신합니다.

## 응답

- 세 한도 가운데 어느 것을 넘어도 `429 rate_limited`를 반환합니다. 코드는 하나로 두어, 대시보드(`public/app/app.js`의 `errors`)와 받은 편지함(`public/app/inbox.js`의 `reasons`)이 같은 문구 "요청이 많습니다. 잠시 후 다시 시도해 주세요."를 보여 줍니다.
- 받은 편지함 화면은 목록을 화면을 열 때와 사용자 동작(필터, 검색 제출, 대화 상태 변경, 계정 연결 해제, 시간대 저장) 때만 다시 읽고, 1분 타이머는 목록을 읽지 않으므로, 보통의 사용으로는 분당 60회에 닿지 않습니다.

## 한도 객체를 쓸 수 없을 때

- 이 세 한도는 열린 쪽으로 실패합니다. 바인딩이 없거나, 한도 객체 호출이 예외를 던지거나, 한도 객체가 OK가 아닌 응답을 주면(`durableLimits`가 예외로 바꿈) 요청을 그대로 처리합니다.
- 그때 요청마다 한 번, `logOperation`으로 `{"event":"rate_limit_unavailable","code":"api_limit_unavailable","correlation_id":...}` 한 줄을 남깁니다. 두 쓰기 한도를 모두 쓸 수 없어도 한 줄입니다. 사용자 ID, 작업 공간 ID, 키, 이메일, 경로는 남기지 않습니다.
- 작업 공간 한도의 바인딩이 없으면 그 한도를 위한 멤버십 읽기도 하지 않습니다. `POST /api/workspace`는 사용자 한도를 쓸지 정하려고 바인딩과 관계없이 멤버십을 읽습니다.
- 인증 한도(`auth_unavailable`)와 #166의 요청별 한도(`workspace_export_unavailable`, `instagram_connect_unavailable`, 게시물 조회와 연결 상태 확인)는 지금처럼 닫힌 쪽으로 실패합니다. 그 한도들은 메일 발송, Supabase의 IP별 예산, Meta Graph 호출, 무거운 내보내기처럼 한 번의 요청이 외부 할당량이나 큰 비용을 쓰는 경로를 지킵니다. 이 기본 한도는 저장량과 DB 읽기의 증가를 묶는 것이므로, 한도 객체가 멈췄다고 대시보드의 모든 쓰기를 멈추지는 않습니다.

## 순서

`appApi`(`src/app/api.ts`)는 다음 순서로 확인합니다.

1. 같은 출처 확인(GET이 아닌 요청), 그리고 `/api/auth/*`의 인증 경로와 그 인증 한도. 인증 경로는 세션 확인 전에 돌아가므로 기본 한도를 쓰지 않으며, 그 밖의 `/api/auth/*` 경로도 접두어로 뺍니다.
2. 세션 확인(`auth.user`).
3. 쓰기면 사용자 한도. DB 풀을 열기 전이므로, 이 한도에서 거절된 쓰기는 DB를 읽지도 쓰지도 않습니다. `POST /api/workspace`는 여기서 쓰지 않고 5단계에서 정합니다.
4. Instagram 공개 연결 제한(`instagram_public_access_restricted`), 그리고 DB 풀 열기.
5. 쓰기면 호출자의 멤버십 읽기와 작업 공간 한도. 경로 처리기보다 먼저이므로, 거절된 쓰기는 멤버십 읽기 하나만 합니다. `POST /api/workspace`는 멤버십을 읽어, 없을 때만 사용자 한도를 씁니다. 멤버 제거는 작업 공간 한도를 건너뜁니다.
6. 경로 처리기. #166의 Instagram OAuth 시작 한도(`INSTAGRAM_CONNECT_LIMIT`)는 처리기 안에서 쓰므로, 기본 한도에서 거절된 OAuth 시작은 그 한도를 쓰지 않습니다. 작업 공간 내보내기, 게시물 조회, 연결 상태 확인은 GET이므로 쓰기 한도와 겹치지 않습니다.
7. `GET /api/inbox`는 처리기에서 `listInbox` 전에 받은 편지함 목록 한도를 씁니다. 거절된 요청은 DB를 읽지 않습니다.

## 한도를 두지 않는 것

- `GET /api/inbox`를 뺀 GET 요청(대화 내용, 연락처, 설정, 운영 상태 등). 내보내기와 게시물 조회, 연결 상태 확인은 #166의 한도를 그대로 씁니다.
- Meta 웹후크(`/webhooks/instagram`), 공개 페이지, Queue 소비자와 Cron. 이것들은 `appApi`를 거치지 않습니다.
- Node 수신기와 작업자. 대시보드 API는 Cloudflare Worker에서만 제공합니다.
- 저장량의 절대 상한과 요금제별 한도(#52).

## 검증

- `src/app/api.test.ts`: 사용자 쓰기 한도를 넘으면 처리기와 DB 풀 열기 전에 `429 rate_limited`, 작업 공간 한도를 넘으면 멤버십 읽기만 하고 `429 rate_limited`, 작업 공간이 없는 사용자는 사용자 한도만 씀, 두 쓰기 한도를 다 쓴 멤버도 `POST /api/workspace`가 200이고 멤버십이 없으면 그 요청이 사용자 한도만 씀, 작업 공간 한도를 다 쓴 소유자도 멤버를 제거함, `GET /api/inbox`를 뺀 GET과 인증 경로는 세 한도를 쓰지 않음, 받은 편지함 목록 한도를 넘으면 DB 전에 `429 rate_limited`, 예외를 던지거나 없는 바인딩은 요청을 통과시키고 고정 코드 한 줄만 남김, 기본 한도에서 거절된 OAuth 시작은 #166 한도를 쓰지 않음. #166 한도가 닫힌 쪽으로 실패하는 기존 테스트는 새 바인딩이 있는 상태에서 그대로 통과합니다.
- `src/cloudflare/auth-limiter.test.ts`: `durableLimits`가 세 한도를 위 이름, 횟수, 창 길이로 만듦.
- `src/cloudflare/runtime.db.test.mjs`: workerd에서 실제 Durable Object로, 작업 공간이 없는 사용자의 121번째 쓰기가 `429 rate_limited`이고 그 뒤에도 GET은 열려 있음.
- 단위·DB·workerd 테스트는 운영 Worker의 동작이나 운영 Durable Object의 상태를 증명하지 않습니다.
