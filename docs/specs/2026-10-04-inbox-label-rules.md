# 인박스 자동 라벨 규칙

## 범위

[이슈 #132](https://github.com/AndrewDongminYoo/auto-chatter/issues/132)입니다.
[라벨·내부 메모](2026-10-03-inbox-labels-notes.md)(#23-B)의 인박스 라벨 위에, 새로 저장되는 텍스트 DM의 키워드로 대화에 라벨을 자동으로 붙이는 규칙을 더합니다.
라벨을 붙이는 일은 아무것도 보내지 않으며, 라벨은 여전히 플로·웹훅·자동 답장 조건에 쓰이지 않습니다.
migration 035가 테이블 하나, 감사 기록의 열과 제약, 작업 공간 삭제 함수 변경을 더하며, 운영 DB 적용과 배포는 이 PR의 범위가 아닙니다.
PR #137과 migration 035는 2026-10-04 `main` 커밋 `4f79511`으로 운영 DB에 적용하고 배포했습니다([운영 기록](../notes/2026-09-26-cloudflare-runbook.md)). 운영에는 라벨과 규칙이 없어, 규칙 관리와 자동 라벨을 운영 데이터로 조작하지 않았습니다.

## 운영자 결정

운영자가 2026-10-04 계획을 승인하면서 정한 세 가지입니다.

- **맞추는 방식**: 댓글 규칙과 같은 정규화(NFC, 앞뒤 공백 제거, 소문자)로 `contains`(키워드 포함)와 `exact`(DM 전체가 키워드와 같음)만 지원하고, 제외 키워드가 먼저입니다. 댓글 규칙의 `all`은 "모든 메시지가 맞음"이라 새 DM마다 라벨을 붙이게 되므로 두지 않습니다.
- **멤버가 뗀 라벨**: 멤버가 한 번이라도 대화에서 뗀 라벨(감사 기록의 `removed`에 있고 `actor_id`가 있는 행)은 규칙이 그 대화에 다시 붙이지 않습니다. 멤버는 직접 다시 붙일 수 있습니다.
- **소급 적용 없음**: 규칙은 규칙이 생긴 뒤 저장되는 텍스트 DM에만 적용합니다. 이미 저장된 DM에는 적용하지 않습니다.

## 정한 값

운영자가 정하지 않은 값은 다음처럼 정했습니다.

| 항목                       | 값                                                         |
| -------------------------- | ---------------------------------------------------------- |
| 작업 공간의 사용 중인 규칙 | 50개(보관한 규칙은 세지 않음)                              |
| 규칙 하나의 키워드         | 1–20개, 각각 앞뒤 공백을 뺀 1–100자(댓글 규칙과 같은 한도) |
| 규칙 하나의 제외 키워드    | 0–20개, 각각 앞뒤 공백을 뺀 1–100자                        |
| 규칙의 범위                | 작업 공간 전체(연결마다 나누지 않음)                       |

글자 수는 PostgreSQL `char_length()`와 같은 코드 포인트 기준입니다.
키워드는 맞출 때와 같은 정규화(`normalizeMatchText`, `src/instagram/comment-rule.ts`)를 거쳐 저장하고, 같은 키워드는 하나만 남깁니다.
화면이 키워드를 쉼표로 나누므로, 정규화한 키워드 안에 쉼표나 줄바꿈(CR, LF)이 있으면 API도 거부합니다.

## 저장

- `instagram_inbox_label_rules`: 작업 공간, 붙일 라벨(`(label_id, workspace_id)`가 `instagram_inbox_labels`를 참조), 맞추는 방식, 키워드, 제외 키워드, 보관 여부, 버전, 만든·바꾼 멤버와 시각을 저장합니다. 지우지 않고 보관만 하며, 보관한 규칙은 되돌릴 수 없습니다. 키워드 배열의 개수와 길이는 CHECK 제약(`inbox_label_rule_keywords_valid`)이 지킵니다.
- 서버 역할은 규칙을 SELECT·INSERT·UPDATE할 수 있고 DELETE 권한은 없습니다. RLS가 켜져 있고 Supabase API 역할은 접근할 수 없습니다.

## 감사 기록

`instagram_inbox_label_events`에 `rule_id`(`(rule_id, workspace_id)`가 규칙을 참조)를 더하고 `actor_id`를 NULL 허용으로 바꿨습니다.
한 행에는 `actor_id`와 `rule_id` 중 정확히 하나가 있습니다(CHECK `instagram_inbox_label_events_source`). 035 이전의 행은 모두 멤버가 있으므로 이 제약을 만족합니다.
규칙이 붙인 변경은 `actor_id`가 없고 `rule_id`가 있으며, 대화 라벨 행의 `updated_by`도 비웁니다.
라벨 변경 이력 화면은 없고, 이력은 DB와 [작업 공간 내보내기](2026-09-30-workspace-export.md)로 읽습니다.

## 적용

DM 수집(`ingestMessages`)이 `storeInboxMessage`에서 DM을 새로 저장했을 때만 규칙을 적용합니다(`applyLabelRules`, `src/instagram/inbox.ts`).

- 인박스가 DM을 저장하는 연결(활성, 인박스 켜짐, 켠 시각 이후의 DM)에서, INSERT가 실제로 저장한 행(`RETURNING`)에만 적용합니다. 다시 전달된 DM은 저장되지 않으므로 아무것도 다시 붙이지 않습니다.
- 텍스트 DM만 맞춥니다. 확인 버튼 응답(postback)은 텍스트가 있어도 맞추지 않습니다.
- 보관하지 않은 규칙을 `(created_at, id)` 순서로 읽어 메모리에서 맞춥니다. 같은 라벨의 규칙이 여럿이면 처음 맞은 규칙이 그 라벨의 규칙입니다.
- 다음 라벨은 건너뜁니다: 보관된 라벨, 이미 대화에 있는 라벨, 멤버가 그 대화에서 뗀 적이 있는 라벨, 그리고 대화의 라벨이 10개를 넘게 되는 라벨(규칙 순서로 앞의 라벨부터 남김).
- 보낸 사람 ID가 라벨 테이블에 저장할 수 없는 형식(40자리 초과)이면 규칙을 적용하지 않습니다. DM은 그대로 저장됩니다.
- 남는 라벨이 없으면 아무것도 쓰지 않습니다. 대화 라벨 행도 만들지 않습니다.
- DM 하나가 여러 규칙에 맞아도 라벨 버전 하나와 감사 기록 한 행만 씁니다. `added`에는 붙인 라벨이 모두 있고, `rule_id`는 맞은 규칙 중 `(created_at, id)`가 가장 앞선 규칙입니다. 그 규칙의 라벨이 이미 있거나 건너뛰었어도 그 규칙을 남깁니다.
- 자동화가 멈춘 연락처와 상담 중인 대화에도 라벨을 붙입니다. 라벨은 아무것도 보내지 않기 때문입니다.
- 규칙은 수집을 실패시키지 않아야 합니다. 수집이 실패하면 저장한 DM과 같은 묶음의 팔로우 확인·응답 대기 진행이 함께 되돌려지기 때문입니다. 그래서 쓰기를 실패하게 만들 라벨(보관됨, 이미 있음, 10개 초과)과 보낸 사람 ID는 쓰기 전에 걸러 냅니다.

## 잠금과 동시 실행

수집은 연결 행 `FOR SHARE`(ID 순서)와 대화 잠금(`lockConversation`, 배타)을 첫 INSERT 전에 이미 잡고 있습니다.
규칙 적용은 그 뒤에 잠금 없이 규칙과 대화 라벨을 읽고, 붙일 라벨을 `FOR SHARE`(ID 순서)로 잠근 채 붙일 라벨이 있는지 정합니다. 남는 라벨이 있을 때만 수동 라벨 변경과 같은 순서로 버전 0 자리 행(`ON CONFLICT DO NOTHING`), 대화 라벨 행 `FOR UPDATE`, 붙일 라벨 `FOR SHARE`(이미 잡은 잠금)를 잡고 다시 계산해 씁니다.
라벨 `FOR SHARE` 덕분에 보관이 확인과 쓰기 사이에 커밋되지 못합니다. 커밋되지 않은 보관을 기다린 경우에는 보관된 라벨로 다시 읽어 붙이지 않으며, 아무것도 쓰기 전이므로 대화 라벨 행도 남지 않습니다.
대화 라벨과 멤버의 라벨 제거 기록은 대화 잠금을 잡아야만 바뀌고, 삭제 함수는 연결 잠금에서 기다리므로 결정과 쓰기 사이에 바뀌지 않습니다. 라벨을 먼저 잠가도 라벨 보관은 UPDATE 한 문장이라 수집이 잡은 잠금을 기다리지 않으므로 교착하지 않습니다.
규칙은 잠그지 않고 읽으므로, 커밋되지 않은 규칙 변경은 다음 DM부터 적용됩니다.

- 같은 대화의 수동 라벨 변경(`PUT .../labels`)은 대화 잠금에서 기다렸다가 바뀐 버전을 보고 `409 label_conflict`를 받습니다. 두 멤버가 겨룰 때와 같습니다.
- 규칙 쓰기(만들기, 수정, 보관)는 연결이나 대화 잠금을 잡지 않습니다. 수정은 규칙 행을 `FOR NO KEY UPDATE`로 잠그고, 보관은 키가 아닌 열의 UPDATE 한 문장이라 같은 행 잠금을 암묵적으로 잡습니다. 둘 다 키가 아닌 열만 바꾸므로, 감사 기록의 외래 키가 규칙 행에 잡는 key-share 잠금과 충돌하지 않아 수집을 기다리지 않습니다.
- 규칙 만들기는 작업 공간 행을 `FOR UPDATE`로 잠근 뒤(`lockWorkspaceForMember`) 사용 중인 규칙 수를 세므로, 동시에 만들어도 50개를 넘지 않고, 초대 수락으로 옮겨 간 멤버의 만들기는 `403 workspace_required`로 거부됩니다.
- 규칙을 만들 때와 내용이 바뀐 수정은 라벨을 `FOR SHARE`로 잠가, 라벨 보관이 확인과 쓰기 사이에 커밋되지 못합니다. 바뀐 것이 없는 수정과 보관은 라벨을 잠그지 않습니다.
- 연결·사람·작업 공간 삭제 함수는 연결 행을 먼저 잠그므로, 라벨을 붙이던 수집 뒤에 줄을 서고 교착하지 않습니다.

## API

모든 경로는 `admin` 이상이 필요하고, GET이 아닌 요청은 같은 출처여야 합니다.

| 요청                                 | 동작                                                                                                                                                        |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/inbox/label-rules`         | 작업 공간의 규칙을 사용 중인 것부터, 각각 적용 순서로 돌려줍니다. 규칙마다 라벨의 ID·이름·보관 여부가 있습니다.                                             |
| `POST /api/inbox/label-rules`        | `label_id`, `match_mode`(`contains`·`exact`), `keywords`, 선택 `excluded_keywords`로 규칙을 만듭니다(201). 50개면 `409 label_rule_limit_reached`입니다.     |
| `PATCH /api/inbox/label-rules/<id>`  | 같은 필드와 `expected_version`으로 규칙을 바꿉니다. 버전이 다르면 `409 label_rule_conflict`와 현재 규칙을, 보관한 규칙이면 `409 label_rule_archived`입니다. |
| `DELETE /api/inbox/label-rules/<id>` | 규칙을 보관합니다. 다시 보관해도 바뀌지 않습니다. 이미 붙인 라벨은 그대로 둡니다.                                                                           |

- 규칙의 라벨은 쓰는 시점에 같은 작업 공간의 보관하지 않은 라벨이어야 합니다(없거나 다른 작업 공간이면 `404 label_not_found`, 보관됐으면 `409 label_archived`). 나중에 라벨을 보관하면 규칙은 남아 건너뛸 뿐이고, 그 규칙을 고치려면 다른 라벨을 골라야 합니다.
- 바뀐 것이 없는 수정은 아무것도 쓰지 않고 버전도 그대로입니다.
- 형식이 틀리면 `400 invalid_label_rule`, 키워드가 틀리면 `400 invalid_label_rule_keywords`입니다.
- 라벨을 보관할 때 그 라벨을 쓰는 규칙이 있어도 거부하지 않습니다(`label_in_use` 없음).

## 화면

관리자 설정의 인박스 라벨 다음에 "자동 라벨 규칙" 칸이 있고, 상담원에게는 보이지 않으며 규칙을 요청하지도 않습니다.

- 사용 중인 규칙 수(`n / 50`), 규칙 목록(라벨, 맞추는 방식, 키워드, 제외 키워드), 수정과 보관 버튼을 보여 줍니다.
- 라벨이 보관된 규칙은 "보관된 라벨"로 표시하고, 그 규칙이 라벨을 붙이지 않는다고 안내합니다.
- 만들기와 수정은 같은 입력 칸을 씁니다. 키워드는 쉼표로 구분하고, 개수와 길이는 보내기 전에 브라우저에서도 확인합니다. 붙일 라벨은 보관하지 않은 라벨만 고를 수 있습니다.
- 다른 화면이 먼저 바꾼 규칙을 저장하면 충돌 안내와 함께 입력 칸이 현재 규칙으로 바뀌어, 다른 변경을 덮어쓰지 않습니다.

## 삭제·내보내기·이동

- 규칙은 라벨 정의처럼 작업 공간의 정의이므로 `delete_workspace_data`만 지웁니다. 규칙을 가리키는 라벨 감사 기록 뒤, 라벨 정의 앞에 지우고 개수를 남깁니다.
- `delete_connection_data`와 `delete_person_data`는 바뀌지 않았습니다. 이미 그 범위의 라벨 감사 기록(규칙이 붙인 행 포함)과 대화 라벨 행을 지우며, 규칙은 남깁니다.
- [작업 공간 내보내기](2026-09-30-workspace-export.md)는 `instagram_inbox_label_rules`를 작업 공간 범위로 내보냅니다. 감사 기록의 `rule_id`도 함께 나갑니다.
- 규칙은 연결이 없어도 있을 수 있으므로, 초대 수락의 작업 공간 이동 검사(`currentWorkspaceMovable`, `deploy/assign-workspace-owner.sql`)가 규칙(보관한 규칙 포함)이 있는 작업 공간을 비어 있지 않다고 봅니다.
