# 플로 실행 현황 리포트

## 범위

[#50](https://github.com/AndrewDongminYoo/auto-chatter/issues/50)의 다음 단계로, 소유자와 관리자가 선택 기간에 생성된 플로 실행의 현재 상태를 확인합니다.
실행 상태와 연결된 최초 비공개 답장 outbox 상태는 별도로 집계합니다.
상담 전환·캠페인·청구·비용 분석과 전달·읽음·전환 추정은 포함하지 않으며 #50을 완료 처리하지 않습니다.

## 조회 계약

`GET /api/reports/flow-runs`는 활성 `owner` 또는 `admin`만 사용할 수 있습니다.
필수 `from`·`before`는 작업 공간 시간대의 `YYYY-MM-DD`이며 시작일을 포함하고 종료일을 제외합니다.
기간은 1~366일이고 `expected_time_zone`은 현재 작업 공간 시간대와 정확히 같아야 합니다.
선택 항목 `connection_id`와 `flow_id`는 각각 같은 작업 공간에 속한 UUID이며 함께 지정할 수도 있습니다.
두 필터는 실행 행의 연결과 플로에 적용하므로 현재 발행 버전의 연결 변경은 과거 실행의 범위를 바꾸지 않습니다.
계정과 플로가 각각 소유한 항목이지만 해당 조합의 실행이 없으면 합계는 0입니다.
비활성 연결과 보관된 플로도 조회 대상입니다.

다른 작업 공간 또는 없는 연결·플로는 각각 404 `connection_not_found`·`flow_not_found`로 거부합니다.
알 수 없는 키, 중복 키, 잘못된 UUID·날짜와 범위는 400 `invalid_report_query`, 바뀐 시간대는 409 `report_time_zone_changed`입니다.
현재 멤버십, 시간대, 필터 소유권과 집계는 한 SQL 문장의 스냅샷에서 확인합니다.
이미 시작한 조회는 그 이후의 권한 변경으로 회수되지 않습니다.
각 날짜의 자정은 PostgreSQL이 변환하고 실제 UTC 경계와 조회 시각을 반환합니다.
DST의 23·25시간 날짜 및 겹치거나 존재하지 않는 자정은 PostgreSQL 규칙을 따릅니다.

## 집계 의미

대상은 `flow_runs.created_at`이 지정 기간 안인 보존된 실행입니다.
기간 중 발생한 상태 변경 횟수나 답장 생성·접수 시각 기준의 통계가 아닙니다.
재전송과 여러 단계 기록은 실행 행을 중복 계산하지 않습니다.
삭제된 실행과 답장은 현재 원장에서 사라지므로 영구적인 과거 통계가 아닙니다.

`run_counts`는 `total`과 다음 일곱 상태의 십진수 문자열 건수입니다.
일곱 상태의 합은 total과 같습니다.

| 항목           | 의미                                                                          |
| -------------- | ----------------------------------------------------------------------------- |
| delivering     | 답장을 outbox에 등록한 실행 상태이며 실제 발송 결과는 별도로 확인             |
| ended          | 경로가 종료된 상태이며 응답 대기 후 종료도 포함; 전달·전환 성공을 뜻하지 않음 |
| skipped        | 이미 답장이 있어 해당 실행에서 새 답장을 등록하지 않음                        |
| failed         | 실행 처리 실패                                                                |
| waiting        | 지연·시각 대기                                                                |
| awaiting_reply | 답장 등록 뒤 응답·만료 대기; outbox가 sent가 아닐 수도 있음                   |
| cancelled      | 재개 시 플로 또는 연결 상태 때문에 취소                                       |

`reply_counts`는 같은 실행들에 연결된 첫 비공개 답장의 `pending`·`sending`·`sent`·`blocked`·`failed`·`unknown`과 `absent` 건수입니다.
`absent`는 현재 연결된 outbox 행이 없다는 뜻이며, 한 번도 답장을 만들지 않았다는 증명은 아닙니다.
일곱 건수의 합은 실행 total과 같습니다.
실행당 outbox 행은 고유 제약으로 최대 하나이며 단계·웹훅·감사 행은 집계에 조인하지 않습니다.
답장의 `sent`는 Meta 접수일 뿐 전달·읽음·성공 전환을 증명하지 않습니다.
2026-11-10부터 `reply_counts.read`는 첫 메시지가 `sent`이고 그 메시지 ID의 읽음이 저장된 실행만 세며, 첫 답장 분할의 합에는 들어가지 않습니다([읽음 확인 건수](2026-11-10-instagram-message-reads.md#리포트의-읽음-확인-건수)).
실행 `ended`와 답장 `sent`는 서로 대체하거나 합산하지 않습니다.
본문, 연락처·댓글·실행 식별자, 자격 증명과 실패 원문은 반환하지 않습니다.

## 화면과 CSV

홈에서 관리자가 날짜·계정·플로를 선택해 조회합니다.
플로 선택 목록은 기존 `/api/flows`의 보관하지 않은 항목이며, 전체 조회에는 보관한 플로의 실행도 포함한다고 표시합니다.
초기 날짜는 작업 공간 기준 최근 7일이고, 브라우저가 그 시간대를 지원하지 않으면 날짜를 직접 입력하도록 안내합니다.
실행 상태와 첫 답장 상태는 각각 구분된 영역에 표시합니다.
조회 기간·시간대·계정·플로·조회 시각을 함께 표시하고, 지원하지 않는 조회 시각 표시는 UTC로 대체합니다.
CSV는 표시한 응답 하나에서 만들며 별도 재조회하지 않습니다.
고정 그룹·지표명, 건수, 검증된 날짜·시간대·필터 UUID만 내보내고 계정·플로 이름과 고객 데이터는 제외합니다.
입력 변경, 새 조회, 작업 공간·역할 초기화와 로그아웃은 결과 및 CSV를 무효화합니다.
늦은 조회나 플로 목록 응답은 이후 입력·세션을 덮어쓰지 못합니다.

## 검증과 운영 경계

실제 DB로 상태 조합, outbox 없음, 단계 중복, 모든 필터 조합, 권한·격리, 생성 시각 경계, DST, 빈 결과와 잘못된 입력을 검사합니다.
기간 밖의 과거 데이터를 포함한 실제 집계 SQL의 실행 계획에서 날짜 조건으로 읽기 범위를 좁히는지 확인합니다.
기존 DB는 배포 전에 전체 `deploy/migrate-multi-user.sql` 실행기로 migration 051의 기간 인덱스를 적용해야 합니다.
일반 인덱스 생성은 트랜잭션 완료까지 해당 테이블의 쓰기를 대기시킬 수 있으므로 운영 적용은 별도 승인을 받습니다.
새 의존성, 실제 발송, 플로 실행 변경과 운영 접근은 없습니다.

`wiki/sources/claude--skills--tdd-bugfix-swarm--skill.md`와 `wiki/concepts/diagnostic-report-pattern.md`는 실제 동작 검사와 검증하지 못한 범위의 명시를 뒷받침합니다.
검색은 11건 중 10건만 반환했고 현재 위키 버전은 확인되지 않았으므로 직접적인 프로젝트 선례를 확인했다고 주장하지 않습니다.

## 2026-11-09 추가: 나누어 보기와 응답 대기

[#50](https://github.com/AndrewDongminYoo/auto-chatter/issues/50)의 마지막 리포트 단계입니다.
이 단계로 #50의 리포트 범위를 마치며, 위 범위의 ‘#50을 완료 처리하지 않는다’는 문장은 2026-10-16 단계를 설명한 것입니다.
위 조회 계약과 집계 의미는 그대로이며, 기존 응답 키의 이름과 의미는 바꾸지 않습니다.
제공자 읽음 이벤트(#312)와 비용 리포트(#313)는 별도 이슈로 나누었습니다.

### 조회와 응답

선택 항목 `group_by`는 `day`·`connection`·`flow` 중 하나이며, 다른 값이나 중복 키는 400 `invalid_report_query`입니다.
응답에는 항상 `group_by`(지정하지 않으면 `null`)와 `reply_wait_counts`가 추가됩니다.
`group_by`를 지정하지 않으면 응답에 `groups` 키가 없습니다.
지정하면 `groups`는 `{ key, run_counts, reply_counts, reply_wait_counts }` 배열이며 각 객체의 세 영역은 최상위와 같은 키와 의미를 가집니다.

- `day`: `key`는 `flow_runs.created_at`을 작업 공간 시간대로 바꾼 날짜 `YYYY-MM-DD`이며 오름차순입니다. 기간 경계와 같은 PostgreSQL 변환을 쓰므로 DST 날짜도 PostgreSQL 규칙을 따릅니다.
- `connection`·`flow`: `key`는 실행에 고정된 `connection_id`·`flow_id` UUID이며 그 문자열 순서로 정렬합니다. 계정·플로 이름은 응답에 넣지 않습니다.
- 실행이 하나 이상 있는 그룹만 나오며, 대상 실행이 없으면 `[]`입니다.
- 각 그룹의 실행 상태와 첫 답장 상태는 그 그룹의 `total`과 같고, 모든 그룹의 각 건수를 더하면 최상위 건수와 같습니다.

멤버십·시간대·필터 소유권 확인과 모든 집계는 여전히 한 SQL 문장이며, 조회 시각 `statement_timestamp()`는 첫 CTE에서 한 번만 읽습니다.
대상 실행은 한 CTE에서 한 번 읽고 합계와 그룹 집계가 함께 사용하므로 기간 인덱스 읽기는 한 번입니다.
migration은 추가하지 않습니다.

### 응답 대기 건수

`reply_wait_counts`는 `reached`·`replied`·`not_replied`의 십진수 문자열 건수이며 `replied + not_replied = reached ≤ total`입니다.

`reached`는 응답 대기 노드에 도달한 실행입니다.
현재 `awaiting_reply`인 실행, 받는이의 DM이 대기를 끝낸 실행(`reply_message_id`가 있음), 비공개 답장을 등록한 뒤 `delivering`이 아닌 상태로 바뀐 실행을 셉니다.
메시지 다음에는 응답 대기만 올 수 있고 대기가 없는 메시지의 실행은 `delivering`에서 바뀌지 않으므로, 세 번째 조건은 응답 대기를 거친 실행만 셉니다.
`flow_step_runs`의 대기 단계로는 정의하지 않습니다.
대기 단계 행은 대기가 답장이나 만료로 이어질 때만 기록되고, 아직 기다리는 실행과 답장·만료 시점에 플로나 연결이 꺼져 취소된 실행에는 남지 않습니다.
같은 답장 대상이 중복이어서 `skipped`가 된 실행은 비공개 답장을 등록하지 않았으므로 대기에 도달하지 않은 것으로 셉니다.

`replied`는 받는이가 보낸 DM이 대기를 끝낸 실행(`flow_runs.reply_message_id IS NOT NULL`)입니다.
이 열은 대기 재개(`src/instagram/store.ts`의 `finish`)만 쓰며, 답장이 실행을 취소하기만 한 경우에도 기록됩니다.
`not_replied`는 도달했지만 답장으로 끝나지 않은 실행이며 아직 기다리는 실행, 만료된 대기, 만료 시점에 취소된 실행, 첫 답장이 발송되지 않아 대기가 시작되지 않은 실행을 포함합니다.
받는이 답장은 받는이가 보낸 DM일 뿐이며 첫 답장의 전달·읽음이나 전환을 뜻하지 않습니다.

### 상담 전환 귀속을 제공하지 않는 이유

플로별 상담 전환 귀속은 제공하지 않습니다.
`instagram_inbox_handoff_events.evidence_reply_id`는 상담 전환을 요청한 사람이 누구인지 보여 주는 신원 증거이며, 그 플로가 상담 전환을 일으켰다는 원인이 아닙니다.
#50의 상담 전환 완료 조건은 [상담 전환 이력 리포트](2026-10-16-handoff-reports.md)가 선택 기간과 계정 필터로 집계하는 시작·해제 건수로 충족하며, 플로별 차원은 위 이유로 2026-11-09에 제외했습니다.

### 나누어 보기 화면과 CSV

플로 리포트 카드에 ‘나누어 보기’ 선택(없음·날짜별·계정별·플로별)을 두며, 바꾸면 다른 입력처럼 결과와 CSV를 지웁니다.
응답 대기 건수는 ‘받는이 답장’ 영역에 ‘답장 대기 도달’·‘답장 받음’·‘답장 없음’으로 표시하고, 답장은 받는이가 보낸 DM이며 전달·읽음·전환을 뜻하지 않는다고 안내합니다.
같은 안내에서 ‘답장 없음’에 아직 기다리는 실행, 만료된 대기, 취소된 실행과 첫 답장이 발송되지 않아 대기가 시작되지 않은 실행이 포함된다고 밝힙니다.
나누어 보면 그룹마다 한 행에 세 영역의 모든 건수를 표로 표시하며, 좁은 화면에서는 표 영역 안에서만 가로로 스크롤합니다.
표 머리글은 두 줄이며 첫 줄의 영역 이름(실행 상태·첫 답장 상태·받는이 답장)이 각 영역의 열을 묶으므로, 실행 상태의 ‘응답 대기’(지금 기다리는 실행)와 ‘답장 대기 도달’(대기에 도달한 적이 있는 실행)을 구분합니다.
행 이름은 날짜, 또는 화면이 이미 불러온 계정·플로 목록의 이름이며, 목록에 없는 비활성·보관·삭제된 항목은 UUID 앞 8자로 표시합니다.
CSV는 기존 열 뒤에 `group_by`·`group_key`를 추가합니다.
최상위 행은 두 열이 비어 있고, 그룹 행은 차원과 날짜 또는 UUID를 담으며 계정·플로 이름과 고객 데이터는 넣지 않습니다.
건수는 `BigInt`로 읽고, 늦은 응답은 이후 입력·세션을 덮어쓰지 못합니다.

### 검증

실제 PostgreSQL로 세 차원의 그룹과 합계, 필터와 함께 쓴 그룹, 다른 작업 공간 제외, 빈 결과, 현지 자정과 23·25시간 DST 날짜의 날짜 그룹, 잘못된 `group_by`를 검사합니다.
응답 대기 건수는 실제 댓글 수집·발송·DM 수집·만료 재개 경로로 만든 답장 완료, 답장으로 취소, 만료, 만료 시 취소, 대기 중, 대기 없는 실행, 중복 제외 실행에서 검사합니다.
기간 밖 실행과 단계 이력을 넣은 실행 계획 검사로 네 필터 조합(없음·계정·플로·둘 다)과 네 차원 선택(없음·날짜·계정·플로)의 16개 조합 모두에서 기간 인덱스를 한 번 읽고 `flow_step_runs`를 읽지 않는지 확인합니다.
