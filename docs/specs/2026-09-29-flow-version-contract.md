# 플로 초안·버전·발행 검증 계약

## 범위

[이슈 #28](https://github.com/AndrewDongminYoo/auto-chatter/issues/28)의 계약입니다.
작업 공간은 플로 초안을 저장하고, 발행 시 검증을 통과한 초안을 바꿀 수 없는 버전으로 고정합니다.
이번 변경은 DB 테이블, 순수 검증 모듈과 작업 공간 범위 API만 포함합니다.
실행 엔진(#29), 편집 화면(#30), 태그·필드 동작 실행과 응답 수집(#31), 대기·지연(#32), 새 시작 트리거(#33)는 포함하지 않습니다.
플로는 아직 실행되지 않으므로 발행 버전이 메시지를 보내거나 기존 댓글 규칙의 처리를 바꾸지 않습니다.
편집 화면은 나중에 #30의 두 번째 부분으로 추가했으며 아래 [편집 화면](#편집-화면)이 정합니다.

## 문서 스키마

플로 문서는 `{schema_version: 1, nodes: [{id, type, config}], edges: [{from, port, to}]}` 형식입니다.
노드 ID·타입·포트는 영문자, 숫자, `_`, `-`로 된 40자 이하 문자열입니다.

| 분류   | 타입                     | 설정                                                                                                                | 출력 포트             |
| ------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------- | --------------------- |
| 트리거 | `instagram_comment`      | `connection_id`, `media_id`, `keywords`, `match_mode`, `excluded_keywords` (기존 댓글 규칙과 같은 상한과 모드)      | `next`                |
| 메시지 | `instagram_message`      | `text` (1,000자 이하), 선택 `button_title` (20자 이하, 버튼이 있으면 본문 640자 이하)                               | `next`                |
| 조건   | `follows_account`        | 빈 설정                                                                                                             | `true` / `false`      |
| 조건   | `has_tag`                | `tag` (연락처 태그와 같은 정규화)                                                                                   | `true` / `false`      |
| 조건   | `field_equals`           | `field_id`, `field_operator` (`eq`, `is_set`, `is_unset`), `eq`일 때 `field_value`                                  | `true` / `false`      |
| 동작   | `add_tag` / `remove_tag` | `tag`                                                                                                               | `next`                |
| 동작   | `set_field`              | `field_id`, 필드 타입에 맞는 `value`                                                                                | `next`                |
| 대기   | `delay`                  | `minutes` (1~10,020 정수, [지연과 재개](2026-09-30-flow-runs.md#지연과-재개))                                       | `next`                |
| 대기   | `wait_until`             | `time` (24시간제 `HH:MM`, 작업 공간 시간대, [시각 대기](2026-09-30-flow-runs.md#시각-대기))                         | `next`                |
| 대기   | `wait_for_reply`         | `timeout_minutes` (1~10,080 정수), 선택 `save_field_id` (text 필드, [응답 대기](2026-09-30-flow-runs.md#응답-대기)) | `replied` / `timeout` |
| 전송   | `webhook`                | `endpoint_id`, `field_ids`, `include_tags` ([외부 전송](2026-10-01-flow-webhook-delivery.md#플로-노드))             | `next`                |

트리거는 정확히 하나이며 들어오는 연결을 가질 수 없습니다.
출력 포트 하나에는 연결을 하나만 둘 수 있고, 비어 있는 포트는 해당 경로의 종료를 뜻합니다.
노드 100개, 연결 200개, 문서 64KB는 서비스 정책 상한이며 Meta가 정한 값이 아닙니다.
메시지 본문의 변수는 `{{comment.text}}`와 `{{field:<uuid>}}`만 허용합니다.
기존 노드의 의미가 바뀔 때만 `schema_version`을 올리며, 노드 타입 추가는 버전을 바꾸지 않습니다.

## 초안과 발행 검증

초안 저장은 문서 형태, 노드·연결의 기본 형식, 중복 노드 ID와 상한만 검사합니다.
편집 중인 불완전한 그래프와 아직 정의되지 않은 노드 타입도 초안으로 저장할 수 있습니다.
초안 저장은 `expected_revision`이 현재 값과 같을 때만 성공하고 revision을 하나 올립니다.

발행은 같은 `expected_revision`을 요구하며 다음을 모두 검사합니다.

- 알 수 없는 노드 타입, 타입별 설정, 누락된 연결 대상, 타입에 없는 포트, 같은 포트의 중복 연결
- 트리거 개수, 트리거로 들어오는 연결, 트리거에서 도달할 수 없는 노드
- 입력을 기다리는 노드를 거치지 않는 순환. 지연(`delay`)과 시각 대기(`wait_until`)는 시간만 기다리므로 여기에 해당하지 않습니다. 응답 대기(`wait_for_reply`)는 아래 두 규칙 때문에 순환을 닫을 수 없으므로, 모든 순환을 거부합니다.
- 응답 대기로 들어오는 연결은 메시지 노드의 `next` 포트에서만 올 수 있습니다(`wait_requires_message`).
- 응답 대기에서 도달할 수 있는 메시지 노드가 없어야 합니다(`message_after_wait`). 대기 뒤에는 동작, 조건, 지연, 시각 대기만 둘 수 있습니다.
- 메시지로 가는 경로의 지연 합계가 지연 상한을 넘는지 여부(`delay_exceeds_reply_window`). 시각 대기는 1,560분으로 셉니다.
- 변수 문법과, 작업 공간의 보관되지 않은 필드만 참조하는지 여부, 필드 타입에 맞는 값. 응답 대기의 `save_field_id`는 text 필드여야 합니다(`invalid_field_type`).
- `webhook` 노드의 주소·필드 검사, 그리고 `webhook` 노드와 응답 대기 양쪽에 적용되는 응답 저장 필드 규칙(`reply_field_not_sendable`). 내용은 [외부 전송](2026-10-01-flow-webhook-delivery.md#플로-노드)이 정합니다.
- 트리거 연결이 같은 작업 공간 소유이고 활성인지 여부
- `follows_account`를 쓰면 트리거 연결에 OAuth 자격 증명이 있는지 여부. 환경 변수로 관리하는 연결은 DB만으로 로그인 방식을 알 수 없으므로 거부합니다.
- 같은 연결·게시물에 켜진 기존 댓글 규칙(`legacy_rule_conflict`)이나 보관되지 않은 다른 발행 플로(`flow_trigger_conflict`)가 있는지 여부

발행 검증은 Meta API를 호출하지 않습니다.
따라서 새 댓글 규칙을 만들 때와 달리, 게시물이 해당 계정 소유인지는 발행 시점에 확인하지 않습니다.
발송 스위치, 토큰 유효성, 동의, 상담 전환과 발송 창은 실행 시점의 guard가 계속 판단합니다.
검증에 실패하면 버전을 만들지 않고 `422 {error: "flow_invalid", errors}`를 반환합니다.
각 오류는 `code`, `path`와 해당하는 경우 `node_id` 또는 `edge_index`를 가집니다.

## 저장과 수명 주기

`flows`는 이름, 초안, revision, 현재 발행 버전 포인터와 보관 여부를 가집니다.
`flow_versions`는 발행 시점의 문서, 트리거 연결·게시물, 참조 필드 목록, 발행자와 시각을 가집니다.
버전 번호는 플로마다 1부터 증가합니다.
트리거 연결·게시물과 참조 필드 목록은 발행 시점의 문서에서 추출한 값이며, 버전 행과 함께 바뀌지 않으므로 문서와 어긋날 수 없습니다.
각 버전은 발행한 초안 revision을 기록하고, 같은 revision을 다시 발행하면 새 버전을 만들지 않고 기존 버전을 `200`으로 반환합니다.
새 버전을 만든 발행은 `201`을 반환합니다.
서버 역할은 `flow_versions`를 UPDATE하거나 DELETE할 수 없으므로 발행 버전은 바뀌지 않습니다.
새로 발행하면 포인터만 새 버전으로 옮기고 이전 버전은 남깁니다.
보관하면 포인터를 비우고 초안 수정과 발행을 막으며, 버전 기록은 남깁니다.
작업 공간마다 보관되지 않은 플로는 50개까지 만들 수 있습니다.
켜기·끄기 스위치는 [플로 실행 계약](2026-09-30-flow-runs.md)이 정합니다.

## 동시성과 기존 기능

발행은 플로 행과 트리거 연결 행을 차례로 잠근 뒤 충돌을 검사합니다.
기존 댓글 규칙을 켜는 저장도 같은 연결 행을 잠그고, 보관되지 않은 발행 플로가 같은 게시물을 쓰면 `409 flow_trigger_conflict`로 거부합니다.
규칙을 끄는 저장과 규칙 워커의 동작은 바뀌지 않습니다.
발행은 참조 필드 행을 공유 잠금으로 읽고, 필드 보관은 현재 발행 버전이 그 필드를 참조하면 `409 field_in_use`로 거부합니다.
응답 대기의 `save_field_id`도 참조 필드에 포함됩니다.

## API

모든 요청은 로그인 세션이 필요하고, GET이 아닌 요청은 같은 출처여야 하며, 다른 작업 공간의 플로는 404로 보입니다.
플로 생성과 초안 저장 요청 본문은 문서 상한에 4KB를 더한 69,632바이트까지 받으며, 다른 API는 기존 16,384바이트 상한을 유지합니다.

| 요청                             | 동작                                          |
| -------------------------------- | --------------------------------------------- |
| `GET /api/flows`                 | 보관되지 않은 플로 목록                       |
| `POST /api/flows`                | `{name, draft?}`로 생성                       |
| `GET /api/flows/:id`             | 초안·revision·현재 발행 버전 번호             |
| `PUT /api/flows/:id`             | `{expected_revision, draft, name?}` 초안 저장 |
| `DELETE /api/flows/:id`          | 보관                                          |
| `POST /api/flows/:id/publish`    | `{expected_revision}` 발행                    |
| `GET /api/flows/:id/versions`    | 버전 목록과 현재 버전 표시                    |
| `GET /api/flows/:id/versions/:n` | 버전 문서                                     |

## 편집 화면

[이슈 #30](https://github.com/AndrewDongminYoo/auto-chatter/issues/30)의 두 번째 부분(part B)인 대시보드의 "플로" 영역입니다.
스키마는 바꾸지 않고 위 API와 [테스트 실행](2026-09-30-flow-runs.md#테스트-실행) API만 씁니다. 서버 변경은 테스트 실행이 선택 키 `expected_revision`을 받게 한 것 하나입니다.
빌드 없는 정적 클라이언트이며, 순수 함수(개요, 배치, 문구, 편집 연산)는 `public/app/flow-editor-model.js`, 화면은 `public/app/flow-editor.js`에 있습니다.
`src/app/flow-editor-model.test.ts`가 순수 함수를 `node:vm`으로 실행해 검사합니다.

- 역할: 관리자와 소유자는 목록, 생성, 열기, 초안 편집·저장, 발행, 켜기·끄기, 보관(확인 창)과 테스트 실행을 합니다. 상담원은 목록과 읽기 전용 단계 목록·그래프만 보며, 편집·발행·켜기·테스트 실행 컨트롤이 없고 `admin`이 필요한 요청(외부 전송 주소 목록 포함)을 보내지 않습니다. 상담원 화면의 외부 전송 단계는 주소 이름 대신 "등록한 주소"로 표시합니다.
- 단계 목록: 트리거에서 연결을 따라 표시하고, 포트가 여럿인 단계는 가지(예/아니오, 응답 받음/시간 초과)마다 따로 보여 줍니다. 둘 이상의 연결로 닿는 단계와 순환으로 다시 닿는 단계는 한 번만 전체를 보이고 나머지는 "→ 단계" 링크로 보입니다. 트리거에서 닿지 않는 단계는 "트리거에서 이어지지 않는 단계"에 따로 모읍니다.
- 편집: 빈 자리에 단계 추가, 이미 연결된 포트 앞에 단계 넣기(새 단계의 첫 포트가 원래 다음 단계로 이어집니다), 타입별 설정 양식, 단계 삭제(들어오고 나가는 연결도 지우며, 뒤에 단계가 있으면 확인), 빈 자리를 기존 단계에 연결, 링크 끊기를 제공합니다. 트리거가 없는 초안에는 "댓글 트리거 만들기"만 보이며, 하나뿐인 트리거는 삭제할 수 없습니다. 초안 저장은 트리거 수를 세지 않으므로 API로 저장한 초안에 트리거가 둘 이상일 수 있고, 그때는 어느 트리거든 삭제할 수 있습니다(발행 검증은 `trigger_count`를 반환합니다). 단계 목록은 문서의 첫 트리거에서 시작합니다.
- 제공하는 타입은 `flowExecutionErrors`가 받는 타입뿐입니다(`follows_account`와 메시지 버튼은 제공하지 않습니다). 메시지 뒤에는 응답 대기만, 응답 대기는 메시지 뒤에만 제공하고, 응답 대기 뒤에는 메시지를 제공하지 않습니다. 기존 단계 연결은 순환을 만들거나 같은 규칙을 어기는 대상을 제공하지 않습니다.
- 기다릴 시간과 응답 대기 시간의 기본값(60분, 1,440분)은 새 단계에만 넣습니다. 비우거나 정수가 아니거나 범위를 벗어난 값은 입력한 그대로 저장해 발행 검증이 그 단계를 가리키게 합니다.
- 필드 선택은 작업 공간의 보관되지 않은 필드만 보이며, 응답 저장은 text 필드만 보입니다. 필드 조건과 필드 값 저장 단계에서 필드를 바꾸면, 같은 타입의 필드일 때는 입력한 값을 이어받고 다른 타입이면 그 필드의 기본값(예/아니요는 "예", 나머지는 빈 값)에서 시작합니다. 문서가 목록에 없는 필드나 계정을 가리키면 "사용할 수 없는" 항목으로 남겨 발행 검증이 해당 단계를 가리키게 합니다. 외부 전송 단계의 사용할 수 없는 필드는 선택된 체크박스로 보이며, 선택을 해제하면 단계에서 빠집니다. 트리거의 게시물은 숫자 ID를 직접 입력합니다. 게시물 목록은 Meta API를 부르므로 이 화면에서 쓰지 않습니다.
- 그래프 미리보기는 문서로 만든 인라인 SVG이며, 트리거에서의 최단 깊이로 열을 나누고 트리거에서 닿지 않는 단계는 마지막 열 뒤에 둡니다. 읽기 전용이고 스크린 리더에는 숨기며(`aria-hidden`), 가로로 스크롤되는 자체 영역 안에 있어 페이지가 넘치지 않습니다. 단계 목록이 같은 내용의 접근 가능한 형태입니다.
- 저장은 `expected_revision`을 보냅니다. `409 revision_conflict`이면 화면의 변경 사항을 그대로 두고 다른 곳에서 먼저 저장했다고 알리며, "최신 초안 불러오기"를 누를 때만 변경 사항을 버리고 최신 초안으로 바꿉니다. 저장하지 않은 변경 사항이 있으면 편집기를 닫거나 다른 플로를 열거나 새 플로를 만들 때 확인하고, 페이지를 떠날 때 브라우저 경고를 띄웁니다. 플로 열기가 겹치면 마지막에 연 플로만 보이고, 불러오는 동안 고친 내용이 있으면 바꾸기 전에 다시 확인합니다. 저장 응답과 저장·발행의 충돌 안내는 요청을 보낸 편집기에만 반영하므로, 그 사이 같은 플로를 닫았다 다시 열었거나 최신 초안을 불러왔으면 새 편집기의 리비전과 변경 상태를 바꾸지 않고 충돌 안내도 띄우지 않습니다.
- 발행과 초안 테스트 실행은 저장한 초안으로 하므로, 저장하지 않은 변경 사항이 있으면 발행 버튼을 끄고 초안 테스트 실행을 막습니다. 초안 테스트 실행도 이 편집기의 `expected_revision`을 보내므로, 다른 탭이나 관리자가 그 사이 초안을 저장했으면 서버가 `409 revision_conflict`로 실행하지 않고, 화면은 결과 대신 저장 충돌과 같은 안내와 "최신 초안 불러오기"를 보입니다. 화면에 없는 초안의 결과를 화면의 단계 이름으로 보이지 않기 위해서입니다.
- 발행, 켜기, 테스트 실행의 `422` 오류는 `node_id`가 가리키는 단계 옆에 한국어로 표시합니다. `edge_index`만 있는 오류는 경로가 `.to`로 끝나면 연결의 도착 단계, 아니면 출발 단계에 붙이고, 단계를 가리키지 않는 오류는 위쪽 요약에만 둡니다. 요약은 단계로 이동하는 링크를 가지며 오류가 나면 초점을 받습니다.
- 켜기와 발행 버전 테스트 실행의 오류, 발행 버전 테스트 실행의 결과는 발행 버전 문서(`GET /api/flows/:id/versions/:n`)를 기준으로 읽습니다. 초안을 발행 뒤에 고쳤으면 같은 단계 ID가 다른 단계를 가리킬 수 있으므로, 키 순서를 무시하고 비교해 초안과 내용이 같을 때만 오류를 초안의 단계에 붙이고 경로를 표시합니다. 다르면 오류는 위쪽 요약에 "발행 버전 vN의 2. 태그 추가"처럼 발행 버전의 단계 번호로 두고, 결과의 단계 이름도 발행 버전 기준으로 붙이며, 경로는 표시하지 않고 그 이유를 결과에 적습니다. 발행 버전을 읽지 못하면 결과의 단계는 단계 ID로 표시하고, 오류는 단계를 밝히지 않고 위쪽 요약에 둡니다.
- 요청 중에도 단계 설정은 고칠 수 있으므로, 발행과 초안 테스트 실행의 오류와 결과는 요청을 보낼 때의 초안을 기준으로 위와 같이 다룹니다. 그 사이 초안이 바뀌었으면 경로를 표시하지 않고, 결과의 단계 이름은 그때의 초안 기준으로 붙이며, 오류는 "테스트한 초안의 …" 또는 "발행하려던 초안의 …"로 위쪽 요약에 둡니다.
- 테스트 실행 패널은 댓글 본문, 태그, 고른 필드의 타입별 값, 응답 본문, 응답 대기에서 갈 가지, 출처(저장한 초안 또는 발행 버전)를 받습니다. 결과로 상태와 실패 사유, 지난 단계와 결과, 메시지 본문, 기다림과 이어 간 방법, 태그·필드 변경, 외부 전송 본문 미리보기를 보여 주고, 지난 단계를 단계 목록과 그래프 양쪽에 표시합니다. 연결과 "→ 단계" 링크는 결과의 단계가 기록한 가지로 지난 것만 표시하므로, 두 가지가 같은 단계로 모여도 실행하지 않은 가지는 표시하지 않습니다. 이 표시는 초안이 실행한 문서와 같은 동안만 남고, 이름이 아닌 초안 내용을 고치면 지웁니다. 입력은 저장하지 않으며 `localStorage`·`sessionStorage`도 쓰지 않습니다.
- 모든 컨트롤은 기본 HTML 요소(버튼, 선택, 입력, `details`)이고 레이블을 가지며 키보드로 조작할 수 있습니다. 끌어 놓기는 없습니다.

화면 확인 기록은 [플로 편집기 화면 검증](../notes/2026-10-02-flow-editor-ui-verification.md)에 있습니다.
