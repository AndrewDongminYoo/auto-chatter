# 사용자가 확인한 연락처 식별자 연결·분리 계약

## 상태와 목적

[#25](https://github.com/AndrewDongminYoo/auto-chatter/issues/25)의 제한된 연결 확인·분리 API와 화면을 로컬에서 구현했습니다.
검증 결과와 운영 미검증 경계는 [구현 검증](../notes/2026-10-21-contact-identity-links-verification.md)에 기록합니다.
기준 코드는 PR #240이 병합된 `2724f9fcd989929383e62b677408a2ecf2ce590b`입니다.
운영자가 저장된 공급자 근거를 확인하고 댓글 연락처와 DM 상대의 연결을 명시적으로 기록하거나 해제할 수 있게 합니다.
이번 설계의 ‘병합’은 두 원본 식별자를 보존하는 연결이며, 연락처 행을 한 행으로 바꾸거나 이력을 옮기는 작업이 아닙니다.
사용자가 확인한 연결과 공급자 근거가 있다는 사실을 각각 표시합니다.
이 범위만으로 #25 전체, 여러 계정의 동일인 병합, #26의 전체 의존성 또는 운영 수용을 완료했다고 판단하지 않습니다.

## 직접 확인한 기준

- [기존 식별자 계약](2026-09-27-inbox-handoff-contract.md)과 [공통 조회 구현](../../src/app/inbox-identity.ts)은 같은 작업 공간·연결에서 성공한 공급자 응답과 원본 댓글 작성자가 일치하는 근거를 사용합니다.
- [연락처 상세 계약](2026-10-04-contact-details.md)과 [구현](../../src/app/contact-details.ts)은 확인된 DM 대화를 조회하며, 동의를 식별자별로 나누어 반환합니다.
- [동의 계약](2026-09-29-channel-consent.md)은 식별자·목적별 원장을 유지하고, 동의나 수신 거부를 이름·숫자 일치로 이전하지 않습니다.
- [개인 삭제 계약](2026-09-30-person-data-deletion.md)은 저장된 공급자 근거와 상담 연결을 따라 삭제 범위를 정하고 수신 거부를 보존합니다.
- [수용 현황표](../notes/2026-09-27-manychat-acceptance-matrix.md)는 #51의 청구월 활성 연락처 원장을 미구현으로 기록합니다.
  이번 설계에서 존재하지 않는 청구 원장의 재계산을 구현 완료로 취급하지 않습니다.

## 최소 지원 범위

하나의 작업 공간·Instagram 연결 안에서 댓글 작성자 하나와 저장된 DM 상대 하나를 연결합니다.
식별자 키는 `(workspace_id, connection_id, identity_kind, identity_value)`이며 숫자 문자열을 그대로 보존합니다.
댓글 작성자에게 여러 DM 상대가 연결될 수 있지만, 한 DM 상대의 현재 연결은 하나의 댓글 작성자만 가리킵니다.
여러 댓글 작성자의 결합, 계정·작업 공간·채널을 넘는 연결, CSV로 연결 만들기, 이름·같은 숫자를 이용한 자동 연결은 지원하지 않습니다.
범용 사람 테이블이나 연결 그래프를 추가하지 않고 기존 식별자 위에 확인 기록만 추가합니다.

연결 쓰기는 활성 `admin` 이상 멤버에게 허용하며, 읽기는 기존 연락처 상세와 같은 `agent` 이상으로 제한합니다.
운영자가 확인 버튼을 눌렀다는 사실은 마케팅 수신 동의가 아닙니다.
고객의 새 동의 근거를 수집하거나 동의 쓰기 API를 대신 호출하지 않습니다.

## 확인과 분리의 의미

### 연결 확인

서버는 기존 `verifiedDmRecipientsSql`로 현재 대화가 선택한 댓글 작성자에게 유일하게 연결되는지 검사합니다.
기존 계약과 같이 성공 상태·공급자 메시지 ID·원본 작성자·미래가 아닌 기록 시각·현재 보관 경계·저장 DM의 존재를 확인합니다.
클라이언트는 화면에서 읽은 `evidence_reply_id`를 보내고 서버는 현재 근거 ID와 정확히 대조합니다.
근거가 바뀌었거나 `unmapped`·`stale`·`ambiguous`이면 저장하지 않고 다시 조회하도록 안내합니다.
운영자의 확인만으로 충돌하거나 없는 공급자 근거를 덮어쓸 수 없습니다.

### 연결 분리

분리는 운영자가 확인한 연결의 현재 상태를 `detached`로 바꾸고 감사 이벤트를 추가합니다.
원본 댓글·DM·공급자 응답·상담 근거를 지우거나 ‘서로 다른 사람’이라고 확정하지 않습니다.
따라서 분리 후에도 기존 연락처 상세의 ‘공급자 근거로 확인된 대화’에는 같은 대화가 나타날 수 있습니다.
화면은 두 사실을 구분하고 분리로 수신 거부가 해제되거나 발송 대상이 바뀐다고 안내하지 않습니다.
근거가 사라졌거나 오래돼도 해당 연결의 관리 권한과 버전이 맞으면 분리할 수 있습니다.
이미 분리된 상태로 새 요청을 보내면 충돌을 반환하며, 동일 요청 키의 재시도만 이전 성공으로 처리합니다.

### 근거의 유효성과 확인 이력

저장 상태는 `confirmed` 또는 `detached`이며, 현재 공급자 근거의 유효 여부는 조회할 때 별도로 계산합니다.
확인 이후 근거가 사라지거나 충돌해도 확인 이력을 자동 수정하지 않습니다.
`confirmed`이면서 현재 근거가 유효하지 않은 기록은 과거 확인으로만 표시하고 재확인 전에는 현재 유효한 연결로 집계하지 않습니다.
근거 유효성은 조회 시점의 사실이며 이후에도 유효하다는 보장이 아닙니다.

## 저장과 API

마이그레이션 `062_contact_identity_links.sql`과 현재 스키마에 아래 저장 구조를 반영했습니다.

- `instagram_contact_identity_links`는 `(workspace_id, connection_id, recipient_id)`를 기본 키로 사용합니다.
  `sender_id`, 상태, 양의 정수 `version`, 현재 근거 답장 ID, 마지막 이벤트 ID와 변경 시각을 저장합니다.
  작업 공간·연결의 복합 외래 키를 두고, 식별자 문자열에는 기존 숫자 1–40자 제한을 적용합니다.
- `instagram_contact_identity_link_events`는 변경 전후 작성자·상태·버전, 작업 종류, 운영자 ID, 서버 기록 시각, 확인 당시 근거 답장 ID와 `request_key`를 저장합니다.
  `(workspace_id, request_key)`는 유일하며 요청 내용도 대조할 수 있게 보관합니다.
  자유 입력 사유, 고객 원문, 자격 증명은 저장하지 않습니다.
  일반 API로 이벤트를 수정하거나 삭제하지 않지만 개인정보 삭제 경로는 아래 기준으로 제거합니다.
- 근거 답장 ID를 현재 존재하는 행의 영구 외래 키로 강제하지 않습니다.
  작성 시 서버가 동일 범위의 근거를 검증하고, 이후 근거 삭제가 원본 데이터 삭제를 막지 않게 합니다.
  조회에서 근거가 없으면 유효하지 않은 상태로 표시합니다.
- `GET /api/connections/:connectionId/contacts/:senderId/identity-links`는 저장된 확인·분리 기록과 현재 근거 유효성을 반환합니다.
  해당 연락처의 저장 기록과 현재 공급자 근거로 확인된 후보를 합쳐 DM 상대의 텍스트 오름차순으로 50개씩 반환하며, `after` 커서는 작업 공간·연결·작성자에 묶습니다.
  응답의 `can_edit`는 조회 시 서버가 확인한 멤버십으로 계산합니다.
  후보가 다른 작성자의 현재 행에 연결돼 있으면 버전과 확인 차단 여부만 반환하며, 그 작성자·상태·과거 근거·감사 이력은 공개하지 않습니다.
- `POST /api/connections/:connectionId/contacts/:senderId/identity-links/:recipientId`는 `action` (`confirm` 또는 `detach`), `request_key`, `expected_version`을 받습니다.
  `confirm`만 필수 `evidence_reply_id`를 받고, `detach`에 이 필드가 오면 거부합니다.
  없는 현재 행은 버전 0으로 취급하고 성공 시 버전을 1 증가시킵니다.
  다른 작성자의 `confirmed` 행이 있으면 거부하며, 먼저 기존 연결을 분리해야 합니다.
  분리된 행을 새 작성자로 확인할 때도 현재 버전을 확인하고 새 근거를 검증합니다.
- 새 연결 API만 기존 응답에 더하며 `contactDetails`, 인박스 문맥과 기존 CSV의 공개 응답 형식은 바꾸지 않습니다.
  성공 응답은 적용한 이벤트와 현재 행을 구분합니다.
  오래된 성공 요청의 재시도는 과거 이벤트를 반환하되 현재 상태를 과거 상태로 되돌리지 않습니다.

기존 세션·동일 출처 쓰기 검사와 `Cache-Control: no-store`를 적용합니다.
미인증은 401, 권한 부족은 403, 소유하지 않은 연결 또는 존재하지 않는 대상은 동일한 404로 처리합니다.
잘못된 요청은 400, 버전·상태·근거 변경 또는 요청 키 내용 충돌은 409입니다.
분리 요청에서는 현재 저장 행의 존재로 대상을 확인하므로 원본 댓글이나 DM이 사라진 기록도 정리할 수 있습니다.
오류 응답에 다른 작업 공간의 존재나 식별자를 포함하지 않습니다.

## 트랜잭션과 동시성

쓰기 한 트랜잭션 안에서 기존 `lockWorkspaceForMember`로 작업 공간을 잠그고 관리자 멤버십을 다시 확인합니다.
그다음 소유한 연결 행을 `FOR NO KEY UPDATE`로 잠근 뒤 현재 연결 행과 버전을 확인합니다.
동일 연결의 확인·분리와 기존 개인·연결 삭제 경로를 직렬화합니다.
멤버십 변경과의 경합은 기존 역할 쓰기 규칙에 맞춰 처리하고 실제 DB 테스트로 확인합니다.
요청 키가 이미 있으면 인증·소유권 확인 뒤 동일 요청인지 검사하며, 성공 당시의 근거가 사라져도 동일한 성공 요청은 재적용하지 않습니다.
새 요청에 대해서만 현재 근거를 검사하고 이벤트 삽입·현재 행 갱신을 함께 커밋합니다.
중간 오류는 둘 다 롤백하며 유일 제약과 버전 조건을 생략하지 않습니다.
동시에 새 공급자 근거가 기록될 수 있으므로 연결 잠금만으로 공급자 사실 전체를 고정했다고 주장하지 않습니다.
후속 읽기는 현재 근거를 다시 계산하며, 이 확인 기록을 발송 guard에 입력하지 않습니다.

## 원장과 재계산 정책

| 대상                         | 확인·분리의 영향                                                                                                                          |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 동의 이벤트와 현재 동의 상태 | 원래 식별자·목적에 남깁니다. 허용·철회를 복사하거나 새 동의 이벤트를 만들지 않습니다.                                                     |
| 자동화·수동 답장·상담 중지   | 기존 키와 공급자 근거를 계속 사용합니다. 수동 확인 기록을 guard에 연결하지 않으며 분리로 중지나 수신 거부를 해제하지 않습니다.            |
| 태그·필드·댓글·DM            | 원본을 옮기거나 합치지 않습니다. 값 충돌 해결이나 대표 이름 선정은 이번 범위에 없습니다.                                                  |
| 세그먼트·CSV·고정 명단       | 기존 댓글 작성자 기준을 유지합니다. 필터 대상 수와 과거 스냅샷을 사람 수로 다시 계산하지 않습니다.                                        |
| 확인된 연결 수               | 현재 행이 `confirmed`이고 현재 공급자 근거도 일치하는 쌍만 조회 시 계산합니다. 별도 집계 캐시나 재계산 작업을 만들지 않습니다.            |
| 발송·플로·상담 리포트        | 기존 이벤트·요청 단위 집계를 유지합니다. 분리로 과거 성공·실패·진행 중 기록을 수정하지 않습니다.                                          |
| 청구월 활성 연락처 원장 #51  | 후속 계약에서 원본 활동과 적용 버전·기간 경계를 먼저 정의해야 합니다. 이번 연결만으로 과거 청구를 소급 할인하거나 추가 청구하지 않습니다. |

이는 #25의 제한된 재계산 정책이며 청구 원장이나 다중 계정 사람 단위 집계의 구현을 대신하지 않습니다.

## 삭제·내보내기·접근 제어

새 테이블은 구현 첫 PR부터 작업 공간 내보내기 분류, RLS·서버 역할 권한, 연결·작업 공간 삭제와 함께 반영합니다.
개인 삭제가 기존 규칙으로 확정한 작성자 또는 상대 중 하나라도 포함된 현재 연결 행과 감사 이벤트를 지웁니다.
이때 연결 행을 지웠다고 상대편 원본까지 삭제 범위를 확장하지 않습니다.
수동 연결은 삭제 범위를 결정하는 새 근거가 아니며, 기존 공급자·상담 연결에 의한 삭제와 수신 거부 보존은 그대로 유지합니다.
다른 작성자로 재연결된 상대의 과거 이벤트도 현재·이전 작성자와 상대 식별자 기준으로 검사해 대상자의 정보가 남지 않게 합니다.
삭제할 이벤트를 마지막 이벤트로 참조하는 현재 행도 함께 제거하지만, 상대편 원본으로 삭제 범위를 확장하지 않습니다.
삭제 건수를 기존 증적에 포함하되 삭제 증적에 원본 식별자를 추가하지 않습니다.

두 테이블 모두 연결 외래 키를 통해 작업 공간에 종속되므로 연결이 없는 빈 작업 공간에 독립적으로 남을 수 없습니다.
두 빈 작업 공간 이동 검사에서 이 전제가 유지되는지 검증하며, 필요 없이 새 분기나 범용 검사기를 추가하지 않습니다.
일반 연락처 CSV의 컬럼은 유지하고, 새 기록은 관리자용 작업 공간 내보내기에서 기존 개인정보·운영자 필드 노출 정책에 맞게 분류합니다.

## 수용 기준

1. 다른 작업 공간·연결, 같은 숫자·이름, 없는 원본, 오래된·미래·모호한 근거로 연결할 수 없습니다.
2. 현재 유효한 근거와 명시적인 관리자 확인이 모두 있을 때만 새 확인 이벤트와 현재 행이 생깁니다.
3. 동일 요청 재시도는 이벤트를 늘리지 않으며, 다른 내용의 요청 키 재사용과 오래된 버전은 409입니다.
4. 동시 확인·분리 중 한 버전의 변경만 성공하며 감사 기록과 현재 행이 일치합니다.
5. 근거 유실 후 분리와 재시도가 가능하고, 기존 공급자 문맥은 분리로 사라지지 않습니다.
6. 확인·분리 전후 동의·수신 거부·대기 발송·태그·필드·세그먼트·고정 명단·리포트 값이 이 작업 때문에 바뀌지 않습니다.
7. 개인·연결·작업 공간 삭제 및 내보내기에서 새 기록을 빠뜨리지 않으며 API 역할은 직접 읽거나 쓸 수 없습니다.
8. 화면은 운영자 확인과 현재 공급자 근거를 구분하고, 확인·분리가 동의·발송 허가가 아님을 설명합니다.
