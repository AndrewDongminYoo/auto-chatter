# 선택 활성화하는 Instagram 수신 인박스

## 목표와 계약

연결 계정의 관리자가 인박스를 선택 활성화하고 이후 받은 텍스트 DM과 확인 버튼 응답을 읽을 수 있게 합니다.
기존 수동 삭제 정책을 적용하며 원격 과거 메시지를 수집하지 않습니다.
기본값은 꺼짐이고 활성화 시각 이전 이벤트는 저장하지 않습니다.
수신 중지·연결 해제는 새 저장을 막지만 보관한 메시지는 소유한 작업 공간에서 계속 열람할 수 있습니다.
비활성화 후 재활성화하면 새 활성화 시각부터 저장합니다.

대화 식별자는 작업 공간·연결·DM 작성자 ID입니다.
댓글 작성자 ID와 같다고 추정하거나 태그·팔로우·동의 정보를 연결하지 않습니다.
기존 확인 응답 처리는 동일하게 유지하고 인박스 저장은 발송이나 확인 처리의 근거가 되지 않습니다.
본문은 로그에 기록하지 않고 화면에서 텍스트로 렌더링합니다.
계정 설정 변경은 인증과 같은 출처 검사를 거쳐 정확한 boolean 본문만 받습니다.

## 범위와 비목표

이번 회차는 수신 텍스트·확인 버튼 응답 저장, 대화·메시지 페이지 조회, 계정별 보관 스위치와 화면을 구현합니다.
첨부·echo·수정·삭제 메시지, 과거 가져오기, 발신 이력, 수동 발송, 팀 역할·배정·내부 메모와 운영 배포는 후속 범위입니다.
이는 공유 인박스의 수신 기반이며 전체 공유 인박스 완료를 의미하지 않습니다.
대화 담당자와 열림·완료 상태는 [#22 계약](2026-10-01-inbox-conversation-assignment.md)이 더하며, 새로 저장한 DM은 완료한 대화를 다시 엽니다.
검색·필터·멤버별 읽음 상태는 아래 [검색, 필터와 읽음 상태](#검색-필터와-읽음-상태)가 더합니다([#23](https://github.com/AndrewDongminYoo/auto-chatter/issues/23)의 첫 부분).
같은 이슈의 라벨·내부 메모(#23-B)는 [라벨·메모 계약](2026-10-03-inbox-labels-notes.md)이 더하고, 리마인더(#23-C)는 다음 회차에서 다룹니다.

## 검색, 필터와 읽음 상태

[#23](https://github.com/AndrewDongminYoo/auto-chatter/issues/23)의 첫 부분입니다.
운영자가 2026-10-03 정한 대로 읽음 상태는 멤버마다 따로 두고, 대화 목록은 마지막 메시지가 최근인 순서로 보이며, 서버와 화면을 한 PR에서 냅니다.
PR #126과 migration 032는 2026-10-03 `main` 커밋 `b227782`으로 운영 DB에 적용하고 배포했습니다([운영 기록](../notes/2026-09-26-cloudflare-runbook.md)). 운영에는 여러 멤버가 없고 저장한 DM이 적어, 검색·필터·읽음 표시를 운영 데이터로 조작하지 않았습니다.

### 대화 목록

`GET /api/inbox`는 대화를 마지막 메시지 시각이 최근인 것부터 돌려줍니다.
시각이 같으면 연결 ID, 수신자 ID 오름차순입니다.
다음 페이지 커서(`after`)는 이 세 값으로 만든 불투명한 값이며, 시각은 PostgreSQL이 저장하는 마이크로초 정밀도 그대로 담아 같은 밀리초 안의 대화도 건너뛰거나 겹치지 않습니다.
이전 키 순서의 커서는 `400`입니다.
페이지를 넘기는 사이 새 DM을 받은 대화는 맨 앞으로 옮겨 가므로 다음 페이지에 다시 나오지 않고, 처음부터 다시 불러와야 보입니다.

필터는 서로, 그리고 기존 `connection_id`와 함께 쓸 수 있습니다.

- `status`: `open` 또는 `closed`. 상태 행이 없는 대화는 열림입니다.
- `assignee`: `me`, `none`(미배정), 또는 멤버의 사용자 UUID. UUID 필터는 모든 역할이 쓸 수 있으며, 목록이 이미 담당자를 보여 주므로 새로 드러나는 정보는 없습니다. 화면은 멤버 선택지를 관리자에게만 보입니다.
- `unread=true`: 호출한 멤버가 아직 읽지 않은 메시지가 있는 대화만.
- `q`: 저장한 DM 본문(`instagram_inbox_messages.text`, 텍스트와 확인 버튼 응답)에서 대소문자를 구분하지 않고 글자 그대로 찾습니다. `%`, `_`, `\`도 특별한 뜻 없이 그 글자로 찾습니다. 1자에서 100자(코드 포인트 기준)까지이며, 앞뒤 공백을 서버가 지우지 않습니다.

모르는 키, 같은 키의 반복, 형식이 틀린 값은 `400 invalid_inbox_query`입니다.
`q`와 `unread`는 어떤 대화를 보일지만 정하고, 각 대화의 `message_count`, `last_message_at`, 정렬 순서는 그 대화의 모든 메시지 기준입니다.
각 대화에는 호출한 멤버의 `unread_count`와 그 수를 센 기준인 호출한 멤버의 읽은 위치 `last_read_message_id`(읽은 적이 없으면 `null`)가 붙습니다.

검색에는 확장이나 새 색인을 쓰지 않습니다.
대화를 마지막 메시지가 최근인 순서로 보이려면 대화마다 가장 최근 메시지를 알아야 하므로, 목록은 검색어와 필터가 없어도 요청마다 작업 공간에 저장한 DM 전체를 읽어 대화별로 묶습니다.
이전의 연결·수신자 순 목록은 `instagram_inbox_messages_conversation_idx` 색인을 따라 51개 대화를 채우면 멈췄으므로, 한 요청이 읽는 메시지 행 수가 페이지만큼에서 작업 공간의 DM 전체로 늘었습니다.
2026-10-03 로컬 PostgreSQL 17에서 대화 20,000개와 메시지 200,000건으로 첫 페이지를 `EXPLAIN ANALYZE`로 비교하자, 이전 쿼리는 메시지 521행을 읽었고 새 쿼리는 200,000행을 모두 읽었습니다.
실행 시간은 두 번 측정에서 이전 쿼리가 1.4ms 이하, 새 쿼리가 약 41ms였습니다.
운영 규모의 한계는 측정하지 않았으며, 목록이 느려지면 색인이나 집계 테이블을 다시 검토합니다.

### 읽음 상태

`instagram_inbox_read_state`(migration 032)는 작업 공간·연결·수신자·멤버마다 읽은 위치(`last_read_message_id`, 인박스 메시지 ID)와 그 위치가 마지막으로 앞으로 간 시각(`read_at`)을 둡니다.
행이 없는 대화는 모든 메시지가 읽지 않음입니다.
읽은 위치는 메시지 행을 가리키는 외래 키가 없는 단순한 최고 기록이고, 쓸 때 API가 그 대화의 메시지인지 확인합니다.
멤버 ID에도 외래 키가 없으며, 모든 읽기와 쓰기가 제거되지 않은 멤버인지 확인합니다.
제거된 멤버의 행은 삭제 함수가 지울 때까지 남습니다.

읽은 위치가 ID 최고 기록이므로, 한 대화의 DM은 ID 순서대로 커밋되어야 합니다([#127](https://github.com/AndrewDongminYoo/auto-chatter/issues/127)).
인박스 메시지 ID는 INSERT가 할당하므로, DM 수집은 배치의 첫 INSERT 전에 저장될 수 있는 대화마다 대화 잠금을 배타로 잡고 커밋까지 쥡니다(`lockInboxConversations`).
그래서 같은 대화로 DM 두 건이 동시에 들어오면 두 번째 DM은 첫 번째가 커밋된 뒤에야 ID를 받고, 그 사이 읽음으로 표시한 위치가 아직 보이지 않던 더 작은 ID를 건너뛰지 않습니다.
잠금 순서와 다른 대화의 DM이 서로 기다리지 않는다는 규칙은 [대화 배정 명세](2026-10-01-inbox-conversation-assignment.md#자동-변경)에 있습니다.
이전에는 ID를 받은 뒤에 대화 잠금을 공유로 잡았기 때문에, 늦게 커밋된 작은 ID 메시지가 읽은 것으로 세어져 배지가 붙지 않고 `unread=true`에서도 빠질 수 있었습니다.

`POST /api/inbox/conversations/<connection>/<recipient>/read`는 본문 `{"message_id": "<ID>"}`로 호출한 멤버의 읽은 위치를 그 메시지까지 옮기고 `{last_read_message_id, read_at, unread_count}`를 돌려줍니다.
ID는 그 작업 공간의 그 대화에 저장된 인박스 메시지여야 하며, 아니면 `404 message_not_found`입니다(연결이 다른 작업 공간이면 `404 connection_not_found`).
더 낮거나 같은 ID는 아무것도 바꾸지 않고 현재 위치를 돌려주므로, 읽은 위치는 뒤로 가지 않습니다.
응답의 위치와 `unread_count`는 쓰기를 커밋한 뒤에 한 번에 읽으므로, 이전 위치를 보인 목록 응답보다 나중 시점의 수입니다.
그 사이 삭제 함수가 대화를 지웠으면 위치는 `null`입니다.
최소 역할은 `agent`이고, 다른 `/api/*` 쓰기처럼 같은 출처여야 합니다.
형식이 틀린 본문, 다른 키, 쿼리 문자열은 `400 invalid_read_request`입니다.

쓰기는 대화 상태 변경(`PUT .../state`)과 같은 순서로 잠급니다: 작업 공간 행 `FOR SHARE`, 호출한 멤버의 `workspace_members` 행 `FOR SHARE`(그 잠금 아래에서 `removed_at`을 다시 확인), 연결 행 `FOR SHARE`, 그다음 행 쓰기입니다.
`delete_workspace_data`는 작업 공간 행을 `FOR UPDATE`로 먼저 잡고 `removeMember`는 작업 공간 행 다음에 멤버 행을 잡으므로, 읽음 쓰기와 서로 기다릴 뿐 교착되지 않습니다.
먼저 커밋한 멤버 제거는 읽음 쓰기를 `403 workspace_required`로 거절하고, 먼저 커밋한 연결·사람·작업 공간 삭제 뒤에는 읽음 행이 남지 않습니다.

세 삭제 함수가 읽음 행을 지웁니다: 연결 삭제는 그 연결의 모든 행, 사람 삭제는 찾아낸 DM 수신자의 모든 멤버 행, 작업 공간 삭제는 작업 공간의 모든 행입니다.
작업 공간 내보내기는 이 테이블을 그대로 내보냅니다.
읽음 상태는 발송, 확인 처리, 상담 전환, 자동화 중지, 대화 상태와 담당자를 바꾸지 않습니다.

### 화면

인박스 위에 받은 DM 검색 상자와 계정·상태·담당자 선택, "안 읽은 대화만" 체크박스가 있습니다.
담당자 선택은 전체·나·미배정이며, 관리자와 소유자에게는 `/api/inbox/assignees`의 다른 멤버도 보입니다. 상담원은 이 목록을 요청하지 않습니다.
대화 목록의 각 대화에는 읽지 않은 메시지가 있을 때 "안 읽음 N" 배지가 글자로 붙습니다.
대화를 열거나 새로고침하면 불러온 가장 최근 메시지까지 읽음으로 표시하고, 목록을 다시 불러오지 않고 그 대화의 배지만 바꿉니다.
목록 응답과 읽음 응답이 엇갈려 도착하면 화면은 더 높은 읽은 위치를 기준으로 센 수를 보이고, 같은 위치를 기준으로 센 두 수 중에서는 큰 수를 보입니다.
이전 메시지를 더 불러오는 것은 읽은 위치를 바꾸지 않습니다.

## 수락 기준

1. 꺼짐·수신 중지·미연결·활성화 전 이벤트는 인박스에 본문을 남기지 않습니다.
   인박스와 별개로, 플로의 응답 대기가 `save_field_id`로 지정한 필드에 응답을 저장하는 경우([#107](https://github.com/AndrewDongminYoo/auto-chatter/pull/107), [응답 대기](2026-09-30-flow-runs.md#응답-대기))와 발송 기록 전에 도착한 응답을 연결을 위해 임시로 남기는 경우([#108](https://github.com/AndrewDongminYoo/auto-chatter/issues/108), [발송 기록 전에 도착한 응답](2026-09-30-flow-runs.md#발송-기록-전에-도착한-응답))는 인박스 설정과 관계없이 본문을 저장합니다.
2. 같은 message ID를 재생해도 한 행만 저장하고 역순 이벤트가 최신 메시지 시각을 되돌리지 않습니다.
3. 다른 작업 공간은 설정·대화·본문을 조회하거나 수정할 수 없습니다.
4. 대화는 마지막 메시지 시각이 최근인 것부터(같으면 계정·수신자 ID 순서로) 안정적으로, 메시지는 최신 수신 기록부터 페이지를 조회합니다.
   처음에는 계정·수신자 ID 순서였고, [#23](https://github.com/AndrewDongminYoo/auto-chatter/issues/23)에서 [최근 메시지 순서](#대화-목록)로 바꿨습니다.
5. 중복 확인 응답·버튼·팔로우 흐름의 기존 계약은 유지합니다.
6. RLS와 DML 서버 역할에 새 테이블을 포함하고 DELETE 권한을 추가하지 않습니다.
7. 실제 브라우저에서 선택·더 보기·실패·늦은 응답·로그아웃과 모바일 폭을 확인합니다.
8. 공개 문구는 선택 활성화한 계정에서만 인박스에 DM 본문을 보관한다는 구현과 일치합니다.
   1번의 두 예외(플로가 저장하도록 지정한 응답, 연결을 위해 임시로 보관하는 응답)도 공개 문구에 적습니다.

## 근거와 선례

현재 계약은 `src/instagram/message-events.ts`, `src/instagram/follow-flow.ts`, `src/app/settings.ts`, `db/schema.sql`과 공개 개인정보 문구에서 확인했습니다.
개인 계정 auto-chatter의 DM retention/inbox Oracle 조회는 `[no precedent found]`이며 Wiki freshness는 확인되지 않았습니다.
2026-09-27 [Meta Send API](https://www.postman.com/meta/instagram/folder/uxudqu0/send-api)는 일반 발송에 상대방의 선대화와 메시지 권한을 요구합니다.
수신 조회는 수동 발송 자격을 부여하지 않습니다.
