# 작업 공간 역할·초대와 서버 권한 검사

## 범위

[이슈 #21](https://github.com/AndrewDongminYoo/auto-chatter/issues/21)의 계약입니다.
첫 구현(PR #96, migration 022)은 한 작업 공간에 여러 멤버가 역할을 가지고 참여하도록 저장 구조를 바꾸고, 모든 작업 공간 API가 서버에서 역할을 검사하게 했습니다.
두 번째 구현(migration 024)은 초대, 멤버 제거, 역할 변경과 소유자용 멤버 화면을 더합니다.
역할에 따라 다른 설정 버튼을 숨기는 화면 정리는 포함하지 않습니다.

## 역할과 저장

`workspace_members.role`은 `owner`, `admin`, `agent` 중 하나입니다.
migration 022는 기존 멤버를 모두 `owner`로 두고, 작업 공간당 멤버를 한 명으로 제한하던 고유 제약을 없앱니다.
작업 공간마다 소유자는 한 명까지만 둘 수 있고, 한 사용자는 여전히 한 작업 공간에만 속합니다.
`POST /api/workspace`로 새 작업 공간을 만든 사용자와 `deploy/assign-workspace-owner.sql`로 지정한 사용자는 소유자가 됩니다.
소유자 지정 스크립트는 다른 소유자가 있는 작업 공간과, 다른 멤버가 남아 있는 이전 작업 공간에서의 이동을 거부합니다.

## 권한

| 작업                                 | owner | admin | agent |
| ------------------------------------ | ----- | ----- | ----- |
| 인박스·대화 맥락 조회                | 가능  | 가능  | 가능  |
| 상담 전환·수동 답장                  | 가능  | 가능  | 가능  |
| 연락처 조회·태그·필드 값·자동화 중지 | 가능  | 가능  | 가능  |
| 수신 동의·거부 기록                  | 가능  | 가능  | 가능  |
| 연결·규칙·플로·필드·세그먼트 조회    | 가능  | 가능  | 가능  |
| 규칙·플로·필드·세그먼트 변경         | 가능  | 가능  | 불가  |
| 계정 연결·해제·발송 스위치           | 가능  | 가능  | 불가  |
| 인박스 보관 켜기·끄기                | 가능  | 가능  | 불가  |
| 연결 데이터 삭제·삭제 기록 조회      | 가능  | 가능  | 불가  |
| 작업 공간 내보내기                   | 가능  | 가능  | 불가  |
| 멤버 초대·제거·역할 변경             | 가능  | 불가  | 불가  |

청구 기능은 아직 없으므로 권한을 정하지 않았습니다.
권한이 부족하면 `403 {error: "role_forbidden"}`, 멤버가 아니면 기존처럼 `403 {error: "workspace_required"}`를 반환합니다.
다른 작업 공간의 자원은 기존처럼 404로 보입니다.

## 초대

소유자는 설정의 멤버 영역에서 이메일과 역할(`admin` 또는 `agent`)을 정해 초대 링크를 만듭니다.
메일은 보내지 않으며, 소유자가 링크를 복사해 직접 전달합니다.
링크는 `/app/#invite=<토큰>` 형식이고, 토큰은 URL 조각에 있어 서버 로그와 Referer로 전달되지 않습니다.
서버는 32바이트 난수 토큰의 SHA-256만 `workspace_invites`에 저장하고, 링크는 만들 때 한 번만 반환합니다.
초대는 7일 뒤 만료되고, 한 번만 쓸 수 있으며, 소유자가 취소할 수 있습니다.
같은 이메일로 다시 초대하면 이전의 열린 초대를 취소하고, 이미 멤버인 이메일은 `409 already_member`로 거부합니다.
작업 공간마다 만료되지 않은 열린 초대는 20개까지 둘 수 있습니다(`409 invite_limit_reached`).

`POST /api/invites/accept`는 로그인해 이메일 인증을 마친 사용자의 이메일이 초대 이메일과 같을 때만 성공합니다.
이메일은 앞뒤 공백을 지우고 소문자로 비교하며, 다르면 `403 invite_email_mismatch`를 반환하고 초대를 쓰지 않습니다.
사용한 초대는 `409 invite_used`, 취소한 초대는 `410 invite_revoked`, 만료한 초대는 `410 invite_expired`, 없는 토큰은 `404 invite_not_found`입니다.
앱은 처음 로그인할 때 작업 공간을 만들므로, 자신만 있고 연결·규칙·플로·필드·필터·열린 초대·진행 중인 OAuth가 없는 작업 공간에서는 옮겨 갈 수 있습니다.
그 밖의 작업 공간에 속해 있으면 `409 workspace_not_empty`로 거부합니다.
수락은 이전 작업 공간 행을 `FOR UPDATE`로 잠근 채 비어 있는지 확인합니다. Instagram 연결 콜백은 공급자 호출 뒤 같은 행을 `FOR SHARE`로 잠그고 멤버십을 다시 확인한 트랜잭션에서 연결을 저장하므로, 콜백 도중 초대를 수락하면 콜백이 `403 workspace_required`로 끝나고 떠난 작업 공간에 연결이 남지 않습니다.
빈 작업 공간을 채울 수 있는 플로·연락처 필드·필터·초대 생성과 Instagram 연결 시작(OAuth state 저장)도 같은 행을 `FOR UPDATE`로 잠근 뒤 같은 트랜잭션에서 멤버십과 역할을 다시 확인하므로(`lockWorkspaceForMember`), 수락이 먼저 커밋되면 `403 workspace_required`로 거부됩니다.
화면은 400·403·404·409·410 같은 확정적인 거부에서만 보관한 초대 토큰을 지우고, 네트워크 오류·세션 만료·요청 제한·서버 오류에서는 토큰을 유지해 다음 로드나 로그인에서 다시 수락합니다.
화면은 링크의 토큰을 탭의 세션 저장소에 두었다가 로그인 뒤 작업 공간을 불러올 때 수락하고, 거부되면 토큰을 지웁니다.
새로 가입한 사용자는 인증 메일이 다른 탭에서 열리므로 인증 뒤 초대 링크를 다시 열어야 합니다.

## 멤버 관리

소유자만 멤버와 열린 초대를 조회하고, 초대를 만들고 취소하고, 다른 멤버의 역할을 바꾸고, 멤버를 제거합니다.

| 요청                                     | 동작                                 |
| ---------------------------------------- | ------------------------------------ |
| `GET /api/workspace/members`             | 제거되지 않은 멤버의 이메일·역할     |
| `PATCH /api/workspace/members/:user_id`  | `{role}`로 `admin`·`agent` 사이 변경 |
| `DELETE /api/workspace/members/:user_id` | 멤버 제거                            |
| `GET /api/workspace/invites`             | 열린 초대 목록(토큰 제외)            |
| `POST /api/workspace/invites`            | `{email, role}`로 초대 링크 생성     |
| `DELETE /api/workspace/invites/:id`      | 초대 취소                            |

소유자는 자신을 바꾸거나 제거할 수 없고(`cannot_change_self`), 소유자 행은 바꿀 수 없습니다(`cannot_change_owner`).
서버 역할에는 DELETE 권한이 없으므로 제거는 `removed_at`과 `removed_by`를 기록하고, 모든 멤버십 조회가 제거된 행을 제외합니다.
제거된 사용자는 다음 요청부터 `403 workspace_required`를 받고, 새 초대를 수락하거나 새 작업 공간을 만들 수 있으며 이때 같은 행을 다시 씁니다.
제거된 소유자는 둘 수 없고, 소유자는 제거되지 않은 멤버 가운데 한 명뿐입니다.
멤버 목록의 이메일은 수락할 때와, 앱이 작업 공간을 불러올 때 로그인 이메일로 기록합니다.

## 검사 방식

`src/app/settings.ts`의 `workspaceFor`는 필요한 최소 역할을 필수 인자로 받으므로, 작업 공간 API마다 권한이 코드에 드러나고 누락은 타입 검사에서 실패합니다.
멤버십과 역할은 요청마다 DB에서 읽으므로, 역할을 낮추거나 멤버를 제거하면 그 변경이 커밋된 뒤의 다음 요청부터 적용됩니다.
검사를 통과한 뒤 진행 중인 요청은 역할 변경과 같은 트랜잭션으로 묶이지 않으므로 끝까지 실행될 수 있습니다.
Supabase 세션 자체는 만료 전까지 유효하지만, 제거된 멤버는 작업 공간 API를 쓸 수 없습니다.
작업 공간 내보내기는 자체 스냅샷 안에서 멤버십과 역할을 함께 읽어 관리자 이상만 허용합니다.
`POST /api/workspace`는 호출자의 작업 공간 ID와 역할을 반환하며, 화면은 소유자에게만 멤버 영역을 보입니다.
화면은 아직 다른 설정 버튼을 역할에 따라 숨기지 않으므로, 상담원이 관리 동작을 누르면 서버의 거부 응답이 표시됩니다.

## 운영 적용

migration 022는 관리자 migration 러너에 포함됩니다.
2026-09-30 운영 DB에 migration 022를 적용하고 이 계약을 포함한 Worker를 배포했습니다. 적용 결과와 권한 조회는 [운영 적용 기록](../notes/2026-09-26-cloudflare-runbook.md)에 있습니다.
운영 작업 공간에는 소유자만 있으므로 상담원·관리자 권한은 운영 데이터로 확인하지 않았습니다.
migration 024(초대와 멤버 관리)는 운영 DB에 적용하지 않았습니다.
