# 연결 단위 데이터 삭제와 삭제 증적

## 범위

[이슈 #58](https://github.com/AndrewDongminYoo/auto-chatter/issues/58)의 첫 구현 범위입니다.
작업 공간 멤버는 연결을 해제한 Instagram 계정의 운영 기록을 한 번에 삭제할 수 있고, 서비스는 개인정보가 없는 삭제 증적을 남깁니다.
사람 단위 삭제, 대시보드 삭제 화면, 작업 공간·로그인 계정 전체 삭제와 데이터 내보내기는 하위 이슈에서 다룹니다.
앱 사용자가 아닌 Instagram 이용자의 삭제 요청은 기존처럼 이메일로 받고 운영자가 확인한 뒤 수동으로 처리합니다.
Meta 앱 설정의 사용자 데이터 삭제 URL과 App Review 제출 내용은 바꾸지 않습니다.

## 본인 확인

요청자는 로그인 세션이 있는 작업 공간 멤버여야 하며, 다른 작업 공간의 연결은 404로 보입니다.
요청 본문의 `confirm_account_id`는 삭제할 연결의 Instagram 계정 ID와 정확히 같아야 합니다.
연결은 먼저 해제되어 있어야 합니다. 즉 비활성, 발송 꺼짐, 저장된 토큰 없음 상태여야 하며, 그렇지 않으면 `409 connection_active`를 반환합니다.
비공개 답장, 팔로우 후속 메시지, 수동 답장 가운데 `sending` 상태인 행이 있으면 `409 sending_in_progress`를 반환합니다.

## 삭제하는 기록

한 트랜잭션에서 해당 연결의 다음 기록을 삭제합니다.

- 수동 답장과 감사 기록, 상담 전환과 이력
- 보관한 수신 DM과 확인 버튼 응답, 확인 메시지 수신 기록
- 연락처 자동화 중지 상태, 태그, 필드 값
- 팔로우 대화, 비공개 답장 outbox, 댓글 이벤트
- 플로 실행과 실행 단계 기록(migration 021부터)
- 동의 기록 중 허용(grant) 상태와, 현재 상태가 참조하지 않는 허용 이벤트

대기 중이거나 실패한 발송도 함께 삭제되므로 나중에 같은 계정을 다시 연결해도 재발송되지 않습니다.

## 보관하는 기록

- 수신 거부(revoke) 이벤트와 현재 상태: 같은 사람에게 다시 발송하지 않기 위해 보관합니다.
- DM 수신자 ID로 기록된 수신 거부가 발송이 확인된 비공개 답장으로 댓글 작성자와 연결되어 있으면, 그 연결을 지우기 전에 같은 목적의 수신 거부를 댓글 작성자 ID로 한 번 더 기록합니다. 근거 참조는 `data_deletion_bridge:<원래 이벤트 ID>`이며, 재연결 후 같은 사람이 댓글을 달아도 계속 차단됩니다.
- 삭제 증적(`data_deletion_records`): 연결 ID, 요청자 ID, 완료 시각과 테이블별 삭제·보관 건수만 가지며 댓글·메시지 내용이나 Instagram 이용자 식별자를 포함하지 않습니다.
- 연결 행: 해제된 상태로 남기며 사업자 계정 ID와 계정명만 가집니다.
- 댓글 규칙, 연락처 필드 정의, 세그먼트, 플로와 발행 버전: 이용자 개인정보가 아닌 운영자 설정입니다.

자동 만료나 주기적 삭제는 두지 않고, 삭제는 요청으로만 실행합니다.

## 동시 쓰기

삭제 함수는 연결 행을 `FOR UPDATE`로 잠급니다(migration 023 전에는 `FOR NO KEY UPDATE`). 이 잠금은 이 연결을 참조하는 행 삽입의 외래 키 잠금과도 충돌하므로, 진행 중인 삽입이 끝난 뒤에 삭제가 시작되고 삭제 중에는 새 발송 행이 생기지 않습니다.
발송 상태를 확인하기 전에 비공개 답장, 팔로우 후속 메시지, 수동 답장 행도 `FOR UPDATE NOWAIT`로 잠급니다(migration 023). 다른 트랜잭션이 그중 한 행이라도 잡고 있으면(커밋되지 않은 발송 선점이나 발송 결과 기록) 기다리지 않고 `409 sending_in_progress`로 거부합니다. 기다리면 발송 결과 기록이 행을 잡은 채 연결 잠금을 기다려 교착 상태가 되기 때문이며, DB 테스트가 두 경합을 재현합니다.
연락처 태그, 필드 값, 자동화 중지 저장은 같은 연결 행을 `FOR SHARE`로 먼저 잠근 뒤 댓글 참여자 여부를 확인하므로, 삭제가 끝난 뒤에는 삭제된 연락처에 값을 다시 쓰지 않습니다.
상담 전환, 수동 답장, 동의 기록은 이미 같은 연결 행을 잠급니다.
팔로우 대화는 수신 기록보다 먼저 삭제해 확인 메시지 수신과 경합하지 않게 합니다.
연결을 해제하기 전에 이미 처리 중이던 웹훅 수신처럼 연결 행을 잠그지 않는 쓰기는 삭제 뒤에 기록될 수 있으므로, 이런 경우 같은 삭제를 다시 실행하면 남은 기록을 지웁니다.

## 권한

삭제는 관리자 소유의 `SECURITY DEFINER` 함수 `public.delete_connection_data(workspace, connection, actor, confirm_account_id)` 하나로만 실행합니다.
서버 역할은 이 함수의 EXECUTE 권한만 가지고, 제품 테이블의 DELETE 권한은 여전히 없습니다.
삭제 증적 테이블은 서버 역할이 읽을 수만 있으며 INSERT·UPDATE·DELETE는 함수만 할 수 있습니다.
Supabase API 역할과 PUBLIC은 함수를 실행할 수 없습니다.
같은 연결을 다시 삭제하면 모든 건수가 0인 증적을 하나 더 남깁니다.

## API

| 요청                                      | 동작                                      |
| ----------------------------------------- | ----------------------------------------- |
| `POST /api/connections/:id/data-deletion` | `{confirm_account_id}`로 연결 데이터 삭제 |
| `GET /api/connections/:id/data-deletions` | 최근 삭제 증적 50개                       |

## 운영 적용

migration 018은 관리자 migration 러너와 접근 권한 스크립트에 포함됩니다.
2026-09-30 운영 DB에 migration 018을 적용하고 이 계약을 포함한 Worker를 배포했습니다. 적용 결과와 권한 조회는 [운영 적용 기록](../notes/2026-09-26-cloudflare-runbook.md)에 있습니다.
같은 날 삭제 전 발송 행을 잠그는 migration 023도 운영 DB에 적용했습니다.
실계정에서의 동작은 아직 검증하지 않았습니다.
