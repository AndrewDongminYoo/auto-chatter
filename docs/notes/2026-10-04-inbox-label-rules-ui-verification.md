# 인박스 자동 라벨 규칙 화면 검증

## 대상과 경계

GitHub [#132](https://github.com/AndrewDongminYoo/auto-chatter/issues/132)의 [자동 라벨 규칙](../specs/2026-10-04-inbox-label-rules.md)을 확인했습니다.
[리마인더 화면 검증](2026-10-04-inbox-reminders-ui-verification.md)과 같은 방식으로, 실제 `public/app` 파일과 실제 `appApi`를 로컬 PostgreSQL 17(포트 5434)의 일회용 DB(`automations_ui`, 실행마다 새로 만들고 확인 뒤 삭제)에 연결한 임시 로컬 서버를 세션 임시 디렉터리에 새로 만들어 사용했습니다.
임시 서버는 `/app/` 응답에 `public/_headers`의 Content-Security-Policy를 그대로 붙였고, 새 DM은 실제 수집 함수(`ingestMessages`)로 저장해 규칙이 실제 경로로 적용되게 했습니다.
Supabase는 세션 쿠키 값으로 `/user` 응답을 돌려주는 대역으로 바꿨고, 대역은 다른 모든 외부 요청을 거절하고 기록하도록 했습니다. 기록된 외부 요청 시도는 0건이었고, 운영 DB·Supabase·Meta·Cloudflare는 호출하지 않았습니다.
합성 데이터는 리마인더 검증과 같은 멤버·연결·대화와 라벨 넷(그중 "이벤트 응모"는 보관됨)에, 규칙 셋("환불 문의" 포함·제외 키워드 있음, "배송 지연" 포함, 라벨이 보관된 "이벤트 응모" 정확히 일치)입니다.
화면 동작은 Playwright 1.63.0으로 headless Chromium을 조작해 확인했습니다.

## 자동 검사

`src/app/inbox-label-rules.db.test.ts`의 16개 테스트가 만들기·조회·수정·보관과 키워드 정규화, 역할·출처·입력 검증과 다른 작업 공간의 라벨·규칙, 쓰는 시점의 라벨 확인(커밋되지 않은 보관 포함), 버전 충돌과 바뀐 것 없는 수정, 50개 한도(동시 만들기 포함), 맞추는 방식(포함, 정확히 일치, 제외 키워드 우선, NFC·대소문자·공백, 버튼 응답 제외), 새 DM에만 적용과 다시 전달된 DM, 멤버가 뗀 라벨, 보관된 라벨·보관한 규칙·10개 한도·40자리를 넘는 보낸 사람 ID, 여러 규칙의 한 버전·한 감사 행과 `rule_id`, 수동 라벨 변경과의 경쟁(`409 label_conflict`), 라벨 보관과의 경쟁, 규칙 쓰기가 수집을 기다리지 않음, 사람 삭제와의 동시 실행, 세 삭제 함수, migration 035 재실행(035 이전 모양에서 제약 검증 포함)과 작업 공간 이동 검사를 확인합니다.
서버 역할이 규칙을 지우지 못하고 규칙이 남긴 감사 행을 쓸 수 있는 것은 `src/cloudflare/access.db.test.ts`가, 관리자 소유자 지정 스크립트의 이동 검사는 `src/app/settings.db.test.ts`가 확인합니다.
잠금이나 검사 하나씩 빼고 같은 파일을 실행해 테스트가 그것을 잡는지 확인했습니다. 실패는 모두 값 확인이나 응답 코드에서 나왔고, 되돌리자 모두 통과했습니다.

- 수집의 라벨 `FOR SHARE`를 빼자 커밋되지 않은 보관을 기다리지 않고 보관될 라벨을 붙였습니다.
- 멤버가 뗀 라벨 검사를 빼자 규칙이 그 라벨을 다시 붙였습니다.
- 버튼 응답 제외를 빼자 버튼 응답에 라벨이 붙었습니다.
- 규칙 수정의 `FOR NO KEY UPDATE`를 `FOR UPDATE`로 바꾸자 수정이 수집을 기다렸습니다.
- 규칙 만들기의 작업 공간 행 잠금을 빼자 동시 만들기가 기다리지 않았습니다.
- 쓰기 전 판단을 빼자 라벨을 하나도 붙이지 않는 DM이 버전 0 행을 남겼습니다(두 테스트 실패).
- 규칙 쓰기의 라벨 `FOR SHARE`를 빼자 커밋되지 않은 보관을 기다리지 않고 규칙을 만들었습니다.

## 브라우저 검사

점검 스크립트의 53개 항목이 모두 통과했습니다.

- 상담원 화면에는 "자동 라벨 규칙" 칸이 없었고, 상담원 세션은 규칙 목록을 요청하지 않았습니다.
- 관리자 화면은 "3 / 50"과 세 규칙을 적용 순서로 보였습니다. 규칙마다 라벨 칩, 맞추는 방식, 키워드와 제외 키워드가 보였고, 라벨이 보관된 규칙은 점선 칩과 "보관된 라벨" 배지, 라벨을 붙이지 않는다는 안내를 보였습니다. 붙일 라벨 목록에는 보관하지 않은 라벨 셋만 있었습니다.
- 키보드만으로 만들었습니다. 라벨 선택에서 "V"를 눌러 VIP를 고르고, Tab으로 맞추는 방식과 키워드(`VIP, 단골 ,vip`), 제외 키워드(`환불`)로 옮겨 입력한 뒤 Enter로 저장했습니다. DB에는 `["vip","단골"]`과 `["환불"]`로 저장됐고 개수가 "4 / 50"이 됐으며 입력 칸이 비워졌습니다.
- 키워드 21개와 101자 키워드는 브라우저가 거부했고 요청을 보내지 않았습니다.
- "배송 지연 라벨 규칙 수정" 버튼에 초점을 두고 Enter를 누르자 입력 칸이 수정 상태(테두리, "규칙 저장", "수정 취소")로 바뀌고 라벨과 키워드가 채워졌으며 초점이 라벨 선택으로 옮겨 갔습니다. 키워드를 바꾸고 Enter로 저장하자 DB에 버전 2로 저장되고 입력 칸이 만들기 상태로 돌아왔습니다.
- 라벨이 보관된 규칙을 수정하자 다른 라벨을 고르라는 안내가 나왔고, 라벨을 고르기 전에는 저장 요청을 보내지 않았습니다. "수정 취소"로 수정 상태를 끝냈습니다.
- 수정 중에 다른 곳에서 규칙을 바꾼 뒤 저장하자 충돌 안내와 함께 입력 칸이 현재 키워드로 바뀌었고, DB의 다른 변경은 그대로였습니다. 다시 저장하자 현재 버전 위에 저장됐습니다(버전 3).
- "보관"은 확인 창을 거쳐 규칙을 보관했고 개수가 "3 / 50"으로 돌아왔습니다.
- 임시 서버의 실제 수집으로 DM 넷을 저장하자, "택배가 아직 도착 안 했어요"만 "배송 지연" 규칙으로 라벨이 붙었고 감사 행은 멤버 없이 그 규칙을 남겼습니다. 제외 키워드가 든 DM, 라벨이 보관된 규칙에 맞는 DM, 보관한 규칙에 맞는 DM에는 라벨이 붙지 않았습니다. 인박스 목록과 연 대화의 라벨 편집 칸이 그 라벨을 보였습니다.
- 390px에서 규칙 목록, 수정 중인 입력 칸, 인박스 목록 모두 문서의 `scrollWidth`가 390을 넘지 않았고, 규칙의 "수정"·"보관" 버튼과 입력 칸의 선택·입력·버튼 높이는 44px 이상이었습니다.
- 페이지 오류와 CSP 위반은 없었습니다. 콘솔 오류 기록은 합성 연결에 토큰이 없어 생기는 기존 규칙 편집기의 게시물 목록 요청(`/api/connections/:id/media`)과, 점검이 일부러 만든 `409 label_rule_conflict` 하나뿐이었습니다.
- 처음 실행의 스크린샷에서, 빈 키워드 칸에 남은 브라우저 검사 메시지가 수정 버튼으로 키워드를 채운 뒤에도 남는 결함을 찾아 고쳤습니다(코드로 채운 값도 키워드 검사를 다시 실행). 그 점검 항목은 고치기 전 코드에서 실패했습니다.
- 점검 스크립트가 결함을 잡는지 보려고 "보관된 라벨" 배지를 그리는 분기를 잠시 끄자 여섯 번째 항목에서 실패했고, 되돌리자 53개 항목이 모두 통과했습니다.
- 운영자 시각 승인용 스크린샷 6장(규칙 목록, 규칙 수정, 규칙으로 라벨이 붙은 대화를 각각 데스크톱과 390px로)은 세션 임시 디렉터리에 PNG로 저장했고 저장소에는 넣지 않았습니다.

## 확인하지 않은 것

- 스크린 리더 낭독과 다크 모드는 확인하지 않았습니다.
- 응답을 받지 못한 저장(네트워크 오류나 5xx)의 안내는 브라우저에서 실행하지 않았습니다.
- migration 035는 운영 DB에 적용하지 않았고 배포하지 않았으므로, 운영 데이터와 실제 Instagram 계정의 DM으로 규칙을 확인하지 않았습니다.
