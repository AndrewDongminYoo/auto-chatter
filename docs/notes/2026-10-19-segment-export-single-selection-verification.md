# 세그먼트 CSV 내보내기 단일 선택 검증

## 범위

[#229](https://github.com/AndrewDongminYoo/auto-chatter/issues/229)의 로컬 검증 기록입니다.
저장된 세그먼트 내보내기가 세그먼트 조건을 내보내기마다 한 번만 계산하고, 행 내용은 키로 25개씩 읽도록 바꾼 변경을 다룹니다.
계약은 [CSV 내보내기 명세](../specs/2026-10-04-contact-csv-export.md#저장된-세그먼트-내보내기)에 있습니다.
기준 커밋은 `e2c88ef`이며, 이 기록은 커밋하기 전 작업 트리에서 실행한 결과입니다.
전체 내보내기(`segment_id` 없음)의 코드는 바꾸지 않았습니다.
배포한 Worker, Hyperdrive, 운영 데이터베이스는 검증하지 않았습니다.

## 실행한 검사

PostgreSQL 17 로컬 클러스터(`127.0.0.1:5434`, `automations_test`)에서 실행했습니다.

| 명령                            | 결과               |
| ------------------------------- | ------------------ |
| `corepack pnpm check-types`     | 통과               |
| `corepack pnpm test`            | 353개 통과, 실패 0 |
| `corepack pnpm test:db`         | 722개 통과, 실패 0 |
| `corepack pnpm test:cloudflare` | 80개 통과, 실패 0  |

## DB 테스트가 확인하는 것

`src/app/contact-csv.db.test.ts`가 다음을 확인합니다.

- 구성원이 0, 1, 25, 26, 51명인 세그먼트를 기본 25행 묶음으로 내보내면, 조건을 계산하는 문장(`evaluation AS MATERIALIZED`)이 한 번이고 키로 읽는 문장이 `ceil(구성원 수 / 25)`번입니다. 구성원 0명이면 키로 읽는 문장이 없습니다.
- 같은 경우마다 내보낸 연락처가 같은 고정 시각의 `listContacts` `segment_id` 목록(51명은 커서로 끝까지 넘긴 결과)과 같고, 행이 같은 데이터의 전체 내보내기 행과 순서까지 같습니다.
- 구성원이 3명일 때 `maxRows: 2`는 키로 읽는 문장 없이 `422 contact_export_too_large`로 전체를 거절하고 커밋하지 않으며, `maxRows: 3`은 3행을 2번의 키 묶음으로 읽고 그 행이 같은 고정 시각의 `listContacts` 목록과 같습니다.
- 선택 문장이 `statement_timeout`을 끈 뒤 끝나지 않으면, 선택 문장 자신의 읽기 제한 시간으로 `timeoutMs: 100` 안에 `503 contact_export_timeout`으로 끝나고, 키로 읽는 문장 없이 연결을 폐기합니다.
- 13가지 조건 정의를 비교하는 기존 테스트, 조건 트리 테스트(`segment-condition-tree.db.test.ts`), DM 활동 테스트(`segment-dm-activity.db.test.ts`)는 비교 부분을 바꾸지 않고 통과합니다. 묶음마다 조건을 다시 계산한다는 횟수 단언 4곳만 한 번 계산으로 바꿨고, 시계가 움직이는 테스트에는 키 읽기 7번 단언을 더했습니다.
- DM 동의 세그먼트 테스트(`segment-dm-consent.db.test.ts`)는 바꾸지 않고 통과합니다.

새 경계 테스트는 구현 전에 작성했고, 기준 코드에서 구성원 1, 25, 26, 51명 경우와 한도 경우가 실패했습니다(조건 계산 횟수 2·3번 또는 키 읽기 0번).
구현 뒤에는 선택 문장의 한도 검사를 `maxRows + 99`로 바꾼 변이에서 한도 테스트가 실패했습니다(키 읽기 2번, 기대 0번).
한도 테스트의 목록 비교는 구현 뒤에 더했으며, 키 묶음에서 키 하나를 빼는 변이(`keys.slice(start, start + limits.batchSize - 1)`)에서 키 읽기 횟수는 맞지만 목록 비교가 실패했습니다.
제한 시간 테스트도 구현 뒤에 작성했습니다.
처음 형태는 선택 문장을 시간 제한 없는 `client.query`로 바꾼 변이에서도 통과했습니다. 앞 문장이 트랜잭션 범위로 설정한 `statement_timeout`이 남아 있었기 때문입니다.
그래서 바꾼 선택 문장이 `SET LOCAL statement_timeout = 0`으로 그 설정을 끄도록 고쳤고, 같은 변이에서 5초를 기다린 뒤 실패하는 것을 확인했습니다.

## 측정

변경 전 수치는 기준 커밋 `e2c88ef`에서 같은 측정 스크립트로 잰 결과이며, 그때 부하 평균은 6~9였습니다.
변경 후에는 그 스크립트를 복사해 작업 트리 코드를 가져오도록 바꾸고, 같은 데이터로 기준 코드도 한 번씩 실행해 `exported_at`만 바꾼 CSV 본문이 같은지 비교했습니다.
데이터는 연락처 5,000명이며, 연락처마다 댓글 1개 또는 4개, 댓글마다 발송된 비공개 답장 1개, 연락처마다 받은 DM 1개가 있습니다.
각 조건을 3회 실행했고, 변경 후 측정 동안 부하 평균은 6.0~6.4였습니다.
두 측정은 시각과 부하가 달라 참고용 수치입니다.

| 연락처당 댓글 수 | 조건                     | 변경 전(`e2c88ef`) | 변경 후        | 본문 동일 |
| ---------------- | ------------------------ | ------------------ | -------------- | --------- |
| 1                | DM 조건 없음             | 730~877 ms         | 121~139 ms     | 예        |
| 1                | DM 동의 `no_record`      | 3,961~4,766 ms     | 128~131 ms     | 예        |
| 1                | DM 활동 7일              | 4,419~4,905 ms     | 131~138 ms     | 예        |
| 4                | DM 조건 없음             | 2,054~2,379 ms     | 123~130 ms     | 예        |
| 4                | DM 동의 `no_record`      | 9,544~10,243 ms    | 161~166 ms     | 예        |
| 4                | DM 활동 7일              | 9,757~13,224 ms    | 167~215 ms     | 예        |
| 1                | 전체 내보내기(변경 없음) | 측정하지 않음      | 542~587 ms     | 예        |
| 4                | 전체 내보내기(변경 없음) | 측정하지 않음      | 1,772~2,276 ms | 예        |

모든 경우에 5,000행을 내보냈습니다.
전체 내보내기는 가장 느린 실행도 10초 한도의 약 23%이므로 후속 이슈를 만들지 않았습니다.
