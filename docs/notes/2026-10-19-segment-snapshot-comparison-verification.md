## 실패를 확인한 검사

- 비교 API 구현 전에 같은 총인원에서 구성원만 달라지는 테스트가 `404 not_found`와 기대값 `200`의 차이로 실패했습니다.
- 화면 구현 전에 비교 버튼 테스트가 요청 횟수 `0`과 기대값 `1`의 차이로 실패했습니다.
- 첫 읽기 뒤 별도 연결에서 필터 수정과 이용자 삭제를 커밋했습니다. 정상 구현은 이전 버전과 명단을 이번 응답에, 새 버전과 남은 명단을 다음 응답에 사용했습니다. 격리 수준만 `READ COMMITTED READ ONLY`로 바꾸자 최초 버전 `1` 대신 `2`를 읽어 실패했습니다. 통제 실험 뒤 원래 소스를 복구했습니다.

## DB와 Worker가 확인한 내용

- 기준 `{A,B}`와 현재 `{B,C}`를 추가 1·제외 1·유지 1로 셉니다.
- 빈 명단은 모두 0이며 연결이 다른 같은 sender는 다른 연락처입니다. 다른 작업 공간은 포함하지 않습니다.
- 현재 대상 5,003명을 잘림 없이 집계합니다. 상세 페이지 50행이나 고정 생성 5,000명 제한을 비교에 적용하지 않습니다.
- 태그·다중 태그·필드·상대 활동·달력 기간·댓글 동의·DM 동의·최근 DM·중첩 그룹·계정 조건은 같은 시각의 기존 연락처 목록과 대조합니다.
- 실제 `delete_person_data` 실행 뒤 원래 인원 수와 남은 기준 인원 수를 분리하며, 비교가 저장된 고정 대상이나 명단을 수정하지 않는지 확인합니다.
- 잘못된 ID·쿼리, 없는/다른 작업 공간의 고정 대상, 상담원·제거된 멤버, 보관한 세그먼트를 거절합니다. 보관 후에도 명단과 CSV는 조회할 수 있습니다.
- workerd 경로는 실제 서버 DB 역할로 변경된 명단 집계, 쿼리 거절, 작업 공간 격리, 상담원 거절을 확인합니다.
- 클라이언트는 결과 표시와 실패 시 이전 결과 삭제, 다른 명단·세션·미저장 수정·동일 필터의 버전 변경 뒤 늦은 응답 무효화를 확인합니다.

## 독립 검토와 수정

백엔드와 클라이언트·문서 범위를 나누어 두 독립 검토자가 확인했습니다.
백엔드에서는 수정이 필요한 결함을 찾지 못했습니다.
클라이언트 검토에서는 필터 이름만 수정할 때 실제 입력 핸들러가 비교 무효화를 호출하지 않는 문제를 확인했습니다.
실제 `app.js` 입력 콜백·`segmentControls()`·`segmentEditChanged()`와 비교 컨트롤러를 실행하는 회귀가 버튼 활성 상태 때문에 실패하는 것을 확인했습니다.
입력 콜백 한 곳을 `segmentControls()`에 연결한 뒤 해당 회귀와 전체 단위 검사를 통과했습니다.
같은 필터의 버전만 바뀐 뒤 늦게 도착하는 응답도 별도 단계로 검사했습니다.
