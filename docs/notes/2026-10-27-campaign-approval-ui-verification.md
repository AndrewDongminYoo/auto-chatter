# 캠페인 실행 승인 화면 검증

## 범위

[#35](https://github.com/AndrewDongminYoo/auto-chatter/issues/35)의 후속 범위로, PR #264의 실행 승인 API를 관리자 캠페인 초안 상세에 표시하고 조작하는 화면을 추가했습니다.
기준 로컬 HEAD는 `e3523cb`입니다.
2026-10-27 운영자가 계획을 승인했습니다.
변경 파일은 `public/app/campaign-drafts.js`, `public/app/app.js`, `public/app/index.html`, `public/app/styles.css`, `src/app/campaign-drafts.test.ts`와 문서입니다.
서버 코드·DB 스키마·migration·의존성은 변경하지 않았고 새로 제공되는 정적 파일도 없습니다.
`app.js`의 변경은 공용 API 래퍼가 409 응답의 `approval`·`draft`를 오류 객체에 전달하는 두 줄과, 승인한 사람을 ‘나’로 표시하기 위한 현재 사용자 ID 전달입니다.
화면 계약은 [실행 승인 화면](../specs/2026-10-21-campaign-drafts.md#실행-승인-화면)에 기록합니다.
템플릿 치환, 실제 발송([#36](https://github.com/AndrewDongminYoo/auto-chatter/issues/36)), 캠페인 단위 예약 상한, 별도 승인 목록 화면은 구현하지 않았으며 #35 전체 완료를 뜻하지 않습니다.

## 자동 검사

실제 화면 모듈을 VM에서 실행하는 기존 하네스에 승인 API의 상태 있는 대체물(최신 승인 먼저인 목록, 생성·예약 변경·취소)을 더하고 승인 검사 42개(아래 API 래퍼·마크업 검사 포함)를 추가했습니다.
검사는 승인 버튼의 활성 조건(새 초안·저장하지 않은 변경·예약 시각 없음·보관·결과 불명인 초안 저장·승인 조회 대기와 실패), 확인 단계(버전·고정 대상·시간대가 붙은 예약 시각 표시, 돌아가기, 확인 전 쓰기 없음), 즉시·예약 요청 본문의 정확한 키, 유효한 승인의 표시(일곱 사유 표와 행 머리글, 2^53을 넘는 수, 승인에 저장된 시간대로 표시한 예약 시각, ‘나’·다른 멤버 표시, 발송 미지원 경고)와 초안 잠금, 예약 변경·취소의 버전과 취소 후 잠금 해제, 409(`campaign_approval_conflict`·`campaign_approval_cancelled`·`approval_exists`·승인 요청의 `campaign_draft_conflict`)의 재표시와 자동 재시도 없음, 시간대 불일치 409, 응답 유실과 429의 같은 요청 재시도, 결과 불명인 승인 요청의 확인 요약과 본문이 시간대 변경·초안 입력 이벤트 뒤에도 유지되는지, 쓰기 중 `aria-busy`, 승인 기록·취소 뒤 결과 제목으로 옮기는 포커스, 초안 저장의 `409 approval_active` 처리, 승인 요청의 `campaign_draft_conflict` 뒤 이전 버전 미리보기 지움, 이 화면에서 새로 저장한 초안(결과 불명 생성의 재시도 성공 포함)의 승인 상태 조회와 그 뒤의 승인, 여섯 무효화(다른 초안 열기·새 초안·세션 초기화·작업 공간 변경·다시 불러온 시간대·저장한 시간대)의 늦은 조회 응답 폐기와 표시 지움, 세션 초기화 뒤의 쓰기 응답 폐기, 403의 화면 초기화, 잘못된 응답 행, ‘발송 가능’ 부재를 다룹니다.
공용 API 래퍼는 `app.js`의 함수 원문을 VM에서 실행해 409 본문의 `approval`과 `draft`가 오류 객체에 그대로 전달되는지 확인하고, 마크업 검사는 입력 레이블·`role="status"` 영역·표 머리글·분 단위 입력(`step` 없음)과 ‘발송 가능’ 부재를 확인합니다.
기존 시간대 변경 검사는 승인 상태를 다시 읽으므로 전체 요청 수 대신 승인 조회를 뺀 요청 수로 목록을 다시 읽지 않는지 확인하도록 바꿨습니다.

판별력은 구현을 한 곳씩 되돌린 뒤 같은 검사 파일을 실행해 확인했고, 모든 변형에서 하나 이상의 검사가 실패했습니다(실행 기록 `mutations.log`).

## 실제 대시보드·Worker 검증

`corepack pnpm build:cloudflare` 뒤 `scripts/segment-acceptance.mjs`를 DB 검사와 공유하지 않는 새 임시 클러스터(5443, 빈 public 스키마)에서 실행했습니다.
실제 정적 앱·Worker·제한된 서버 DB 역할을 사용하고 외부 인증만 합성 응답으로 대체하며, `SEND_ENABLED`는 `false`입니다.
스크립트 자체는 변경하지 않았습니다.
시작 전 부하 평균은 1분 기준 5.1이었습니다.
소유자 세션으로 실제 API를 호출해 `vip` 태그 저장 필터, 그 고정 대상(2명), 그 대상을 참조하는 초안 하나를 만들었고, 관리자 연결로 작업 공간 시간대를 `America/New_York`으로 바꿨습니다(브라우저 시간대는 `Asia/Seoul`).

`agent-browser`의 이름 있는 세션에서 다음을 확인했습니다.

- 초안을 열면 ‘실행 승인’ 영역이 나타났고, ‘예약’과 `2026-10-28T09:00`을 고르자 승인 버튼이 켜졌습니다.
  예약 입력의 값은 `datetime-local`이 키 입력을 받지 않아 페이지에서 값을 넣고 `input` 이벤트를 보내는 방식으로 넣었습니다.
- 승인 버튼을 누르면 확인 단계가 열리고 포커스가 확인 제목으로 옮겨졌으며, 초안 ‘버전 1’, 고정 대상, `2026-10-28 09:00 (America/New_York)`이 표시됐습니다. 이 시점의 승인 요청은 0건이었습니다.
- ‘승인 기록’ 뒤 DB의 승인은 `scheduled`, `scheduled_at` 2026-10-28 13:00 UTC, `America/New_York`이었습니다.
  화면은 발송 미지원 경고, 실행 시점 `2026. 10. 28. 오전 9:00:00 (America/New_York)`, 승인한 사람 ‘나’, 승인 시점 원래·남은 인원 2명, 일곱 사유 표(연결 발송 불가 2명, 나머지 0명)를 표시했고, 초안 입력·저장·보관이 잠기고 잠금 안내가 보였습니다.
- 예약을 `2026-10-29T10:00`으로 바꾸자 승인 버전이 2가 되고 표시가 바뀌었습니다.
- 소유자 API 호출로 예약을 한 번 더 바꿔 버전 3으로 만든 뒤, 화면(버전 2)에서 승인을 취소하면 `409 campaign_approval_conflict`로 바뀐 예약(`2026-10-30T11:15`)을 다시 표시하고 잠금을 유지했습니다.
  다시 취소하면 ‘최근 승인 · 취소됨’, 취소한 사람·시각이 표시되고 초안 입력·저장이 풀렸으며 승인 버튼이 다시 보였습니다.
  취소 확인 대화상자는 페이지의 `confirm`을 항상 허용으로 바꿔 넘겼으므로 브라우저 대화상자 자체는 확인하지 않았습니다.
- ‘즉시’ 승인은 확인 단계에 ‘즉시’를 표시했고, DB에는 `immediate`와 빈 예약 시각·시간대로 저장됐습니다.
- 화면이 유효한 승인을 표시하는 동안 API로 취소하고 ‘승인 상태 새로고침’을 누르면 취소된 상태로 바뀌고 초안 잠금이 풀렸습니다.
  이어서 API로 새 즉시 승인을 만든 뒤 화면에서 실제 키 입력으로 본문을 고쳐 저장하면 `409 approval_active` 안내가 표시되고, 입력한 본문을 유지한 채 승인 영역이 그 승인을 다시 읽어 초안을 잠갔습니다. DB의 초안은 버전 1 그대로였습니다.
- 그 승인을 화면에서 취소한 뒤에는 저장하지 않은 본문 때문에 승인 버튼이 꺼져 있었고, 저장해 버전 2가 된 뒤 확인 단계에 ‘버전 2’가 표시됐습니다.
- 390px 폭·다크 모드에서 확인 단계와 유효한 승인 표시 모두 문서 폭 390px, 카드와 표의 스크롤 폭과 표시 폭이 350px로 가로 스크롤이 없었고, 캡처로 대비를 확인했습니다.
- 카드(`#campaign-drafts-section`)에 한정한 axe 4.12.1 검사는 유효한 승인을 표시한 밝은 데스크톱, 확인 단계를 연 다크 390px, 유효한 승인을 표시한 다크 390px 모두 위반 0개·미완료 0개였습니다.
  같은 범위의 승인 영역에 alt 없는 이미지를 임시로 넣으면 `image-alt` 위반 1개를 보고해 검사가 실제로 범위를 읽는 것을 확인한 뒤 제거했습니다.
- 승인 영역 문자열에 ‘발송 가능’이 없었습니다. 카드 전체에서는 기존 초안 요약의 ‘발송 가능한 인원 수는 아닙니다’만 일치했습니다.
- 상담원으로 다른 세션에 로그인하면 캠페인 카드와 승인 영역이 숨겨지고 ‘실행 승인’ 문구가 화면에 없었으며, 같은 세션의 `GET /api/campaign-approvals`는 `403 role_forbidden`이었습니다.

검사 후 비공개 답장 outbox와 수동 답장은 0행, 동의 이벤트는 0행, 승인은 4행(유효 1행)·감사 기록 9행으로 승인 화면이 발송 원장을 바꾸지 않았습니다.
브라우저 세션과 Worker를 종료하고 Worker 포트의 연결 거절을 확인했습니다.
5443 클러스터는 확인용 데이터가 남아 있으므로 다음 수용 검사 전에 새로 만들어야 합니다.
캡처·axe 결과·시드 스크립트·검사 실행 기록은 저장소 밖의 `../pr-loop-reviews/auto-chatter/2026-10-27-campaign-approval-ui/`에 보관합니다.

## 한계

- 실제 Instagram 계정·운영 DB·배포 Worker·실제 발송은 사용하지 않았습니다.
- 브라우저 검사는 검토 반영 전 코드로 실행했습니다. 검토 반영의 화면 변경은 결과 불명인 승인 요청이 있을 때 확인 요약을 지우지 않는 조건 하나와, 승인 기록·취소 뒤 결과 제목(`tabindex="-1"`)으로 포커스를 옮기는 것, 그리고 두 번째 검토의 승인 초안 충돌 뒤 미리보기 지움과 새로 저장한 초안의 승인 상태 조회이며 단위 검사로만 확인했습니다.
- 승인 목록 API는 최신 100개만 돌려주므로, 더 오래된 유효 승인이 있는 초안은 화면에서 승인이 없는 것처럼 보일 수 있습니다. 이때 승인 요청은 `409 approval_exists`로 그 승인을 받아 표시하고, 초안 저장은 `409 approval_active`로 거절됩니다. 브라우저에서는 이 경우를 재현하지 않았습니다.
- 응답 유실·429·늦은 응답·시간대 변경 무효화는 단위 검사로만 확인했고 브라우저에서 네트워크를 끊어 재현하지 않았습니다.
- 승인한 사람은 현재 사용자이면 ‘나’, 아니면 ‘다른 멤버’와 사용자 ID 앞 8자리로 표시합니다. 관리자는 멤버 목록을 읽을 수 없어 이름·이메일을 표시하지 않습니다.
- 스크린 리더의 실제 낭독은 확인하지 않았습니다. 안내가 문서에 미리 있는 `role="status"` 영역에 들어가는 구조까지 확인했습니다.
