# 연락처 식별자 연결·분리 구현 검증

## 구현 범위와 상태

[승인된 계획](../plans/2026-10-21-contact-identity-links.md)의 저장·API·화면을 구현했습니다.
기준 HEAD는 `2724f9fcd989929383e62b677408a2ecf2ce590b`이며, 아래 검증은 커밋 전 작업 변경을 대상으로 수행했습니다.
새 의존성은 추가하지 않았습니다.
운영 마이그레이션·배포·실계정 발송·GitHub 변경은 수행하지 않았으며, 새 화면은 2026-10-21 운영자가 승인했습니다.
#25 전체와 임의 ID·여러 계정의 동일인 병합은 완료하지 않았습니다.

현재 공급자 근거가 있는 같은 연결의 댓글 작성자·DM 상대만 관리자가 확인할 수 있습니다.
분리는 운영자 확인만 해제하며, 공급자 근거가 사라진 뒤에도 가능합니다.
요청 키·버전·근거 ID를 검사하고 감사 이벤트와 현재 행을 함께 저장합니다.
동의·원본 식별자·발송 guard·태그·필드·세그먼트·리포트는 변경하지 않습니다.
두 테이블의 개인정보 내보내기·삭제·RLS·서버 역할 권한을 같은 변경에 포함했습니다.

## 자동 검사

| 검사                                                  | 읽는 대상과 결과                                                                                   |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `corepack pnpm install --frozen-lockfile`             | 기존 잠금 파일로 설치 성공, 의존성·잠금 파일 변경 없음                                             |
| `corepack pnpm check-types`                           | TypeScript 정적 타입 검사 성공                                                                     |
| `corepack pnpm test`                                  | 순수 로직·실제 화면 모듈의 VM 검사 367개 통과                                                      |
| `TEST_DATABASE_URL=... corepack pnpm test:db`         | 실제 임시 PostgreSQL의 API·권한·삭제·원장 검사 740개 통과                                          |
| `TEST_DATABASE_URL=... corepack pnpm test:cloudflare` | 실제 Worker 번들·제한된 DB 역할·런타임 검사 80개 통과                                              |
| 전체 migration runner 대조                            | 기준 HEAD의 스키마에 전체 runner를 적용한 DB와 새 스키마 DB의 새 제약·RLS·ACL·삭제 함수 3개가 일치 |

DB 검사는 합성 데이터가 있는 로컬 전용 PostgreSQL에서 순차 실행했습니다.
새 DB 테스트 13개는 재시도·버전 충돌·근거 변경·권한·삭제 경합·감사 삽입 후 롤백·페이지 경계·재연결 개인정보 삭제를 검사합니다.
원장 불변성 검사는 실제 허용·철회, 중지, 대기 답장, 태그와 고정 대상 행을 넣고 변경 전후 값과 기존 발송 동의 판정을 비교합니다.
작업 공간 fixture에도 두 테이블을 넣어 기존 내보내기·전체 삭제 검사가 빈 테이블만 읽지 않게 했습니다.
개인 삭제 경합은 `pg_stat_activity`의 잠금 대기를 확인해 두 실행 순서를 재현했습니다.
전체 runner 비교기는 제약 문자열을 손상한 음성 대조군에서 불일치를 확인한 뒤 실제 결과를 비교했습니다.

구현 전 새 경로의 404, 누락된 화면 컨트롤러, 감사 이벤트 UPDATE 권한 허용을 실패로 확인했습니다.
첫 전체 DB 실행에서 과거 마이그레이션으로 삭제 함수를 복원하는 기존 fixture 5곳이 최신 함수를 덮어쓰는 실패를 확인했습니다.
해당 fixture의 복원 목록에 062를 추가한 뒤 전체 740개가 통과했습니다.
접근 제어 fixture도 두 새 테이블을 명시적으로 정리하도록 수정해 반복 실행의 외래 키 제거 부작용을 막았습니다.

변경 경로를 명시한 `trunk fmt`·`trunk check`와 `git diff --check`도 통과했습니다.
검증 후 이름을 지정한 브라우저 세션, 로컬 Worker와 임시 PostgreSQL 두 개를 종료했고 해당 포트의 리스너가 없음을 확인했습니다.

## 로컬 브라우저 검증

실제 정적 앱과 Worker, 제한된 DB 역할을 사용했습니다.
외부 인증만 합성 응답이며 외부 HTTP·발송은 비활성화했습니다.
기존 수동 수용 fixture의 구성을 별도 증거 디렉터리로 복사하고 이번 기능용 댓글 1001·DM 9001의 공급자 근거를 넣었습니다.
운영 계정이나 운영 DB를 사용하지 않았습니다.

- 관리자 확인 → DB `confirmed`, 버전 1을 확인했습니다.
- 확인 해제 → DB 버전 2와 기존 공급자 대화가 화면에 남는 것을 확인했습니다.
- 키보드 Tab·Enter로 다시 확인 → 버전 3을 확인했습니다.
- 합성 공급자 근거 삭제 후 갱신 → 과거 확인 안내와 해제 버튼이 남았습니다.
- 상담원으로 새 로그인 → 현재 상태는 보이지만 확인·해제 버튼은 없었습니다.
- 관리자 화면이 버전 3을 표시하는 동안 별도 API 요청으로 해제한 뒤 화면에서 해제 → 409 안내와 최신 해제 상태로 갱신됐습니다. DB는 버전 4·이벤트 4개를 유지해 추가 저장이 없었습니다.
- 근거와 저장 기록이 없는 연락처 → 빈 상태 안내를 확인했습니다.
- 390px 화면에서 가로 문서 폭도 390px였고 확인·해제·근거 유실 화면에 가로 잘림이 없었습니다.
- 세션 변경 신호를 보내면 기존 연락처가 지워졌습니다. BFCache·늦은 응답 폐기·저장 잠금 초기화·새 서버 권한 사용은 실제 앱 코드를 실행하는 VM 검사로 확인했습니다.

충돌 검사는 두 독립 브라우저 관리자 로그인이 아니라 동일 관리자 세션의 별도 API 변경으로 경합을 재현했습니다.
브라우저 자동화 데몬이 응답하지 않아 한 차례 세션을 닫고 새로 시작했으며, 이후 상담원·충돌·빈 상태 검사를 완료했습니다.
새 세션의 브라우저 오류 조회는 빈 결과였습니다.
네트워크 결과 불명 상태의 동일 요청 키 재사용과 409의 자동 재저장 금지는 VM·DB 테스트로 검증했으며, 실제 브라우저 네트워크 단절을 주입하지는 않았습니다.
