## 범위와 배포 상태

2026-09-29에 `auto-chatter`의 운영 Worker 배포와 Supabase 프로젝트 `asjjftrioaxzspkbtebf`를 조회했습니다.
Worker 버전 `9c424163-508b-460e-9b36-fb8f167deb71`이 배포 비율 100%로 실행 중이며, 전역 `SEND_ENABLED=false`입니다.

전역 발송 중지 상태이므로 계정별 발송 설정만으로는 메시지가 전송되지 않습니다.

## 백업과 데이터베이스 접근

운영 Supabase 백업 목록에는 복구 가능한 항목이 표시되지 않았고, PITR은 비활성화되어 있습니다.
DM 보관을 켜기 전에 `public` 스키마의 압축 덤프를 Git에서 제외된 `deploy/secrets/backups/2026-09-29-issue13/public-pre-inbox-opt-in.dump`에 저장했습니다.
파일 크기는 102,279바이트이고 SHA-256은 `90a2b46c43e2117ea572227d4be5d5c8e10819e7fe932c09a96c90297c5b56e1`입니다.
`pg_restore --list`, 스키마 추출, 데이터 추출이 각각 성공해 아카이브를 읽을 수 있음을 확인했습니다.
실제 복원 훈련은 수행하지 않았으며, 이 덤프에는 Supabase 관리형 `auth` 스키마가 포함되지 않습니다.
따라서 이 파일만으로 전체 서비스를 새 프로젝트에 복구할 수 있다고 판단하지 않습니다.
이 덤프는 DM 보관을 켜기 전 상태이므로 이후 저장된 텍스트 DM과 확인 버튼 응답을 복구할 수 없습니다.
최신 운영 데이터의 별도 암호화 백업과 서버 외부 보관, 백업 주기 및 복원 훈련은 아직 확인하지 못했습니다.

운영 DB의 제품 테이블 19개가 모두 존재하고 RLS가 켜져 있음을 관리자 연결로 확인했습니다.
`anon`, `authenticated`, `service_role`에는 해당 테이블의 SELECT·INSERT·UPDATE·DELETE 권한이 없습니다.
`auto_chatter_server`에는 19개 테이블의 SELECT·INSERT 권한이 있고 DELETE 권한은 없습니다.
UPDATE 권한은 17개 테이블에만 있으며, 두 감사 이벤트 테이블에서는 회수되어 있습니다.
마이그레이션 015에서 추가한 `token_obtained_at`과 `token_refresh_attempted_at` 컬럼이 모두 존재합니다.
작업 공간 회원 1명이 Supabase Auth 사용자와 연결되어 있으며, 참조가 끊긴 회원은 없었습니다.
이 조회는 현재 스키마와 권한을 확인하지만 모든 마이그레이션의 실행 이력을 증명하지는 않습니다.

로그인하지 않은 요청으로 `/api/me`는 401을, 임의 연결의 DM 보관 변경 요청은 403을 반환했습니다.
이 응답은 비인증 요청의 차단만 확인합니다.
다른 사용자의 작업 공간 접근 차단은 운영 계정이 하나뿐이어서 실계정 사이에서 아직 검증하지 못했습니다.

## 새 DM 보관 확인

계정 관리자가 `ai.you.wanted`의 DM 보관을 켠 뒤 테스트 계정에서 새 DM 한 건을 보냈습니다.
운영 DB의 보관 시작 시각은 2026-09-29 03:01:48 UTC이고, 새 DM의 메시지 시각은 03:09:55 UTC입니다.
해당 문구와 일치하는 기록은 한 건이며, 전체 보관 기록도 한 건입니다.
보관 시작 시각보다 앞선 메시지 기록은 없었습니다.
운영 DB에는 `(connection_id, message_id)` 고유 제약이 적용되어 있습니다.
기존 메시지를 같은 키로 다시 삽입하는 트랜잭션에서 `ON CONFLICT DO NOTHING`이 새 행을 0건 반환했고, 트랜잭션은 롤백했습니다.
이 확인은 DB 중복 방지 동작을 보여 주지만, 같은 Meta 이벤트를 다시 전달한 웹훅 재생 테스트는 아닙니다.

## 운영 화면과 Meta 연결 확인

로그인된 Chrome에서 운영 앱의 인박스를 새로고침해 `ai.you.wanted`의 보관 DM 두 건이 표시되는 것을 확인했습니다.
각각 보관 시작 후 전송한 첫 DM과 보관 재개 후 전송한 DM이며, 중지 기간의 DM은 목록에 나타나지 않았습니다.
운영 앱의 `Meta 상태 확인`은 필수 웹훅 구독 필드가 모두 확인되지 않아 같은 Instagram 계정의 재연결이 필요하다고 표시했습니다.
Meta 개발자 화면의 Instagram Webhooks 목록에서는 `messaging_postbacks`가 `구독 취소됨`으로 표시됐습니다.
이 화면은 계정별 구독 필드를 보여 주지 않으므로 앱의 계정 상태 확인 결과와 같은 범위의 증거로 간주하지 않습니다.
확인 버튼의 실제 표시와 클릭 후 postback 수신은 아직 검증하지 않았습니다.

계정 관리자가 `ai.you.wanted`를 재연결한 뒤 운영 앱의 `Meta 상태 확인`은 댓글·DM·확인 버튼 구독 필드가 모두 반환됐다고 표시했습니다.
이는 계정의 구독 필드 응답을 확인한 결과이며, 실제 이벤트 수신까지 증명하지는 않습니다.
운영 DB에서 수신과 DM 보관은 켜져 있고, 기존 보관 DM 두 건이 유지됐습니다.
재연결로 DM 보관 시작 시각이 2026-09-29 03:43:27 UTC로 갱신되고 계정 발송 설정은 꺼졌습니다.
전역 발송도 중지 상태이며, 활성 규칙과 대기 중인 발송 요청은 각각 0건입니다.
기존 두 게시물에는 동일한 테스트 계정에 대한 발송 이력이 있어, 중복 방지 제약을 유지한 실제 확인 버튼 테스트에는 새 게시물 또는 다른 테스트 계정이 필요합니다.

## 확인 버튼 실발송 관찰

계정 관리자의 승인을 받아 새 Adobe 게시물 `18103465040127641`에 정확히 일치하는 댓글 `auto-chatter 버튼 검증 1351` 규칙을 만들었습니다.
첫 DM에는 `확인` postback 버튼을 설정하고 팔로우 확인 흐름을 켰으며, 첫 DM과 팔로워·미팔로워 후속 문구는 승인받은 테스트 문구를 사용했습니다.
테스트 전 활성 규칙과 대기 발송은 0건이었고, 새 게시물에는 이 발신자의 발송 이력이 없었습니다.
`minzzi._.andrew`가 앱에서 확인한 Instagram 링크의 게시물에 승인된 댓글을 한 건 남겼고, 운영 DB에 댓글 이벤트와 outbox가 각각 한 건 기록됐습니다.
첫 처리에서는 발송 전 검증 중 오류로 `pending` 재시도가 예약됐지만, 다음 처리에서 첫 DM이 `sent`가 되고 공급자 메시지 ID가 기록됐습니다.
로그인된 Chrome의 Instagram 대화에서는 승인된 첫 DM 문구가 보였지만 그 아래 `확인` 버튼은 보이지 않았습니다.
따라서 Chrome 화면만으로는 버튼 표시와 클릭을 확인할 수 없었습니다.

테스트를 중지하고 Worker 버전 `a866ae90-ed63-4e55-89fe-8d0ccde4e20b`에서 전역 `SEND_ENABLED=false`를 확인했습니다.
계정별 발송과 Adobe 테스트 규칙도 껐으며 수신과 DM 보관은 켜진 상태를 유지했습니다.
종료 조회에서 대기 중인 비공개 답장·팔로우 후속 DM·수동 답장은 각각 0건입니다.
첫 DM의 팔로우 확인 흐름은 `waiting`으로 남았지만 규칙과 계정 발송이 꺼져 있어 새 확인 응답을 처리하지 않습니다.
이후 운영자가 제공한 2026-09-29 14:12경의 모바일 Instagram 앱 화면에는 같은 첫 DM 아래 `확인` 버튼과 `확인` 응답이 보입니다.
운영 DB에는 2026-09-29 05:12:23 UTC의 `postback` 한 건이 저장됐고, 응답 내용은 `확인`이며 수신자가 테스트 팔로우 대화의 수신자와 일치합니다.
같은 시점의 보관 텍스트 DM은 추가되지 않았으므로, 이 응답이 버튼 postback으로 수신된 것을 확인했습니다.
다만 발송을 이미 중지해 팔로우 대화는 `waiting`, `confirmed_at`은 비어 있고 후속 DM 공급자 메시지 ID도 없습니다.
이번 관찰은 버튼 표시와 postback 보관까지 검증하며, 팔로우 조회·분기·후속 DM 발송까지 검증한 것은 아닙니다.

## 복구 절차와 남은 검증

복구가 필요하면 먼저 전역 발송을 중지한 상태를 유지하고 수신 변경을 멈춥니다.
덤프의 체크섬을 대조한 뒤 Supabase 기본 역할이 있는 격리된 복구 DB에 `auto_chatter_server` `NOLOGIN` 역할만 먼저 만들고, 제품 테이블은 만들지 않습니다.
그다음 전체 아카이브를 `pg_restore --exit-on-error`로 복원해 데이터 관계와 사용자 소유권을 검사합니다.
복원 뒤 RLS와 역할 권한을 확인하고, 필요한 접근 설정만 적용합니다.
관리형 Auth 데이터와 연동 자격 증명의 복구 방법을 별도로 확인한 후에만 운영 경로를 전환합니다.
운영 DB에 이 덤프를 곧바로 덮어쓰는 절차는 검증하지 않았습니다.

Meta 웹훅을 실제로 재전송했을 때의 중복 차단은 아직 확인하지 않았습니다.
확인 버튼은 모바일 앱에서 표시되고 postback이 보관됐지만 Chrome 웹에서는 같은 버튼이 보이지 않았습니다.
클라이언트별 표시 차이의 원인과 발송을 켠 상태의 팔로우 조회·후속 DM 결과는 아직 확인하지 않았습니다.
이 검증이 끝나기 전에는 #13을 완료로 처리하지 않습니다.

테스트 직후 기본값으로 다시 배포해 버전 `c825eebe-e1f9-4950-8a95-a550e854f238`이 00:44:00Z부터 100% 활성화됐고, 버전 조회에서 `SEND_ENABLED=false`를 확인했습니다. 전역 발송이 켜져 있던 시간은 약 3분입니다.
운영자가 대시보드에서 규칙과 계정 발송을 껐고, 종료 조회(00:47:58Z)에서 계정 발송 꺼짐, 활성 규칙 0개, 대기·발송 중·unknown 발송 0건, 웹훅 전송 0건을 확인했습니다. 남은 `waiting`은 09-29의 reply 3뿐입니다.
이 결과로 버튼 postback에서 팔로우 조회, 미팔로우·팔로워 분기, 후속 DM 발송까지 운영에서 확인했습니다.

### 웹에서 버튼이 보이지 않는 이유

Meta의 [Instagram Messaging 버튼 템플릿 문서](https://developers.facebook.com/documentation/business-messaging/instagram-messaging/button-template)(2026-10-07 확인)는 "The button template is currently not available in the web version."이라고 밝힙니다.
09-29에 Chrome 웹에서 버튼이 보이지 않은 것은 이 제한과 일치하며, 코드 결함으로 보지 않습니다. 웹 사용자는 확인 키워드를 직접 입력해 같은 흐름을 진행할 수 있습니다.

### 웹훅 재전송 중복 차단

Meta의 실제 재전송은 서비스가 일으킬 수 없어 관찰하지 않았습니다.
대신 운영 DB에 재전송을 흡수하는 제약이 있는지 조회했습니다. 댓글 이벤트 `UNIQUE (connection_id, comment_id)`, 발송 `UNIQUE (connection_id, media_id, sender_id)`, 확인 receipt `PRIMARY KEY (connection_id, message_id)`, 인박스 DM `UNIQUE (connection_id, message_id)`가 모두 있습니다.
CI 배포 검사(`.github/workflows/ci.yaml`의 `Verify signed event persistence and replay protection`)는 Node 수신 경로에 합성 자격 증명으로 서명한 같은 댓글 요청을 두 번 보내 발송 행이 한 건만 생기는지 확인합니다. 이 검사는 Cloudflare 수신 경로와 DM 재전송을 다루지 않으며, 실제 Meta 재전송의 관찰은 남은 한계로 둡니다.
