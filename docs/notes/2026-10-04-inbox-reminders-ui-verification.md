# 인박스 리마인더 화면 검증

## 대상과 경계

GitHub [#23](https://github.com/AndrewDongminYoo/auto-chatter/issues/23)의 마지막 부분인 [리마인더](../specs/2026-10-04-inbox-reminders.md)(#23-C)를 확인했습니다.
[라벨·메모 화면 검증](2026-10-03-inbox-labels-notes-ui-verification.md)과 같은 방식으로, 실제 `public/app` 파일과 실제 `appApi`를 로컬 PostgreSQL 17(포트 5434)의 일회용 DB(`automations_ui`, 실행마다 새로 만들고 확인 뒤 삭제)에 연결한 임시 로컬 서버를 세션 임시 디렉터리에 새로 만들어 사용했습니다.
임시 서버는 `/app/` 응답에 `public/_headers`의 Content-Security-Policy를 그대로 붙였습니다.
Supabase는 세션 쿠키 값으로 `/user` 응답을 돌려주는 대역으로 바꿨고, 대역은 다른 모든 외부 요청을 거절하고 기록하도록 했습니다. 기록된 외부 요청 시도는 0건이었고, 운영 DB·Supabase·Meta·Cloudflare는 호출하지 않았습니다.
합성 데이터는 라벨·메모 검증과 같은 멤버 넷, 연결 둘, 대화 여섯 개에 더해, 작업 공간 시간대를 `America/New_York`으로 두고 상담원의 리마인더 셋(기한이 지난 것, 이틀 뒤, 90초 뒤)과 다른 상담원의 기한이 지난 리마인더 하나입니다.
브라우저는 `Asia/Seoul` 시간대로 실행해, 화면이 브라우저가 아니라 작업 공간 시간대를 쓰는지 확인했습니다.
화면 동작은 Playwright 1.63.0으로 headless Chromium(chrome-headless-shell 1243)을 조작해 확인했습니다.

## 자동 검사

`src/app/inbox-reminders.db.test.ts`의 17개 테스트가 다른 멤버의 조회·변경 거부, 시간대 변환과 일광 절약 시간의 건너뛴 시각·두 번 있는 시각(`America/New_York`, `Europe/Berlin`), 시간대를 바꿔도 저장 시각이 그대로인 것, 1분·90일 경계와 요청 검증, 멤버·대화마다 진행 중 하나(동시 만들기 포함), 버전 충돌과 버전마다 감사 한 행, 완료가 취소하고 다시 열어도 되살리지 않음(직접 다시 열기와 새 DM의 `auto_reopen`), 멤버 제거의 취소, 출처·멤버십 검사, `reminder=due` 필터와 커서, 세 삭제 함수(사람 삭제는 그 DM 수신자만), 삭제 함수·멤버 제거·대화 완료와의 동시 실행, migration 034 재실행과 제약을 확인합니다.
서버 역할이 리마인더 감사 기록을 고치거나 지우지 못하고 리마인더를 지우지 못하는 것은 `src/cloudflare/access.db.test.ts`가 확인합니다.
잠금이나 취소 하나씩 빼고 같은 파일을 실행해 테스트가 그것을 잡는지 확인했습니다. 실패는 모두 값 확인이나 응답 코드에서 나왔고, 되돌리자 모두 통과했습니다.

- 대화 lock을 빼자, 커밋 전 만들기 뒤의 완료가 기다리지 않아 리마인더가 남았고, 커밋 전 완료 뒤의 만들기가 리마인더를 만들었습니다(두 테스트 실패).
- 멤버 행 `FOR SHARE`를 빼자 멤버 제거가 그 멤버의 쓰기를 기다리지 않아 취소한 개수가 0이었습니다.
- 연결 행 `FOR SHARE`를 빼자 연결·사람 삭제와의 동시 실행 테스트가 실패했습니다.
- 작업 공간 행 `FOR SHARE`를 빼자 작업 공간 삭제와의 동시 실행 테스트가 교착으로 `503`을 받았습니다.
- 완료 시 취소, 완료한 대화 검사, 멤버 제거 시 취소를 각각 빼자 해당 테스트들이 실패했습니다.

## 브라우저 검사

점검 스크립트의 57개 항목이 모두 통과했습니다.

- 상담원 화면의 "리마인더" 배지는 1(기한이 지난 자기 리마인더 하나)로 강조됐고, 다른 상담원의 리마인더가 있는 대화에는 칩이 없었습니다. 기한이 지난 대화의 칩은 "리마인더 기한 · …"으로 다른 모양이었고, 이틀 뒤 리마인더는 "리마인더 · …"였습니다.
- 키보드: "리마인더" 버튼에 초점을 두고 Enter로 필터를 켜자 기한이 된 대화 하나만 남았고 `aria-pressed`가 `true`였으며, Space로 끄자 여섯 대화가 다시 보였습니다. 대화는 버튼에 초점을 두고 Enter로 열었습니다.
- 리마인더가 없는 대화의 편집 칸은 "아직 내 리마인더가 없습니다."와 "작업 공간 시간대(America/New_York)"를 보였고, 기본값은 뉴욕 시각으로 약 한 시간 뒤였습니다. 날짜를 정하고 Tab을 일곱 번 눌러 날짜 입력 안의 칸들과 달력 버튼을 지나 메모로 간 뒤 입력하고 Enter로 저장하자, DB에는 뉴욕 시각 그대로 저장됐고 편집 칸이 "리마인더 변경"과 "완료로 표시"·"리마인더 취소"로 바뀌었으며 목록을 새로 그리며 그 대화에 칩이 붙었습니다.
- 메모를 바꾸자 "저장하지 않은 변경이 있습니다."가 보였고 저장하자 버전 2가 됐습니다. 201자 메모는 글자 수가 "201 / 200"으로 보이고 입력이 유효하지 않아 요청을 보내지 않았습니다.
- 기한이 지난 리마인더는 "기한이 지났습니다 · …"로 강조됐고, 메모만 바꾸자 지난 기한을 그대로 둔 채 버전 2가 됐습니다. "완료로 표시"를 키보드로 누르자 DB 상태가 `done`이 되고 배지가 다음 목록 로드에서 0이 됐으며 칩이 사라졌습니다. "리마인더 취소"는 사유 `manual`로 취소했습니다.
- 같은 멤버가 다른 곳에서 리마인더를 만든 대화에서 저장하자 "이미 내 리마인더가 있습니다" 안내와 함께 편집 칸이 기존 리마인더로 바뀌었고, 다시 저장하자 새로 만들지 않고 기존 리마인더를 바꿨습니다(버전 2).
- 리마인더가 있는 대화를 "완료 처리"하자 리마인더가 `conversation_closed`로 취소되고, 편집 칸이 완료한 대화에는 둘 수 없다는 안내와 함께 막혔습니다.
- 시계를 3분 앞당기자(Playwright clock) 1분 타이머가 90초 뒤 리마인더의 칩을 "리마인더 기한"으로 바꾸고 배지를 하나 올렸으며, 그동안 API 요청은 없었습니다.
- 390px에서 배지와 필터를 켠 목록, 편집 칸, 기한이 지난 리마인더의 편집 칸 모두 문서의 `scrollWidth`가 390을 넘지 않았고, "리마인더"·"새로고침" 버튼, 날짜·메모 입력, "리마인더 저장"·"완료로 표시"·"리마인더 취소"의 높이는 44px 이상이었습니다.
- 페이지 오류와 CSP 위반은 없었습니다. 콘솔 오류 기록은 합성 연결에 토큰이 없어 생기는 기존 규칙 편집기의 게시물 목록 요청(`/api/connections/:id/media`) 셋과, 점검이 일부러 만든 `409 reminder_exists` 하나뿐이었습니다.
- 처음 실행에서 대화를 완료 처리한 뒤 편집 칸이 바로 다시 그려지지 않는 결함을 찾아 고쳤습니다(상태 변경 뒤 편집 칸도 다시 그림). 기한이 지난 리마인더의 메모만 바꾸는 저장이 날짜 입력의 최솟값에 막히지 않는지도 확인했습니다.
- 점검 스크립트가 결함을 잡는지 보려고 목록 칩을 그리는 분기를 잠시 끄자 세 번째 항목에서, 지난 기한에도 날짜 최솟값을 두게 되돌리자 메모 변경 항목에서 실패했습니다. 코드를 되돌리고 `trunk fmt` 뒤 새 DB에서 다시 실행하자 57개 항목이 모두 통과했습니다.
- 리뷰에서 지적된 저장하지 않은 변경 확인을 별도 점검 스크립트(5개 항목)로 확인했습니다. 페이지를 떠나지 않도록 `beforeunload` 이벤트를 직접 보내, 로그아웃·계정 연결 확인과 같은 `hasDrafts()`를 읽었습니다. 리마인더가 없는 대화에서 메모를 한 글자 쓰고 지우거나, 메모를 쓴 채 대화를 완료 처리하면 확인이 뜨지 않았고, 메모를 남겨 두면 확인이 떴습니다. 고치기 전 코드로 같은 스크립트를 실행하자 세 항목이 실패했고, 고친 코드에서는 다섯 항목과 기존 57개 항목이 모두 통과했습니다.
- 리뷰에서 지적된 배지 개수와 완료 처리 중의 대화 읽기를 별도 점검 스크립트(14개 항목)로 확인했습니다. 첫 목록에 기한 전으로 실린 리마인더가 기한을 지난 뒤 다음 페이지를 불러와도 배지가 그 리마인더를 한 번만 셌고(2), 브라우저 시계로 기한이 된 리마인더의 대화를 연 뒤 1분 타이머가 돌아도 배지가 그대로였습니다(3). 다음 페이지는 첫 응답의 커서를 가장 오래된 대화보다 뒤로 바꿔 빈 페이지로 만들었습니다. 완료 처리 요청을 붙잡아 둔 채 새로고침의 대화 읽기가 진행 중 리마인더를 받고, 완료 처리가 끝난 뒤에 그 응답이 도착하게 하자, 편집 칸은 완료한 대화 안내를 유지했고 "완료로 표시"가 다시 나타나지 않았습니다. 고치기 전 코드로 같은 스크립트를 실행하자 배지가 3과 2로 보였고 취소된 리마인더가 편집 칸에 돌아와 네 항목이 실패했고, 고친 코드에서는 14개 항목과 기존 57개 항목이 모두 통과했습니다.
- 리뷰에서 지적된 초안의 기준 버전과 같은 탭의 시간대 변경을 별도 점검 스크립트(20개 항목)로 확인했습니다. 상담원이 메모 초안을 쓰는 동안 같은 상담원의 다른 브라우저가 리마인더를 바꾸고, 첫 화면에서 대화를 새로고침해 바뀐 리마인더가 보인 뒤 초안을 저장하자 `409 reminder_conflict`가 왔고 DB에는 다른 화면의 메모가 남았으며, 다시 저장하자 그 버전 위에 초안이 저장됐습니다. 관리자가 `America/New_York`에서 리마인더를 만들고 메모 초안을 쓴 채 같은 탭에서 시간대를 `Asia/Seoul`로 저장하자, 편집 칸이 "작업 공간 시간대(Asia/Seoul)"와 서울 시각의 기한을 보이고 초안을 지운 이유를 안내했으며, 보이는 기한을 하루 뒤로 바꿔 저장하자 DB의 `due_at`이 정확히 24시간 움직였습니다. 고치기 전 코드로 실행하자 덮어쓰기(200)가 일어났고, 시간대 수정만 되돌리면 편집 칸이 뉴욕 시간대를 유지해 기한이 11시간만 움직이는 등 다섯 항목이 실패했습니다. 고친 코드에서는 20개 항목과 기존 57개 항목이 모두 통과했습니다.
- 리뷰에서 지적된 리마인더 저장과 대화 완료 처리의 겹침을 별도 점검 스크립트(13개 항목)로 확인했습니다. 상담원이 리마인더를 만들거나(POST) 바꾸는(PATCH) 저장의 응답을 서버 커밋 뒤 브라우저 앞에서 붙잡아 두자 "완료 처리"가 비활성이었고, 응답이 도착한 뒤 편집 칸이 보이는 진행 중 리마인더는 DB와 일치했습니다. 반대로 완료 처리 응답을 붙잡아 두자 리마인더 저장·완료로 표시·취소와 메모 칸이 비활성이었고, 완료 처리 뒤 편집 칸과 DB 모두에 진행 중 리마인더가 없었습니다. 고치기 전 코드로 실행하자 저장 중에 완료 처리가 실행되어 두 경로 모두 DB에서 취소된 리마인더가 편집 칸에 진행 중으로 돌아오는 등 일곱 항목이 실패했습니다. 메모 칸이 완료 처리 요청과 함께 잠기게 되어, 앞의 저장하지 않은 변경 점검은 메모 칸 잠금 대신 완료 처리가 끝나기를 기다리도록 바꿨고, 바꾼 스크립트도 1차 수정 전 코드에서 세 항목이 실패했습니다. 고친 코드에서는 13개 항목과 기존 57개, 14개, 20개, 5개 항목이 모두 통과했습니다.
- 리뷰에서 지적된 리마인더 저장과 같은 탭의 시간대 변경의 겹침을 별도 점검 스크립트(8개 항목)로 확인했습니다. 관리자가 `America/New_York`에서 리마인더를 만들거나(POST) 바꾸는(PATCH) 저장의 응답을 서버 커밋 뒤 브라우저 앞에서 붙잡아 둔 채 같은 탭에서 시간대를 `Asia/Seoul`로 저장하고 응답을 놓아주자, 편집 칸의 기한이 DB의 `due_at`을 서울 시각으로 읽은 값과 같았고 "작업 공간 시간대(Asia/Seoul)"를 보였습니다. 고치기 전 코드로 실행하자 두 경로 모두 편집 칸이 뉴욕 시각(`02:00`, 저장값은 서울 `15:00`)과 이전 시간대 이름을 보여 네 항목이 실패했습니다. 고친 코드에서는 8개 항목과 기존 57개, 14개, 20개, 13개, 5개 항목이 모두 통과했습니다.
- 리뷰에서 지적된 일광 절약 시간이 끝나기 직전의 날짜 최솟값을 별도 점검 스크립트(7개 항목)로 확인했습니다. 목록 응답의 `checked_at`을 바꿔 화면의 서버 시각을 정하고, `America/New_York`에서 시계가 되돌아가기 45분 전(`2026-11-01T05:15Z`, 동부 일광 절약 시간 01:15)에 `01:10`을 고르자 입력이 유효했고 저장 요청이 그 값으로 나갔습니다. PostgreSQL은 이 시각을 나중 것(`06:10Z`)으로 읽으므로 55분 뒤입니다. 되돌아간 뒤(`06:30Z`)와 시계가 바뀌지 않는 날(`2026-10-20T15:00Z`)에는 최솟값이 정확히 1분 뒤(`01:31`, `11:01`)였고 지난 시각은 거부됐습니다. 고치기 전 코드로 실행하자 최솟값이 `01:16`이라 `01:10`이 거부되어 세 항목이 실패했습니다. 고친 코드에서는 7개 항목과 기존 57개, 14개, 20개, 13개, 8개, 5개 항목이 모두 통과했습니다.
- 운영자 시각 승인용 스크린샷 6장(배지와 필터, 리마인더 편집, 기한 상태를 각각 데스크톱과 390px로)은 세션 임시 디렉터리에 PNG로 저장했고 저장소에는 넣지 않았습니다.

## 확인하지 않은 것

- 스크린 리더 낭독, 다크 모드, 실제 기기의 날짜 선택기(Chromium의 `datetime-local` 값은 `fill`로 넣었습니다)는 확인하지 않았습니다.
- 응답을 받지 못한 저장(네트워크 오류나 5xx)의 안내와 리마인더 목록 API(`GET /api/inbox/reminders`)는 브라우저에서 실행하지 않았고, 목록 API는 DB 테스트로만 확인했습니다.
- 일광 절약 시간이 바뀌는 날의 화면 입력은 브라우저에서 만들지 않았고, 변환 규칙은 DB 테스트로만 확인했습니다.
- migration 034는 운영 DB에 적용하지 않았고 배포하지 않았으므로, 운영 데이터와 실제 Instagram 계정으로 이 화면을 확인하지 않았습니다.
