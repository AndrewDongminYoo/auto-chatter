# 대시보드 메뉴별 화면 검증

## 대상과 경계

[메뉴별 화면과 시작하기](../specs/2026-10-06-app-menu-views.md)를 확인했습니다.
[자동 라벨 규칙 화면 검증](2026-10-04-inbox-label-rules-ui-verification.md)과 같은 방식으로, 실제 `public/app` 파일과 실제 `appApi`를 로컬 PostgreSQL 17(포트 5434)의 일회용 DB(`automations_ui`, 실행마다 새로 만들고 확인 뒤 삭제)에 연결한 임시 로컬 서버를 세션 임시 디렉터리에 새로 만들어 사용했습니다.
임시 서버는 `/app/` 응답에 `public/_headers`의 Content-Security-Policy를 그대로 붙였고, Supabase는 세션 쿠키 값으로 `/user` 응답을 돌려주는 대역으로 바꿨습니다. 대역은 다른 모든 외부 요청을 거절하고 기록했으며, 기록된 외부 요청 시도는 0건이었습니다.
합성 데이터는 소유자·관리자·상담원이 있고 연결과 규칙이 없는 막 가입한 작업 공간입니다. Instagram을 거쳐야 하는 연결과 규칙 만들기는 임시 서버가 DB에 직접 넣었고, 계정의 발송 켜기는 계정 화면의 실제 버튼으로 바꿨습니다. 서비스 전체 발송 설정은 임시 서버의 환경 값으로 바꿨습니다.
화면 동작은 Playwright로 headless Chromium을 조작해 확인했고, 스크린샷은 저장소 밖에 두었습니다.

## 자동 검사

`corepack pnpm check-types`와 `corepack pnpm test`(239개)가 통과했습니다. 바뀐 파일은 브라우저에서만 실행되므로 이 검사들은 화면 동작을 확인하지 않습니다.

## 브라우저 검사

점검 스크립트의 72개 항목이 모두 통과했습니다.

- 막 가입한 소유자는 로그인하면 홈만 보고, 홈 링크에 `aria-current="page"`가 붙으며, 첫 표시에서는 초점이 옮겨지지 않았습니다.
- 운영과 같이 새 연결이 제한된 상태에서는 1단계가 "연결 제한 중"으로 표시되고 이동 링크가 없었으며, 설명이 연결 제한을 알렸습니다. 연결을 열고 다시 열자 1단계만 열려 있고 2·3단계는 "계정을 먼저 연결하세요"로 잠겨 있었으며, 3단계 설명이 전체 발송 중지를 알렸습니다.
- 여섯 메뉴를 차례로 누르자 주소가 그 메뉴로 바뀌고, 그 화면만 보이고, `aria-current`가 옮겨지고, 화면 영역에 초점이 가고, 맨 위로 이동했습니다. 소유자에게 보인 구역은 spec의 메뉴 표와 같았습니다.
- 뒤로 가기와 앞으로 가기가 화면을 바꿨고, 연락처 필터에 입력한 글이 다른 메뉴를 다녀와도 남았습니다.
- 인증 링크 모양(`access_token=x&type=recovery`)과 초대 링크 모양(`invite=abc`)의 주소 변경, 본문 바로가기(`#main`)는 화면을 바꾸지 않았습니다. `#flows-section`은 자동화, `#inbox`와 `#inbox-section`으로 새로 연 페이지는 인박스를 보여 줬습니다.
- 관리자는 시작하기를 보고, 상담원은 보지 않았습니다. 상담원의 설정 화면에는 지금과 같이 작업 공간 설정만 보였습니다.
- 연결을 넣은 뒤에는 1단계가 완료로 바뀌고 2·3단계가 열렸으며, 2단계 링크가 자동화 화면을 열었습니다. 규칙을 넣고 계정 화면에서 발송을 켜자 홈의 2단계가 완료, 3단계가 "전체 발송 재개 대기"로 바뀌었고 시작하기는 남아 있었습니다. 전체 발송을 켜고 다시 열자 시작하기가 사라지고 발송 배너가 켜진 상태를 보였습니다.
- 390px 폭에서 메뉴와 페이지가 가로로 넘치지 않았고(메뉴 350px), 메뉴 링크 높이는 모두 44px였습니다.
- 페이지 오류와 CSP 위반은 없었습니다. 콘솔에는 대역이 막은 게시물 목록 요청(`/api/connections/<id>/media`)의 503만 남았습니다.

`viewFromHash()`가 메뉴가 아닌 값에 홈을 돌려주도록 바꾸자 본문 바로가기 항목이 실패했고, 되돌리자 다시 모두 통과했습니다.
연결 제한 항목은 처음 실행에서 1단계가 "전체 발송 재개 대기"로 표시되는 실제 결함을 잡았고, 고친 뒤 통과했습니다.

## 구조 검사

- 구역을 옮긴 `index.html`의 `id` 속성은 바꾸기 전 247개가 모두 남았고, 새로 생긴 것은 화면 여섯 개와 시작하기의 요소뿐이며 중복은 없었습니다.
- 한 화면의 동작이 다른 화면의 요소에 초점을 주거나 스크롤하는 호출은 없었습니다. `focusEditor()`의 세 호출은 모두 자동화 화면 안에 있고, 인박스와 플로 모듈은 다른 구역의 요소를 읽지 않습니다.
- "위의", "상단의"처럼 위치로 구역을 가리키는 문구 다섯 개는 모두 같은 화면 안의 요소를 가리킵니다.

## 화면 다듬기 관점

`make-interfaces-feel-better`의 full 범위로 바뀐 부분을 확인했습니다.

| 구분   | 확인한 근거                                | 결과                                                            |
| ------ | ------------------------------------------ | --------------------------------------------------------------- |
| 글자   | 시작하기 제목·설명, 단계 번호              | 기존 제목·`hint` 스타일 사용, 단계 번호는 고정 폭 숫자          |
| 표면   | 단계 행과 이동 버튼, 1280px·390px 스크린샷 | 기존 반경 토큰과 테두리, 이동 링크 높이 44px                    |
| 모션   | 화면 전환, 단계 상태 변화                  | 애니메이션을 더하지 않음; 상태는 글자·배지로 표시               |
| 아이콘 | 완료 표시(✓)                               | 장식으로만 쓰고 화면 읽기에서는 빼며 "완료" 배지가 같은 뜻 전달 |
| 성능   | 전환 방식                                  | `hidden` 속성만 바꾸며 `transition`·`will-change`를 더하지 않음 |

남은 수정 필요 사항은 없습니다(Approve). Safari·Firefox와 실기기 확인은 아래와 같이 하지 않았습니다.

## 확인하지 않은 것

운영 화면, 실제 Instagram 연결과 발송, Safari·Firefox, 실기기 터치와 화면 읽기 프로그램의 실제 음성 출력은 확인하지 않았습니다.
