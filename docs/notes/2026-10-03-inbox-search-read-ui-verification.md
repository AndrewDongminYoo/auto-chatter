# 인박스 검색·필터·읽음 상태 화면 검증

## 대상과 경계

GitHub [#23](https://github.com/AndrewDongminYoo/auto-chatter/issues/23)의 첫 부분인 [검색, 필터와 읽음 상태](../specs/2026-09-27-instagram-inbox.md#검색-필터와-읽음-상태)를 확인했습니다.
라벨·내부 메모(#23-B)와 리마인더(#23-C)는 이 변경에 없고 다음 회차에서 다룹니다.
실제 `public/app` 파일과 실제 `appApi`를 로컬 PostgreSQL 17(포트 5434)의 일회용 DB(`automations_ui`, 실행마다 새로 만들고 확인 뒤 삭제)에 연결한 임시 로컬 서버를 사용했습니다.
임시 서버는 `/app/` 응답에 `public/_headers`의 Content-Security-Policy를 그대로 붙였습니다.
Supabase는 세션 쿠키 값으로 `/user` 응답을 돌려주는 대역으로 바꿨고, 대역은 다른 모든 외부 요청을 거절하고 기록하도록 했습니다. 기록된 외부 요청 시도는 0건이었고, 운영 DB·Supabase·Meta·Cloudflare는 호출하지 않았습니다.
합성 데이터는 소유자·관리자·상담원 두 명, 연결 둘(`ui_shop`, `ui_studio`, 둘 다 연결 해제 상태), 대화 여섯 개와 메시지 여덟 개입니다. 상담원은 대화 둘을 모두 읽었고 하나는 둘째 메시지까지 읽은 상태로 시작했습니다.
화면 동작은 Playwright 1.62로 headless Chromium(chrome-headless-shell 1243)을 조작해 확인했습니다.

## 자동 검사

`src/app/inbox-search-read.db.test.ts`의 16개 테스트가 목록 순서와 커서, 필터 조합, 검색의 글자 그대로 일치, 읽음 위치, 멤버 제거, 세 삭제 함수와의 동시 실행, migration 032 재실행을 확인합니다.

- 마지막 메시지 시각이 같은 대화 네 개가 50번째와 51번째 사이에 걸치고, 그 앞뒤 대화가 같은 밀리초 안에서 1마이크로초씩 다른 53개 대화를 두 페이지로 나눠 읽으면 순서대로 한 번씩 나옵니다. 커서의 시각을 밀리초로 잘라 보내도록 잠시 바꾸자 이 테스트가 실패했습니다.
- 읽음 쓰기에서 연결 행 `FOR SHARE`를 빼자 연결·사람 삭제와의 동시 실행 테스트 셋이 실패했고(삭제 뒤에 읽음 행이 남음), 멤버 행 `FOR SHARE`를 빼자 먼저 커밋한 멤버 제거 뒤에도 읽음 쓰기가 `200`으로 끝나 실패했습니다. 두 실패 모두 잠금 대기 시간 초과가 아니라 값 확인에서 나왔습니다. 잠금을 되돌리자 모두 통과했습니다.
- 상담원의 멤버 행을 다른 트랜잭션이 잡은 채로 읽음 쓰기와 작업 공간 삭제를 차례로 시작하면, 읽음 쓰기가 작업 공간 행을 먼저 잡고 있어 삭제가 그 뒤에 줄을 섰고, 멤버 행을 풀자 읽음 쓰기(`200`)와 삭제가 차례로 끝나 읽음 행이 남지 않았습니다. 작업 공간 행 `FOR SHARE`를 빼자 같은 테스트가 `deadlock detected`로 실패했고, 되돌리자 통과했습니다.
- 읽음 쓰기를 커밋 직전에 붙잡아 둔 채 연결·사람·작업 공간 삭제를 시작하면 삭제가 기다렸다가 읽음 행을 지웠고, 반대로 삭제를 열어 둔 채 읽음 쓰기를 보내면 삭제가 커밋된 뒤 읽음 쓰기가 `404` 또는 `403`으로 끝나 읽음 행이 남지 않았습니다. 교착은 없었습니다.

## 브라우저 검사

같은 점검 스크립트의 29개 항목이 모두 통과했습니다.

- 상담원 목록은 마지막 메시지가 최근인 대화부터 나왔고, 읽지 않은 메시지가 있는 대화 넷에만 "안 읽음 1" 배지가 글자로 붙었습니다. 상담원의 담당자 선택은 전체·나·미배정뿐이었고, 임시 서버의 요청 기록에 상담원의 `/api/inbox/assignees` 요청은 없었습니다.
- 키보드: "새로고침"에서 Tab으로 검색 상자에 가서 `배송`을 입력하고 Enter를 누르자 본문에 `배송`이 있는 대화 셋만 남았습니다. 이어서 Tab으로 검색 버튼, 계정, 상태, 담당자, "안 읽은 대화만"으로 초점이 옮겨 갔고, 체크박스에서 Space를 누르자 검색과 함께 적용되어 대화 둘이 남았습니다. "안 읽은 대화만" 다음 Tab은 첫 대화로 갔고, Enter로 그 대화를 열었습니다.
- 선택 상자의 값(담당자 나·미배정·멤버, 상태 진행 중·완료)은 키보드 대신 Playwright의 `selectOption`으로 골랐습니다. [플로 편집기 검증](2026-10-02-flow-editor-ui-verification.md)에 적은 대로 headless Chromium에서는 닫힌 `<select>`에 보낸 합성 키로 값이 바뀌지 않기 때문입니다. 검색과 "나"를 함께 고르면 대화 둘, 진행 중을 더하면 하나가 남았고, 맞는 대화가 없으면 "검색어나 보기 조건에 맞는 대화가 없습니다."가 보였습니다. 검색 상자를 비우면 대화 여섯 개가 다시 보였습니다.
- 대화를 열자 목록을 다시 불러오지 않고 그 대화의 배지만 사라졌고, DB의 읽은 위치가 그 대화의 가장 최근 메시지 ID와 같았습니다. 읽음 요청은 한 번이었고, 새 메시지 없이 "대화 새로고침"을 눌러도 읽음 요청이 더 가지 않았습니다.
- 관리자로 들어가면 담당자 선택에 자기를 뺀 다른 멤버가 보였고, 다른 상담원을 고르자 그 상담원의 대화만 남았습니다. 상담원이 읽은 대화도 관리자에게는 "안 읽음 1"로 보여 읽음 상태가 멤버마다 따로임을 확인했습니다.
- 390px에서 목록, 검색 결과, 연 대화 모두 문서의 `scrollWidth`가 화면 너비(390)를 넘지 않았고, 검색 상자·검색 버튼·상태·담당자 선택·"안 읽은 대화만" 줄의 높이는 44px 이상이었습니다.
- 페이지 오류와 CSP 위반은 없었습니다. 콘솔 오류는 기존 규칙 편집기의 게시물 목록 요청(`/api/connections/:id/media`)이 받은 `409 media_reconnect_required`의 리소스 로드 기록뿐이며, 합성 연결에 토큰이 없어서 생깁니다.
- 점검 스크립트가 결함을 잡는지 보려고 대화를 열 때의 읽음 요청을 잠시 빼고 실행하자 배지가 사라지기를 기다리다 시간 초과로 멈췄습니다. 코드를 복원하고 DB를 새로 만들어 다시 실행하자 29개 항목이 모두 통과했습니다.
- 운영자 시각 승인용 스크린샷 6장(상담원 목록, 검색과 안 읽음 필터, 연 대화, 관리자의 담당자 필터는 데스크톱, 검색 결과와, 연 대화와 배지가 사라진 목록을 함께 담은 화면은 390px)은 세션 임시 디렉터리에 PNG로 저장했고 저장소에는 넣지 않았습니다.

## 확인하지 않은 것

- 실제 키보드로 선택 상자를 여닫는 동작, 스크린 리더 낭독, 다크 모드는 확인하지 않았습니다.
- 대화 목록의 "대화 더 보기"(51개 이상)는 브라우저에서 실행하지 않았고, 커서는 DB 테스트로만 확인했습니다.
- 읽음 요청이 실패했을 때 배지를 그대로 두는 동작과, 열어 둔 대화에 새 DM이 온 뒤 새로고침하면 다시 읽음으로 표시하는 동작은 브라우저에서 실행하지 않았습니다.
- 저장한 DM이 많은 작업 공간의 목록 비용은 로컬 합성 데이터로 한 번 비교했을 뿐이며([스펙](../specs/2026-09-27-instagram-inbox.md#검색-필터와-읽음-상태)), 검색어를 넣은 요청과 운영 규모에서는 측정하지 않았습니다.
- migration 032는 운영 DB에 적용하지 않았고 배포하지 않았으므로, 운영 데이터와 실제 Instagram 계정으로 이 화면을 확인하지 않았습니다.
