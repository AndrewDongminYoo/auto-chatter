# 인박스 상담 전환 로컬 검증

## 범위

ManyChat 대체 루프 7회차의 [명세](../specs/2026-09-27-inbox-human-handoff.md)와 [계획](../plans/2026-09-27-inbox-human-handoff.md)을 구현했습니다.
[#17](https://github.com/AndrewDongminYoo/auto-chatter/issues/17)의 조회 근거를 상담 상태에 연결하며 [#18](https://github.com/AndrewDongminYoo/auto-chatter/issues/18)의 수동 답장 구현 전에 자동화 중지 경계를 완성합니다.
수동 발송·발신 이력·화면·운영 배포·실계정 검증은 수행하지 않았으며 이슈 전체 완료를 선언하지 않습니다.

## 실패와 수정

상담 API 5건은 경로 부재로 실패했고, 자동화 guard 6건은 상담 중인 연락처의 claim·응답 수신·발송 전 검사에서 실패했습니다.
독립 플래그와 각 guard를 추가한 뒤 통과했습니다.
동시 직접 중지와 상담 시작 테스트에서 연결 행의 `FOR UPDATE`가 연락처 삽입의 외래 키 `KEY SHARE`와 충돌하는 교착 상태를 재현했습니다.
연결 잠금을 `FOR NO KEY UPDATE`로 좁혀 상담 변경의 직렬화를 유지하면서 외래 키 검사를 허용했습니다.
두 요청의 성공과 직접 중지 보존을 확인했습니다.
전체 재검사에서 기존 팔로우 fixture가 모의 완료·확인 응답의 같은 밀리초 때문에 비결정적으로 미팔로우 응답을 건너뛰었습니다.
공급자 완료와 두 확인 응답의 시각을 분리하고 첫 분기의 발송 결과도 즉시 확인하도록 fixture를 수정했습니다.
실제 빠른 확인 응답의 기존 시각 조건은 이 상담 전환 범위에서 변경하지 않았습니다.

013 최초 적용과 재실행, 근거·수신 기록을 잃은 뒤 재개, 근거가 바뀐 재시작, 여러 대화의 독립 중지 사유를 확인합니다.
감사 INSERT를 트리거로 실패시켜 상담 상태·중지 사유·감사 행이 함께 롤백되는 것도 확인했습니다.
API 역할은 새 테이블을 읽을 수 없고 두 서버 역할은 감사 UPDATE·DELETE를 할 수 없습니다.
새 Compose DB 초기화 스크립트의 실제 권한 SQL도 실행해 감사 UPDATE를 금지합니다.
처음에는 전체 테이블 UPDATE 허용 때문에 실패했고 감사 테이블의 UPDATE를 명시적으로 회수한 뒤 통과했습니다.
조회·정책 검사는 발송 예약이 아니며 최종 검사 이후의 공급자 POST는 취소할 수 없습니다.

## 독립 검토와 문서 정합성

거래·CAS·소유권·권한과 자동화 guard·회귀 fixture를 나누어 읽기 전용 독립 리뷰를 수행했습니다.
추가 코드 결함은 보고되지 않았고, 마이그레이션 최초 적용 증거 부족은 012 구조에서 013을 적용하는 fixture로 보강했습니다.
README·CLAUDE·Cloudflare·단일 서버·다중 사용자 안내의 현재 runner 범위를 003–013으로 맞췄습니다.
관리자 삭제 순서는 감사 행 → 상담 전환 행 → 기존 연락처 중지·outbox·연결 순서를 포함하며 서버 DELETE 권한을 확대하지 않습니다.
기존 백로그 작성 당시의 003–012 기록과 이전 운영 배포 기록은 역사적 근거로 보존합니다.
Oracle의 근거·미확인 상태 보존 선례와 직접 선례 부재는 명세에 출처·적용 방향과 함께 기록했습니다.
