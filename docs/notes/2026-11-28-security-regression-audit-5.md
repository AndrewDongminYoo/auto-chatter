# 보안 회귀 점검 5차: 작업 공간 공개 API (#62)

## 범위

[4차 점검](2026-11-09-security-regression-audit-4.md) 뒤에 [#48](https://github.com/AndrewDongminYoo/auto-chatter/issues/48)로 새로 열린 작업 공간 공개 API를 2026-11-28 `main` `67a9572` 기준으로 점검했습니다.
이 API는 이 서비스에서 처음으로 외부 요청이 연락처를 바꾸고 메시지 발송을 일으키는 경로입니다.

1. API 키: 발급·해시 보관·만료·폐기와 설정 화면 #417(migration 080)
2. 연락처 읽기: `GET /v1/contacts` #418
3. 연락처 쓰기: `PATCH /v1/contacts/{connection_id}/{sender_id}`, `GET /v1/fields` #420(migration 081)과 태그 정규화 #421
4. 플로 시작: `GET /v1/flows`, `POST /v1/flows/{flow_id}/starts` #422(migration 082)

4차 점검 뒤에 합쳐진 다른 기능(인박스 첨부 #412, 활성 연락처 #407·#408·#410·#411, 요금제 한도 #414·#416, 토큰 키 회전 등)은 이번 범위에 넣지 않았습니다.
기능별 불변 조건은 [CLAUDE.md](../../CLAUDE.md), [기능별 불변 조건](../agents/feature-invariants.md)과 각 명세가 소유하므로 여기서 다시 적지 않습니다.

세 관점으로 나눠 코드를 읽었습니다.

- 인증, 권한, 작업 공간 경계
- 남용, 한도, 멱등성, 입력 처리
- 발송 안전성과 DB 데이터 경로

## 고친 것

### 1. 키를 확인한 뒤 폐기·만료된 키로 플로를 시작할 수 있음 (중간)

- 키는 `src/app/public-api.ts`에서 트랜잭션 밖에서 한 번 읽고, `startFlow`는 키를 다시 읽거나 잠그지 않았습니다.
- 관리자의 폐기, 만든 멤버의 제거·강등에 따른 자동 폐기, 만료가 키 확인과 시작 커밋 사이에 일어나면 시작이 커밋되고 첫 DM이 나갔습니다.
- 두 관점에서 각각 같은 문제를 찾았습니다. 연락처 쓰기 설계는 같은 시간 차를 받아들였지만, 메시지를 보내는 플로 시작 설계에는 언급이 없었습니다.
- 시작 트랜잭션 안에서 키 행을 잠그고 폐기·만료를 다시 확인해, 없어진 키는 같은 `401 invalid_api_key`로 거절합니다.

### 2. 발송 직전에 검증된 DM 신원을 다시 확인하지 않음 (낮음)

- 외부 시작 실행의 발송 직전 검사는 시작할 때 고른 수신자를 그대로 썼습니다.
- 시작 뒤 다른 댓글 작성자가 같은 수신자로 연결되어 신원이 모호해져도 그대로 보냈습니다. 캠페인 발송은 같은 경우를 `no_dm_identity`로 막습니다.
- 외부 시작 실행의 발송 직전 검사에 캠페인과 같은 신원 재확인을 더했습니다. 연결이 사라지면 다시 시도하지 않고 `blocked`(`no_dm_identity`)로 끝납니다. DM 트리거 실행은 바뀌지 않습니다.

### 3. IPv6 주소를 바꿔 IP별 한도를 피할 수 있음 (낮음)

- 공개 API의 IP별 한도 키가 `CF-Connecting-IP` 원문이어서, IPv6 /64 하나를 가진 클라이언트는 주소마다 새 한도 창을 얻었습니다.
- 존재하지 않는 키를 보내는 요청이 DB 조회를 만들므로, [API 키 설계](../specs/2026-11-27-workspace-api-keys-design.md)가 이 한도로 막으려던 비용 증폭이 IPv6에서는 막히지 않았습니다. 데이터 노출은 없습니다.
- IPv6는 /64 접두사로 묶어 셉니다. IPv4와 형식이 맞지 않는 값의 처리는 그대로입니다.

### 4. 플로 시작의 `sender_id`에 짝 없는 서로게이트를 받음 (참고)

- 태그와 필드 값은 짝 없는 서로게이트를 거절하지만, 플로 시작의 `sender_id`는 받았습니다. 요청 해시는 원래 문자열로 계산하는데 PostgreSQL에는 U+FFFD로 저장됩니다.
- 발신자 ID는 숫자라서 결과는 `contact_not_found`였고 보안 영향은 없었습니다. 다른 입력과 같이 `400 invalid_request`로 거절합니다.

## 추가한 회귀 테스트

각 테스트는 고치기 전의 코드에서 실패하고 고친 뒤 통과하는 것을 확인했습니다. 만료된 키의 단언과 DM 트리거 실행의 회귀 방지 테스트는 예외이며, 아래에 적었습니다.

- `src/app/public-flow-starts.db.test.ts`: 다른 연결에서 멤버 제거에 따른 키 폐기를 커밋하지 않은 채 두고 시작을 보낸 뒤, 시작이 잠금을 기다리는 것을 확인하고 폐기를 커밋합니다. 시작은 `401 invalid_api_key`와 `WWW-Authenticate` 헤더를 받고, 요청 키·시작·실행·발송 행이 하나도 남지 않습니다. 고치기 전에는 `202`였습니다.
- 같은 파일: 폐기된 키로 같은 요청을 다시 보내면 `401`입니다. 고치기 전에는 저장된 결과를 다시 돌려줬습니다. 만료된 키를 시작 함수에 직접 넘기는 단언도 함께 있으며, 이 단언만 따로 실패시켜 보지는 않았습니다.
- `src/app/public-flow-starts.db.test.ts`: 시작 뒤 다른 댓글 작성자가 같은 수신자에게 보낸 비공개 답장이 `sent`가 되면 첫 DM이 `blocked`(`no_dm_identity`)로 끝나고 POST가 없습니다. 고치기 전에는 `sent`였습니다.
- `src/instagram/dm-flow-delivery-worker.db.test.ts`: 같은 상황의 DM 트리거 실행은 이전과 같이 동작합니다. 회귀 방지용이라 고치기 전에도 통과합니다.
- `src/app/public-api.test.ts`: 같은 /64의 압축·전개·IPv4 꼬리 표기가 한 한도 키(`2001:db8:1:2::/64`)를 쓰고, 다른 /64는 다른 키를, IPv4는 원래 주소를, 형식이 맞지 않는 값은 `unattributed`를 씁니다.
- `src/app/public-api.test.ts`의 플로 시작 본문 검사: `sender_id`의 `U+D800`과 `U+DC00`이 `400 invalid_request`입니다.

같은 작업 트리에서 `check-types`와 `lint`, `build:cloudflare`가 exit 0이었고, `test` 741개, `test:db` 1,130개, `test:cloudflare` 105개가 통과했으며, `trunk check --all`은 625개 파일에서 문제가 없었습니다.

## 고치면서 정한 것

- 폐기된 키로 같은 요청을 다시 보내도 저장된 결과를 돌려주지 않고 `401`입니다. 인증 단계가 이미 폐기된 키를 거절하므로, 시작 트랜잭션 안의 키 확인을 재전송 처리보다 먼저 둡니다.
- 키 행은 `FOR SHARE`로 잠급니다. 폐기는 키 열을 바꾸지 않아 `FOR NO KEY UPDATE`를 잡는데, `FOR KEY SHARE`(외래 키가 잡는 잠금)는 이와 충돌하지 않기 때문입니다. 같은 키의 마지막 사용 기록은 시작 트랜잭션이 끝날 때까지 잠깐 기다립니다.
- IPv4가 들어 있는 IPv6 주소(`::ffff:a.b.c.d`)는 IPv4 주소로 셉니다. 이런 주소가 모두 한 /64를 나눠 쓰지 않게 하려는 것입니다. 주소 형식을 통과했지만 주소가 아닌 값(`1::2::3` 등)은 `unattributed`로 셉니다.

## 확인한 의심 사항

- 키 형식과 조회: 형식 검사가 조회보다 먼저이고, 조회는 SHA-256 해시의 고유 인덱스 일치라서 문자열 비교의 시간 차가 없습니다. 폐기·만료 키는 SQL에서 거릅니다.
- 키가 없거나, 형식이 틀리거나, 모르는 키이거나, 폐기·만료된 키는 모두 같은 `401 invalid_api_key`입니다.
- 한도 순서: IP별 한도는 헤더를 읽기 전에, 키별 한도는 인증 뒤 라우팅 전에 쓰며 둘 다 닫힌 쪽으로 실패합니다. 한도 키는 `CF-Connecting-IP`만 읽고 `X-Forwarded-For`는 읽지 않습니다.
- 경로와 메서드: 끝의 `/`, 이중 `/`, 대문자 `/V1/`은 어떤 경로와도 맞지 않습니다. `HEAD`, `OPTIONS`, 모르는 메서드는 인증 뒤 `405`이며 마지막 사용을 기록하지 않습니다. 경로의 `%2F`는 발신자 값으로만 풀립니다.
- 권한: `/v1/key` 외의 모든 경로가 `contacts:read`를, 쓰기가 `contacts:write`를, 두 플로 경로가 `flows:start`를 본문을 읽기 전에 요구합니다.
- 작업 공간 경계: 세 API의 모든 질의가 키의 작업 공간에 묶입니다. 다른 작업 공간의 연결·필드·플로 ID는 없는 ID와 같은 응답이고, 다른 작업 공간의 커서는 위치로만 쓰여 아무것도 돌려주지 않습니다. 요청 키는 작업 공간마다 따로입니다.
- 수신자 선택: 수신자는 공급자가 확인한 비공개 답장의 수신자에서만 나오며, 요청에는 `sender_id`만 있어 수신자를 조작할 수 없습니다.
- 데이터 노출: 연락처 응답에 댓글 작성자의 사용자명, 동의 상태, 댓글이나 DM 본문이 없고, 플로 목록에 정의와 메시지 본문이 없습니다. 내보내기는 `key_hash`와 `request_hash`를 뺍니다.
- 대시보드 키 관리: 목록·발급·폐기가 `admin`이고 작업 공간에 묶이며, 원래 키는 `no-store`인 발급 응답에만 나옵니다. 발급과 멤버 제거·강등은 작업 공간 잠금으로 직렬화됩니다.
- 멱등성: 같은 요청 키의 동시 요청은 고유 인덱스에서 기다린 뒤 다시 받거나, 첫 요청이 롤백되면 진행합니다. 거절된 요청은 키 행도 롤백합니다. 삭제 뒤에는 해시가 고정 표시값이라 `409`입니다.
- 입력: 본문 크기는 스트림을 읽으며 세므로 `Content-Length`를 믿지 않습니다. 중복 키, 객체가 아닌 본문, 모르는 키, `__proto__`는 `400`입니다. 숫자는 64비트 실수로 정확히 담기는 값만, 날짜는 왕복 검사를 통과한 값만 받습니다.
- SQL은 모두 상수 조각과 `$n` 매개변수로 만들고, 사용자 입력이 응답 헤더에 들어가지 않습니다. 대시보드에는 `innerHTML`이 없어 키 이름이 HTML로 들어갈 수 없습니다.
- 발송 직전 검사: 실행 상태, 플로 켜짐, 연결과 토큰, 24시간 창, 수신 거부와 명시적 마케팅 동의, 댓글 연락처와 수신자의 일시 중지, 상담 전환, 활성 연락처 한도를 claim 뒤와 POST 직전에 다시 읽습니다.
- 잠금: 시작의 작업 공간·플로·연결 잠금이 세 삭제 함수, 플로 끄기와 직렬화되고, 수신자별 advisory lock이 DM 시작과 같습니다.
- DB: 새 두 테이블은 RLS가 켜져 있고 서버 역할은 SELECT와 INSERT만 가집니다. 세 삭제 함수의 FK 순서가 맞고, `delete_connection_data`는 `search_path`가 고정된 SECURITY DEFINER입니다. migration 080~082는 다시 적용해도 같은 상태로 끝납니다.

## 받아들인 성질

- 키가 없거나 형식이 틀린 요청도 IP별 한도 호출 비용을 씁니다. 형식 검사를 한도보다 먼저 하면 이 비용은 줄지만, 공격자 쪽 비용도 거의 없어 얻는 것이 적습니다.
- 거절된 플로 시작과 같은 요청의 재전송도 작업 공간의 시간당 쓰기 한도를 씁니다. 한도 객체는 트랜잭션 안에서 되돌릴 수 없기 때문이며 설계와 불변 조건에 적혀 있습니다. 거절된 요청을 세지 않는 연락처 쓰기와 다릅니다.
- 연결당 시간당 DM 시작 한도는 DM 시작과 같이 잠금 없이 세므로 동시 요청에서 조금 넘을 수 있습니다. 수신자별 10분 대기 거절도 `429 rate_limited`이고 `Retry-After`가 없습니다.
- 받아들인 시작이 상담 전환, 수신자 일시 중지, 연결 일시 중지, 발송 스위치 때문에 미뤄지면 24시간 창이 열려 있는 동안 늦게 나갈 수 있습니다. 기존 DM 플로 발송과 같이 다시 시도하는 검사들이며, 늦어지는 시간은 24시간 창이 제한합니다.
- 이미 받아들인 시작의 첫 DM은 키를 폐기해도 멈추지 않습니다. 폐기는 새 시작만 막습니다.

## 테스트하지 않은 항목

- Cloudflare Worker에서 오는 요청의 `CF-Connecting-IP`가 공유 주소인지는 저장소 코드로 확인할 수 없습니다. 그렇다면 Worker 위의 연동들이 IP별 한도 창 하나를 나눠 씁니다.
- Workers 런타임이 `HEAD`를 처리기에 넘기기 전에 `GET`으로 바꾸지 않는지는 확인하지 않았습니다.
- 운영 Worker에서 이 수정들의 동작은 확인하지 않았습니다. 단위·DB·workerd 테스트는 운영 동작을 증명하지 않습니다.
