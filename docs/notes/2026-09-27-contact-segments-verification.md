# 세그먼트 검증 기록

## 구현과 자동 검사

저장된 세그먼트 API가 없는 상태에서 목록의 기대 HTTP 200 대신 404를 관찰했습니다.
저장 테이블이 없는 로컬 DB에서도 생성 검사가 실패한 뒤 migration 009를 추가했습니다.
실제 PostgreSQL은 작업 공간·계정 격리, 정규화 이름 중복, 태그 변경 뒤 목록 갱신, 보관 뒤 조회 거부, 49개에서 동시 생성 후 50개 제한과 마이그레이션 재실행을 검사합니다.
workerd는 제한된 서버 역할로 생성·조회·보관하며 다른 사용자 조회·보관이 404인 것을 확인합니다.
새 테이블의 RLS는 활성화하고 DELETE 권한은 부여하지 않습니다.
타입 검사, 단위 98개·DB 93개·workerd 22개가 통과했습니다.

## UI

운영 CSP를 적용한 로컬 UI에 합성 계정·세그먼트·댓글 참여자를 주입했습니다.
fixture에서 세그먼트를 제거하면 기대한 저장 필터 검사가 실패하는 것을 확인했습니다.
저장 HTTP 503 뒤 이름 보존, 저장 성공 뒤 목록 갱신, 세그먼트로 연락처 조회와 태그 초안이 있을 때 전환 취소를 확인했습니다.
필터 보관은 태그 초안을 버리도록 요청하지 않고 초안을 보존합니다.
선택이 없으면 보관 버튼을 비활성화합니다.
로그아웃 뒤 지연된 세그먼트 목록·생성 응답은 초기화된 상태에 반영되지 않습니다.
첫 지연 목록 fixture는 GET method를 잘못 검사해 요청을 가로채지 못했으며, 실제 GET을 가로채는지 확인한 뒤 검사했습니다.

## 운영 경계

프로젝트 전용 Oracle 선례는 `[no precedent found]`였고 Wiki 최신성은 확인되지 않았습니다.
운영 마이그레이션·배포·실계정 변경·발송은 수행하지 않았습니다.
적용 전에는 migration 009와 서버 접근 스크립트가 필요합니다.
활성 세그먼트의 50개 제한은 서버 API의 작업 공간 잠금으로 보호하며 관리자 직접 SQL의 수량 제한은 아닙니다.
세그먼트는 현재 계정·단일 태그 조건만 지원하고 DM 수신 동의나 발송 가능 상태를 나타내지 않습니다.

## 로컬 리뷰

UI 읽기 전용 리뷰는 차단할 발견 사항이 없었습니다.
서버 리뷰는 새 명세의 404 문장이 기존 수동 계정 필터에도 적용되는 것으로 해석되는 문제를 지적했습니다.
PR #6의 수동 필터가 이미 빈 목록을 반환하는 것을 확인하고 공개 API 유지 지침에 따라 동작은 보존했습니다.
404 계약은 새 세그먼트 생성의 계정 참조·세그먼트 조회·보관으로 명시했습니다.
서버 리뷰의 그 외 격리·동시 생성·업그레이드·권한 범위에서는 추가 발견 사항이 없었습니다.

## 호스팅 리뷰 보완

태그 초안 때문에 목록을 갱신하지 않는 보관 경로에서 다음 페이지가 보관된 segment_id를 사용해 404가 되는 문제를 확인했습니다.
실제로 다음 페이지를 반환하는 브라우저 fixture로 이 실패를 관찰했습니다.
보관 성공 후 기존 목록의 조회 조건을 동일한 계정·태그 조건으로 바꾸고 커서와 초안을 유지합니다.
수정 후 다음 페이지가 추가되고 태그 초안·계정·태그 조건이 보존되는 검사가 통과했습니다.
화면 배치와 문구는 기존 승인 이미지에서 변경되지 않았습니다.
