# 외부 전송 설정 화면 검증

## 대상과 경계

GitHub #47의 [외부 전송](../specs/2026-10-01-flow-webhook-delivery.md#설정-화면) 설정 영역을 확인했습니다.
실제 `public/app` 파일과 실제 `appApi`를 로컬 PostgreSQL 17의 일회용 DB(`automations_ui`, 확인 뒤 삭제)에 연결한 임시 로컬 서버를 사용했습니다.
임시 서버는 `/app/` 응답에 `public/_headers`의 Content-Security-Policy를 그대로 붙였습니다.
Supabase는 세션 쿠키 값으로 `/user` 응답을 돌려주는 대역으로 바꿨고, 로그인은 이 대역 서버가 쿠키를 직접 설정하는 방식으로 대신했습니다. 대역은 다른 모든 외부 요청을 예외로 막았고, 운영 DB·Supabase·Meta·Cloudflare는 호출하지 않았습니다.
전달 단계(`deliverDueWebhooks`)는 실행하지 않았으므로 DNS 조회나 외부 주소로의 요청도 없었습니다.
`TOKEN_ENCRYPTION_KEY`는 실행할 때마다 새로 만든 임의 키입니다.

합성 데이터는 소유자와 상담원 멤버 각 1명, 연결 하나(`ui_shop`), 플로 하나, 주소 하나(`ui_crm`, 경로가 300자 넘는 URL), 전송 3건(`dead` 6회·HTTP 503·`http_error`, `sent` 1회·HTTP 204, `retry` 2회·`timeout`)입니다.
전송의 `payload`와 댓글 작성자 ID, 댓글 본문에는 화면에 나오면 찾을 수 있도록 표시 문자열을 넣었습니다.
화면 동작은 Chrome에서 확인했습니다.
폐기·끄기·다시 보내기의 확인 창은 `window.confirm`을 승인으로 바꿔 문구만 기록하고 넘겼습니다.

## 소유자

- 작업 공간 설정과 운영 상태 아래에 "외부 전송" 영역이 보였고, `ui_crm`의 이름·URL·켜짐 상태·유효한 키 ID와 발급 시각, 최근 전송 3건이 표시됐습니다.
- 전송 목록에는 주소 이름, 상태("전송 중단", "전송 완료", "재시도 대기"), "시도 6회 · 마지막 HTTP 상태 503 · 실패 사유: 수신 서버가 오류로 응답" 같은 결과 줄, 생성·전송 시각이 표시됐습니다. "다시 보내기" 버튼은 `dead` 행에만 있었습니다.
- `http://` 주소와 IP 주소(`https://10.0.0.1/x`)로 추가하면 서버가 `400 invalid_webhook_url`로 거부했고, 화면은 허용하는 주소 규칙을 안내했습니다. 공백만 있는 이름은 `invalid_webhook_endpoint` 문구가 나왔습니다.
- `sales_crm`(`https://crm.example.com/hook`)을 추가하자 비밀 영역이 열려 `whsec_`로 시작하는 비밀과 키 ID, 한 번만 보여 준다는 안내가 표시됐고, 입력 칸은 비워졌습니다.
- 비밀 영역이 열린 채로 새로 고치자 영역은 닫혀 있었고 입력 값과 안내 문장은 비어 있었습니다. "키 교체" 뒤에 "닫기"를 눌러도 같았습니다.
- 비밀이 보이는 동안에도 비밀은 읽기 전용 입력 칸의 값에만 있었고 문서 텍스트와 HTML에는 없었습니다. `sessionStorage`는 비어 있었고, `localStorage`에는 `public/app`이 쓰지 않는 키 하나(`public/app`에 `localStorage` 사용이 없음을 grep으로 확인)만 있었으며 그 값에 `whsec_`는 없었습니다.
- "키 교체" 뒤 `sales_crm`은 "키 교체 중" 배지와 키 두 개를 보였고, "키 교체" 버튼은 비활성화됐습니다. 같은 화면에서 교체 요청을 직접 보내면 `409 webhook_rotation_in_progress` 문구가 나왔습니다.
- "이전 키 폐기"는 확인 창을 거쳐 먼저 발급한 키를 폐기했고, 남은 키 하나로 바뀌었습니다. 키가 하나일 때 폐기 요청을 직접 보내면 `409 webhook_key_required` 문구가 나왔습니다.
- `ui_crm`의 "끄기"는 확인 창을 거쳐 "꺼짐"으로 바뀌었습니다. 꺼진 주소의 `dead` 전송에서 "다시 보내기"를 누르면 `409 webhook_endpoint_inactive` 문구가 나왔습니다.
- 주소를 4개 더 만들어 켜진 주소가 5개인 상태에서 `ui_crm`을 켜면 `409 webhook_endpoint_limit_reached` 문구가 나왔고, 하나를 끈 뒤에는 켜졌습니다.
- 켜진 주소의 `dead` 전송을 다시 보내자 그 행은 "전송 대기 · 아직 시도하지 않았습니다"가 됐고 버튼이 사라졌습니다. 같은 전송을 다시 요청하면 `409 webhook_delivery_not_dead` 문구가 나왔습니다.
- 외부 전송 영역의 HTML과 텍스트에 `payload` 값, 댓글 작성자 ID, 댓글 본문, 비밀은 나오지 않았습니다. 댓글 작성자 ID는 기존 연락처 영역에만 표시됐습니다.
- 페이지를 불러오는 동안 콘솔 오류와 CSP 위반은 없었습니다.

## 상담원

- 작업 공간 화면은 보였고 외부 전송 영역과 운영 상태 영역은 숨겨졌습니다.
- 임시 서버의 요청 기록과 브라우저의 resource 기록 모두에 `/api/webhooks` 요청이 없었습니다.
- 같은 화면에서 직접 보낸 `GET /api/webhooks/endpoints`는 `403 role_forbidden`이었습니다.

## 좁은 화면

같은 출처에서 연 390px 너비 팝업 창(스크롤 막대를 뺀 문서 너비 375px)에서 비밀 영역을 연 상태로 확인했습니다.
문서의 `scrollWidth`는 375px로 넘치지 않았고, 외부 전송 영역 안에 화면 밖으로 나간 요소가 없었습니다.
같은 검사는 일부러 넣은 300자 한 줄 요소를 넘침으로 찾아냈으므로, 긴 URL과 키 ID가 줄바꿈된다는 결과로 볼 수 있습니다.
라이트 모드만 확인했고 다크 모드는 확인하지 않았습니다.

## 남은 검증

`TOKEN_ENCRYPTION_KEY`가 없을 때의 `503 webhooks_unavailable` 문구는 코드로만 확인했고 화면에서 재현하지 않았습니다.
비밀 영역의 "복사" 버튼은 누르지 않았습니다. 자동화 환경에서는 사용자 동작 없이 클립보드 쓰기가 실패할 수 있으므로, 복사와 그 실패 시 선택 안내는 확인하지 않았습니다.
주소 추가와 키 교체 요청 도중 세션이 초기화되면 비밀을 표시하지 않는 처리는 브라우저 확인 뒤에 추가했으므로 코드로만 확인했습니다.
비밀 영역이 열려 있거나 주소 추가·키 교체 요청이 처리 중인 동안 두 동작을 모두 막는 처리도 리뷰 뒤에 추가했습니다. 이 처리는 위의 실제 `appApi` 환경이 아니라, 실제 `public/app` 파일에 `/api` 응답만 흉내 낸 임시 서버(교체·추가 응답 300ms 지연)와 headless Chromium으로 확인했습니다.
그 환경에서 키 교체 뒤 비밀 영역이 열린 동안 다른 주소의 "키 교체"와 "주소 추가"는 비활성화됐고, 눌러도 요청이 나가지 않아 먼저 받은 비밀이 그대로 남았습니다. "다시 불러오기" 뒤에도 비활성화가 유지됐습니다. "닫기"를 누르면 "주소 추가"와 키가 하나인 주소의 "키 교체"만 다시 켜졌고, 키가 두 개인 주소의 "키 교체"는 계속 비활성화됐습니다.
새로 연 화면에서 두 주소의 "키 교체"와 "주소 추가"를 한 번에 누르면 요청은 첫 교체 하나만 나갔습니다. 고치기 전 `app.js`로 같은 확인을 돌리면 비밀이 다음 결과로 바뀌었고 요청은 세 개가 나갔습니다.
실제 `appApi`와 DB로는 이 처리를 다시 확인하지 않았고, 비활성화 이유를 알리는 안내 문장도 화면에서 보지 않았습니다.
브라우저 확인 뒤 리뷰에서 바꾼 두 문구도 화면에서 다시 보지 않았습니다. `dead` 행의 전송 시각 자리는 "아직 전송하지 않음" 대신 "보내지 못함"으로 표시되며 단위 테스트로 확인했고, `invalid_webhook_endpoint` 문구는 서버가 같은 코드로 거부하는 줄바꿈과 보이지 않는 서식 문자도 안내하도록 고쳤습니다.
migration 031을 운영 DB에 적용하지 않았고 배포하지 않았으므로, 운영 데이터와 실제 전송으로 이 화면을 확인하지 않았습니다.
