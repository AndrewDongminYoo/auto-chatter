## 자동 검사 (#277)

실제 화면 모듈을 VM에서 실행하는 기존 하네스에 검사 18개를 추가했습니다(이 파일의 검사는 135개입니다).
기존 검사 두 곳은 바뀐 계약에 맞췄습니다. 생성 성공 안내 검사는 새 문구를 확인하고, 승인 마크업 검사는 영역 제목의 `tabindex="-1"`을 확인합니다.
검사가 확인하는 내용은 다음과 같습니다.

- 거절 뒤 포커스(7개): 생성, 예약 변경, 취소의 거절마다 두 승인 제목 중 기대한 하나에만 포커스가 갑니다. 표시한 승인이 남으면 그 승인의 제목으로 갑니다(`approval_exists`, `campaign_schedule_out_of_range`, `campaign_approval_cancelled`, `campaign_approval_not_found`). 표시한 승인이 없거나 승인 상태를 다시 읽으면 영역 제목으로 갑니다(`campaign_schedule_timezone_changed`, 승인 요청의 `campaign_draft_conflict`, 쓸 수 없는 승인을 담은 `campaign_approval_conflict`). 가짜 DOM의 포커스 표시는 지워지지 않으므로 쓰기 직전에 두 제목의 표시를 지웁니다.
- 성공 본문 불일치(6개): 생성은 다른 승인 ID와 다른 초안의 승인을 받습니다. 예약 변경은 다른 승인 ID와 `cancelled`를 받고, 취소는 다른 승인 ID와 여전히 `approved`인 승인을 받습니다. 모두 결과 불명 안내를 보이고 승인 제목과 요약을 바꾸지 않으며 요청을 유지합니다. 같은 버튼은 ‘같은 요청 재시도’가 되고 재시도는 첫 요청과 같은 경로·방법·본문을 보냅니다. 생성은 확인 단계와 재시도 요약을 유지하고 돌아가기를 숨기며, 예약 변경 중에는 취소 버튼이 꺼져 아무것도 보내지 않습니다. 재시도가 올바른 본문을 받으면 승인이 표시되고 요청이 풀립니다.
- 생성 재시도가 돌려받은 현재 상태(2개): 첫 생성 요청은 응답을 잃어 결과 불명이 되고, 같은 요청 재시도부터는 서버가 같은 `id`의 승인을 매번 같은 현재 상태로 돌려줍니다. 재시도는 첫 요청과 같은 경로·방법·본문입니다. `executed`를 받으면 ‘최근 승인 · 실행 시작됨’과 실행이 시작되었다는 안내를 보이고 실행을 한 번 읽어 실행 현황 패널을 표시합니다. `cancelled`(그사이 다른 탭이나 관리자가 취소한 승인)를 받으면 ‘최근 승인 · 취소됨’과 기록된 뒤 취소되었다는 안내를 보이고, 실행을 읽지 않으며 초안 잠금을 풉니다. 둘 다 요청을 풀어 ‘같은 요청 재시도’를 거두고 표시한 승인의 제목으로 포커스를 옮깁니다.
- 생성은 서버가 돌려줄 수 있는 세 상태(`approved`, `executed`, `cancelled`)를 모두 받아들이므로, 생성의 상태 불일치는 따로 검사하지 않습니다. 세 상태 밖의 값은 `renderApproval`이 이미 거부합니다.
- 거절 안내 되살리기(2개): 승인 요청이 `campaign_draft_conflict`로 거절되면 승인 상태를 다시 읽는 조회를 열어 둡니다. 대조 검사에서는 그 조회가 끝난 뒤 거절 안내를 되살립니다. 다른 검사에서는 그동안 시간대 변경(세대를 바꾸지 않음)으로 새 조회를 시작해 먼저 끝낸 다음 열어 둔 조회를 끝내며, 거절 안내를 되살리지 않습니다.
- 성공 문구(1개): 생성과 예약 변경 성공 안내가 정확히 새 문구이고 ‘메시지는 전송되지 않았습니다’와 ‘발송 가능’을 포함하지 않습니다. 취소 안내는 그대로입니다.

판별력은 구현을 한 곳씩 되돌린 뒤 같은 검사 파일을 실행해 확인했습니다(`node --test --test-reporter=tap src/app/campaign-drafts.test.ts`, 실행 뒤 원래 파일로 복원).
모든 변형에서 하나 이상의 검사가 실패했습니다.

| 변형                                                     | 실패 수 |
| -------------------------------------------------------- | ------- |
| 거절 뒤 포커스 이동 제거                                 | 7       |
| 성공 본문의 승인 ID 검사 제거                            | 3       |
| 생성 성공 본문의 초안 ID 검사 제거                       | 1       |
| 성공 본문의 상태 검사 제거                               | 2       |
| 생성 성공에서 `executed`를 받아들이지 않음               | 1       |
| 생성 성공에서 `cancelled`를 받아들이지 않음              | 1       |
| 거절 안내 되살리기의 승인 조회 요청 번호 비교 제거       | 1       |
| 승인 상태를 다시 읽을 때도 표시한 승인의 제목으로 포커스 | 1       |
| 생성 성공 안내를 이전 문구로 되돌림                      | 2       |
| 예약 변경 성공 안내를 이전 문구로 되돌림                 | 1       |
| 영역 제목의 `tabindex="-1"` 제거                         | 1       |

거절 안내 되살리기의 초안 ID 비교는 별도로 실패시키는 검사가 없습니다.
다른 초안 열기, 새 초안, 세션 초기화는 모두 승인 조회 요청 번호를 올리므로, 지금 코드에서 요청 번호가 같고 초안만 다른 상태는 만들 수 없습니다.

## 자동 검사 (#278)

`src/app/segment-snapshots.db.test.ts`의 ‘the HTTP routes create, list, read pages of and download a snapshot with identifiers only’ 검사는 CSV 전체 텍스트에서 `9001`(고정 대상 DM 수신자 ID)을 찾았습니다.
그래서 무작위 `snapshot_id`나 `segment_id` UUID에 `9001`이 들어 있으면 실패했습니다(CI run 40833463934, `segment_id` `39001a08-…`).
이제 이미 파싱한 행의 필드 가운데 `9001` 또는 `'9001`과 같은 것이 없는지 확인합니다. 다른 문자열(댓글·DM 원문, 세그먼트 이름, `shop`)의 부분 문자열 검사는 유지합니다.

127.0.0.1:5449의 PostgreSQL 17 클러스터에서 `automations_test`를 지우고 다시 만든 뒤, 그 검사만 실행하면서 새 확인 바로 앞에 값을 임시로 넣어 판별력을 확인했습니다. 실행 뒤 원래 파일로 복원했습니다.

| 임시로 넣은 값                                                | 결과 |
| ------------------------------------------------------------- | ---- |
| 없음                                                          | 통과 |
| 세그먼트 ID 필드를 `39001a08-0000-4000-8000-000000000000`으로 | 통과 |
| 발신자 필드를 `'9001`로                                       | 실패 |
| 행 끝에 `9001` 필드 추가                                      | 실패 |

같은 UUID에 이전 정규식(`/RAW COMMENT SECRET|RAW DM SECRET|Lead buyers|shop|9001/`)을 적용하면 일치합니다. 즉 이전 검사는 이 UUID에서 실패했습니다.

## 검증 한계

이 검사들은 가짜 DOM과 가짜 API 위의 화면 모듈과, 격리된 로컬 PostgreSQL의 HTTP 경로를 확인합니다.
실제 브라우저의 포커스 이동과 화면 낭독기 동작, 배포된 Worker, 운영 DB는 확인하지 않았습니다.
