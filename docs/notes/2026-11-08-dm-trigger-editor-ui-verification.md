# DM 트리거 편집기 화면 검증

## 대상과 경계

[#292](https://github.com/AndrewDongminYoo/auto-chatter/issues/292)의 [편집기](../specs/2026-11-08-instagram-dm-start-triggers.md#편집기) 동작을 확인했습니다.
실제 `public/` 파일과 실제 `appApi`를 로컬 PostgreSQL(포트 5437)의 일회용 DB(`automations_ui292`, `db/schema.sql` 적용, 확인 뒤 삭제)에 연결한 임시 로컬 서버를 사용했습니다.
임시 서버는 `/app/` 응답에 `public/_headers`의 Content-Security-Policy를 그대로 붙였고, 요청마다 새 연결 풀을 `appApi`에 넘겼습니다(Worker처럼 `appApi`가 풀을 닫습니다). DB에는 `postgres` 역할로 연결했으므로 서버 역할의 권한 제한은 이 확인에 들어가지 않았습니다.
Supabase는 세션 쿠키 값으로 `/auth/v1/user` 응답을 돌려주는 대역으로 바꿨고, 로그인은 대역 서버가 쿠키를 직접 설정하는 방식으로 대신했습니다.
다른 모든 외부 요청은 예외로 막고 기록하도록 했으며, 기록된 외부 요청 시도는 0건이었습니다. 운영 DB·Supabase·Meta·Cloudflare는 호출하지 않았습니다.
합성 데이터는 소유자·관리자·상담원 멤버 각 1명, 켜진 연결 하나(`ui_shop`, 합성 암호문), 텍스트 필드 하나(`관심사`)입니다.
화면 동작은 Playwright 1.62가 headless Chromium(chrome-headless-shell 1248)을 조작해 확인했습니다. 서버와 점검 스크립트는 세션 임시 디렉터리에 두었고 저장소에는 넣지 않았습니다.
확인 창은 모두 승인했습니다. 화면 너비는 1280px입니다.

## 관리자: DM 키워드 플로

- 트리거가 없는 플로에 "댓글 트리거 만들기", "DM 키워드 트리거 만들기", "DM 기본 응답 트리거 만들기" 버튼 셋이 보였습니다.
- DM 키워드 트리거를 만들자 초점이 그 트리거의 계정 선택으로 갔습니다. 양식은 계정, DM 조건, 키워드, 제외 키워드 넷이었고 게시물 ID는 없었습니다.
- 키워드 `가격`, `링크`와 "정확히 일치"를 고르자 단계 요약이 "ui_shop · 정확히 일치: 가격, 링크"가 됐고, "모든 DM"을 고르면 키워드 입력이 숨겨졌습니다.
- 그다음 DM 조건을 "키워드 포함"으로 다시 골랐고 제외 키워드는 입력하지 않았습니다. 그래서 아래의 발행과 테스트 실행 두 번은 모두 "키워드 포함", 키워드 `가격`·`링크`, 제외 키워드 없음 조건으로 했습니다.
- 트리거 뒤의 추가 목록에는 "메시지 보내기" 하나만 있었습니다. 메시지를 추가하자 그 양식에 변수 선택이 없고 "변수를 쓸 수 없습니다" 안내가 보였으며, 메시지 뒤에는 추가 양식이 없었습니다.
- 저장하고 발행하자 "v1을 발행했습니다. 켜야 새 DM에 실행됩니다."가 나왔고, 켜기 뒤에는 "플로를 켰습니다. 새 DM부터 발행 버전으로 실행합니다."가 나왔습니다.

## 관리자: 테스트 실행

- DM 플로의 테스트 입력란 이름은 "DM 내용"이었고, 연락처 태그, 연락처 필드 값, 응답 본문, 응답 가지 입력은 숨겨져 있었습니다.
- `가격 알려주세요`로 초안을 테스트하자 결과에 메시지 본문과 "DM 24시간 응답 기간은 확인하지 않았습니다" 안내가 나왔습니다. 요청 본문의 키는 `source`, `comment_text`, `expected_revision` 셋뿐이었습니다.
- `안녕하세요`로 테스트하자 "입력한 내용이 트리거 조건에 맞지 않아 실행을 만들지 않습니다."가 나왔습니다.

## 관리자: 기본 응답 충돌과 API 초안

- 첫 DM 기본 응답 플로는 발행하고 켤 수 있었습니다. 같은 계정에 두 번째 기본 응답 플로를 만들어 발행하자 `422`가 돌아왔고, 트리거 단계에 "같은 계정에 켜진 DM 기본 응답 플로가 이미 있습니다."가 표시됐습니다.
- 첫 플로를 끄고 두 번째 플로를 발행해 켠 뒤 첫 플로를 다시 켜자, 켜기 `422`가 같은 문구로 "발행 버전을 켤 수 없습니다." 아래에 표시됐습니다.
- API로 DM 키워드 트리거, 태그 추가, `{{comment.text}}`가 든 메시지의 초안을 저장(`200`)하고 편집기에서 열자 저장·발행 버튼이 보였습니다. 발행하자 "2. 태그 추가"에 `dm_trigger_unsupported_node`, "3. 메시지 보내기"에 `dm_trigger_unsupported_variable` 문구가 표시됐고, 그 메시지 양식에도 변수 선택이 없었습니다.

## 관리자: 댓글 플로

- 댓글 트리거 양식에는 게시물 ID 입력이 그대로 있었고, 트리거 뒤의 추가 목록은 응답 기다리기를 뺀 단계 9종이었습니다. 메시지 양식의 변수 선택에는 "댓글 본문"이 있었습니다.
- 저장하고 발행하자 "v1을 발행했습니다. 켜야 새 댓글에 실행됩니다."가 나왔습니다. 테스트 입력란 이름은 "댓글 본문"이고 태그 입력이 보였으며, 결과에는 "7일 댓글 답장 기간" 안내가 그대로 나왔습니다.

## 상담원

- DM 키워드 플로를 열면 단계 2개가 보였고, 저장·발행·켜기 버튼, 테스트 실행 영역, 단계 목록 안의 버튼·선택·입력·`details`가 없었으며 상태 문구는 읽기 전용 안내였습니다.
- 임시 서버의 요청 기록에서 상담원의 쓰기 요청(`POST /api/workspace` 제외), `/api/webhooks`, 테스트 실행 요청은 0건이었습니다.

## 콘솔과 점검 스크립트

- 페이지 오류는 없었습니다. 콘솔 오류는 의도한 `422` 3건(발행 둘, 켜기 하나)과, 임시 서버에 Meta 설정이 없어 Meta 호출 전에 돌아온 게시물 목록 요청(`/api/connections/:id/media`)의 `503`뿐이었습니다.
- 점검 스크립트가 결함을 잡는지 보려고 DM 플로에서 메시지만 허용하는 규칙(`flowFits`)을 잠시 지우자, 브라우저 확인 2개(추가 목록이 단계 9종으로 늘어남, 메시지 뒤에 추가 양식이 생김)와 `src/app/flow-editor-model.test.ts`의 테스트 2개가 실패했습니다. 파일을 복원하고 포맷한 코드에서 DB를 새로 만들어 다시 실행하자 확인 33개가 모두 통과했습니다.
- 그 뒤 리뷰에서 플로 끄기 확인 문구가 "새 댓글(으)로"로 바뀐 것을 찾아, 트리거 종류마다 "새 DM으로"·"새 댓글로"를 쓰도록 고쳤습니다. 화면 코드를 마지막으로 고친 다음 DB를 새로 만들어 점검 스크립트를 다시 실행했고, 댓글 플로를 켰다가 끄는 확인과 끄기 확인 문구 확인(DM 플로는 "새 DM으로", 댓글 플로는 "새 댓글로", "(으)로"는 없음)을 더해 확인 35개가 모두 통과했습니다.
- 그 뒤 리뷰에서 끄기와 켜기가 발행 버전에 작용하는데 위 문구는 초안의 트리거 종류를 읽는다는 점을 찾아, 끄기 확인 문구를 "새 실행을 시작하지 않고"로, 켜기 안내를 "플로를 켰습니다. 지금부터 발행 버전으로 새 실행을 시작합니다."로 트리거 종류와 무관하게 바꿨습니다. 위 두 문구 기록은 이 변경 전의 것이며, 바꾼 문구는 브라우저에서 다시 확인하지 않았습니다.
- 시각 확인용 데스크톱 캡처 7장(시작 버튼, DM 키워드 트리거 양식, 메시지가 있는 DM 플로, DM 테스트 결과, 기본 응답 충돌, API 초안 오류, 상담원 화면)은 세션 임시 디렉터리에 저장했고 저장소에는 넣지 않았습니다.

## 확인하지 않은 것

- 390px 너비, 실제 키보드 조작, 스크린 리더 낭독, 다크 모드는 확인하지 않았습니다. 선택 상자의 값은 Playwright의 `selectOption`으로 골랐습니다.
- `dm_keyword_conflict` 표시, 초안과 발행 버전의 트리거 종류가 다를 때의 테스트 입력 표시, DM 트리거 삭제는 브라우저에서 실행하지 않았습니다. 트리거 삭제 조건과 연결 대상은 `src/app/flow-editor-model.test.ts`로만 확인했습니다.
- 배포하지 않았으므로 운영 데이터와 실제 Instagram 계정으로 이 화면을 확인하지 않았습니다(#293). #292의 완료 조건인 화면 검토는 병합 뒤에 합니다.
