# 플로 편집기 화면 검증

## 대상과 경계

GitHub #30의 두 번째 부분인 [플로 편집 화면](../specs/2026-09-29-flow-version-contract.md#편집-화면)을 확인했습니다.
실제 `public/app` 파일과 실제 `appApi`를 로컬 PostgreSQL 17(포트 5434)의 일회용 DB(`automations_ui`, 확인 뒤 삭제)에 연결한 임시 로컬 서버를 사용했습니다.
임시 서버는 `/app/` 응답에 `public/_headers`의 Content-Security-Policy를 그대로 붙였습니다.
Supabase는 세션 쿠키 값으로 `/user` 응답을 돌려주는 대역으로 바꿨고, 로그인은 대역 서버가 쿠키를 직접 설정하는 방식으로 대신했습니다.
대역은 다른 모든 외부 요청을 예외로 막고 기록하도록 했으며, 기록된 외부 요청 시도는 0건이었습니다. 운영 DB·Supabase·Meta·Cloudflare는 호출하지 않았습니다.
합성 데이터는 소유자와 상담원 멤버 각 1명, 연결 하나(`ui_shop`, 합성 암호문), 필드 셋(`관심사` 텍스트, `방문 횟수` 숫자, `구매 고객` 예/아니요), 켜진 외부 전송 주소 하나(`ui_crm`)입니다.
화면 동작은 Playwright 1.62로 headless Chromium(chrome-headless-shell 1243)을 조작해 확인했고, 각 실행 전에 DB를 새로 만들었습니다.
확인 창은 기록한 뒤 시나리오에 따라 승인하거나 취소했습니다.

## 관리자 화면에서 키보드로 만들기

- 선택 상자의 값 고르기를 뺀 조작은 탐색 막대의 "플로" 링크부터 Tab·Shift+Tab 이동, 글자 입력, Enter와 Space로 했고 마우스 클릭은 쓰지 않았습니다.
- 선택 상자의 값 8건(추가할 단계 종류 4건, 응답 저장 필드, 테스트 필드, 응답 가지, 테스트 출처)은 Tab으로 초점을 옮긴 뒤 Playwright의 `selectOption`으로 골랐습니다. macOS의 headless Chromium과 Chrome for Testing 모두 닫힌 `<select>`에 보낸 합성 키(한글 입력, 화살표, Space)로 값이 바뀌지 않았기 때문입니다. 실제 키보드로 선택 상자를 여닫는 동작은 확인하지 않았습니다.
- 새 플로 이름을 입력하고 Enter를 누르면 편집기가 열리고 초점이 편집기 제목으로 갔습니다. "댓글 트리거 만들기" 뒤에는 초점이 트리거의 계정 선택으로, 새 단계를 추가하면 그 단계의 첫 입력으로 갔습니다.
- 태그 조건, 예 가지의 메시지 보내기, 그 뒤의 응답 기다리기(60분, 응답을 `관심사`에 저장), 응답 받음 가지의 외부 전송(`ui_crm`, `방문 횟수`와 태그), 아니오 가지의 태그 추가로 단계 6개를 만들었습니다.
- 트리거 뒤의 추가 목록에는 응답 기다리기가 없었고, 메시지 뒤에는 응답 기다리기만, 응답 기다리기 뒤에는 메시지 보내기가 없었습니다. 예 가지 맨 앞에 넣는 목록에는 메시지 보내기가 없었습니다.
- 저장하기 전에는 "저장 전" 배지가 보이고 발행 버튼이 꺼져 있었습니다.
- 메시지 본문을 비운 채 저장하고 발행하자 `422`가 돌아왔고, 위쪽 요약("문제 1개")이 초점을 받았으며 "3. 메시지 보내기" 단계 옆에 "이 단계의 설정을 모두 채우고 형식과 범위를 확인해 주세요."가 표시됐습니다. 요약의 단계 링크에서 Enter를 누르면 초점이 그 단계 제목으로 갔습니다.
- 본문을 채워 저장하고 발행하자 v1이 발행됐고 요약이 사라졌습니다. "켜기"로 플로를 켰습니다.

## 테스트 실행

- 태그 `VIP`, `방문 횟수` 3, 응답 본문, 응답 받음 가지로 실행하면 트리거 → 태그 조건(예) → 메시지 → 응답 기다리기(응답 받음) → 외부 전송 경로가 단계 목록과 그래프에 표시됐습니다(단계 5개, 그래프 노드 5개). 결과에는 변수를 채운 메시지 본문, 응답 받음으로 이어 간 기다림, `관심사` 필드 변경, `"type": "flow.webhook"`과 태그가 든 외부 전송 본문이 나왔습니다.
- 시간 초과 가지로 실행하면 경로가 응답 기다리기에서 끝났고(단계 4개), 태그를 비우면 태그 조건의 아니오 가지로 가서 `태그 "일반" 추가`가 표시됐습니다.
- 발행 버전으로 트리거 키워드가 없는 댓글을 실행하면 "발행 버전 v1 · 댓글이 트리거 조건에 맞지 않아 실행을 만들지 않습니다."가 나왔습니다.
- 실행 뒤 `localStorage`와 `sessionStorage`에 입력한 댓글과 응답 본문이 없었습니다.

## 충돌, 떠나기 경고, 보관

- 같은 브라우저의 두 번째 탭에서 같은 플로의 이름을 바꿔 저장한 뒤, 첫 탭에서 태그 조건의 태그를 `우수고객`으로 고쳐 저장하자 `409`가 돌아왔습니다. 충돌 안내가 보이고 초점이 "최신 초안 불러오기"로 갔으며, 입력한 `우수고객`은 그대로 남아 있었습니다.
- 그 상태에서 "편집기 닫기"를 누르면 "저장하지 않은 플로 변경 사항을 버릴까요?" 확인 창이 떴고, 취소하자 편집기가 열린 채로 남았습니다.
- "최신 초안 불러오기"를 누르자 이름이 두 번째 탭의 값으로 바뀌고 태그가 `vip`로 돌아왔습니다.
- 두 번째 탭에서 만든 다른 플로를 "보관"하면 확인 창을 거쳐 목록에서 사라졌습니다.

## 상담원

- 플로 목록과 읽기 전용 안내가 보였고, 플로를 열면 단계 6개와 그래프 노드 6개가 보였습니다.
- 만들기 양식, 이름 입력, 저장·발행·켜기·보관 버튼, 테스트 실행 영역은 숨겨졌고 단계 목록 안에 버튼·선택·입력·`details`가 없었습니다. 외부 전송 단계는 "등록한 주소로 태그, 방문 횟수 전송"으로 표시됐습니다.
- 임시 서버의 요청 기록에서 상담원 요청 13건에 `/api/webhooks`, 테스트 실행, 플로 생성·저장·발행·켜기·끄기·보관 요청은 없었습니다. 같은 필터를 소유자 요청에 적용하면 22건이 잡혔습니다.

## 화면 너비와 콘솔

- 1280px과 390px에서 문서의 `scrollWidth`가 화면 너비를 넘지 않았고, 플로 영역에서 그래프 영역 밖으로 화면 오른쪽을 넘는 요소가 없었습니다. 390px에서 그래프는 자체 영역 안에서 가로로 스크롤됐고(1104px > 348px), 6개가 된 탐색 막대도 넘치지 않았습니다. 390px에서 테스트 결과를 연 상태와 상담원 화면도 같았습니다.
- 페이지 오류와 CSP 위반은 없었습니다. 콘솔 오류는 의도한 `422` 발행 거절과 `409` 충돌, 그리고 기존 규칙 편집기의 게시물 목록 요청(`/api/connections/:id/media`)이 받은 `503`의 리소스 로드 기록뿐이었습니다. 이 `503`은 임시 서버에 `META_GRAPH_VERSION`을 설정하지 않아 Meta 호출 전에 돌아온 `instagram_not_configured`입니다.
- 운영자 시각 승인용 스크린샷(편집기, 테스트 실행 결과, 충돌 안내, 상담원 화면은 데스크톱과 390px, 발행 오류는 데스크톱)은 세션 임시 디렉터리에 PNG로 저장했고 저장소에는 넣지 않았습니다.

## 리뷰 수정 뒤 추가 확인

리뷰에서 나온 세 가지 수정을 같은 임시 서버와 새로 만든 `automations_ui`에서 다시 확인했습니다. 첫 필드가 예/아니요가 되도록 예/아니요 필드 `가`를 하나 더 넣었고, 확인 뒤 DB를 삭제했습니다. 외부 요청 시도는 0건이었습니다.

- 발행 v1을 \[트리거, `태그 추가`(s2)\]로 만들고 초안을 \[트리거, `태그 제거`(s2)\]로 저장한 뒤 발행 버전으로 테스트하면, 결과의 단계가 "2. 태그 추가"로 나오고 "태그 제거"는 나오지 않았습니다. 결과에 "발행 버전 v1이 지금 화면의 초안과 달라 단계 목록과 그래프에는 경로를 표시하지 않았습니다."가 나왔고, 단계 목록과 그래프에 경로 표시가 0개였습니다. 바꾸지 않은 초안의 플로에서는 이 안내가 없고 경로가 단계 목록과 그래프에 표시됐습니다(표시 5개).
- 발행 오류가 "2. 태그 제거"에 붙은 상태에서 트리거 바로 뒤에 단계를 넣자, 위쪽 요약의 링크와 단계 목록이 함께 "3. 태그 제거"로 바뀌었습니다.
- 첫 필드가 예/아니요일 때 "필드 값 저장"을 추가하면 요약이 "가에 예 저장"이었고, 저장한 초안의 값은 `true`였습니다.
- 확인 스크립트가 결함을 잡는지 보려고 경로 비교와 요약 재계산을 잠시 되돌려 실행하자 위 첫 두 항목의 확인 6개가 실패했습니다. 코드를 복원하고 포맷한 최종 상태에서 DB를 새로 만들어 다시 실행하자 확인 12개가 모두 통과했습니다.
- 켜기의 `422`를 발행 버전 기준으로 표시하는 동작과 발행 버전을 읽지 못했을 때의 표시는 브라우저에서 실행하지 않았고, 같은 순수 함수를 `src/app/flow-editor-model.test.ts`로만 확인했습니다. 스크린샷은 발행 버전이 초안과 다른 테스트 결과(데스크톱) 1장을 더했습니다.

## 두 번째 리뷰 수정 뒤 추가 확인

리뷰에서 나온 두 가지 수정을 같은 임시 서버와 새로 만든 `automations_ui`에서 다시 확인했고, 확인 뒤 DB를 삭제했습니다. 외부 요청 시도는 0건이었습니다.

- 플로 A를 여는 요청의 응답을 Playwright의 요청 가로채기로 붙잡아 둔 채 플로 B를 열고 이름을 고친 뒤 A의 응답을 풀어 주자, 편집기는 B와 고친 이름을 그대로 유지했고 확인 창도 뜨지 않았습니다.
- 변경 사항이 없는 C를 연 상태에서 A를 열고, A를 불러오는 동안 C의 이름을 고치자 A의 응답이 온 뒤 "저장하지 않은 플로 변경 사항을 버릴까요?" 확인 창이 떴고, 취소하자 C와 고친 이름이 남았습니다.
- 초안에서만 쓰는 텍스트 필드를 외부 전송 단계(`ui_crm`, 그 필드와 `관심사`)에 넣고 저장한 뒤 필드를 보관하자 `200`이 돌아왔습니다. 편집기에서 발행하면 "2. 외부 전송" 옆에 보관된 필드 오류가 표시됐고, 단계 편집에 "사용할 수 없는 필드 1 · 보관됐거나 없음" 체크박스가 선택된 채 보였습니다. 키보드(Space)로 선택을 해제하고 Enter로 저장하자 저장된 `field_ids`는 `관심사` 하나였고, 이어서 발행하자 v1이 발행됐습니다.
- 확인 스크립트가 결함을 잡는지 보려고 요청 순서 확인과 체크박스 반영을 잠시 이전 동작으로 되돌려 실행하자 확인 5개가 실패했고(A가 B를 덮어씀, 보관된 필드가 저장에 남음), 발행을 기다리다 시간 초과로 멈춰 발행 확인과 콘솔 확인은 실행되지 않았습니다. 코드를 복원하고 포맷한 최종 상태에서 DB를 새로 만들어 다시 실행하자 확인 12개가 모두 통과했습니다.
- 스크린샷은 보관된 필드가 선택된 외부 전송 단계(데스크톱) 1장을 더했습니다. 390px 너비와 상담원 화면은 이 수정으로 다시 확인하지 않았습니다.

## 세 번째 리뷰 수정 (브라우저에서 확인하지 않음)

리뷰에서 나온 두 가지 수정은 브라우저에서 다시 확인하지 않았습니다. 수정 당시 부하 평균이 9를 넘어 임시 서버와 브라우저를 다시 띄우지 않았습니다.

- 기다릴 시간과 응답 대기 시간을 비우거나 잘못 입력하면 기본값 대신 입력한 그대로 저장하는 수정은 `src/app/flow-editor-model.test.ts`로 확인했습니다. 빈 값, `0`, `1.5`, `-3`을 넣은 문서는 발행 검증에서 두 단계 모두 `invalid_config`를 받고, 오류가 그 단계에 붙습니다. 저장값을 숫자로 바꾸는 함수를 이전처럼 빈 값에 `null`을 돌려주도록 잠시 바꾸자 이 테스트가 실패했고, 복원 뒤 통과했습니다. 단계 요약은 빈 값을 "시간 미입력", 잘못된 값을 "잘못된 시간"으로 보입니다.
- 테스트 실행과 발행 중에 초안을 고쳤을 때 결과와 오류를 요청을 보낼 때의 초안 기준으로 읽는 수정은 화면 코드에만 있어 자동 테스트가 없습니다. 기준 문서가 다를 때 쓰는 비교와 단계 이름 함수는 기존 테스트("a published version that differs from the draft keeps its own step names and errors")가 확인합니다.

## 네 번째 리뷰 수정 (브라우저에서 확인하지 않음)

리뷰에서 나온 두 가지 수정은 이번에 임시 서버와 브라우저를 다시 띄워 재현하지 않았습니다.

- 초안 저장은 문서 형태만 검사하므로 댓글 트리거의 키워드나 외부 전송 단계의 `field_ids`가 배열이 아닌 초안도 저장됩니다. 이런 초안을 열면 편집기가 멈추던 문제는 목록 값을 읽는 함수(`flowStoredList`)로 고쳤고, `src/app/flow-editor-model.test.ts`로 문자열과 숫자는 항목 하나로, 그 밖의 값은 빈 목록으로 보이며 발행 검증이 그 단계를 짚는 것을 확인했습니다. 편집기에서 그 단계를 고치면 화면에 보이는 목록이 저장됩니다.
- 플로 만들기와 보관 요청이 끝난 뒤 편집기를 닫기 전에, 요청 중에 고친 내용이나 그 사이에 연 다른 플로가 있으면 다시 확인 창을 띄우는 수정은 화면 코드에만 있어 자동 테스트가 없고, 코드로만 검토했습니다. 보관한 플로의 확인 창을 취소하면 편집기는 남지만 저장, 발행, 켜기, 보관, 테스트 실행 버튼은 비활성화됩니다.

## 다섯 번째 리뷰 수정 뒤 추가 확인

리뷰에서 나온 세 가지 수정을 같은 임시 서버와 새로 만든 `automations_ui`에서 다시 확인했고, 확인 뒤 DB를 삭제했습니다. 텍스트 필드 `메모`를 하나 더 만들었고, 외부 요청 시도는 0건이었습니다.

- 태그를 `t2`로 고쳐 저장하는 `PUT`을 Playwright의 요청 가로채기로 붙잡아 둔 채 편집기를 닫고(확인 창 승인) 같은 플로를 다시 열었습니다. 다시 연 편집기가 `t1` 초안을 보인 뒤 저장 응답을 풀어 줘도 "저장 전" 배지가 생기지 않았고 저장 버튼은 꺼져 있었습니다. 다시 연 편집기에서 태그를 `t3`로 고쳐 저장하자 충돌 안내가 떴고, 저장된 태그는 `t2`로 남았습니다.
- 필드 값 저장 단계에서 값을 `new`로 고친 뒤 다른 텍스트 필드로 바꾸면 값이 `new`로 남았습니다. 숫자 필드로 바꾸면 빈 값, 예/아니요 필드로 바꾸면 "예"에서 시작했습니다. 값을 고치고 필드를 바꿔 저장하면 새 필드와 고친 값이 저장됐습니다. 필드 값 조건 단계(값이 같음)에서도 다른 텍스트 필드로 바꾸면 고친 값이 남았습니다.
- 초안 테스트 실행 뒤 단계 목록 2곳, 배지 2개, 그래프 3곳에 경로가 표시됐습니다. 플로 이름만 고치면 표시가 그대로였고, 단계 설정에 글자 하나를 입력하면 단계 목록, 배지, 그래프, 범례에서 표시가 모두 사라졌으며 초점은 입력란에 남았습니다.
- 확인 스크립트가 결함을 잡는지 보려고 저장 응답 확인, 값 이어받기, 경로 지우기를 잠시 이전 동작으로 되돌려 실행하자 확인 8개가 실패했습니다. 다시 연 편집기가 "저장 전"이 됐고, 그 상태에서 실제로 고친 내용은 변경 없음으로 계산되어 저장 버튼이 꺼졌습니다. 필드를 바꾸면 값이 `old`로 돌아갔고, 설정을 고친 뒤에도 경로 표시가 남았습니다. 코드를 복원하고 포맷한 최종 상태에서 다시 실행하자 확인 18개가 모두 통과했습니다.
- 저장 요청이 `409`로 끝나기 전에 편집기를 다시 연 경우와 발행 요청의 `409`가 다시 연 편집기에 충돌 안내를 띄우지 않는 동작, "최신 초안 불러오기"의 늦은 응답이 그 사이 다시 연 편집기의 변경 사항을 버리지 않는 동작은 브라우저에서 실행하지 않았고, 코드로만 검토했습니다. 이번에는 스크린샷을 더하지 않았고, 390px 너비와 상담원 화면도 다시 확인하지 않았습니다.

## 여섯 번째 리뷰 수정 뒤 추가 확인

리뷰에서 양 끝 단계를 지났다는 이유만으로 실행하지 않은 가지의 연결까지 경로로 표시된다는 지적이 나왔습니다. 경로 표시는 이제 결과의 단계가 기록한 가지(`true`/`false`, `replied`/`timeout`)로 지난 연결만 고릅니다. 같은 임시 서버와 새로 만든 `automations_ui`에서 확인했고, 확인 뒤 DB를 삭제했습니다.

- 태그 조건의 예 가지가 `태그 추가`를 거쳐 `태그 제거`로, 아니오 가지가 곧바로 같은 `태그 제거`로 가는 초안을 만들었습니다. 태그 `vip`로 초안 테스트를 실행하면 그래프 연결 3개와 단계 4개가 표시됐고, 단계 목록의 아니오 가지 링크("→ 태그 제거")는 표시되지 않았습니다. 태그를 비우면 그래프 연결 2개와 단계 3개가 표시됐고, `태그 추가`는 표시되지 않았으며 아니오 가지 링크가 표시됐습니다.
- 확인 스크립트가 결함을 잡는지 보려고 그래프와 링크 표시를 이전 규칙으로 잠시 되돌리자, 예 가지 실행에서 그래프 연결이 4개로 늘고 아니오 가지 링크가 표시되어 확인이 실패했습니다. 코드를 복원한 최종 상태에서 두 확인이 모두 통과했습니다.
- 콘솔 오류는 위에 적은 게시물 목록 요청의 `503` 기록뿐이었고, 페이지 오류와 CSP 위반은 없었습니다.
- 응답 기다리기의 두 가지가 같은 단계로 모이는 경우는 브라우저에서 실행하지 않았고, `src/app/flow-editor-model.test.ts`에서 `planFlowRun`이 만든 단계로만 확인했습니다. 스크린샷은 더하지 않았습니다.

## 일곱 번째 리뷰 수정 뒤 추가 확인

리뷰에서 두 가지가 나왔습니다. 초안 테스트 실행은 서버에 저장된 초안을 실행하는데 화면은 결과를 편집기가 가진 초안의 단계 이름과 경로로 보였으므로, 다른 탭이 그 사이 저장하면 다른 단계를 가리켰습니다. 또 초안 저장은 트리거 수를 세지 않아 트리거가 둘인 초안이 저장될 수 있는데, 편집기는 모든 트리거의 삭제 버튼을 숨겨 그 초안을 고칠 수 없었습니다.
테스트 실행 API가 선택 키 `expected_revision`을 받게 했고(다르면 `409 revision_conflict`), 편집기는 초안 테스트 실행에 자기 revision을 보냅니다. 트리거는 하나뿐일 때만 삭제 버튼을 숨깁니다.
같은 임시 서버와 새로 만든 `automations_ui`에서 확인했고, 확인 뒤 DB를 삭제했습니다.

- 편집기를 연 뒤 API로 같은 플로의 초안을 저장해(`태그 추가`를 같은 ID의 `태그 제거`로 바꿈) 초안 테스트를 실행하면, 요청에 편집기의 revision 1이 실렸고 서버가 `409`로 거절했습니다. 결과 영역에는 "다른 곳에서 초안을 먼저 저장해 테스트하지 않았습니다. …"만 나왔고, 저장 충돌 안내가 보이며 초점이 "최신 초안 불러오기"로 갔고, 경로 표시는 0개였습니다. "최신 초안 불러오기" 뒤 다시 실행하면 `200`이었고 결과의 단계는 "태그 제거"였습니다.
- 트리거 두 개가 같은 단계로 이어지는 초안을 API로 저장하고 열면 두 트리거 모두에 "단계 삭제"가 있었습니다. 두 번째 트리거의 편집 메뉴를 Enter로 열고 삭제 버튼에서 Enter를 누르자(확인 창 수락) 그 트리거가 사라졌고, 남은 트리거에는 삭제 버튼이 없었으며 저장이 `200`이었습니다.
- 콘솔 오류는 의도한 `409`와 위에 적은 게시물 목록 요청의 `503` 기록뿐이었고, 페이지 오류와 CSP 위반은 없었습니다.
- 서버 검사를 잠시 끄자 `src/app/flow-test-run.db.test.ts`의 새 테스트가 `409` 대신 `200`으로 실패했고, 삭제 조건을 이전 규칙으로 되돌리자 `src/app/flow-editor-model.test.ts`의 새 테스트가 실패했습니다. 브라우저 확인은 수정 전 코드로 다시 돌리지 않았습니다.
- 스크린샷은 테스트 실행 충돌(데스크톱)과 트리거 두 개의 편집 메뉴(데스크톱) 2장을 더했습니다. 390px 너비와 상담원 화면은 이 수정으로 다시 확인하지 않았습니다.

## 최종 코드로 다시 확인

일곱 번째 리뷰 수정까지 반영한 최종 코드로 같은 점검 스크립트(`check.mjs`)를 새 `automations_ui` DB에서 다시 실행했고, 34개 항목이 모두 통과했습니다.
콘솔 오류는 의도한 422(발행 오류), 409(저장 충돌)와 하네스가 Meta 게시물 목록을 대체하지 않아 생기는 503뿐이었고, CSP 위반은 없었습니다.
운영자 시각 승인용 화면 캡처(데스크톱과 390px의 편집기, 테스트 결과, 충돌 안내, 상담원 화면, 발행 오류)는 이 실행에서 다시 찍었습니다. 앞 절의 캡처는 그 전 코드 기준입니다.

## 확인하지 않은 것

- 실제 키보드로 선택 상자를 여닫는 동작, 스크린 리더 낭독, 다크 모드는 확인하지 않았습니다.
- 브라우저에서 단계 삭제(위의 트리거 삭제 제외), 기존 단계 연결과 링크 끊기, 플로 끄기, 테스트 실행의 `422`, 페이지를 떠날 때의 브라우저 경고는 실행하지 않았습니다. 편집 연산과 오류 배치, 문구는 `src/app/flow-editor-model.test.ts`로만 확인했습니다.
- 운영자의 화면 승인은 아직 받지 않았고, 배포하지 않았으므로 운영 데이터와 실제 Instagram 계정으로 이 화면을 확인하지 않았습니다.
