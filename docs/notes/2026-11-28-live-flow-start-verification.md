# 외부 플로 시작 API 실발송 실계정 검증

## 범위와 승인

[#48](https://github.com/AndrewDongminYoo/auto-chatter/issues/48)의 플로 시작 API([#422](https://github.com/AndrewDongminYoo/auto-chatter/pull/422), [설계](../specs/2026-11-28-public-flow-start-design.md))가 운영에서 실제 키로 플로를 시작하고 첫 DM을 실제로 보내는지 확인했습니다.
2026-11-28에 운영 DB 조회, 대시보드에서 시험 플로 켜기와 `flows:start` 키 발급, Deploy 워크플로 끄기와 `SEND_ENABLED=true` 배포, 실제 DM 1건 발송, 종료 후 `false` 배포와 워크플로 다시 켜기, 시험 키 폐기와 시험 플로 끄기를 승인했습니다.
진행 중에 켜져 있던 댓글 규칙 하나를 시험 동안 끄는 것도 따로 승인했습니다(아래 "첫 시도").

| 항목        | 값                                                                                  |
| ----------- | ----------------------------------------------------------------------------------- |
| 연결        | `ai.you.wanted` (`a5df4215-fb1e-46d4-93f4-13c0176fb031`)                            |
| 테스트 계정 | 제 다른 Instagram 계정 하나(댓글 작성자이자 DM 수신자, 2026-11-19 검증과 같은 계정) |
| 시험 플로   | "트리거 테스트"(`8ce8be9c`, `instagram_dm_keyword`, 첫 메시지 하나)                 |
| 배포한 코드 | `25495aec2fa9ef9e6fe94ace0f4281c854174753` (발송 창 동안의 활성 버전과 같은 커밋)   |

메시지 본문, 테스트 계정의 ID와 Meta 메시지 ID는 이 노트에 적지 않습니다.

## 사전 점검

2026-11-28 07:08Z~08:06Z에 운영 DB를 읽기 전용 트랜잭션으로 조회했습니다.

- 연결 하나가 `active`, `send_enabled`, 유효한 토큰(만료 2027-01-09)을 갖추고 있었습니다.
- 대기 중인 발송 행(비공개 답장, DM 플로, 캠페인, 수동 답장, 외부 전송)과 실행할 캠페인 승인이 0건이었습니다.
- `delivering` 상태의 DM 실행 2건은 2026-11-19 검증에서 남은 것으로, 대기 중인 발송 행이 없어 다시 보내지 않습니다.
- 켜진 플로는 없었고, 켜진 댓글 규칙은 팔로우 조건 규칙 하나였습니다.
- 테스트 계정은 검증된 DM 수신자이며 명시적 마케팅 동의(2026-11-18 기록)가 있었지만, 마지막 DM이 2026-11-26 11:25Z라서 24시간 창이 닫혀 있었습니다. 테스트 계정에서 08:05:46Z에 DM을 한 통 보내 창을 열었고, 외부 시작의 수신자 판정이 시작 가능(단계 7)으로 바뀐 것을 확인했습니다.

## 준비

- 대시보드 탭에서 시험 플로를 켰습니다.
- `flows:start` 키를 발급했습니다. 첫 키(`fba8cae4`)는 발급 응답에서 키 대신 접두사를 담아 쓸 수 없었으므로 바로 폐기했고, 두 번째 키(`8faf052f`, 만료 2026-12-28)를 썼습니다.
- 발송을 켜기 전에 이 키로 `GET /v1/flows`가 시험 플로 하나를 돌려주고, `POST /v1/flows/{id}/starts`가 `409 sending_disabled`로 거절되는 것을 확인했습니다.

## 첫 시도: `contact_busy`

- Deploy 워크플로를 끄고(대기·진행 중인 실행 없음 확인), 08:09Z에 활성 커밋을 `--var SEND_ENABLED:true`로 배포했습니다(버전 `1df1a27a`).
- 08:09:59Z의 시작 요청은 `409 contact_busy`로 거절되었습니다.
- 원인은 2026-11-19 검증에서 남은 테스트 계정의 팔로우 대화(`waiting`)였습니다. 이 대화를 만든 팔로우 조건 규칙이 켜져 있어서, 외부 시작은 설계대로 진행 중인 대화로 보고 거절했습니다.
- 08:11:00Z에 같은 커밋을 기본값으로 다시 배포해 발송을 껐습니다(버전 `5596990b`). 발송이 켜져 있던 동안 새 발송 행, 시작 행, 요청 키 행은 0건이었습니다. 거절된 시작이 아무것도 쓰지 않는다는 점도 운영에서 확인되었습니다.

## 실발송

- 대시보드에서 팔로우 조건 규칙(`8de28211`)을 껐습니다.
- 08:15:42Z에 다시 `SEND_ENABLED=true`로 배포했습니다(버전 `7b96f6bb`).
- 08:15:58Z의 시작 요청이 `202 {start_id: 0c27929c…, run_id: 9d37f68d…, status: "queued"}`를 돌려주었습니다.
- 발송 행은 08:15:57Z에 생기고 08:16:09Z에 `sent`가 되었으며, Meta 메시지 ID가 기록되었습니다.
- 같은 요청 키와 같은 본문으로 다시 보낸 요청은 같은 `202` 본문을 돌려주었고, 시작 행과 요청 키 행은 각각 1건 그대로였습니다.
- 08:16:56Z에 기본값으로 다시 배포해 발송을 껐습니다(버전 `de19db8b`). 발송이 켜져 있던 동안 나간 것은 이 DM 1건뿐이었습니다(비공개 답장, 캠페인, 수동 답장, 팔로우 응답 0건).

## 복구

- 팔로우 조건 규칙을 다시 켜고, 시험 플로를 끄고, 시험 키 두 개를 모두 폐기했습니다. 남은 키는 원래 있던 읽기 전용 키 하나입니다.
- 활성 버전(`de19db8b`, 태그 `25495ae`, `SEND_ENABLED=false`)을 확인한 뒤 Deploy 워크플로를 다시 켰습니다. 그사이 `main`이 움직이지 않아 추가 배포는 없었습니다.

## 확인하지 않은 것

- 테스트 계정 화면에서의 수신은 이 노트를 쓸 때 확인하지 않았습니다. 발송 행의 `sent`와 Meta 메시지 ID가 근거입니다.
- 같은 키에 다른 본문을 보내는 `409 idempotency_conflict`, 발송 직전의 동의 철회와 일시 중지 차단, 여러 연락처의 연속 시작과 시간당 한도는 실계정에서 확인하지 않았습니다. 이 동작들은 DB·workerd 테스트가 다룹니다.
- 2026-11-19에 남은 팔로우 대화가 `confirmed_at`이 있는데도 `waiting`인 이유는 조사하지 않았습니다.
