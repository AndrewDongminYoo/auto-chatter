# 캠페인 초안 발송 조건 미리보기 화면 검증

## 범위

[#35](https://github.com/AndrewDongminYoo/auto-chatter/issues/35)의 후속 범위로, PR #258의 읽기 전용 미리보기 API(`GET /api/campaign-drafts/:id/preview`)를 관리자 캠페인 초안 상세에 표시하는 화면을 추가했습니다.
기준 로컬 HEAD는 `52263dd`입니다.
2026-10-26 운영자가 계획을 승인했습니다(명시적 버튼으로만 조회, 상단 경고와 사유별 표).
변경 파일은 `public/app/campaign-drafts.js`, `public/app/index.html`, `public/app/styles.css`, `src/app/campaign-drafts.test.ts`와 문서이며 서버 코드·DB 스키마·migration·의존성은 변경하지 않았습니다.
새로 제공되는 정적 파일은 없습니다.
화면 계약은 [관리 화면의 발송 조건 미리보기 화면](../specs/2026-10-21-campaign-drafts.md#발송-조건-미리보기-화면)에 기록합니다.
템플릿 치환·예약·승인·outbox 생성·실제 발송·비용 상한은 구현하지 않았으며 #35 전체 완료를 뜻하지 않습니다.

## 실패 재현과 수정

- 실제 화면 모듈을 VM에서 실행하는 미리보기 검사 16개를 먼저 추가했고, 구현 전에는 모두 실패했습니다.
  검사는 버튼으로만 조회, 클릭마다 한 번 조회, 두 경고, 일곱 사유의 API 순서·행 머리글, 2^53을 넘는 10진 문자열 수, 작업 공간 시간대의 기준 시각, ‘발송 가능’ 부재, 조회 중 busy 상태, 저장하지 않은 변경 중 비활성화, 보관된 초안 미리보기, 다른 초안·버전 응답 무시, 404·429·네트워크·잘못된 수 응답의 안내와 재클릭, 403의 화면 초기화를 다룹니다.
- 늦은 응답 폐기는 입력 변경·저장·보관·다른 초안 열기·새 초안·세션 초기화·작업 공간 변경마다 응답을 보류한 뒤 무효화하고 응답을 풀어 확인합니다.
  풀어 주는 응답의 `draft_version`은 무효화 뒤 열려 있는 초안의 버전(저장·보관 뒤 4, 나머지 3)과 같으므로 버전 비교가 아니라 무효화만 응답을 버릴 수 있고, 폐기된 경우 상태 줄이 비어 있는지(버전 불일치 안내가 없는지)도 확인합니다.
  같은 방식으로 무효화하지 않은 대조 검사는 결과를 그립니다.
- 검토에서 저장·보관·새 초안 폐기 검사가 버전 불일치 검사 덕분에 통과해 무효화를 판별하지 못한다는 지적을 받아 위처럼 고쳤고, 검사 10개를 더했습니다.
  이미 그려진 결과가 일곱 무효화마다 지워지는지 확인하는 검사 7개, 저장·보관 요청이 끝나기 전에 도착한 응답을 버리는지 확인하는 검사 2개, 다시 누르면 이전 결과가 조회 중에 지워지는지 확인하는 검사 1개입니다.
- 다른 탭 세션 신호와 뒤로 가기 복원은 기존 `invalidateContactSession`이 `campaignDrafts.reset()`을 호출하는 경로로 전달되며, 앱 원본에서 그 연결을 확인하는 검사를 추가했습니다.
- 판별력 확인을 위해 저장소 밖 복사본에서 구현을 한 곳씩 바꿔 실행했고, 모든 변형에서 하나 이상의 검사가 실패했습니다.
  `clearEditor()`의 `clearPreview()` 제거는 8개(다른 초안 열기·새 초안·세션 초기화·작업 공간 변경의 폐기와 화면 지움), `save()`의 제거는 6개(저장·보관의 폐기·화면 지움·요청 중 폐기), 입력 리스너의 제거는 2개, 조회 시작의 제거는 1개, 미리보기 요청 번호 검사 제거는 7개, 버전 비교 제거는 1개가 실패했습니다.
  `showDraft()`에 있던 `clearPreview()`는 호출하는 두 곳(`openDraft`의 `clearEditor`, `save`의 시작)이 이미 지우고 그 사이에는 읽기·저장 중이라 조회가 시작될 수 없어 관찰할 수 없는 중복이었으므로 제거했습니다.
- 기존 검사 하네스는 이벤트마다 한 개의 리스너만 저장하므로 입력 리스너를 하나로 합쳤고, 하네스가 태그·속성을 기록하도록 확장해 `th`·`scope`·`aria-busy`를 검사합니다.

## 자동 검사

아래 표는 최종 코드(검토 반영 후)에서 실행한 결과만 적습니다.

| 명령                                                                 | 클러스터           | 결과                           |
| -------------------------------------------------------------------- | ------------------ | ------------------------------ |
| `corepack pnpm check-types`                                          | 없음               | 통과                           |
| `corepack pnpm test`                                                 | 없음               | 428개 통과                     |
| `corepack pnpm test:db`                                              | 5436(공유)         | 754개 중 730개 통과, 24개 실패 |
| `corepack pnpm test:db`                                              | 5438(새 전용 임시) | 754개 통과                     |
| `corepack pnpm test:cloudflare`(`build:cloudflare` 포함, 배포 안 함) | 5438(새 전용 임시) | 80개 통과                      |
| 변경 경로를 지정한 `trunk fmt`·`trunk check`                         | 없음               | 통과                           |

단위 검사는 실제 화면 모듈의 상태·요청·응답 처리를 실행하지만 DOM과 HTTP는 대체물이며, 렌더링은 아래 브라우저 검사로 확인했습니다.
브리프가 지정한 5436 클러스터에서는 최종 코드의 `test:db`가 통과하지 못했습니다.
실패 24개는 모두 식별자 연결 검사와, 같은 테이블에 행을 넣는 작업 공간 삭제·내보내기 검사이며 `instagram_contact_identity_links_pkey` 기본 키 중복 또는 `identity_link_conflict`로 실패했습니다.
읽기 전용 `pg_constraint` 조회에서 5436의 `instagram_contact_identity_links`에는 `db/schema.sql`이 선언한 `(connection_id, workspace_id)` → `instagram_connections` 외래 키가 없고, `instagram_contact_identity_link_events`에는 외래 키가 하나도 없었습니다.
검사 전 정리(`TRUNCATE workspaces CASCADE`)는 외래 키를 따라서만 퍼지므로 두 테이블에 닿지 않으며, 실행 뒤 식별자 연결 테이블에 4행이 남아 있었습니다.
이 변경은 서버 코드·스키마를 바꾸지 않습니다.
검토 전 실행에서는 같은 시각에 다른 파일 순서로 진행된 다른 `test:db` 실행(주체 미확인)이 겹친 뒤부터 이 차이가 나타났습니다.
공유 클러스터는 고치지 않았으며, 최종 코드는 새로 만든 전용 임시 PostgreSQL 17 클러스터(5438)에서 단위·`test:db`·`test:cloudflare` 연쇄 명령이 428·754·80개 모두 통과했습니다.
확인 뒤 5438 클러스터를 종료했습니다.
검토 전에는 `instagram-subscription-check.db.test.ts`의 밀리초 단위 시각 비교가 한 번 실패했고 그 파일만 다섯 번 다시 실행하면 모두 통과했으나, 최종 실행에서는 재현되지 않았습니다.

## 실제 대시보드·Worker 검증

`scripts/segment-acceptance.mjs`를 DB 검사와 공유하지 않는 새 임시 클러스터(5437, 빈 public 스키마·애플리케이션 역할 없음 확인)에서 실행했습니다.
실제 정적 앱·Worker·제한된 서버 DB 역할을 사용하고 외부 인증만 합성 응답으로 대체하며, `SEND_ENABLED`는 `false`이고 합성 인증 외의 외부 요청은 fixture가 거절합니다.
스크립트 자체는 변경하지 않았습니다.
기동 후 저장소 밖의 일회용 시드 스크립트로 관리자 연결을 사용해 다음을 넣었습니다.

- 기존 합성 연결을 발송 켜짐·가짜 암호문·30일 뒤 만료로 바꾸고, 발송이 꺼진 두 번째 연결을 추가했습니다. 가짜 암호문은 열 조건만 채우며 복호화·발송에 쓰이지 않습니다.
- 작업 공간 시간대를 `America/New_York`으로 바꿨습니다(브라우저 시간대는 `Asia/Seoul`).
- 일곱 사유에 각각 1·2·1·1·2·1·3명이 해당하는 11명의 고정 대상과, 이를 참조하는 초안 하나와 보관된 초안 하나를 넣었습니다. 사유 조건은 미리보기 DB 검사의 fixture 구성을 따랐습니다.

`agent-browser`의 이름 있는 세션에서 다음을 확인했습니다.

- 소유자로 초안을 열면 ‘발송 조건 미리보기’ 버튼이 보이고, 페이지 fetch 계측에서 미리보기 요청은 0건이었습니다.
  버튼을 누르면 요청 1건이 발생했습니다.
- 두 경고(Instagram 마케팅 미지원, 서비스 전체 발송 꺼짐)가 수 위에 따로 표시됐습니다.
- 표는 열 머리글(조건·인원)과 일곱 행 머리글이 있고, 각 행 수가 시드와 같았습니다(조건 통과 3명).
  원래·현재 11명, 예상 공급자 호출 수 3회, 요금제 일괄 발송 한도 ‘정해지지 않음’을 표시했습니다.
- 기준 시각은 `2026. 10. 26. 오전 10:43:38 (America/New_York)`로, 같은 순간의 한국 시각(23:43)이 아닌 작업 공간 시간대로 표시됐습니다.
- 미리보기 영역 문자열에 ‘발송 가능’이 없었습니다.
- 실제 키 입력 한 글자로 결과가 지워지고 버튼이 비활성화됐으며, 지우면 버튼만 다시 활성화되고 결과는 돌아오지 않았습니다.
- 미리보기 응답을 3초 지연시키는 페이지 fetch 계측 아래에서 조회 직후 보관된 초안을 열면, 늦게 도착한 이전 초안의 결과가 그려지지 않았습니다.
  같은 지연에서 전환 없이 보관된 초안을 조회하면 조회 중 버튼이 비활성화·`aria-busy="true"`·‘확인하는 중…’이었고, 끝난 뒤 결과가 그려졌습니다.
  보관된 초안의 입력은 읽기 전용으로 유지됐습니다.
- 초안을 연 뒤 관리자 연결로 DB 버전을 올리고 조회하면 결과를 그리지 않고 다시 불러오기 안내를 표시했습니다.
  저장된 값을 다시 불러온 뒤(버전 2) 조회하면 결과가 그려졌습니다.
- 합성 `pageshow`(`persisted: true`) 신호에서 결과와 카드가 지워졌습니다.
  실제 브라우저 BFCache 진입 자체를 재현한 검사는 아닙니다.
- 상담원으로 다른 세션에 로그인하면 캠페인 카드와 미리보기가 숨겨지고 버튼 문구가 화면에 없었으며, 같은 세션의 직접 미리보기 API 호출은 `403 role_forbidden`이었습니다.
- 390px 폭·다크 모드에서 문서 폭은 390px, 표 영역의 스크롤 폭과 표시 폭은 모두 350px로 가로 스크롤이 없었고, 캡처로 대비를 확인했습니다.
- 카드(`#campaign-drafts-section`)에 한정한 axe 4.12.1 검사는 결과가 그려진 밝은 데스크톱과 다크 390px 모두 위반 0개·미완료 0개였습니다.
  같은 범위에 alt 없는 이미지를 임시로 넣으면 `image-alt` 위반 1개를 보고해 검사가 실제로 범위를 읽는 것을 확인한 뒤 제거했습니다.

검사 후 비공개 답장 outbox는 시드한 10행(모두 시드 당시의 `sent`), 수동 답장 0행, 동의 이벤트는 시드한 9행, 초안은 2행으로 미리보기가 원장을 바꾸지 않았습니다.
브라우저 세션과 Worker를 종료하고 Worker 포트의 연결 거절을 확인했습니다.
5437 클러스터는 확인용으로 데이터가 남아 있으므로 다음 수용 검사 전에 새로 만들어야 합니다.

### 경고 영역 수정 후 재확인

위 검사 뒤 자체 검토에서, 빈 경고 영역을 `display: none`으로 숨기면 실시간 영역이 접근성 트리에서 빠져 경고가 들어갈 때 영역과 내용이 함께 나타나므로 안내되지 않을 수 있다는 점을 찾았습니다.
CSS를 바꿔 빈 영역의 여백·테두리·배경만 0으로 두고 렌더링은 유지했습니다.
새로 만든 임시 클러스터(5439)에서 같은 수용 스크립트와 시드를 다시 실행해 다음을 확인했습니다.

- 초안을 연 뒤 조회 전에 경고 영역의 계산된 `display`는 `block`, 높이는 0이었고, 접근성 트리에서 미리보기 영역 아래 `status` 두 개(경고 영역·상태 줄)가 보였습니다.
- 다크 390px의 빈 상태 캡처에 남는 상자가 없었고 문서 폭은 390px였습니다.
- 조회 후 두 경고와 일곱 사유(1·2·1·1·2·1·3명)가 같게 표시됐고 ‘발송 가능’이 없었습니다.
- 카드에 한정한 axe 4.12.1 검사는 다크 390px와 밝은 데스크톱 모두 위반 0개·미완료 0개였습니다.

브라우저·Worker를 종료하고 5439 클러스터는 삭제했습니다.
캡처와 실행 기록은 저장소 밖의 `../pr-loop-reviews/auto-chatter/2026-10-26-campaign-draft-preview-ui/`에 보관합니다.

## 한계

- 실제 Instagram 계정·운영 DB·배포 Worker·실제 발송은 사용하지 않았습니다.
- 시드는 관리자 연결로 직접 넣은 합성 데이터이며, 웹후크 수신으로 만든 실제 대화의 분포를 대신하지 않습니다.
- 브라우저 검사는 검토 반영 전 코드로 실행했습니다. 검토 반영의 화면 코드 변경은 관찰할 수 없는 중복 `clearPreview()` 한 줄의 제거뿐이며, 브라우저 검사는 다시 실행하지 않았습니다.
- 스크린 리더의 실제 낭독은 확인하지 않았습니다. 경고 영역이 문서에 미리 있고 비어 있을 때도 접근성 트리에 남는 `role="status"` 실시간 영역이라는 구조까지 확인했습니다.
