대상은 여섯 묶음입니다.

1. 발송 조건: 요금제별 월간 캠페인 발송 한도 #309, 24시간 창을 위한 마지막 수신 DM 시각 #365(migration 072)

5. 보고서: 캠페인 실행 보고서 #310, 플로 실행 보고서 분류 #314, 이전 보고서의 기본 날짜 #317, 읽음 확인 건수 #322
6. 로그와 대시보드: Meta 오류와 pg 오류 분류 #318·#323·#369, 전체 발송 상태 다시 읽기 #342, 발송 설정 #357, 표시 보호 #349·#360

디자인 토큰과 배치만 바꾼 #330~#340은 서버 텍스트가 DOM에 들어가는 방식을 바꾸지 않아 제외했습니다.
AI 자원(#55~#57)은 아직 구현되지 않아 이번에도 제외했고, 실제 Meta 웹후크 재전송, 운영 작업 공간 격리([#13](https://github.com/AndrewDongminYoo/auto-chatter/issues/13)), 삭제한 캠페인 행의 예산 이월(캠페인 실행 명세에 적힌 알려진 한계)도 범위 밖입니다.
기능별 불변 조건은 [CLAUDE.md](../../CLAUDE.md), [기능별 불변 조건](../agents/feature-invariants.md)과 각 명세가 소유하므로 여기서 다시 적지 않습니다.

방법은 1~4차와 같습니다.
각 기능마다 누가 호출할 수 있는지, 악의적인 호출자가 무엇을 시도할 수 있는지, 방어가 어디에 있는지, 그 공격을 실제로 시도하는 테스트가 무엇인지를 묶음별 표로 적고, 테스트가 없던 변형에는 그 영역을 소유한 기존 테스트 파일에 회귀 테스트를 추가했습니다.
추가한 테스트는 기존 방어를 지키는 회귀 테스트이므로 처음부터 통과합니다.
그래서 테스트마다 방어 코드를 일시적으로 제거하거나 결함을 심어 실패를 한 번 확인한 뒤 원래 코드로 되돌렸고, 되돌린 뒤 `git diff --stat`에 테스트 파일만 남는 것을 확인했습니다.
작은 수정으로 고칠 실제 결함은 찾지 못했으므로 제품 코드는 바꾸지 않았습니다.

### 7. SECURITY DEFINER 함수, 권한, 데이터 경로 등록

migration 070~072는 기존 `delete_connection_data`를 다시 정의하고, 073은 함수를 추가하지 않습니다.
이 점검의 로컬 PostgreSQL(포트 5435)에서 `pg_proc`의 `prosecdef`인 public 함수를 읽으면 4차와 같이 `delete_connection_data`와 `delete_expired_oauth_states` 둘뿐이고, 둘 다 `search_path=public, pg_temp`입니다. `access.db.test.ts`가 이 목록을 정확히 비교합니다.
새 테이블 세 개(`instagram_message_reads`, `instagram_follow_messages`, `instagram_dm_last_inbound`)는 `access.db.test.ts`의 카탈로그 검사(RLS, API 역할 권한 없음, 서버 역할 DELETE·TRUNCATE 없음)를 받고, `instagram_follow_messages`는 UPDATE도 회수됩니다(`deploy/supabase-access.sql`, `deploy/init-app-user.sh`).
세 테이블은 `instagram_connections` 행을 외래 키로 요구하므로 작업 공간 이동 확인에 넣을 필요가 없습니다. 073은 `instagram_comment_rules`에 열과 CHECK와 부분 유일 인덱스만 더합니다.

## 확인한 의심 사항

- 읽음의 읽은 사람이 그 메시지의 저장된 받는이와 같은지는 확인하지 않습니다. [읽음 명세](../specs/2026-11-10-instagram-message-reads.md#저장과-중복)가 비공개 답장 행은 받는이 ID가 비어 있을 수 있어서 이렇게 정했습니다. 읽음 이벤트는 Meta가 서명하고, 메시지 ID는 같은 연결에서만 찾으며, 보고서는 메시지마다 `EXISTS`로 한 번만 셉니다. 영향은 보고서 건수뿐이고 발송 조건에는 쓰이지 않으므로 바꾸지 않았습니다.
- 월간 한도의 달은 작업 공간의 현재 시간대로 나눕니다. 월말에 관리자가 시간대를 바꾸면 이미 시작한 실행이 다른 달로 세어질 수 있습니다. 시간대 변경은 관리자 권한이고, 실행 시작이 같은 잠금 아래에서 다시 세므로 한도보다 많이 보내는 경로는 만들지 않습니다.
- 보관 경로는 처리기 앞의 `workspaceFor`로만 역할을 확인하고 쓰기 문장 안에서 다시 확인하지 않습니다. 4차 점검이 적은 템플릿·라벨·필드의 수정·보관 경로와 같은 형태입니다.
- 마지막 수신 시각은 `ingestMessages`가 받은 계정의 활성 연결 모두에 씁니다. `instagram_connections.account_id`가 `UNIQUE`이므로 한 계정의 연결은 하나뿐입니다.

## 추가한 회귀 테스트

각 테스트는 아래 방법으로 방어를 빼거나 결함을 심어 한 번 실패하는 것을 확인했고, 되돌린 뒤 제품 코드의 diff는 없습니다.
심을 때는 커밋하지 않는 백업 파일로 정확히 한 곳만 바꾸고 다시 복사해 되돌렸습니다.

- `http.db.test.ts` "a wrongly signed or unsigned read or DM body stores no read and no last inbound time": 읽음 본문과 DM 본문을 다른 비밀의 서명, 0으로 채운 서명, 빈 서명, 서명 없이 보내면 모두 `403`이고 읽음과 마지막 수신 시각이 0건인지, 같은 본문을 올바르게 서명하면 각각 1건이 생기는지 확인합니다. `verifySignature`의 마지막 줄을 `return suppliedDigest.length === expectedDigest.length;`로 바꾸면 `AssertionError: sha256=431c…`(`actual: 200`, `expected: 403`)로 실패했습니다.
- `http.db.test.ts` "a signed messaging_seen event stores one read of a sent message and stores no inbox DM (#312)"에 단언 하나를 더했습니다. 서명된 읽음 이벤트 뒤 `instagram_dm_last_inbound`가 비어 있는지 확인하며, 기존 인박스 단언보다 앞에 두어 인박스가 꺼진 연결에서도 같은 결함을 잡습니다. `parseMessageEvents`가 `event.read`를 빈 텍스트 메시지로 받도록 바꾸면 "a read event must not open the DM window"(`actual: 1`, `expected: 0`)로 실패했습니다.
- `dm-flow-delivery-worker.db.test.ts` "echo, self and misaddressed DM events of a signed body keep no last inbound time (#300)": `is_echo`가 참인 메시지, `is_self` 이벤트, 계정이 보낸 echo 모양의 이벤트, 다른 계정 앞 DM을 웹후크 본문으로 해석해 저장하면 마지막 수신 시각이 없고, 같은 이벤트에서 위조한 필드만 빼면 받은 연결에 한 행이 생기는지 확인합니다. `message.is_echo === true` 조건, `event.is_self === true` 조건, `event.recipient.id !== entry.id` 조건을 하나씩 빼면 세 번 모두 "Expected values to be strictly deep-equal"로 실패했습니다(발신자 `9050`의 행이 연결 `C`에 생김). echo 모양의 이벤트는 발신자 조건과 받는이 조건이 함께 막으므로 한 조건만 빼서는 실패하지 않습니다.
- `message-reads.db.test.ts` "a read of a message ID that another connection stored in any send table leaves no row": 다른 연결이 여섯 발송 테이블에 저장한 메시지 ID의 읽음을 이 계정으로 보내면 행이 없고, 같은 ID를 그 계정으로 보내면 그 연결에 여섯 행이 생기는지 확인합니다. `instagram_follow_messages` 조회와 `campaign_deliveries` 조회에서 각각 `s.connection_id=c.id AND`를 빼면 두 번 모두 이 테스트만 실패했습니다(`pass 9`, `fail 1`).
- `comment-rule-archive.db.test.ts` "an agent or a removed administrator cannot archive an existing rule": 같은 작업 공간의 상담원은 `403 role_forbidden`, 제거된 관리자는 `403 workspace_required`이고 규칙이 켜진 채 목록에 남는지 확인합니다. `archiveRule`의 역할을 `"agent"`로 낮추면 `actual: 200`, `expected: 403`으로 실패했습니다. 역할 확인을 보관 `UPDATE` 뒤로 옮기면(`UPDATE`는 `"agent"` 역할로 얻은 작업 공간으로 실행하고 그 뒤에 `workspaceFor(pool, user, "admin")`) 이 테스트만 `actual: 2026-11-20T13:24:19.121Z`, `expected: null`로 실패했고, `workspace-roles.db.test.ts`의 역할 표 테스트는 통과했습니다(`pass 16`, `fail 1`).
- `campaign-approvals.db.test.ts` "a reschedule into this month and a new approval that each fit alone serialize and cannot both pass": 다음 달 승인과 새 초안을 두고 작업 공간 행을 잡은 동안 일정 변경(이번 달로)과 새 승인을 보낸 뒤, 둘이 잠금을 기다리는지 확인하고 놓습니다. 먼저 기다린 일정 변경은 `200`, 새 승인은 `409 broadcast_limit_reached`(`reserved: "1"`)이며, 이번 달에 걸린 승인이 하나인지 확인합니다. `transaction()`의 `lockWorkspaceForMember`를 건너뛰면 "1 requests did not wait for the workspace lock"으로 실패했고, 기존 승인 경쟁 테스트도 `[201, 201]`로 함께 실패했습니다. 일정 변경의 한도 확인만 건너뛰는 변이(`if (months.moved && false)`)는 이 테스트가 아니라 기존 "approvals in force due in the same month count, ..." 테스트가 잡았습니다. 일정 변경이 먼저 끝나면 새 승인이 그 예약을 세어 거절되기 때문입니다.
- `campaign-approvals.db.test.ts` "a reschedule queued behind a new approval counts that approval and keeps its schedule": 위 테스트와 순서를 바꿔 새 승인이 먼저 잠금을 기다리고 일정 변경이 그 뒤에 기다리게 합니다. 새 승인은 `201`, 일정 변경은 `409 broadcast_limit_reached`(`reserved: "1"`)이며, 옮기려던 승인이 `scheduled`, 버전 1로 남는지 확인합니다. 일정 변경이 잠금 전에 한도를 읽는 결함을 심으면(`transaction()`에 잠금을 건너뛰는 인자를 더해 일정 변경만 건너뛰고, `UPDATE` 직전에 작업 공간 행을 `FOR UPDATE`로 잡음) 이 테스트만 `actual: 200`, `expected: 409`로 실패했고, 일정 변경이 먼저인 위 테스트는 통과했습니다.
- 위 두 테스트는 UTC 다음 달 시작 5분 전부터 건너뜁니다(`nearMonthEnd`). `now()`로 넣은 발송 999건이 잠금을 기다리는 사이 지난달로 넘어가면 두 요청이 모두 통과해 기대한 `409`가 나오지 않기 때문입니다. 기존 "two approvals that each fit alone wait for the workspace lock and cannot both pass"에도 같은 시간 경계가 있지만 이번 범위 밖이라 그대로 두었습니다.

## 테스트하지 않은 항목

- 운영 DB의 권한, 운영 Worker, 실제 Meta 발송과 실제 읽음·echo 이벤트는 확인하지 않았습니다. 이 점검의 테스트는 모두 로컬 PostgreSQL에서 실행합니다.
- Cloudflare Worker의 웹후크 경로(`src/cloudflare/index.ts`)는 Node 수신기와 같은 `verifySignature`, `ingestMessages`, `ingestMessageReads`를 쓰고 DM은 채널 어댑터(`src/instagram/channel-adapter.ts`)를 거쳐 같은 `parseMessageEvents`로 해석하므로 이번 서명·echo 테스트는 Node 수신기와 함수 수준에서만 추가했습니다. Worker 쪽은 기존 `worker.db.test.ts`의 읽음 종단 테스트와 `test:cloudflare`가 근거입니다.
- 이번에는 브라우저 렌더링 하네스를 다시 실행하지 않았습니다. #349와 #360은 표시값을 텍스트로 바꾸는 쪽으로만 바꿨고, sink 검사가 모든 대시보드 스크립트를 읽습니다. 보고서 CSV를 실제 스프레드시트에서 열어 보지 않았습니다.
- 월말 자정을 넘는 잠금 대기와 시간대 변경의 조합은 기존 "the campaign allowance places the month and immediate approvals by the post-lock reference clock"(`plans.db.test.ts`) 밖으로는 시험하지 않았습니다.
