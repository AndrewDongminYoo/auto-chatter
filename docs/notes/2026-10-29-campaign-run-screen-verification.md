# 캠페인 실행 현황 화면 검증

## 범위

[#36](https://github.com/AndrewDongminYoo/auto-chatter/issues/36)의 세 번째 PR(③ 화면)로, 실행된 승인 아래에 실행 현황과 실행 취소를 표시하는 관리자 화면을 추가했습니다.
기준 로컬 HEAD는 `9ecc418`입니다.
2026-10-29 운영자가 계획을 승인했고, 자동 갱신 없이 명시적 새로고침만 쓰기로 했습니다.
변경 파일은 `public/app/campaign-drafts.js`, `public/app/app.js`, `public/app/index.html`, `public/app/styles.css`, `src/app/campaign-drafts.test.ts`와 문서입니다.
서버 코드, DB 스키마, migration, 의존성, `SEND_ENABLED`는 바꾸지 않았습니다. 승인 응답에 이미 `run_id`가 있어 서버 API를 추가할 필요가 없었습니다.
`app.js`의 변경은 공용 API 래퍼가 409 응답의 `run`을 오류 객체에 전달하는 한 줄입니다.
화면 계약은 [실행 현황 화면](../specs/2026-10-27-campaign-runs.md#실행-현황-화면)에 기록합니다.
#36과 [#35](https://github.com/AndrewDongminYoo/auto-chatter/issues/35)는 이 PR 뒤에도 열린 상태로 남습니다.

## 자동 검사

실제 화면 모듈을 VM에서 실행하는 기존 하네스에 실행 API의 상태 있는 대체물(조회, 취소와 세 가지 409)을 더하고, 실행 패널 검사 19개를 추가했습니다(이 파일의 검사는 96개에서 115개가 되었습니다). 기존 API 래퍼 검사에는 `run` 전달을 더했습니다.
검사가 확인하는 내용은 다음과 같습니다.

- 실행된 승인을 열면 실행을 한 번 읽고, 상태, 작업 공간 시간대의 시작 시각, 시작 시점 원래·남은 인원, 일곱 사유 표(`candidate`는 ‘조건 통과’), 발송 행 일곱 상태(대기, 보내는 중, 보냄, 실패, 차단, 결과 불명, 취소)를 2^53을 넘는 수까지 정확히 표시합니다.
- 취소된 실행은 취소 시각을 보이고, 취소된 실행과 완료된 실행에는 취소 버튼이 없습니다.
- 승인이 없거나, 유효하거나, 취소된 초안에서는 실행을 읽지 않고 패널을 숨깁니다.
- 새로고침은 누를 때마다 정확히 한 번 읽고, 그 밖에는 다시 읽지 않습니다. 화면 모듈에 `setInterval`과 `setTimeout`이 없습니다.
- 취소는 확인 단계를 거치며, 확인 전과 돌아가기 뒤에는 아무것도 보내지 않습니다. 확인 단계를 연 뒤 서버의 버전이 바뀌어도 표시한 `expected_version`을 보냅니다.
- 성공하면 취소한 행 수와, 보내는 중인 행이 있을 때만 되돌릴 수 없다는 안내를 보이고 응답의 실행으로 다시 표시하며 결과 제목으로 포커스를 옮깁니다.
- `campaign_run_conflict`, `campaign_run_cancelled`, `campaign_run_completed`는 응답이 담은 실행으로 다시 표시합니다. 충돌 뒤의 새 취소는 응답이 담은 버전을 씁니다. 실행을 담지 않은 거절은 실행을 다시 읽습니다.
- 네트워크 오류, 503, 429, 잘못된 성공 본문은 같은 요청만 다시 보냅니다. 그동안 다른 초안 열기, 새 초안, 승인 상태 새로고침, 시간대 변경은 요청을 바꾸지 못하며, 새로고침으로 더 새로운 버전을 읽어도 재시도는 처음 버전을 보냅니다.
- 늦은 실행 조회 응답은 새 초안, 같은 초안 다시 열기, 승인 다시 읽기, 세션 초기화, 작업 공간 변경 뒤에 버립니다. 다른 실행 ID의 응답도 버립니다. 세션 초기화 뒤에 도착한 취소 응답도 버립니다.
- 조회 실패는 안내와 새로고침만 남깁니다. 조회나 취소의 403은 화면을 초기화합니다. 승인 쓰기가 실행된 승인을 담은 409를 받으면 그 실행을 읽습니다.
- 마크업 검사는 패널이 승인 영역 안에 있는지, 상태 줄이 `role="status"`와 `aria-live="polite"`인지, 문구(보내기 직전 재확인, 서비스 전체 발송, 보냄과 결과 불명의 뜻, 대기 행 취소와 보내는 중인 행을 되돌릴 수 없음)와 ‘발송 가능’ 부재를 확인합니다.

판별력은 구현을 한 곳씩 바꾼 뒤 같은 검사 파일을 실행해 확인했습니다. 모든 변형에서 하나 이상의 검사가 실패했습니다.

| 변형                                                      | 실패 수 |
| --------------------------------------------------------- | ------- |
| API 래퍼가 `run`을 전달하지 않음                          | 1       |
| 실행 조회·취소 응답의 요청 번호와 승인 검사 제거          | 1       |
| 다른 실행 ID의 조회 응답을 받아들임                       | 1       |
| 409가 담은 실행을 무시함                                  | 3       |
| 429에서 고정한 취소 요청을 버림                           | 1       |
| 보낼 때 표시 중인 실행의 버전을 다시 읽음                 | 1       |
| 결과 불명인 취소가 있어도 다른 초안 열기·새 초안을 허용함 | 1       |
| 실행 새로고침이 고정한 취소 요청을 버림                   | 1       |
| 승인을 읽은 뒤 실행을 읽지 않음                           | 16      |
| 보내는 중인 행 안내를 빼먹음                              | 1       |

첫 검사 작성 중에는, 조회 중에 실행 새로고침 버튼이 꺼져 있어 ‘더 새로운 실행 조회’를 그 버튼으로 만들 수 없었습니다. 그래서 검사가 승인 다시 읽기로 더 새로운 조회를 만들도록 바꿨습니다.
첫 변형 실행에서 ‘보낼 때 버전을 다시 읽음’이 통과했습니다. 결과 불명 검사를 새로고침이 더 새로운 버전을 읽도록 강화한 뒤 이 변형도 실패했습니다.

아래 표는 최종 코드에서 실행한 결과입니다. 클러스터는 이 작업에 배정된 PostgreSQL 17.11 임시 클러스터(5447)이며, 첫 실행 전에 public 스키마에 테이블이 없었습니다.

| 명령                                                                 | 클러스터 | 결과       |
| -------------------------------------------------------------------- | -------- | ---------- |
| `corepack pnpm check-types`                                          | 없음     | 통과       |
| `corepack pnpm test`                                                 | 없음     | 500개 통과 |
| `corepack pnpm test:db`                                              | 5447     | 821개 통과 |
| `corepack pnpm test:cloudflare`(`build:cloudflare` 포함, 배포 안 함) | 5447     | 87개 통과  |
| 변경 경로를 지정한 `trunk fmt`·`trunk check`                         | 없음     | 통과       |

`test:cloudflare` 안의 `pnpm build:cloudflare`는 이 셸의 PATH에서 Homebrew pnpm 12를 찾아 `ERR_PNPM_BAD_PM_VERSION`으로 실패했습니다. 저장소 밖의 임시 디렉터리에 `corepack enable --install-directory`로 pnpm 10.34.9 shim을 만들어 PATH 앞에 두고 실행했습니다. 저장소와 전역 설정은 바꾸지 않았습니다.

## 한계

- 실제 Instagram 계정, 운영 DB, 배포한 Worker, 실제 발송은 사용하지 않았습니다. 운영 화면에서 이 패널을 열거나 실행을 취소하지 않았습니다.
- 브라우저 검사(`scripts/segment-acceptance.mjs`, 390px 폭, 다크 모드, axe)는 실행하지 않았습니다. 렌더링, 포커스, 실시간 영역의 동작은 DOM 대체물을 쓴 단위 검사로만 확인했습니다.
- 응답 유실, 429, 늦은 응답은 단위 검사로만 확인했고 브라우저에서 네트워크를 끊어 재현하지 않았습니다.
- 실행 현황은 자동으로 갱신하지 않습니다. 화면의 수는 마지막으로 읽은 시점의 값입니다.
- 결과 불명인 취소가 있는 동안의 시간대 변경은 승인과 실행을 다시 읽지 않으므로, 표시된 시각은 요청이 해결될 때까지 이전 시간대로 남습니다.
