# 초대 링크 잠금 화면 검증

## 대상과 경계

PR #118 리뷰에서 찾은 문제를 고친 변경을 확인했습니다. 멤버 영역에서 초대 링크가 보이는 동안 "초대 링크 만들기"를 다시 누르면 새 링크가 먼저 받은 링크를 덮어써, 한 번만 반환되는 첫 링크를 다시 볼 수 없었습니다.
고친 뒤에는 초대 요청이 처리 중이거나 링크 영역이 열려 있는 동안 "초대 링크 만들기"가 비활성화되고 제출도 무시되며, 새로 넣은 "닫기"를 누르거나 요청이 실패해야 다시 켜집니다.
세션이 초기화되면 링크 영역을 닫고, 초기화 전에 보낸 요청의 응답 링크는 표시하지 않습니다(`segmentsGeneration` 확인).

실제 `public/app` 파일(`index.html`, `app.js`, `inbox.js`, `webhook-labels.js`, `styles.css`)을 임시 로컬 서버로 제공하고, `/api` 응답만 흉내 냈습니다.
임시 서버는 `/app/` 응답에 `public/_headers`의 Content-Security-Policy를 그대로 붙였습니다.
흉내 낸 응답은 소유자 세션(`/api/me`, `POST /api/workspace`), 빈 연결·규칙, 멤버 1명, 초대 목록, 로그아웃, 초대 생성(300ms 지연, 요청마다 `tok-1`, `tok-2`처럼 다른 링크, 실패 모드에서는 `409 invite_limit_reached`)입니다. 그 밖의 `/api` 요청(운영 상태, 외부 전송, 인박스, 연락처, 처리 내역)은 404로 돌려줬습니다.
실제 `appApi`, DB, Supabase, Meta, Cloudflare는 호출하지 않았습니다.
화면 동작은 Playwright가 내려받아 둔 `chrome-headless-shell`(Chromium)을 Node.js 24의 내장 WebSocket으로 DevTools 프로토콜에 연결해 확인했습니다.
고치기 전 결과는 같은 환경에서 `app.js`와 `index.html`만 `HEAD`(`73542f9`) 사본으로 바꿔 얻었습니다.
제출은 입력 칸에 이메일을 넣고 `form.requestSubmit()`을 불러 보냈습니다. 이 호출은 버튼이 비활성화돼 있어도 제출 이벤트를 일으키므로, 버튼 상태뿐 아니라 처리기 안의 확인도 함께 검사합니다.

## 결과

| 확인                                 | 고치기 전                            | 고친 뒤                                                                 |
| ------------------------------------ | ------------------------------------ | ----------------------------------------------------------------------- |
| 링크가 보이는 동안 두 번째 초대      | 링크가 `tok-2`로 바뀜, 생성 요청 2개 | 링크가 `tok-1` 그대로, 생성 요청 1개, 버튼 비활성화                     |
| 새 화면에서 제출 두 번을 연달아 보냄 | 생성 요청 1개                        | 생성 요청 1개                                                           |
| "닫기"                               | 버튼 없음                            | 입력 값이 비고 영역이 닫히며 버튼이 다시 켜짐, 다음 초대는 `tok-2` 표시 |
| 생성 요청 실패(`409`)                | 확인하지 않음                        | 영역은 닫힌 채이고 버튼이 바로 다시 켜짐                                |
| 요청 처리 중 로그아웃(응답 1초 지연) | 확인하지 않음                        | 응답이 온 뒤에도 영역은 닫혀 있고 값은 비었으며 버튼은 켜져 있음        |

- 연달아 보낸 제출은 고치기 전에도 요청이 하나만 나갔습니다. 기존 `action()`이 처리 중인 버튼을 바로 비활성화하고 비활성화된 버튼의 제출을 무시하기 때문입니다. 고치기 전의 결함은 요청이 끝난 뒤 링크가 보이는 동안의 두 번째 초대였습니다.
- 로그아웃 확인에서 초기화 뒤 문서의 HTML에 `tok-` 문자열은 없었습니다.
- 두 버전 모두 `localStorage`와 `sessionStorage`는 비어 있었습니다. 만든 링크는 입력 칸 값에만 두고 저장하지 않습니다. `app.js`의 `sessionStorage` `pending-invite`는 초대받은 사람이 링크를 열 때 수락용 토큰을 보관하는 기존 처리이며 이 변경과 관계없습니다.
- 콘솔 오류는 흉내 내지 않은 `/api` 요청의 404와 실패 모드의 409 응답 기록뿐이었고, 스크립트 예외와 CSP 위반은 없었습니다. 확인을 마친 뒤 허용하지 않은 주소의 이미지를 일부러 넣자 `img-src` 위반이 같은 오류 기록에 잡혔으므로, 이 수집 방식은 CSP 위반을 찾아낼 수 있습니다.

## 남은 검증

실제 `appApi`와 DB로는 확인하지 않았고, 좁은 화면과 다크 모드에서 "닫기" 버튼의 배치도 보지 않았습니다.
"복사" 버튼은 누르지 않았습니다.
배포하지 않았으므로 운영 화면에서 확인하지 않았습니다.
