# CSV 태그 변경 적용 검증

## 범위

[#25](https://github.com/AndrewDongminYoo/auto-chatter/issues/25)의 [CSV 태그 변경 적용](../specs/2026-10-17-contact-csv-import.md)을 검증했습니다.
[사전 검사](2026-10-17-contact-csv-preview-verification.md)와 같은 파서·분류·스냅샷 함수를 사용하고, 변경 예상 행만 한 트랜잭션에서 교체합니다.
신규 연락처·식별자 병합/분리·운영 배포는 포함하지 않습니다.

## 자동 검사

기준 커밋은 `87d8c90`(사전 검사 병합)입니다.
구현 전 라우트가 없을 때 DB 적용 테스트 5개가 `404 !== 200/422/409`로 실패하는 것을 확인했고, 화면 테스트는 목록 재조회 호출을 제거하면 1개가 실패하는 것을 확인한 뒤 원상 복구했습니다.
로컬 `automations-postgres` 컨테이너(postgres:17-alpine, 5433)의 `automations_test`에서 검사했으며 운영 DB는 사용하지 않았습니다.

| 검사                                                      | 읽은 대상과 결과                                                                             |
| --------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| `corepack pnpm check-types`                               | TypeScript 소스·테스트 타입 검사 통과(종료 코드 0)                                           |
| `corepack pnpm test`                                      | 요청 형태·본문 한도 상수·공유 파서·화면 적용 컨트롤을 포함한 단위 테스트 312개 통과          |
| `TEST_DATABASE_URL=<local> corepack pnpm test:db`         | 적용·거절·낡은 결과 두 순서·삭제 경합·권한을 포함한 DB 테스트 657개 통과(아래 플레이크 참고) |
| `TEST_DATABASE_URL=<local> corepack pnpm test:cloudflare` | 제한된 서버 역할의 적용·복원·상담원 거절을 포함한 workerd 테스트 78개 통과                   |
| `trunk fmt` · `trunk check --ci`                          | 변경 파일 포맷 뒤 검사 통과                                                                  |

`test:db`는 이 기록의 마지막 실행에서 657개가 모두 통과했지만, 리뷰 재실행에서는 두 번 모두 `src/app/settings.db.test.ts:3709`의 시계 단언(최근 댓글 활동 `activity_window.before`를 `Date.now()`와 비교) 하나가 실패해 656/657로 종료 코드 1이었고, 기준 커밋 `87d8c90`의 전체 실행에서도 같은 테스트만 실패했습니다(651/652).
해당 파일만 단독 실행하면 통과하므로 이 변경과 무관한 기존 플레이크이며, 이 PR에서는 고치지 않습니다.
`test:db` 전체가 빨간 채로 끝나면 그 실패가 이 테스트 하나인지 먼저 확인하십시오.

DB 검사가 비교한 내용은 다음과 같습니다.

- 변경 2행·변경 없음 1행 파일을 적용한 뒤 모든 public 테이블의 전후 내용을 비교해 `instagram_contact_tags`만 달라졌고, 그 안에서도 변경 행의 태그만 바뀌었음을 확인했습니다.
- 같은 파일의 두 번째 적용은 `applied: 0`, 모든 행 `unchanged`이며 테이블 내용이 첫 적용 직후와 같았습니다.
- 형식 오류·중복·없는 연락처·타 작업 공간 연결이 각각 한 행 있는 파일은 `422 contact_import_rejected`와 행별 결과를 돌려주고 `ROLLBACK`만 남겼으며 테이블은 처음과 같았습니다.
- 사전 검사 뒤 `saveContactTags`가 먼저 커밋된 경우(작업 공간 잠금 직후 실행) `409 contact_import_stale`이고 응답의 현재 태그가 수정값이며 쓰기가 없었습니다.
- 두 번째 클라이언트가 연결 `FOR SHARE`와 `lockContact`를 쥔 상태에서 적용을 시작하면 `pg_locks`에 대기 중 자문 잠금이 1개 생기고 스냅샷 SELECT는 실행되지 않았습니다. 잠금을 쥔 쪽이 태그를 바꾸고 커밋하면 `409`, 바꾸지 않고 커밋하면 `200`으로 두 행이 모두 교체됐습니다.
- 스냅샷 읽기 직후 변경 예상 연락처의 댓글 이벤트를 삭제하면 쓰기 행 수가 모자라 `409`로 거절되고 `COMMIT`이 없었습니다.
- 상담원·멤버 아닌 사용자·제거된 관리자는 `403`, 쿼리 문자열과 잘못된 `expected` 형태 8종은 `400`, 한도보다 1바이트 큰 본문은 `413`이며, `workspaceFor` 뒤 트랜잭션 안에서 역할이 내려가면 `403`이었습니다.

단위 검사는 `CONTACT_IMPORT_APPLY_REQUEST_BYTES`가 기존 상수에서 계산된 값과 같고, 128KiB CSV와 500행 × 20태그 × 40자(`\u0001`, JSON 6바이트) 본문이 `readJson`을 통과하며 1바이트 초과는 `413`임을 확인했습니다.
깨진 CSV·크기 초과·레코드 수를 넘는 `row`는 커넥션을 잡기 전에 공유 파서와 요청 검사가 거절했습니다.
화면 검사는 실제 `public/app/contact-csv-preview.js`를 읽어 적용 컨트롤이 변경 있는 깨끗한 결과에서만 보이고, 파일 변경·`invalidate`·`reset`·뒤로 가기 캐시 복원·세션 신호에서 제거되며 그 뒤 적용 요청을 보내지 않음을 확인했습니다.
적용 요청은 보관한 CSV 문자열과 변경 행의 `{row, current_tags}`를 보내고, 성공 시 적용 행을 렌더링하고 목록을 한 번 재조회하며 파일 선택을 유지했습니다.
호스트가 저장하지 않은 초안 때문에 재조회를 건너뛰면(`reloadContacts`가 `false`) 상태 줄에 목록을 새로 고치지 않았다는 안내가 붙고, 재조회했으면 붙지 않음을 확인했습니다.
무효화 뒤 도착한 적용 응답은 무시했고, `422`/`409`는 서버의 최신 행을 렌더링하고 적용 컨트롤을 숨겼습니다.

## 검증하지 않은 것

- `[UNVERIFIED: real browser]` 실제 브라우저에서 적용 컨트롤·체크박스·목록 재조회를 구동하지 않았습니다. 화면 검증은 DOM 대체물 위의 컨트롤러 테스트에 한정됩니다.
- 운영 DB·배포·Meta 호출·실사용 파일은 검증하지 않았습니다.
- 액션이 있는 플로우의 댓글 수집 배치와 적용이 같은 `lockContact`를 다른 순서로 잡아 생기는 교착(`40P01`, [스펙 4단계](../specs/2026-10-17-contact-csv-import.md#입력과-결과))은 리뷰가 두 pg 클라이언트로 재현했지만 자동 테스트로는 두지 않았습니다. 어느 쪽이 중단되어도 부분 쓰기가 없다는 점은 트랜잭션 구조에서 추론한 것입니다.
- 식별자 병합/분리와 #25 전체 완료 조건은 남아 있습니다.
