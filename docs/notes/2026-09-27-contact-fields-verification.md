# 사용자 정의 필드 검증

## 실패와 수정

필드 목록의 404와 실제 DB를 사용하는 생성 API의 404를 확인한 뒤 구현했습니다.
실제 로컬 화면에서도 필드 생성 POST가 발생하지 않는 실패를 먼저 확인했습니다.
서버 검증 중 C1 제어 문자와 배열형 연산자를 잘못 허용하는 실패를 재현하고 문자열 타입과 Unicode 제어 문자 검사를 보완했습니다.

화면 리뷰는 로그아웃 뒤 진행 중이던 작업 공간 응답이 화면을 다시 채울 수 있는 경로를 지적했습니다.
실제 로컬 브라우저에서 계정 정보와 처리 내역이 복원되는 실패를 각각 재현했습니다.
기존 세션 초기화에서 증가하는 세대 값을 조회 시작 시 캡처하고, 비동기 응답 후 화면을 변경하기 전에 검사했습니다.
수정 후 두 응답이 무시되는 것을 확인했습니다.

전체 DB 테스트를 다시 실행했을 때 기존 초기화 목록이 새 연락처 테이블을 제거하지 않아 참조만 끊기는 실패가 나타났습니다.
제품 테이블을 명시적으로 제거하는 기존 HTTP·reply-worker·Cloudflare worker 테스트의 목록을 보완했습니다.
같은 테스트 DB에서 DB → workerd → DB 순서로 다시 실행해 모두 통과했습니다.

## 자동 검증

- corepack pnpm check-types: 통과했습니다.
- corepack pnpm test: 100개가 통과했습니다.
- 로컬 automations_test의 corepack pnpm test:db: 100개가 통과했습니다. workerd 검사 뒤 재실행도 100개가 통과했습니다.
- 같은 별도 로컬 DB의 corepack pnpm test:cloudflare: 22개가 통과했습니다.
- JavaScript 문법 검사와 git diff --check가 통과했습니다.
- 변경 경로에 한정해 Trunk 검사 결과를 PR 준비 기록에 남깁니다.

DB 검사는 실제 저장·검색·필드 보관·동시 제한·계정과 작업 공간 격리·0·false·빈 문자열과 미입력 구분·50건 페이지 이동·마이그레이션 재실행을 읽습니다.
workerd 검사는 실제 서버 인증·제한된 DB 역할의 필드 생성·조회·값 저장·조건 조회·외부 작업 공간 거부·보관을 실행합니다.
새 두 테이블의 RLS 활성화, API 역할의 SELECT 거부와 서버 DELETE 권한 부재를 확인했습니다.
테스트는 별도 로컬 DB와 합성 인증 응답을 사용하며 실제 Meta 호출이나 운영 DB 접근을 하지 않습니다.

## 화면과 리뷰

합성 계정과 연락처를 사용하는 실제 로컬 UI에서 필드 생성 실패의 이름 보존·성공 후 초기화, 숫자·예/아니요 저장, 값 제거, 실패 시 초안 보존, 필드 전환 취소, false·미입력 필터와 저장된 숫자 0 조건 복원을 확인했습니다.
늦은 필드 POST, 작업 공간 계정 응답과 처리 내역 응답이 로그아웃 이후 화면을 복원하지 않는 것을 확인했습니다.
390px 화면에서 문서 폭도 390px였습니다.
화면 이미지는 모든 연락처 컨트롤을 담기 위해 긴 뷰포트로 캡처하며 좁은 화면의 기능 검사는 동일한 390px 폭에서 실행했습니다.
요소 단위 캡처가 빈 배경을 담은 것을 직접 확인한 뒤 실제 뷰포트 캡처로 교체했습니다.

서버와 화면에 대한 독립적인 읽기 전용 적대적 리뷰를 실행했습니다.
서버 리뷰는 남은 주요 계약 위반을 발견하지 않았고, 화면 리뷰가 지적한 세션 경로를 수정한 뒤 해당 경로를 재확인해 CLEAR를 받았습니다.
운영자의 새 화면 승인은 PR 병합 전에 별도로 받아야 합니다.

호스팅 리뷰에서 현재 수동 검색 조건의 필드를 보관하면 선택한 ID가 남아 목록 갱신이 실패하는 경로를 확인했습니다.
실제 로컬 화면에서 실패를 재현한 뒤, 해당 보관 작업의 확인 문구에 조건 해제를 안내하고 성공 시 그 필드 조건만 해제했습니다.
계정·태그 조건은 유지하면서 목록을 다시 조회하고 보관된 값이 표시되지 않는 것을 확인했습니다.
다른 경로에서 필드가 사라진 경우에는 기존 조건을 사용할 수 없는 상태로 남겨 검색 범위가 조용히 넓어지지 않도록 유지했습니다.

후속 호스팅 리뷰의 새로고침 순서 문제도 지연된 필드 응답으로 재현했습니다.
필드 조회가 성공한 뒤 연락처를 다시 구성해 새 필드와 보관된 필드가 첫 새로고침에 반영되도록 수정했습니다.
필드 조회 실패 시 이전 정의로 목록을 다시 만들지 않고, 조회 중 편집한 초안의 폐기 취소와 로그아웃 뒤 늦은 응답도 확인했습니다.

## 적용과 한계

마이그레이션 010과 서버 접근 설정은 배포 전 관리자 트랜잭션으로 적용해야 합니다.
개인정보처리방침과 삭제 안내에 직접 입력하는 연락처 태그·필드 값의 목적과 수동 삭제 범위를 추가했습니다.
기존 RLS를 완화하거나 서버 DELETE 권한을 추가하지 않았습니다.
정의 보관은 값이나 이름의 영구 삭제가 아닙니다.
서비스의 필드 수량·타입·길이 제한은 서버 API 계약이며 관리자 직접 SQL에 동일한 검증을 보장하지 않습니다.
운영 DB·배포·실계정 변경·발송과 필드 자동 수집·메시지 변수는 검증하거나 구현했다고 주장하지 않습니다.
관련 Oracle 선례는 `[no precedent found]`이며 Wiki freshness는 확인되지 않았습니다.
